THE FINDING THAT MADE THIS TASK EXIST is F4 (HIGH): an expired or revoked session did
not clear the offline queue, and the queue had no account, so one account's queued days
drained into - and showed under - the NEXT account on the same device. Fixed by scoping
the device's record to the account that recorded it (R303): a local-only, opaque
account tag in the entry primary key, set at sign-in, drained and displayed per account,
set aside (never lost) for an account that is not current, and released to that account
when it signs back in. A real v2->v3 Room migration tags pre-F4 rows UNOWNED (never
sent, never shown) rather than wiping or mis-attributing them.

ALSO FIXED: F2/F6 (R304) - the release build declares no location permission until
detection ships (proven from the built APK); F8 - "today" and the tax year are computed
when used, not frozen at Activity construction, so a session across midnight no longer

THE MIGRATION (R187/R303, no destructive fallback). EntryEntity gains a LOCAL-ONLY
accountTag, and it joins the primary key: (accountTag, dayDate, portion), mirroring the
server's @@unique([userId, dayDate, portion]) - the only shape under which one account's
set-aside day and another's same (dayDate, portion) coexist without either overwriting
the other. DATABASE_VERSION goes 2 -> 3 (NOT 1 -> 2: the DB was already at v2 for the
AN6a tally; the prompt's "v1 -> v2" is shorthand - PARKED reasoning below). MIGRATION_2_3
recreates the entry table (SQLite cannot alter a primary key in place) and copies every
existing row across with accountTag = 'UNOWNED'. Its CREATE TABLE matches, column for
column and in order, the createSql Room generates for schemas/3.json (verified by diff),
so runMigrationsAndValidate passes. MonReleveMigrationTest now opens a GENUINE v2 database
with one real row and runs the real migration, asserting the row SURVIVES and is tagged
UNOWNED.

HOW EXISTING ROWS WERE ASSIGNED - the two branches, each named:
- UNOWNED branch (the real pre-F4 upgrade path): a pre-F4 row's account is UNRECOVERABLE
  - the address was never persisted by pre-fix builds, /api/v1/me omits it (web/lib/me/
  read.ts), and the tokens are opaque. So the migration tags every existing row UNOWNED:
  held, never sent, never shown, never mis-attributed. NOT adopting them to whoever signs
  in next is deliberate - adoption would be F4 reborn. (MonReleveMigrationTest's v2->v3
  case takes this branch.)
- OWNED branch (every row going forward): record() tags the row with the current account
  at the tap, the way the mutation id is born at the tap. (AccountScopeTest and
  CallbackControllerTest take this branch.)

THE ACCOUNT IDENTITY (the new on-device design decision, with the operator's guardrails):
- The only identity the device can know is the EMAIL the magic-link callback carries;
  /api/v1/me deliberately omits it, and the tokens are opaque and rotate. Verified the
  callback carries a non-blank email on the only release sign-in path: CallbackLink.parse
  returns null unless token AND email are non-blank, so exchange() always has one; the
  debug SessionInjectionActivity takes an explicit email extra.
- FAIL CLOSED: accountTagOf returns null for a blank address (CallbackLink already rejects
  blank), so a blank address sets NO tag rather than a shared blank one; a row recorded
  with no active account is tagged UNOWNED (held), never mis-tagged.
- COLLISION: the tag is a SHA-256 hex digest (256-bit) of the normalised address, so a
  collision between two real people is not a practical concern. It is also opaque and
  non-reversible, and never on the wire (EntriesWire omits it) - the raw address, a
  credential in this product's threat model, never enters Room (which is not backup-
  excluded) nor a backup (the account prefs ARE backup-excluded).

THE FIX (commit 84fd75a). SyncEngine drains dao.pendingForAccount(current); a null
account drains nothing. The repository observes dao.observeAllForAccount(current); a null
account resolves to UNOWNED, which owns no real row, so the shell shows nothing rather
than the previous account's days. CallbackController sets the tag at sign-in;
DeviceLocalStore.clearForSignOut clears it (R303: R295 still clears everything);
ErasureCensusTest covers monreleve.account; the backup rules exclude it.

THE GREEN. JVM: AccountScopeTest's four cases pass; CallbackControllerTest asserts sign-in
sets the tag; LocalStoreTest asserts sign-out and deletion clear it; :app:gate BUILD
SUCCESSFUL (835 then 836 unit tests). ON-DEVICE GREEN (OWED, RAM-blocked, handoff):
android/scripts/an-fix-crossaccount.mjs is prepared to report CROSS_ACCOUNT_LEAK=false (B
owns 1, A owns 0 after B's drain) and SET_ASIDE_RELEASED=true (A signs back in -> A owns
2, B still 1), with a shot of B's main shell holding none of A's days.

A SIGNING BACK IN. AccountScopeTest.aDifferentAccountsPendingDaysAreSetAside proves it on
the JVM: after B's context sees and sends none of A's two rows (they remain in the store),
syncing under A's account posts both of A's rows. The on-device confirmation is the
script's A-resignin phase (OWED).
