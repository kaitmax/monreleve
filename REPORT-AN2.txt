THE PORT
====================================================================
File-by-file, TS to Kotlin, all thirteen calc-engine source files
(main) map 1:1 by responsibility (no index.ts equivalent - Kotlin's
package itself is the barrel, nothing to port):

  types.ts            -> Types.kt (grew across every increment into
                          the single home for every sealed/data type;
                          detekt's MatchingDeclarationName pressure -
                          fired on Denominator.kt/Warnings.kt/
                          AllowedDays.kt each introducing their own
                          top-level data class - consistently pushed
                          shared types there rather than splitting
                          files, which is why this is the one file
                          that grew far past its TS counterpart's
                          size rather than staying proportional)
  rules.ts             -> Rules.kt (RULES_2026, ruleSetFor)
  regime.ts            -> Regime.kt (regimeFor)
  denominator.ts       -> Denominator.kt (ceilProrated, missionCapFor,
                          resolveDenominator)
  granularity.ts       -> Granularity.kt (classifyTeleworkHours)
  waterfall.ts         -> Waterfall.kt (runWaterfall)
  validate.ts          -> Validate.kt (validateInput, split into
                          rangeErrors/dayFieldErrors after a detekt
                          CyclomaticComplexMethod failure)
  declarable-rate.ts   -> DeclarableRate.kt (declarableRateFor -
                          truncates)
  raw-rate.ts          -> RawRate.kt (rawRateFor - rounds up)
  headroom.ts          -> Headroom.kt (floorToHalfDay, headroomFor -
                          floors)
  warnings.ts          -> Warnings.kt (warningsFor, all eight
                          variants)
  calculate.ts         -> Calculate.kt (calculateTelework, the
                          pipeline assembly)
  allowed-days.ts      -> AllowedDays.kt (allowedTeleworkDays)

Two genuine type-design bugs found by reading the TS source directly
rather than assumed from the spec's prose (both fixed before
increment 4's code depended on them further):
  - InputField (Kotlin enum mirroring validate.ts's field tags) had
    the wrong members in its first draft (EMPLOYMENT_RATE/
    PERIOD_FRACTION/GRANULARITY - none of which validate.ts actually
    assigns) and was missing DENOMINATOR, which IS assigned. Fixed to
    the four fields validate.ts actually uses.
  - teleworkDays/missionDaysFrance/missionDaysThirdState and
    swissTaxedDays/frenchTaxedDays/creditedMissionDays were typed Int
    in the first draft; HALF_DAY granularity's 0.5 increments are the
    ORDINARY case in this domain, not an edge case (confirmed against
    validate.test.ts's own `teleworkDays: 10.5` case), so all six are
    Double.

One considered, documented type-design difference that stays a
difference rather than being "fixed" to match TS structurally:
DenominatorMethod.Exact.totalWorkDays is Int in Kotlin, where the TS
side's equivalent field can hold NaN under one test case (a "never
throws" property test passing Number.NaN through it). Int cannot
represent NaN. Rather than widen every downstream type
(DenominatorOutcome, TeleworkResult, WaterfallInput) to Double to
support one TS-only edge case, the Kotlin side keeps the domain
constraint ("a denominator basis is always a whole day count") and
the one inexpressible TS test case is named rather than silently
dropped: AllowedDaysTest.kt's own "never throws" test comments this
exactly, testing the NaN path through periodFraction (which IS
Double) instead.

Test files: 1:1 by responsibility with web/tests/unit/calc-engine's
own files that AC1-4 name (RulesTest, RegimeTest, DenominatorTest +
DenominatorConformanceTest, GranularityTest, MissionCapTest,
WaterfallTest + GenevaWaterfallTest + GenevaConformanceTest,
ValidateTest, RatesTest + RateConformanceTest, HeadroomTest,
WarningsTest, CalculateTest, AllowedDaysTest, Arbitraries +
Properties1To4Test + Properties5To8Test). Six TS files have no
Kotlin counterpart and were not ported - named under NOTICED BUT NOT
TOUCHING, none required by AC1-4.

THE PROPERTY TESTS (AC3)
====================================================================
Arbitraries.kt: validInputArb, built the same way
web/tests/unit/calc-engine/arbitraries.ts builds it - valid BY
CONSTRUCTION (resolveDenominator computes the real totalWorkDays
first, then splitSteps partitions a step budget into three day-count
fields that provably cannot exceed it), not generate-and-discard,
which would spend most of 10 000 runs on inputs the engine refuses.
Covers part-time (employmentRate 1-100), mid-year periods
(periodMonths 1-12), both denominator methods, all three
granularities, and both a known (2026) and unknown/fallback (2027)
tax year - each confirmed reached by "the generator itself" test in
Properties1To4Test.kt, not assumed from the generator's construction
alone.

PROPERTY_RUNS = 10_000, PROPERTY_SEED = 20260907L (fixed, matching
the TS side's FIXED_SEED/FIXED_RUNS exactly - ruling R24's own
argument: a rotating seed on a blocking check goes red on a case
nobody can reproduce). FALSIFY_RUNS = 2_000 for the deliberately-
broken variants, same fixed seed.

Properties1To4Test.kt (11 tests) and Properties5To8Test.kt (14
tests), matching properties-1-4.test.ts / properties-5-8.test.ts's
cases and structure exactly:
  1. swissTaxedDays + frenchTaxedDays == totalWorkDays (the day
     partition is exact)
  2. declarableRate <= 40 whenever regimeApplies
  3. creditedMissionDays <= missionCap AND <= fiscalCeilingDays -
     teleworkDays
  4. remainingToSocial >= remainingToFiscal (always at least as much
     social room as fiscal), including the negative-headroom case
  5. rawRate is monotonic in teleworkDays
  6. declarableRate never exceeds rawRate
  7. truncation never overstates (checked against the exact
     unrounded value computed on integers - ruling R16's own
     argument: comparing two floats would compare the defect against
     itself) and loses less than one hundredth
  8. swapping the France/third-state mission split never increases
     creditedMissionDays (in fact leaves it identical - the credit is
     min(total, budget), stronger than the spec strictly requires,
     pinned as its own test)

Every invariant is paired with a DELIBERATELY BROKEN variant Kotest
must falsify - via `shouldThrow<Throwable> { checkAll(...) { ... } }`,
Kotlin's equivalent of the TS side's `expect(() => fc.assert(...)).
toThrow(...)`. All eight break-pairs, plus "the generator itself"
(produces only inputs the engine accepts; reaches every dimension AC1
names) and "the two rate rules stay separated" (they disagree on at
least some input, or one is dead code; they agree exactly when no
mission day is uncredited) ported and green. 10 000 x 8 + reach/
isolation checks = every property ran the full case count this
session, not a reduced count for speed.

Kotest's checkAll/PropTestConfig signatures were confirmed directly
against the resolved jar (javap on kotest-property-jvm-5.9.1.jar)
rather than assumed from partial online documentation, which is what
surfaced the missing bind import in the first place (see SUMMARY).
