THE QUEUE (increment 2) -- where the mutation id is born, and why there
--------------------------------------------------------------------------------
clientMutationId is a UUID minted INSIDE record(), at the moment the person taps,
and persisted with the row BEFORE any network call (there is no network in
EntryRepository). An id minted at send time would be regenerated on every retry,
turning a safe replay into a duplicate write -- the queue's whole safety rests on
that id being stable from the tap, which AC3 then relies on.

clientClaimedAt is the device's clock at the tap (deviceClaimNow(clock)), an ISO
instant WITH OFFSET in the device's own zone, sent verbatim and never used by the
client to compute lateness. Its format is fixed (yyyy-MM-dd'T'HH:mm:ss.SSSxxx) so
the seconds field is never omitted, which the server's zod would reject.

Pending is a DURABLE state (Room on disk), surfaced by observePending() and shown
in the recorder as the persistent words "En attente de synchronisation", never a
toast (DESIGN-SYSTEM section 2). An edit read-modify-writes, PRESERVING the
server-assigned columns (serverId, firstRecordedAt, lastModifiedAt) so a
re-record of a synced day keeps its immutable evidence moment locally (advisor
call). Coalescing is @Upsert on the composite PK: an edit REPLACES the pending
row with a new id, so the queue never holds two mutations for one day.

--------------------------------------------------------------------------------
SYNC (increment 3) -- one worker, one round trip, a rejected payload
--------------------------------------------------------------------------------
ONE WORKER AT A TIME. SyncScheduler enqueues UNIQUE work; WorkManager never runs
two concurrently. APPEND_OR_REPLACE, not KEEP: a record made while a drain runs
still gets its own drain rather than being dropped. Network-constrained,
exponential backoff.

ONE ROUND TRIP. SyncEngine snapshots pending, batches at MAX_BATCH_ITEMS (the
server's named constant, asserted equal to schema.ts by BatchLimitParityTest,
R181), POSTs, and on 200 reconciles each local row FROM THE SERVER'S ROW (R217) --
serverId, firstRecordedAt, lastModifiedAt and all -- not from what the client
sent. A concurrency guard only marks a row SYNCED if it is STILL the same pending
mutation that was sent, so an edit made mid-flight is not clobbered.

A REJECTED PAYLOAD IS A CLIENT DEFECT (R198). A 400/409/413 for a payload the
client built marks the batch FAILED -- held out of pending() so it is NEVER
retried (retrying a rejected payload can never succeed) -- and surfaced via the
FAILED sync state and SyncOutcome.Settled(defects>0), not via android.util.Log
(which is stubbed in JVM tests and would leak note text at runtime). A network
fault is Retryable (rows stay pending); no session is reported so the worker
stops rather than backing off forever against an absent session. The R210 replay
handling is shared with the authenticated GET through one code path
(SessionManager.attempt), so it cannot drift between GET and POST.

--------------------------------------------------------------------------------
ORDERING EVIDENCE (increment 4) -- what the queue can and cannot emit
--------------------------------------------------------------------------------
STRUCTURAL, not a matter of timing. The store keys on (dayDate, portion) and
record() coalesces onto that key, so the queue holds AT MOST ONE pending mutation
per (dayDate, portion). From a SINGLE DEVICE:
  - it can never place two items for one (dayDate,portion) in a batch, so the
    server's reserved conflict (409) can never fire against it; and
  - it can never emit two out-of-order mutations for one day, because there is
    only ever one to emit.
So the section-6.4 reversion is NOT reachable from one device. It requires TWO
devices with two independent queues (device A's older-but-genuinely-new mutation
arriving after device B's newer one, winning by server receipt) -- which no
single-device coalescing can prevent. Encoded in OrderingEvidenceTest
(aBatchNeverCarriesTwoItemsForOneDayAndPortion); recorded in docs/api-v1.md 6.4
under "AN5 evidence". The product is single-user and effectively single-device
today, so the reversion is not reachable in practice now. The decision -- keep
server-receipt order or move to clientClaimedAt -- stays the operator's, unchanged
by AN5 (the rule is frozen, R156). See QUESTIONS.

OFFLINE (AC2)
--------------------------------------------------------------------------------
Airplane mode ON. Recorded three days offline (25/26/27.09 as HOME) -- each showed
"En attente de synchronisation". Edited one (27.09 -> Suisse/CH) -- it coalesced to
CH, still pending, ONE row. Force-stopped and relaunched the app: all three
pending rows PERSISTED (Room on disk), the 27.09->CH edit included. Airplane OFF,
tapped Synchroniser: the queue drained, every row showed "Synchronise".

Read back from the container DB: exactly 4 Entry rows (25/26 HOME, 27 CH -- the
edit won, no lost edit; 28 HOME from AC1); 4 EntryEvents, all CREATED, count 1
per day -- no duplicate, one event per mutation.

THE ARITHMETIC, STATED (not left as a surprise): AC2 was 4 taps (3 records + 1
edit) but 3 wire mutations, because the 27.09 edit REPLACED a still-pending
mutation before any sync -- so it produced one CREATED event carrying CH, not a
CREATED(HOME)+MODIFIED(CH) pair. With AC1's 28.09 that is 4 rows / 4 CREATED
events total. This is the designed outcome of offline coalescing; whether it is
the desired PRODUCT semantics is parked for the operator (see QUESTIONS).

--------------------------------------------------------------------------------
PARKED (PARKAN-<n>)
--------------------------------------------------------------------------------
PARKAN-1 (carried from AN4): OS App Link verification is not testable --
  monreleve.ch does not resolve and assetlinks.json needs the Play signing key.
  The callback was driven by naming CallbackActivity explicitly (adb -n), which
  proves the app's HANDLING, not the OS's verification. Unchanged by AN5.
PARKAN-2: sign-out does not clear the local store. AN5 assumes a single-user
  device (no userId column). If a shared device or account switch is ever in
  scope, sign-out must clear Room, and the schema may need userId -- which is the
  migration the harness exists to make safe. Conservative: deferred, not built.
PARKAN-3: AC2 coalescing semantics. An offline record-then-edit of one day
  coalesces to a single CREATED event (final value), never CREATED+MODIFIED. This
  is correct queue behaviour (no lost edit, no duplicate) but it means the
  EntryEvent trail does not record that the day was first HOME then CH while
  offline. Whether the product WANTS that intermediate history is a decision;
  parked for the operator.
PARKAN-4: granular FAILED. A 400 marks the WHOLE batch FAILED rather than parsing
  issues[] to fail only the offending item(s). Safe (no infinite retry) and never
  hit in AC1-AC3 (the client builds valid payloads), but a refinement worth a
  ruling if per-item recovery is wanted.
