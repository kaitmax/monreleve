QUESTIONS
---------
Q1. HOW `production` IS REALIGNED AFTER A ROLLBACK (10.1, "After a rollback").
    After a Coolify rollback, or Coolify's own health rollback, `production`
    still names the failed SHA. A Restart or the next push deploys that head
    (applications.php 21; job 3171, 3227-3231). That blocks every environment
    change, including the DB rotation's restart and P2 item 5b, until it is
    resolved. The options, not chosen here:
    (a) Force-push PREVIOUS to `production`. That is not a fast-forward. By
        reading, its auto-deploy re-uses PREVIOUS's image, which means another
        swap.
    (b) Fix forward: a new commit, promoted from step 0, with no restart
        before it.
    (c) Another way the operator prefers.
Q2. A RELEASE THAT CARRIED A MIGRATION. A rollback runs the previous code
    against the migrated schema, and /api/ready cannot see the difference.
    Nothing in the repository shows that the previous code works on the newer
    schema, and nothing reverses a migration. Three ways out: roll back by
    image anyway, fix forward, or require migrations to be additive. The
    runbook states the fact and does not choose.
Q3. HOW MANY ROLLBACK IMAGES TO KEEP, AS A POLICY. The source requires one,
    PREVIOUS, for a one-step rollback; more is the operator's choice.
    Coolify's own cleanup, by default and as read for this application's
    container naming, already keeps only one previous image.
