CUSTOM TABS (dependency and fallbacks)
====================================================================
DEPENDENCY (R136). androidx.browser 1.8.0 - the AndroidX library for
the Custom Tabs protocol (no Google Play Services, no account). Its
CustomTabsIntent + toolbar-colour API have existed since 1.2.0, so the
feature needs nothing recent. 1.8.0, NOT the 1.10.0 latest stable
(verified at developer.android.com/jetpack/androidx/releases/browser,
fetched 2026-10-06): 1.8.0 is the mature stable that compiles against
this project's compileSdk 35 with NO compileSdk bump - an out-of-scope
build-config change - the same "mature stable, not bleeding edge"
reasoning the catalog applies to work/kotest, and R156's conservative
choice with the advisor unavailable. Covered by the existing AndroidX
attribution on the licences screen; checkLicences stays green, so no
licences change was needed.

OPENING (MainActivity.launchCustomTab, composition root). The page
opens inside the app's context with the brand token in the toolbar
(LightColors.brand.toArgb(); never a raw colour - the token fence
holds). setShowTitle(true).

FALLBACK CHAIN, in one place (R299, never a crash):
  1. A Custom Tab is an ACTION_VIEW intent with extras, so a device
     with an ordinary browser but no Custom Tabs provider gets the
     ordinary browser automatically - CustomTabsIntent does not require
     a provider.
  2. A device with NO browser at all makes startActivity throw
     ActivityNotFoundException, which openLegalLink (the caller's seam)
     catches to show the address instead (R299), proven JVM-side by
     LegalLinkTest's two branches.
Wired as openLegal's open seam, so BOTH the A propos rows AND the
sign-in consent links open in a Custom Tab.

REGISTER-COVERAGE REGEX DOES NOT MATCH THE PARK-<n> SERIES. The
CITATION regex in web/scripts/register-coverage.mjs is the eight
characters P,A,R,K,A,N,?,- followed by one-or-more digits. The "?"
binds to the single preceding "N", so the pattern parses as "PARKA"
plus an optional "N" - it matches the PARKAN-<n> series (and even a
spurious PARKA-<n> form), but it does NOT match the PARK-<n> series at
all. Verified with node: a PARK-<n> token returns null while a
PARKAN-<n> token matches. The intended pattern is "PARK" plus an
optional "AN" - a non-capturing group around the "AN" would fix it.
Consequence: every PARK-<n> citation in every REPORT-*.txt (and the
same check the Kotlin RegisterCoverageTest shells out to) goes
UNCHECKED - a verifier silently not checking the series its own comment
names ("PARK-12 or PARKAN-18"), the exact class the project guards
against. Not touched: out of scope for AN-LINKS, and fixing the regex
would turn a green check red across historical reports until each
PARK-<n> they cite is reconciled, which is its own task. This report's
PARK-13 references are accurate and resolve by hand (parking.md line
589); PARKAN-30 is the one the check does verify, and it passes.
