R510 - THE SERVER GRACE WINDOW: NOT BUILT, A QUESTION
--------------------------------------------------------------------------------
No server file changed (`git diff origin/main...HEAD -- web/` is empty).

THE PROPOSAL: accept a refresh token presented again within N seconds of its own
rotation, instead of revoking the session.

WHAT IT REMOVES, for any client still holding the just-rotated token:
  - the in-process race R506 reproduced - which R507 has ALREADY removed in this
    app at its source;
  - THE LOST RESPONSE, which nothing on a client can remove: the client sends
    R0, the server rotates (R0 and its access token consumed), the response
    never arrives - a dropped connection, the transport's read timeout, the
    process killed mid-response. The client still holds R0; its next refresh is
    today a replay, and the session ends. With R507 in place this is the
    remaining way this app can sign itself out;
  - a future second process, or an iOS client with its own concurrency error.

WHAT IT COSTS: R210, inside the window. A replay presented within N seconds is
no longer caught at that moment - a thief who captured R0 and presents it inside
the window after the real client's rotation, or the real client presenting it
after a thief rotated first.

THE EXACT BEHAVIOUR, and the two are not equivalent:
  (a) THE SAME NEW PAIR - the second presentation receives exactly the pair the
      first did. One chain survives, so when the two holders later diverge,
      reuse detection fires as it does today: a theft inside the window is
      detected LATER, not never. COST: tokens.ts stores hashes only ("THE HASH
      IS STORED, NEVER THE TOKEN"), so the server cannot hand the pair out
      again unless it keeps the successor's plaintext for the window
      (encrypted, then deleted) or DERIVES the successor from the presented
      token and a server secret (an HMAC), recomputing it without storing it.
  (b) A FRESH PAIR - the session forks into two independent live chains whose
      refreshes never collide, so a theft inside the window is NEVER detected.

RECOMMENDED (the operator's decision - it softens R210): (a), the same pair,
DERIVED rather than stored; a window of 60 SECONDS; every in-window acceptance
logged with its session, so the window's use is measured and reversible. Why not
"a few seconds": the race a few seconds would cover is gone (R507). What remains
is the lost response, and its retry cannot arrive before the client's read
timeout (UrlConnectionTransport: 15 s connect, 15 s read), then waits for the
next call or WorkManager's backoff (MIN_BACKOFF_MILLIS, 10 s) - 15 to 30 s after
the rotation by the code's own constants. Five seconds would cover none of it.
THE ALTERNATIVE, equally defensible: no window until the server records a
TOKEN_REPLAYED that R507 does not explain - it is recorded per session, so it is
measurable before it is softened.
