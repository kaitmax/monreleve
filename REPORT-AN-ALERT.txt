WHEN (each rule, its test)
====================================================================
The pure decision is decideThresholdAlert(optedIn, current, previous) in
detection/ThresholdAlertDecision.kt. The crossing is projectedThresholdCrossing /
crossingOf in forecast/ThresholdForecast.kt - it runs the EXISTING engine
(dossier.forecastResults, R281) on the imagined year and reads its declarable rate
against the RuleSet ceilings (R181 - the thresholds come from the RuleSet, never
typed). Each WHEN rule has a JVM test and an on-device case.

JVM (detection/ThresholdAlertDecisionTest.kt - test-first: RED on unresolved refs,
then GREEN):
  - "the first crossing of the fiscal threshold notifies"   not-crossed -> crossed = alert.
  - "staying crossed does not notify again"                  crossed -> crossed = null.
  - "falling back under then re-crossing notifies again"     crossed -> not-crossed (null,
       state saved not-crossed) then -> crossed = alert (a new crossing).
  - "crossing the social threshold notifies for social".
  - "both thresholds crossing at once announces the graver social threshold".
  - "opted out sends nothing and leaves the state untouched" optedIn=false = null,
       state unchanged (so re-opting-in later evaluates from the last opted-in state).
  - "no rhythm means no projection and no alert"             current=null = null.
JVM (forecast/ThresholdForecastTest.kt):
  - "crossingOf is inclusive on the compliant side (R32)"    40.00 not crossed, 40.01
       crosses fiscal; 49.90 not crossed, 49.91 crosses social (same strict-> as zoneFor).
  - "an all-suisse rhythm crosses neither threshold"         0 % via the real engine.
  - "a three-day-a-week domicile rhythm crosses both thresholds"  ~65 % via the real
       engine (teleworkDays stays under the 240 total, so the year is accepted).
  - "no rhythm yields no crossing".

The last crossing state per threshold is kept on the phone (settings/ThresholdAlert.kt
- ThresholdAlertStore, sharing monreleve.detection so sign-out/deletion sweeps it,
R289/R295/R303). The forecast is recomputed when the record or the rhythm changes
(a MainShell LaunchedEffect keyed on the projected rate + the opt-in runs
maybeAlertThreshold off the main thread) and once a day after the checks conclude
(SamplingWorker, before the evening reminder). maybeAlertThreshold self-gates and
posts NOTHING unless a threshold is newly crossed.

ON-DEVICE (debug trigger ThresholdAlertActivity, post count as the discriminator -
a post increments the system's per-day post_frequency count):
  1 first crossing   POSTED (count 1->2)   (expect true)   PASS
  2 staying crossed  NOT posted (2->2)      (expect false)  PASS
  3a fall back       NOT posted (2->2)      (expect false)  PASS
  3b re-cross        POSTED (2->3)          (expect true)   PASS
  4 same-day merge   POSTED (3->4)          (expect true)   PASS
  5 opt-out          NOT posted (4->4)      (expect false)  PASS

====================================================================
THE SAME-DAY MERGE
====================================================================
NEVER TWO MON RELEVE NOTIFICATIONS THE SAME DAY. The alert and the evening reminder
SHARE notification id 1001, so at most one exists at a time, and both route through
ONE composeDaily / EveningNotifier.postDaily (R206 - one home for the merge rule):
  - both due   -> the evening reminder with the alert's sentence joined and the record
                  buttons KEPT (NotificationCopy.alertTitle, the alert's one home);
  - one due    -> that one;
  - neither    -> nothing.
JVM (detection/ThresholdAlertDecisionTest.kt): composeDaily tested four ways - Merged,
Alert alone, Evening alone, None.
maybeAlertThreshold, on a new crossing, computes the evening notice (ignoring the
once-a-day gate, so a reminder already shown is replaced by the merged one with its
buttons) and posts the composed result; maybeNotifyEvening, when it posts, joins any
alert that already fired today. In SamplingWorker the alert runs BEFORE the reminder,
so a coinciding crossing posts ONE merged notification and the reminder then skips.

ON-DEVICE case 4 (a concluded working day - the S9 clock was 23:16 Paris, past the
17:00 last check window - with no entry, evening opted in): ONE notification,
channel=monreleve.evening.proposal, ACTIONS=3 (the record buttons En Suisse / Domicile
/ Autre KEPT), title "Ou avez-vous travaille aujourd'hui ?" with the date AND the
joined alert sentence "Votre rythme prevu depasser..." (screenshot notif-04-merge.png).
vis=PRIVATE with a publicVersion. The post count rose by exactly one.

R340 - A PROJECTION/ALERT IS NEVER A RECORD (the "nothing written" test)
====================================================================
THE COMPUTE IS PURE: projectedThresholdCrossing / crossingOf and decideThresholdAlert
/ composeDaily take values and return values (no store, no DAO, no network, no clock
but the parameter). The engine run inside is forecastResults, which ForecastR340Test
(foundation, green) proves writes nothing.
THE SOURCE SCAN (detection/ThresholdAlertR340Test.kt, NEW, in :app:gate): asserts the
alert's files (ThresholdForecast, ThresholdAlertDecision, settings/ThresholdAlert,
EveningNotifier) contain NO entry-write seam (.record( / .upsert( / RecordCommand), so
a future edit that tried to record a day from the alert path turns it red. It composes
with Fence 7 (detection/ never references EntryRepository/RecordCommand).
THE DEVICE STORE PROOF (the handover deliverable). monreleve.db was read after all
WHEN cases (7 alert triggers, several notifications posted, including the merge):
  entry        0   (unchanged - no day recorded)
  pending      0   (the mutation queue - unchanged)
  daily_tally  0   (unchanged)
  weekly_rhythm 1  (the rhythm set via the UI - a planning preference, R341, the ONE
                    allowed local write; NOT a record)
COMPUTING AND FIRING THE ALERT WROTE NOTHING TO THE RECORD: PASS. The server is never
called (the alert is all local engine); the releve, the PDF and the annex have no seam
from the alert path at all.
