R591 - SCOPE ADDITION: A RACE LOSER ANSWERS granularity_conflict  commit c11ebf8
================================================================================
Added by the operator on 2026-10-26 after this task's own gates met it (PARK-O1
below). lib/entries/write.ts: retryOnceIfRaceLost wraps the transaction; it
retries EXACTLY ONCE, ONLY when the error's code is P2034, 40P01 or 40001 (or
the SQLSTATE is in Prisma's meta); everything else is rethrown untouched; a
retry that fails again falls through to today's mapping (write_failed); there
is no third attempt. One console.warn line when it retries.
THE TEST FORCES THE PATH (tests/db/entries-retry.test.ts, 6 tests, through the
route): the cached client's $transaction runs the REAL transaction and throws
the deadlock inside it on the chosen attempts - after the body's writes where
the case needs them - so PostgreSQL rolls the attempt back as it would a real
victim.
  RED on the old code: 5 failed | 1 passed -
    "expected 500 to be 400"  (a loser against the winner's FULL)
    "expected 500 to be 200"  (a loser with nothing to conflict with; 40P01,
                               40001 alike)
    "expected 1 to be 2"      (a double failure: only one attempt)
    (passing: "any other failure behaves as before" - not retried, 500)
  GREEN: 6 passed -
    loser vs winner's other granularity: 400 granularity_conflict, 2
      attempts, event count unchanged;
    no conflict: 200, 2 attempts, EXACTLY ONE row and ONE CREATED event -
      the rolled-back first attempt left none;
    SQLSTATE 40P01 and 40001 retried the same way;
    retry fails again: 500 write_failed, exactly 2 attempts, no row, no event;
    any other error: not retried (1 attempt), 500 write_failed.
  The 100-run race test stays: 8 of 8 runs green after the change (800 races);
