THE NETWORK LAYER (increment 1)
--------------------------------------------------------------------
HTTP CLIENT: the platform HttpsURLConnection behind a thin HttpTransport
seam, on Dispatchers.IO (R136 - no OkHttp/Ktor/Retrofit for a handful
of JSON endpoints). The seam is why the refresh state machine and the
single-flight proof run as plain JVM tests against a fake.

JSON: org.json - the library AN2 already brought for the fixtures,
reused, not a second. On a device it is the platform's; the unit tests
get the real JVM impl via the existing test dependency. Its
read-what-you-ask parsing satisfies the contract's ignore-unknown-keys
obligation (docs 6.5) structurally, where a strict serialiser would
need configuring.

BASE URL PER BUILD TYPE (BuildConfig.API_BASE_URL): debug is
http://10.0.2.2:<port> (frontalierPort gradle property, default 3000 -
a neighbour holding 3000 moves us, R170's shape), release is
https://monreleve.ch. Cleartext is permitted only to 10.0.2.2 in the
DEBUG network security config and NOWHERE in release, with the release
deny EXPLICIT because minSdk 26 defaults cleartext to permitted (only
API 28+ flipped it).

checkReleaseCleartext (a gate task, dependsOn processReleaseManifest -
R182, so it never runs before the merged manifest exists) reads the
MERGED release manifest and the release network config and fails if
cleartext is permitted anywhere. THE DEFECT IT FOUND IN ITSELF: its
first run failed, reporting the release config permits cleartext - but
the config said "false". The regex had matched the string
cleartextTrafficPermitted="true" inside the config's own COMMENT (which
names it as the value to plant). Fixed by stripping XML comments before
matching. Then proven by planting the value in the ELEMENT (R180):
FAILED for the right reason, reverted.

ERROR MAPPING (R198): AuthServerCode maps every auth code (docs 1.4 /
bearer.ts) to its own ClientAction; an unrecognised code is preserved,
never guessed (docs 6.5); a Network failure is a distinct type from a
Server failure, so "could not connect" is never read as "the link was
already used".

TOKEN STORAGE (increment 2)
--------------------------------------------------------------------
NOT EncryptedSharedPreferences. androidx.security:security-crypto was
DEPRECATED in April 2025 (1.1.0-alpha07) over main-thread StrictMode
violations and keyset corruption on some OEMs, verified by web search,
and the relay forbids building on a deprecated API. SPEC 10 names
EncryptedSharedPreferences, so SPEC's mechanism is out of date - the
same shape as R209's Auth.js line (DEVIATIONS).

CHOSEN: the platform Android Keystore directly (R136). An AES-256-GCM
key that never leaves the Keystore; the pair serialised to JSON,
encrypted, and the ciphertext plus a fresh per-save IV kept in an
ordinary SharedPreferences. No new dependency. This delivers SPEC 10's
actual requirement - "stored in Keystore-backed storage".

setUserAuthenticationRequired(false): silent refresh must work while the
phone is locked, so the key is not gated on a device unlock. An
unreadable stored blob (an invalidated key, a corrupt ciphertext) is
not a crash: load() drops the pair and returns null, and the caller
signs in again - the local mirror of the server's unknown_token
"corrupted stored token" case.

PROVEN by an instrumented test on emulator-5554 (real AES-GCM, not a
JVM stub): save -> load returns the same pair; clear drops it; an empty
store loads null.

WHAT CANNOT LEAK (increment 2, AC3)
--------------------------------------------------------------------
LOG FENCE: no token, refresh token or email reaches a log line. A
source scanner (LogFenceTest) forbids a log/print sink sharing a line
with a credential word, plus TokenPair.toString() redacts both tokens
for the leak a generic serialiser (a crash reporter, Log.d("$pair"))
would produce. Proven adversarially - a planted Log.d(refreshToken)
turned it RED (R7/R178: the app logs nothing, so a plant is the proof).

BACKUP: the token store AND the pending-sign-in store are excluded from
BOTH fullBackupContent (API 26-30) AND dataExtractionRules (31+, cloud
backup AND device transfer) - a restored backup must not resurrect a
session, and device transfer is the channel fullBackupContent cannot
express. The Keystore key is device-bound anyway; excluding the
ciphertext is the explicit second guarantee. BackupRulesTest asserts
both files, both channels.

FLAG_SECURE: RECORDED, NOT SPRINKLED. No screen renders a token or the
sign-in link - the email screen shows an email the user typed, the
check-email and callback screens show messages, and the link is read
from the outbox, never displayed. noRawTokenReachesTheUiLayer asserts
the premise (ui/ holds no raw token). Applying FLAG_SECURE to the
callback screen would have blacked out AC2's own required screenshots
for nothing on screen to hide, so it is applied nowhere and the reason
is recorded here rather than the flag scattered performatively.

THE CALLBACK (increment 4, AC2)
--------------------------------------------------------------------
CallbackActivity is the App Link target (exported, singleTop,
autoVerify) for FW22's frozen callback path (R195). The incoming URI is
UNTRUSTED (android-intent-security, AN0): CallbackLink.parse validates
scheme, host and path against the frozen shape and extracts token+email
(a pure java.net.URI, JVM-tested), applied identically in onCreate AND
onNewIntent (setIntent first, so a singleTop warm delivery is trusted
no more than a cold one). The exchange then GETs the app's OWN
configured base URL, never a host taken from the incoming URI. No
intent redirection; only the App Link, the LAUNCHER and the dev
activities are exported.

LOGIN-CSRF: a co-installed app can fire the exported callback with a
VALID link for an account the user never requested. SignInController
remembers the requested address (PendingSignInStore, persisted so it
survives process death); the callback refuses a link whose email does
not match, and refuses one with no pending request at all (MISMATCH),
before any exchange. This is "never act on extras an external app could
supply" applied to the whole flow.

THE FOUR-DISTINCT QUESTION, ANSWERED HONESTLY. The relay's AC2 asks for
"expired, used, unknown, malformed" as distinct states. The server
collapses expired/used/unknown into ONE invalid_link 400 by design
(callback route lines 43-52: distinguishing them would tell whoever
holds a stale link whether it was ever valid). The client consumes that
exactly (R195), so it renders what it can honestly tell apart:
  MALFORMED    - a foreign host/scheme/path or a missing parameter,
                 decided by the client before any call.
  MISMATCH     - a valid link for an unrequested account (login-CSRF),
                 decided by the client before any call.
  INVALID_LINK - the server's one 400 for unknown/expired/used.
  NETWORK      - could not reach the server.
The three expired/used/unknown are not separable; that limit is the
contract's, not a client defect, and is stated rather than faked.

SEEN (by adb am start, the intent fired directly at the activity):
  MALFORMED    - fired a foreign-host URI -> "Ce lien est incomplet ou
                 incorrect." The app's own validation refused it.
  MISMATCH     - fired a valid-shape URI for stranger@x.ch with no
                 pending request -> "Ce lien ne correspond pas a la
                 demande de connexion en cours sur cet appareil."
                 Delivered via onNewIntent (warm), re-validated.
  INVALID_LINK - fired a bogus token with the pending email set ->
                 server 400 invalid_link -> "Ce lien n'est plus
                 valable... demandez-en un nouveau."
  SIGNED       - fired the REAL token from the outbox -> server 200 ->
                 "Vous etes connecte." (the AC1 loop below).

SINGLE-FLIGHT REFRESH (increment 5)
--------------------------------------------------------------------
Two requests racing an expiry must not BOTH refresh: the second's
refresh replays the first's rotated token, and a replay ends the whole
session (R210 turned against ourselves). SessionManager.refresh takes a
mutex; a caller that finds the stored refresh token already rotated
while it waited returns the new pair rather than refreshing again.

PROVEN by firing TEN concurrent refreshes and asserting EXACTLY ONE
rotation reached the server. FW22's report records a TWO-way race
PASSING against a broken implementation and only the ten-way catching
it, so this deviates upward from the relay's "two" deliberately, and
says so.

R210's distinction is kept in the outcomes and seen in the walkthrough:
an expired access token whose refresh fails is SessionExpired (an
ordinary lapse); revoked_session/unknown_token on a still-held token -
what a replay produces - is SessionEnded, tokens cleared. The server
does not label the replay in the refresh answer (auth-api.ts defers
that to FW26's account screen), so the client distinguishes
revoked_session from an ordinary expiry, which is the achievable and
honest form of "renders differently from expiry".
