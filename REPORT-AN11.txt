DETERMINISTIC, NO DRAIN RACE (the fix the prompt asked for). The prior session hit
a race: it recorded a pending day, restarted the container, relaunched and tried to
read the releve before WorkManager drained the row. This session does not restart
before reading. ReleveController.load() fires only on init/retry, and the Room
observer folds pendingCount onto the EXISTING Loaded state via copy() WITHOUT
refetching (the controllers survive tab switches via MainShell's `remember`). So:
the releve is loaded from the server (offline=false); the container is STOPPED (the
server is unreachable but the device is still networked, so the enqueued SyncWorker
runs and is refused - the row stays PENDING, never drained); a day is recorded on
Aujourd'hui; switching back to the Releve tab shows the same server document with
the pending line folded in. Driver booleans: r287line=true, offline-banner-absent
=true. R119-by-count on the count is asserted in increment 2's committed test.
