R217: WHAT THE ANSWER NOW CARRIES
--------------------------------------------------------------------
  { "status": "ok", "written": 2, "duplicates": 1,
    "entries": [ {...}, {...}, {...} ] }

  THE SHAPE IS THE READ PATH'S, FROM THE READ PATH'S CODE. Not a
  second serialiser that agrees today: `readEntriesWhere` is now the
  one home (R206) and both routes call it. A test asserts the two
  routes return objects that are equal for the same day, which is
  the enforcement point rather than the comment above it.

  DUPLICATES ARE INCLUDED, AND THAT IS THE HALF THAT MATTERS. A
  client retries precisely because it never received the first
  answer. A replay that withheld the rows would deny the timestamps
  to the one caller that cannot obtain them any other way, and the
  second round trip would survive in exactly the case R217 exists to
  remove. The test that says so is named for it.

  THE SNAPSHOT IS READ INSIDE THE TRANSACTION. Read afterwards it
  would be a different moment from the one being reported, and a
  concurrent write could land between them - so the answer would
  describe a state the caller's request never produced.

  A REFUSAL CARRIES NO `entries` KEY AT ALL. The batch is
  all-or-nothing; an error must not hand back rows suggesting
  something landed.

THE DOCUMENT NOW SAYS WHAT THE FREEZE FORBIDS
--------------------------------------------------------------------
Three operations forbidden - renaming a field, removing a field or
code, and changing what an existing field MEANS. The third is called
out as the worst, because nothing fails: the client parses happily
and is wrong.

Four things left free, and the first is the escape hatch: adding a
field to a RESPONSE. Adding one to a REQUEST is NOT free, and the
asymmetry is stated - a new optional request field is fine, making an
existing one required is not.

R217 is written into the document as the worked example, so the next
session meets the reasoning rather than re-deriving it. A test
asserts all five phrases are present: without it, a future session
reads FROZEN as "nothing changes" and leaves improvements unmade that
break nobody, which is how this response nearly kept its two round
trips.

R218: WHY THE DIRECTION HAD TO BE REVERSED
--------------------------------------------------------------------
THE RULING'S WORDING WAS "a module that imports the Prisma client
selects test:db". Measured before building it:

  lib/entries/schema.ts      imports no '@prisma/client'
                             imports no '@/lib/db/client'

So the forward rule does not select the module whose omission raised
Q77 in the first place. schema.ts is the API contract that tests/db
drives end to end, and it reaches the database only by being imported
BY write.ts, which imports it.

THE QUESTION THE SELECTOR ACTUALLY ASKS is "could changing this file
break test:db?", and that is answered by reachability FROM the suite
rather than by what each file imports. So `databaseClosure` walks the
import graph outward from every tests/db/*.test.ts and returns what
it reaches - 85 files today.

  IN   lib/entries/schema.ts   <- Q77's case, now covered
  IN   app/api/v1/entries/route.ts  <- R204: the suite drives the
                                      route, so the route is in scope
  IN   lib/entries/day.ts      <- three hops from a seed
  IN   lib/calc-engine/index.ts
  out  lib/ui/core/styles/tokens.scss

  THE PATH LIST SURVIVES AS A FLOOR, NOT AS THE RULE. prisma/**,
  lib/db/**, tests/db/** and the two configs stay, because a
  migration and a config are not reachable through an import. What
  they are no longer asked to do is KEEP UP - which is the part that
  failed three times.

  A REGEX, NOT A PARSER, and the trade is stated where it lives: a
  TypeScript program costs seconds on every gate run to answer in a
  different way what this answers in milliseconds. It over-matches -
  a specifier inside a comment counts - and over-matching is the SAFE
  direction: the cost is running test:db when it was not needed,
  never skipping it when it was.

  AND THE OVER-SELECTION DIRECTION IS ASSERTED, because a closure
  that swallowed the repository would make test:db run on every
  change and the selection would stop meaning anything - R132's own
  failure mode, reached from the safe side. Plant B proves the test
  fires.

A TEST THAT TAUGHT ME THE CONTRACT
--------------------------------------------------------------------
I wrote a test asserting that a batch naming one day twice collapses
into a single entry in its final state - guarding against an answer
built from each upsert's return value, where the first row would be
stale by the time it was sent.

It failed, and the reason was better than the test: the schema
already refuses a batch that repeats a (dayDate, portion), with

  "entries[1] repeats 2026-04-07 FULL, already at entries[0].
   One batch may not carry two versions of one day."

So the hazard cannot arise - it is foreclosed a layer earlier than
where I was defending. The test now asserts the rule that actually
fires, including that nothing landed, and says in its own comment why
it was rewritten: if that validation rule is ever relaxed, the
answer's freshness quietly becomes load-bearing and this is where
somebody should find that out.

Recorded because the honest version of "my test failed" here is "my
test was wrong about the product", and the product was better than
the test.

FINDINGS: A LATE REPLAY SILENTLY DESTROYS AN EDIT
--------------------------------------------------------------------
FOUND WHILE READING THE WRITE PATH FOR R217, CONFIRMED BY PROBE, AND
THEN DEMONSTRATED END TO END IN THE WALKTHROUGH.

The duplicate set is one query:

  tx.entry.findMany({ where: { userId,
    clientMutationId: { in: items.map(i => i.clientMutationId) } } })

`Entry.clientMutationId` holds the id of the LAST write applied to
that row, not every id ever applied. So:

  1. mutation A writes 2026-04-07 as CH.        row carries A
  2. mutation C edits it to HOME.               row carries C
  3. the queue retries A - as a queue does when
     it never received the answer to A.
  4. the lookup for A finds nothing. A is NOT a
     duplicate. A is APPLIED.
  5. the day is CH again. The edit is gone.

WALKTHROUGH STEP 7, VERBATIM:

  status: ok  written: 1  duplicates: 0
  {"clientMutationId":"r217-a","dayDate":"2026-04-07","kind":"CH",
   "note":"bureau","firstRecordedAt":"2026-09-21T10:03:34.157Z",
   "lastModifiedAt":"2026-09-21T10:03:35.016Z"}

`written: 1` on a mutation id the server had already applied, and the
row is back to CH with the pre-edit note. The reader's correction is
gone from the record.

WHAT IS NOT LOST: the trail. EntryEvent is append-only, so the edit
and the revert are both on it, and lastModifiedAt moves. The
DOCUMENT can still show what happened. It is the current state - what
the app displays and what the dossier counts - that is wrong.

WHY IT IS PLAUSIBLE IN THE FIELD RATHER THAN THEORETICAL: step 3 is
exactly what an offline queue does. The client posts A, the tunnel
eats the response, the user edits the day on the same device, and the
queue flushes A on reconnect. D30's idempotency key is doing its job
for the SIMPLE replay - walkthrough step 2 proves that - and stops
working the moment the row has moved on.

THE FIX IS NOT OBVIOUS, WHICH IS WHY IT IS A QUESTION. The dedup set
could be built from EntryEvent, which holds every mutation id ever
applied - one more query and an index. But that changes what D30
MEANS: today "already seen" is a property of the row, and it would
become a property of the account's history. That is a product
decision about what a client may assume, and this contract froze two
days ago.

NOT TOUCHED. The design panel predicted this in the abstract during
FW23 - "inequality proves only that the last write was not yours" -
and the prediction was about the CLIENT re-sending. This is the
server accepting what the client re-sent. Same root, other end.

QUESTIONS
--------------------------------------------------------------------
Q78. *** THE ONE THAT MATTERS. *** A late replay of an already-applied
     mutation id silently reverts a newer edit - confirmed end to end,
     reproduction in FINDINGS. Should "already seen" be a property of
     the ROW (today) or of the ACCOUNT'S HISTORY (build the dedup set
     from EntryEvent, which holds every id ever applied - one more
     query and an index)? The second closes it, and changes what D30
     means for a client. It is a product decision on a contract that
     froze two days ago, so it is asked rather than answered. If the
     answer is the second, it should land before AN5 rather than
     after, for the same R217 reason: response-shape changes are
     cheap now and expensive once handsets have them.

Q79. `conflict` is frozen in the document and may have no producer
     reachable from the route. Keep it as a reserved code, or remove
     it before AN5 ships and a client branches on something that
     cannot happen? Removing is the operation the freeze forbids, so
     it is now or never.
