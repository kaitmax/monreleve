MAPPING
--------------------------------------------------------------------------------
Each minified build writes its mapping to app/build/outputs/mapping/<variant>/mapping.txt
(release and audit both present, ~27-28 MB each). It is NOT committed - build/ is
gitignored (verified: git check-ignore flags it; no mapping.txt is tracked). WHY IT IS
NEEDED: there is no crash-reporting SDK, by design, so a user-reported stack trace from
a release build arrives obfuscated; mapping.txt is what deobfuscates it. It is a
PER-RELEASE artifact (R8's renaming differs per build), so it must be ARCHIVED for each
released versionCode. In AN14b it is uploaded to the Play Console (which stores and
applies it); until then it lives beside the build and the release process must keep it.

VERSIONCODE
--------------------------------------------------------------------------------
THE SCHEME: a plain monotonic integer, +1 per uploaded build, never reused and never
decreased. WHY: Play rejects an upload whose versionCode is <= the highest already
uploaded, forever, and the ceiling is 2,100,000,000; the simplest rule that cannot be
got wrong is a hand-incremented integer, and it leaves the whole range. It is NOT
derived from versionName (a semver bump must not force a code jump) nor from the wall
clock (opaque, and two builds in one minute would collide). It stays 1 until the first
upload (AN14b); reversible until then. When AN14b wires CI, the counter can move to a
CI build number, which is still monotonic.
(While editing this block I accidentally DROPPED versionName, and the aapt2 read of the
built APK - not any gate, which does not check versionName - caught it: the APK briefly
declared versionName=''. Restored to "0.1.0"; the final APK declares versionName
"0.1.0". Recorded under DEVIATIONS.)

targetSdk 36, the R8 keep set (empty) - is identical. So a claim proven on the audit
variant's MINIFIED bytecode is a claim about the release's minified bytecode, with the
