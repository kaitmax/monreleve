LAST YEAR'S RELEVE - CAN THE APP SHOW IT?
====================================================================
STATE CONFIRMED (from source): the app shows ONLY the current tax year.
`taxYear = Year.now(Europe/Paris)` is computed once in MainActivity and
threaded through MainGraph.build to every controller; ReleveController
takes that one `taxYear` and `load()` always fetches it. There is no year
selector. This is exactly PARKAN-26 (AN11), which deferred FD7's year
chip as the conservative option and recorded it "NEEDS an operator
decision on whether past-year viewing is wanted, and if so which years
the selector offers."

The DossierApi layer ALREADY supports any year: `DossierApi.fetch(year)`
reads `/api/v1/dossier?year=$year` and caches per year; ReleveController's
fetch seam is `suspend (Int) -> DossierResult`. Only the composition root
pinning one year (MainActivity `taxYear = Year.now(Europe/Paris)`, threaded
through rememberMainControllers -> MainGraph.build) stops a past-year view.
On the device this session (see THE PHONE) each account opened on its
CURRENT-year releve (2026) with no way to reach 2025.

DECISION: the year switch is PARKED, not built this session (PARKAN-26).
R156 conservative + reversible, no advisor. The reasons, in order of
weight:
  a) WHICH YEARS TO OFFER IS AN UNRESOLVED PRODUCT DECISION, and CLAUDE.md
     forbids inventing one. PARKAN-26 already records it: "NEEDS an operator
     decision on whether past-year viewing is wanted, and if so which years
     the selector offers." The prompt gives the MOTIVATION (from January a
     person needs year N-1) but not the SET or the edge-case presentation.
  b) THE READ-BACK PRODUCED EVIDENCE THAT THE NAIVE VERSION MISLEADS.
     Camille's 2024 returns a syntactically valid, all-zero "0 % compliant"
     releve (basis 80, everything 0) because her activity began in Sep 2024
     but no 2024 data exists; Sam's 2025 returns a 500. A selector that
     offered "every year in the activity period" would present a misleading
     document (the R198 shape, client-side) and a hard error. Choosing the
     offered set AND the empty/closed-year banner copy is the product
     decision in (a), now with a concrete reason it matters.
  c) IT IS NOT "PURE PRESENTATION OF A FIGURE THE PAYLOAD CARRIES" (the
     prompt's and the orchestrator's bar for adding in this task). It is a
     new UI surface: mutable selected-year state in ReleveController (today
     `taxYear` is an immutable constructor val used by load/export/
     pendingCount), a selector in ReleveHeader, French copy in fr/ReleveCopy,
     JVM controller tests, and REGENERATED Paparazzi baselines - under a
     RAM-constrained machine and a thermally-flaky phone.

ANDROID GATE IMPLICATIONS: none. No Android code changed this session, so
:app:gate is unaffected and no baseline moved.

WHAT BUILDING IT WOULD TAKE (so the follow-up is mechanical once the year
set is decided):
  - ReleveController: add a `selectedYear` StateFlow initialised to taxYear,
    a `selectYear(year)` that re-runs load() and recomputes pendingCount for
    that year; have export()/pathFor()/fallbackFilename() read selectedYear.
    (DossierApi already caches per year, so switching back is instant.)
  - A bounded year list: the stated use case is {current, previous}; do NOT
    offer years with no data (Camille 2024) or out-of-activity years (Sam
    2025) - that is the operator decision, and the empty/closed banner copy
    with it.
  - ReleveHeader: a small segmented/chip selector (existing tokens), FD7's
    year chip (deferred under PARKAN-26).
  - fr/ReleveCopy: the chip label(s) and a "closed year" vs "provisional"
    banner distinction (BANNER_PROVISIONAL already exists for the current
    year).
  - Tests: a controller test driving selectYear across a scripted fetch;
    Paparazzi baselines for the selector at default + 200 % (regenerated
    with a stated reason, R135).
