INCREMENT 3 - R220
--------------------------------------------------------------------
RED     "never treats another user mutation id as seen"
        AssertionError: expected undefined to be 1
        The second account's write was refused 409 rather than landing.
GREEN   337 in the database suite.

MIGRATION  DROP INDEX Entry_clientMutationId_key
           CREATE UNIQUE INDEX Entry_userId_clientMutationId_key
                 ON "Entry"("userId", "clientMutationId")

SAFE ON EXISTING DATA BY CONSTRUCTION: the new constraint is strictly
WEAKER than the one dropped. Anything unique globally is unique within
an account, so no existing row can violate it. Written by hand from
`prisma migrate diff` output because `migrate dev` refuses to run
non-interactively when it has a warning to show, and applied with
`db:deploy`.

PLANTS, on the live index rather than on source:
  the GLOBAL unique restored  -> caught by BOTH layers: the database
      constraint test and the route behaviour test
  the composite DROPPED       -> caught by two constraint tests
Restores verified by reading pg_indexes back, and the first restore
had NOT landed - a shell-mangled $executeRawUnsafe - which is why the
verification exists.

THE REACHABILITY CHANGE, AGAINST THE FREEZE'S ASYMMETRY. No field
changes. The response for a given request changes only in the
direction of SUCCEEDING where it previously failed wrongly: a second
account's legitimate write now lands instead of being refused 409.
Nothing a client could have relied on is removed, because nothing
should have relied on a stranger's id reserving its own.

Q79 IS NOW ONE REASON. The `conflict` row reads: reserved, no path
produces it today, kept for the out-of-order case in 6.4.

AND I VERIFIED "NO PATH PRODUCES IT" RATHER THAN INHERITING IT. The
one case I could construct that might still raise P2002 is a
concurrent double-submit of the same mutation id, where two
transactions both find nothing and both insert. Measured:

  submission A: ok, written 1, duplicates 0, code null
  submission B: ok, written 1, duplicates 0, code null
  rows created: 1

No conflict - the upsert's update branch absorbs the second. So the
document's claim holds for the ordinary AND the concurrent case.

  A SIDE-OBSERVATION worth one line: both callers were told
  written: 1 while ONE row exists. Not data loss - the row is correct
  and R217's returned entries are accurate - but a client summing
  `written` across retries to track queue progress would over-count.

THE PRE-FW24 CHECK
--------------------------------------------------------------------
Asked for before FW24 rather than during it: does the demo year still
satisfy R197 (a scenario consistent as one) and R120 (two derivations
of a figure that disagree) after R219's and R220's migrations touched
these tables?

  demo-year.test.ts   26 passed, including its R120 block
  shape after both migrations:
    users 2, entries 262, events 264
    events carrying a mutation id :   2
    events with NULL (pre-R219)   : 262
    client ids shared across rows :   0

BOTH HOLD. And the useful fact for FW24: the demo year's trail is
entirely in the PRE-R219 shape, which a fresh seed reproduces. That is
the exact case R219's Entry fallback exists for, so it is exercised by
the demo year rather than only by its own test.

FW24 IS UNAFFECTED: lastModifiedAt derives from EntryEvent.recordedAt
and action, never from clientMutationId, so aggregation reads nothing
that changed. R220 changed an index, not a column.

  ONE THING TO DECIDE LATER, NOT NOW: the seed does not populate
  EntryEvent.clientMutationId, so a freshly seeded demo year is
  unrealistic in that one respect - a real user's events, written
  through the API after R219, carry it. It does not affect FW24. It
  would affect an AN-series task testing dedup against the demo year.
  Q81.
