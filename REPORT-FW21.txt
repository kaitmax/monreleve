SCHEMA JUSTIFICATION (R187)
--------------------------------------------------------------------
A schema is a contract with a client that cannot be redeployed. From
this task the Android app is a consumer: a column renamed later is a
migration plus an app release plus every version still in the field
calling the old shape. So every field is in SPEC 8 or named here.

User - all in SPEC 8: id, email (unique), emailVerified, name, canton,
employmentRate, denominatorKind, exactTotalWorkDays, granularity,
loggingMode, detectionConsentAt, activityStartDate, reminderTime,
reminderEnabled, organizationId, createdAt.

  organizationId   D33, RESERVED, no features built. In SPEC. Added
                   now because a nullable column on an EMPTY table
                   costs nothing - no index, no constraint, no code
                   path reads it - and the same column on a table
                   holding real rows is a migration. It is the one
                   field here that exists for a future, and it is
                   specified rather than invented.
  reminderTime     A STRING, NOT A DateTime, and this is the one
                   modelling decision in the file. "17:30" is a
                   wall-clock time: it means half past five where the
                   reader lives, on both sides of a DST boundary,
                   which a timestamp cannot say without carrying a
                   date nobody meant.
  no `image`       The Auth.js AdapterUser type carries one. Nothing
                   in SPEC 8 and nothing in this product displays an
                   avatar, and an unused column is a promise to a
                   client that will eventually read it. See P4-1: if
                   FW22's adapter needs it, it is one nullable column
                   on a table that will still be empty.

Device - all in SPEC 8 (D21, replacing PushSubscription): id, userId,
fcmToken (unique), platform, appVersion, lastSeenAt, createdAt.

Entry - all in SPEC 8 v2.1: id, userId, dayDate, portion, kind,
absenceReason, clientMutationId (unique), note, provenance,
detectedKind, detectedAt, clientClaimedAt, firstRecordedAt, updatedAt.
Unique (userId, dayDate, portion); index (userId, dayDate).

  dayDate @db.Date   A DAY IS A DAY. As a timestamp the recorded day
                     would depend on the offset of whatever wrote it -
                     2026-04-07 in Paris is 2026-04-06T22:00Z, and a
                     naive read gives back the sixth. SPEC 8: "A UTC
                     day-boundary bug here is a wrong record." A test
                     asks information_schema for EVERY dayDate column
                     in the schema, so EntryEvent cannot drift from
                     Entry.
  the unique key     IS THE SYNC CONTRACT, not a tidiness index. A
                     client that posts, loses the response and posts
                     again must not produce two rows for one
                     afternoon: the ratio this product computes is a
                     count of days, so a duplicate is a wrong answer.
                     Deliberately NOT (userId, dayDate) - a half-day
                     pair is what D9 exists for.

EntryEvent - all in SPEC 8: id, userId, entryId, action, kind,
provenance, detectedKind, dayDate, portion, recordedAt,
clientClaimedAt. Indexes (userId, entryId) and (entryId, recordedAt).

  duplicated fields  ON PURPOSE, not normalisation debt. An event
                     records what was true AT THE TIME, so reading the
                     trail does not depend on the row still existing
                     or still saying the same thing. A trail that had
                     to join back to Entry would report today's value
                     for a day corrected twice.
  NO FK on entryId   SPEC 8 declares none, and the reason is the
                     same. An entry that is deleted leaves its events
                     behind, still readable, still carrying the kind
                     and the day they recorded. A cascade there would
                     let a deletion erase the evidence that the day
                     was ever declared.
  user relation      THE ONE ADDITION, justified by D11: "suppression
                     du compte ... removes user, entries, events,
                     devices". Erasing a person must erase their
                     events, and the cascade is how.

CONSTRAINTS - R196, and why there are four rather than one
--------------------------------------------------------------------
The prompt asks for the absence rule as a database concern. SPEC 8
states three more invariants in the same grammatical form, so all of
them are constraints. Prisma's schema language cannot say "required
iff", so these are hand-written below its output - and a rule that
lives only in a Zod schema lives in ONE of the writers. The seed is a
second, a migration a third, a support query at 02:00 a fourth.

User_employmentRate_range
  1-100. A rate of 0 is not a part-timer, it is somebody who does not
  work here.

User_exactTotalWorkDays_iff_exact
  BOTH DIRECTIONS. Forward: EXACT with no total leaves the engine
  without a denominator. Reverse - the one that bites: a total left on
  a SIMPLIFIED240 row is a number a later reader will use, and the
  engine takes its denominator from the KIND, so the row carries a
  figure that disagrees with the calculation and nothing says which
  wins.

Entry_absenceReason_iff_absent
  BOTH DIRECTIONS. ABSENT never reaches the engine - absences are
  filtered out before counting - so a CH row carrying an absence
  reason is a day that READS as absent in the dossier and COUNTS as
  worked in the calculation.

Entry_detectedKind_when_detected
  SPEC 8: "Whenever a proposal existed, detectedKind is stored EVEN
  WHEN THE USER OVERRODE IT. Deleting the overridden detection to make
  the record look tidier is a review rejection." A DETECTED_CORRECTED
  row with no detectedKind is that tidied record: the correction has
  nothing left to be a correction OF.
  FORWARD DIRECTION ONLY - see QUESTIONS.

IMMUTABILITY PROOFS (AC2)
--------------------------------------------------------------------
Three triggers. Each rejection below was produced by attempting the
write and capturing what came back; each is asserted by the RULE'S
NAME, never by "it threw" - a test that only checks for rejection is
satisfied by a typo in a column, a missing foreign key, or the
database being down.

REJECTED - EntryEvent UPDATE
  prisma.entryEvent.update({ data: { kind: 'HOME' } })
  -> Database error. Code: P0001. Message: EntryEvent is append-only
     (SPEC 8): UPDATE rejected. An event records what was true at the
     time it was written. Correcting one in place makes every dossier
     it backs unverifiable - append a new event instead.

REJECTED - EntryEvent UPDATE THAT CHANGES NOTHING
  Same message. The rule is about the STATEMENT, not whether the
  bytes moved: a trigger that let harmless updates through would have
  to decide what harmless means, inside the one table that must not
  be argued with.

REJECTED - EntryEvent DELETE (single row, user alive)
REJECTED - EntryEvent DELETE (deleteMany, no WHERE)
  -> Database error. Code: P0001. Message: EntryEvent is append-only
     (SPEC 8): DELETE rejected while the user still exists. An event
     may only disappear together with the person it belongs to (D11,
     account deletion) - never on its own.

REJECTED - Entry.firstRecordedAt moved BACKWARD to 2020-01-01
REJECTED - Entry.firstRecordedAt moved FORWARD to 2030-01-01
  -> Database error. Code: P0001. Message: Entry.firstRecordedAt is
     immutable (SPEC 8): attempted to change X to Y. It is the server
     clock at first receipt, and the late flag and the dossier both
     rest on it.
  BOTH DIRECTIONS because the rule is not "cannot be backdated".
  Moving a receipt forward hides a record made on time as effectively
  as moving one back hides a late one.

ACCEPTED, and this half is not padding - a table nobody can write to
satisfies every rejection above and is useless:
  EntryEvent INSERT           or there is no trail at all
  Entry UPDATE of kind        SPEC 8's "latest wins" correction path,
                              which is the product's main interaction
  Entry UPDATE naming
    firstRecordedAt with its
    own current value         an ORM is entitled to write every
                              column; the trigger compares VALUES
                              rather than inspecting the statement
  User DELETE cascading to
    entries and events        D11, and /confidentialite publishes it

WHY DELETE IS NOT SIMPLY REFUSED - the design decision in this task.
D11 says account deletion "removes user, entries, events, devices". A
trigger refusing every DELETE would enforce the audit rule by breaking
the privacy one. So: an event may never be removed ON ITS OWN, which
is a record being tidied; it may disappear WITH the person, which is
the record being destroyed at their request with nothing left behind
to be misread.

The two are told apart because PostgreSQL deletes the parent row
before firing the referential action, so the User is already invisible
to the transaction when a cascade reaches the trigger, and still
visible when somebody deletes an event directly. VERIFIED EMPIRICALLY
ON THROWAWAY TABLES BEFORE THE TRIGGER WAS WRITTEN rather than assumed
from documentation - a probe showed "parent still visible = t" on a
direct delete and "= f" during the cascade - and both directions are
asserted in the suite, so a PostgreSQL that reordered this would fail
a test rather than silently make every account undeletable.

WHY A TRIGGER AND NOT A REVOKE OR A RULE. REVOKE binds a role: it
holds against the application user and not against the superuser a
migration runs as, and it is invisible in the schema. CREATE RULE ...
DO INSTEAD NOTHING discards the write silently, and an audit trail
that quietly ignores writes cannot be told apart from one that accepts
them. A trigger raises, naming the rule.

THE ERRCODE REVERSAL. All three RAISEs first carried USING ERRCODE =
'restrict_violation' - SQLSTATE 23001, semantically correct. Prisma
maps it to P2003 and reports "Foreign key constraint violated on the
(not available)", with the real text buried in
err.meta.driverAdapterError.cause. FW23's error handling would have
been written against that. Left at plpgsql's default P0001, Prisma
surfaces the message itself. A GUARD THAT REJECTS CORRECTLY AND
EXPLAINS ITSELF WRONGLY sends the next person to the wrong place, at
the moment they are least able to argue with it.

NOTICED BUT NOT TOUCHING
--------------------------------------------------------------------
1. AM/PM ARE ONLY LEGAL WHEN granularity = HALF_DAY (SPEC 8), and
   that is NOT enforced in the database. It cannot be cheaply: a CHECK
   constraint cannot reference another table, so it would need a
   trigger. And it should probably not be - granularity is mutable
   while entries are historical, so a person switching back to whole
   days would retroactively invalidate their own past half-days and a
   trigger would block legitimate edits. This marks the boundary of
   R196's "where the database can express it". FW23's write path.

QUESTIONS
--------------------------------------------------------------------
Q66. Entry_detectedKind_when_detected is enforced in the FORWARD
     direction only: a DETECTED_CONFIRMED or DETECTED_CORRECTED row
     must carry detectedKind. The reverse - a MANUAL row must carry
     NONE - follows from the definitions ("MANUAL when the user chose
     it outright", so no proposal existed) and would make the pair
     symmetric with User_exactTotalWorkDays_iff_exact.

     I did not enforce it because SPEC does not STATE it, and the
     asymmetry of cost is real: enforcing only what is stated can
     never refuse a row SPEC permits, while enforcing what is merely
     implied can. A MANUAL row carrying a detectedKind would be a
     record that discloses a signal while claiming none existed, which
     argues for the constraint.

     Ruling wanted. If yes, it is one line in a new migration against
     an empty table.

Q67. EntryEvent has no foreign key on entryId, matching SPEC 8. That
     means a deleted Entry leaves events pointing at an id that no
     longer resolves - deliberate, because the trail must outlive the
     row it records. Confirming this is the intent, since FW23's
     delete path and FW24's dossier both depend on it.
