INCREMENT 3 - CONTAINER
================================================================================

Three named widths against R64's three tokens, and no fourth by any route.

"NO ARBITRARY WIDTHS ACCEPTED - the prop is a union, and a test asserts no
other value compiles." That clause cannot be tested at runtime: there is no
value you can pass to show that a DIFFERENT value would have been refused. A
runtime test could only show an invalid width is ignored, which is a weaker
claim and would still let <Container width="1337px"> compile and ship.

So the assertion is a type, by R65's mechanism. Container.types.ts carries
three directives:

  '1337px'              an arbitrary length - what a caller reaches for
  'content'             a plausible NAME - the old $layout-content-max, and
                        more dangerous than the first because it looks like it
                        belongs
  a value typed string  the one a caller actually hits, from a route param or
                        a prop threaded through a wrapper. The two literals
                        would be rejected by a widened union too; only this
                        proves the prop is not assignable FROM string.

Falsified by widening the union to `string`: all three become TS2578 and the
build fails.

The stylesheet is guarded too. The test COUNTS the max-width rules and requires
every one to name a --layout-* width, so a fourth is caught even when it uses a
token rather than a raw value. Falsified by appending a data-width="wide" rule:
"expected 4 to be 3".

TWO ENVIRONMENT LESSONS, both R61.

  The widths are asserted as TOKEN NAMES, not pixels. jsdom computes no layout
  and resolves no custom property - getComputedStyle returns the literal
  "var(--layout-public)". The numbers are pinned centrally against the compiled
  token layer; what the component owes is reaching for the right token.

  Reading the stylesheet needed an explicit path, NOT new URL(...,
  import.meta.url). Under jsdom import.meta.url is an http:// URL and
  readFileSync rejects it with "The URL must be of scheme file". The FW8
  component tests use the URL form safely because they run in NODE; this file
  needs jsdom for render(). Invisible until it throws.

Container emits a plain div, not a landmark: it is layout, and a landmark here
would fight the page that already has one.

ONE GAP RECORDED AT THE SITE, not a blocker for increment 3 and a blocker for
increment 4: the media query uses a raw 768. See Q1.

THE R66 SWEEP - AND WHY THE FIRST VERSION OF IT WAS WRONG
================================================================================

My first sweep concluded: only two files use Testing Library queries, the two
formatted-number assertions were already fixed, no normalising matcher exists
anywhere, and all lib/fr copy is codepoint-clean. An adversarial audit refuted
three parts of that.

THE MECHANISM, MEASURED - and it corrects me. I had assumed the normaliser
touches both sides of a comparison. It touches only the DOM side:

  DOM U+00A0  vs  matcher ASCII space  ->  MATCHES, silently
  DOM U+202F  vs  matcher U+202F       ->  NO MATCH, loud red against
                                           correct content

Both directions are bad and the asymmetry is what makes one silent. This is
live, not hypothetical: correct French typography puts U+00A0 before a colon,
lib/fr/errors.ts already ends a sentence with one, and every copy file is
marked TODO-COPY. When copy review lands, a text query on that sentence goes
red against CORRECT copy - and the obvious repair, retyping the constant with
an ordinary space, lands exactly on the silent row.

FINDING 1 - R66 HAD NO ENFORCEMENT. My claim that no normalising matcher exists
was true of USAGE and false of AVAILABILITY: @testing-library/jest-dom is in
package.json, installed, imported by nothing, and its whole normalising set -
toHaveTextContent, toHaveValue, toHaveDisplayValue, toHaveAccessibleName,
toHaveAccessibleDescription - was one import away with nothing stopping it.
Now fenced by no-restricted-imports carrying the measured reason.

The fence went into the EXISTING spike-quarantine block, not a new one: flat
config replaces a rule rather than merging it, so a second block for the same
files would have silently deleted the spike fence. Verified both still bite.

FINDING 2 - A COMMENT THAT CLAIMED SOMETHING FALSE. DataGrid's header said "a
cell is rendered exactly as given, U+202F and all". It was not: the assertion
compares formatDays output against formatDays output, so changing
GROUP_SEPARATOR moves both sides together. Proven by changing it to an ordinary
space:

  the old tautological assertion   1 passed   (silently green)
  the new codepoint assertion      FAILED     expected 32 to be 8239

The claim is now true rather than softened. What it pins differs from what
format-number.test.ts pins: not the formatter, but that the component does not
sanitise or re-encode on the way through.

FINDING 3 - TWO NORMALISERS STACKING IN PLAYWRIGHT.
e2e/composants.visual.spec.ts read innerText() and then trim(): innerText is
the BROWSER-rendered text, and trim() strips U+00A0 and U+202F because both are
Unicode Space_Separator. A stray no-break space either side of the figure was
silently removed. Now textContent, compared exactly.

ALSO CONVERTED, while green rather than later under a red run: every prose text
query in FieldGroup and DataGrid now reads textContent. FieldGroup's use the

THE CONTRAST AUDIT WAS ABOUT TO BLOCK A CORRECT COMPONENT
================================================================================

Found by the pre-flight inventory, before a line of PublicShell was written.

The audit's derived half walks every component stylesheet, takes each block
that sets a colour, and measures it against BOTH page surfaces at the gate its
font-size implies. Right for text on the page; wrong for anything painting its
own background. The header CTA is "brand fill, white label", so its rule sets
colour: var(--colour-surface) over background: var(--colour-brand). Measured
with a probe stylesheet carrying exactly that rule:

  __Probe .cta: --colour-surface on --colour-surface is 1.00:1, below 4.5:1
  __Probe .cta: --colour-surface on --colour-canvas is 1.06:1, below 4.5:1

White on white, against a 4,5 gate, on the element with the highest contrast in
the product.

WHY THAT IS WORSE THAN A FALSE RED. The natural response mid-increment is to
add the CTA to the exemption list beside .chip and .icon - and that removes the
header's only text from the audit permanently. An audit that fires on correct
work teaches people to exempt things, which is how it stops covering what is
worth covering.

Fixed: a rule declaring its own background is audited against THAT, once;
anything else keeps both surfaces. A test asserts BOTH BRANCHES are exercised,
because if every rule declared a background SURFACES would never be checked,
and if none did the new branch would be dead code that looks alive. 87 tests
with the probe, 86 without.

That test needed its own correction: its first version asserted a declared
background is never one of the page surfaces, and failed on FieldGroup's input,
which sets background: var(--colour-surface) and is correct.

DEVIATIONS
================================================================================

1. FIELDGROUP TAKES A FUNCTION AS children. The prompt says "the control slot
   (children - composition, not a props bag)". A plain slot cannot be wired:
   FieldGroup would have to reach into an element it does not own via
   cloneElement and assume the child accepts aria-describedby, which is
   untypeable and silently wrong for a fragment or a wrapped child. A props
   bag would fix the control to <input>. Documenting the contract would make
   the guarantee a convention, which is what the component exists to replace.
   The function hands the caller exactly the attributes the control must
   carry - props going TO the caller rather than coming from it, which is the
   direction that makes them provable. Every test asserts on the real <input>
   the caller rendered.

   Six of those tests failed on their first run against a component the markup
   dump proved CORRECT. Testing Library registers its own afterEach cleanup
   only when a global afterEach exists, which needs vitest globals: true - not
   set in this repo, on purpose. Without an explicit afterEach(cleanup) every
   render accumulates in one jsdom document and screen queries search a page
   holding several copies. The same fix was applied to FW8's axe sweep, where
   all eighteen states were accumulating: it passed either way, but the rules
   axe evaluates against the DOCUMENT rather than the container - duplicate
   ids above all - were being asked about a page that never exists.

2. TWO DATAGRID TESTS WOULD HAVE PASSED FOR THE WRONG REASON, same cause.
   Testing Library's default normaliser collapses whitespace, and U+202F - the
   narrow no-break space formatDays uses as a group separator - is whitespace
   to that regex. So getByText(formatDays(1247)) searches for "1<U+202F>247"
   while the DOM text has been normalised to "1 247" with an ordinary space.

   One failed loudly against a correct table, and a codepoint dump showed the
   cell was exactly right - 31 202f 32 34 37 on both sides. The worse half was

   existed. Both now read textContent, which is stricter than the query helper
   rather than looser - had the first matched, it would have matched EITHER
