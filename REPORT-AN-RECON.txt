THE COMPARISON (section 1): DONE - source, the gap function, rounding
====================================================================

THE SCREEN (ui/screens/comparison/ComparisonScreen.kt): top bar
"Comparaison"; H1 "Votre employeur a-t-il le meme chiffre ?"; the lead; the
attestation field "Taux indique par votre employeur pour <annee>" (French
format, comma, optional percent/NBSP); the pairing card "Votre releve <X> %"
beside "Votre employeur <Y> %"; the gap "Ecart : N,NN points, soit environ M
jours." (the figure part bold, as the design draws); the causes; the info
line "Votre releve ne dit pas qui a raison : il montre, jour par jour, ce
qui a ete enregistre et quand."; and the primary CTA "Voir mes journees jour
par jour". Reached from a "Comparer avec mon employeur" button on the releve
(every year).

COMPLETED YEAR ONLY. The current year is REFUSED WITH AN EXPLANATION (no
input, no gap, no causes): "La comparaison porte sur une annee terminee.
L'attestation de <annee> n'existe pas encore ; votre employeur la
transmettra en janvier <annee+1>." This is why the year switch comes first.

THE RATE IS THE SERVER'S DOSSIER figure for the year - the releve's
declarableRate (R287), read from the releve's Loaded state the overlay is
opened over; NEVER a phone-side calculation. If days are still unsynced
(pendingCount > 0), the screen says so (reuses ReleveCopy.pendingNotSynced).

THE GAP, in ONE TESTED PURE FUNCTION (dossier/EmployerComparison.kt,
employerGap), never UI arithmetic:
    points      = |employerRate - releveRate|, two decimals (HALF_UP, so an
                  exact difference like 41,25 - 39,16 = 2,09 is recovered,
                  never truncated to 2,08)
    environDays = floor(points / 100 * basisDays * 2) / 2   (DOWN to the
                  half-day, so "environ" never overstates)
    basisDays   = dossier.tiles.workedDays (the server's prorated basis for
                  the year, SPEC 7.4 - open Q3, confirmed below)
The JVM test pins the design sample (sample data): 41,25 % vs 39,16 % on a
240 basis -> 2,09 points, environ 5,0 jours; plus the floor-to-half-day
(1,00 point on a 155 basis -> 1,5, not 2,0), equal-figures -> zero, and an
employer figure BELOW the releve -> positive (absolute). formatPoints (the
two-decimal HALF_UP points formatter) was added to fr/format/Numbers.kt with
its own test.

THE CAUSES (section 2): DONE - each, from the record only
====================================================================
dossier/EmployerComparison.kt comparisonCauses, rendered by
ComparisonScreen's CauseRow. Each is a FACT from the person's own record,
never a guess about the employer:
  - LES MISSIONS (only when mission days are logged): "<missionDays> jours
    dans votre releve, tous comptes : la limite est de <cap>." The counted
    figure is PARKAN-49's creditedMissionDays (so the regime-lost case reads
    "12 jours ... 0 comptes"); the cap is the year's RuleSet missionCapDays
    (added to ReleveRules; name the rule, interpolate the figure, R153/R147).
    Opens the day-by-day record.
  - LA METHODE DE CALCUL (always): "Votre releve utilise la methode
    simplifiee, <basis> jours." or, for EXACT, "... les jours ouvres
    communiques par votre employeur." Opens the record.
  - DES JOURNEES NON RENSEIGNEES (only when any): "<N> jours ouvres sans
    saisie dans votre releve." N = annex rows with recorded == false (the
    server's annex universe is the weekdays, so the count is the unrecorded
    working days directly, R206). Opens the record.
  - PLUSIEURS EMPLOYEURS (always, general context - NOT a count): "Avec
    plusieurs employeurs, chacun declare le taux correspondant a ses propres
    jours." From the verified AFC Geneve row (REG-UPDATE source C). Not
    tappable (there is no second-employer datum in the record).
  - "Votre releve ne dit pas qui a raison" - the app never says who is right.
    The vocabulary ban (certifie/atteste/conforme/valide/approuve) holds.

R342 - THE EMPLOYER FIGURE STAYS ON THE PHONE
====================================================================
settings/EmployerFigure.kt. The attestation rate is kept phone-only,
account-tagged ("employer.<accountTag>.<year>"), in the monreleve.detection
SharedPreferences file - the same file the detection mode, evening opt-in
and threshold alert share, so DeviceLocalStore.clearForSignOut() ->
SharedPrefsDetectionModeStore.clear() sweeps it on sign-out and deletion
(R289/R295/R303). No new /v1 field; EntriesWire omits it; sync never sees
it; there is NO code path that sends it. The tag is read live from
AccountStore (passed as a () -> String? supplier so settings/ carries no
dependency on account/); fail closed to null -> no read, no write (R303).
  PROOF (unit): EmployerFigureStoreTest - a figure saved under one account
  is invisible to another, is kept per year, fail-closed with no account,
  and gone after the sweep. ErasureCensusTest is the file's guard (it
  requires every "monreleve.*" store to be erased by deletion;
  monreleve.detection is listed). The on-device "nothing reached the server"
  proof is in WALKTHROUGH.

====================================================================
R340 - A PROJECTION IS NEVER A RECORD (the "nothing written" test)
====================================================================
ComparisonR340Test: computing a comparison (buildComparison, employerGap,
comparisonCauses) takes values and returns values - it leaves the record
handed in unchanged and writes to NO store (entries, queue, server, releve,
PDF, annex). The only write in the whole feature is the person's explicit
entry of the employer figure, to the phone-only store (R342) - computing the
gap never writes it (the test asserts the store stays empty while many
comparisons are computed). The server /v1 fields delivered in PARKAN-49 are
server reads, not projections, so R340 does not attach to them.
