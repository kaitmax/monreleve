THE ONE AUTHORIZED /v1 CHANGE, additive only (R217). Two fields were added to
GET /api/v1/dossier, both COMPUTED BY THE ENGINE (never arithmetic in a

                        state together). It is result.creditedMissionDays read
                        through; never recounted. When the regime is lost it is
                        0 while the Missions tile shows twelve - the Alex case
                        the document could not state before (12 logged, 0
                        counted). This is the datum the "missions" cause (section
                        2) reads from the record.

                        (telework alone), so it can never exceed the fiscal
                        ceiling while telework is under it. COMPUTED BY THE
                        ENGINE on a SECOND run (R281) over the same person with
                        the mission rows removed - never a division of the tiles
                        (FW12). rateWithoutMissions <= declarableRate always;
                        equal when no mission day is credited.

SECTION 0 - PARKAN-26 (THE YEAR SWITCH): HANDED OFF
====================================================================
NOT built this session. The operator decision SEED-RELEVE parked is now MADE by
the relay prompt: "every tax year that has days, newest first, opening on the
current year, previous year one tap away; a read-only view of what
/api/v1/dossier?year= already serves (R328); R310 for the chosen year."

WHAT IS ALREADY IN PLACE (so the follow-up is mechanical):
  - DossierApi.fetch(year) reads /api/v1/dossier?year= and caches per year
    (data/local/DossierCache), so switching back is instant - confirmed by
    DossierApiTest and by SEED-RELEVE's read-backs.
  - ReleveController's fetch seam is suspend (Int) -> DossierResult; only the
    constructor taxYear val (threaded from MainActivity Year.now(Europe/Paris)
    via MainGraph.build) pins one year today. load() always fetches taxYear.

WHAT BUILDING IT TAKES:
  - ReleveController: a selectedYear StateFlow initialised to taxYear; a
    selectYear(year) that re-runs load() for that year and recomputes
    pendingCount for it (pendingEntriesForYear(entries, selectedYear));
    export()/pathFor()/fallbackFilename() read selectedYear, not the
    constructor taxYear. R310: selectedYear must survive rotation/text-size/dark/
    kill - keep it in a rememberSaveable at the shell OR re-seed from a saved
    Int; the controller is not recreated on a config change, but a process kill
    needs the saveable.
  - WHICH YEARS TO OFFER. The prompt says "every tax year that has days, newest
    first, opening on current, previous one tap away." With no years-list
    endpoint, the conservative read is to probe {current, current-1} and offer a
    year only when its dossier returns recordedEntries > 0 (SEED-RELEVE proved
    the naive version misleads: Camille 2024 returns a VALID all-zero document,
    Sam 2025 returns read_failed - so an offered-year must be gated on
    recordedEntries > 0, and an out-of-activity year's 500 must not be offered).
    The current year is always offered (it is live). This is a bounded probe;
    do NOT offer a year with no days (that is the "has days" clause) and do NOT
    offer a future year (the route 400s future_year anyway).
  - ReleveHeader: a small segmented/chip selector above the identification card
    (FD7's deferred year chip), using existing tokens; an unstyled anchor is
    impossible (R173) - it is a Compose control, so use the brand/selected
    tokens the rhythm toggles use. Newest first, current selected by default.
  - fr/ReleveCopy: the chip label(s). The provisional banner already branches on
    the current year; a CLOSED past year must read differently from a
    provisional one (SEED-RELEVE flagged this - a closed year is complete, not
    "annee en cours"). Add a "releve de l'annee N (annee close)" caption.
  - Tests: a ReleveControllerTest driving selectYear across a scripted fetch
    (the year changes, the pending count recomputes, export path follows);
    Paparazzi baselines for the selector at default + 200 %, regenerated with a
    stated reason (R135).

THE SCREEN, as designed (Employeur.dc.html):
  - Top bar "Comparaison", back arrow.
  - H1 "Votre employeur a-t-il le meme chiffre ?"
  - Lead: "En janvier, votre employeur transmet votre taux de teletravail de

  - A text input, label "Taux indique par votre employeur pour <annee>", the

  - A card pairing "Votre releve <X> %" beside "Votre employeur <Y> %", then
    "Ecart : N,NN points, soit environ M jours."
  - "D'ou peut venir l'ecart ?" - the causes list (section 2 below).
  - The info line: "Votre releve ne dit pas qui a raison : il montre, jour par

    certifie/atteste/conforme/valide/approuve).
  - A primary button "Voir mes journees jour par jour".

THE RULES (the relay prompt, section 1):
  - COMPLETED YEAR ONLY. The current year has no employer figure yet, so a
    current-year comparison is REFUSED WITH AN EXPLANATION (not silently). The
    comparison is therefore reached only for a completed year - which is why the
    year switch (above) comes first. On the current year the screen says the
    attestation for this year does not exist yet (filed next January).
  - THE RATE IS THE SERVER'S DOSSIER figure for that year - the releve's
    declarableRate (R287), NEVER a phone-side calculation. If days are still
    unsynced (pendingCount > 0 for that year), the screen SAYS SO, as the releve
    does (reuse ReleveCopy.pendingNotSynced).
  - R342 (the employer figure stays on the phone). THE EMPLOYER'S FIGURE IS
    PHONE-ONLY, tagged with the account, cleared on sign-out (R303/R295) - NO
    new server field, nothing reaches the server. Model it on the existing
    account-tagged local stores that the sign-out/deletion sweep already clears
    (the detection prefs in the monreleve.detection namespace, swept by the same
    path as ThresholdAlertStore in AN-ALERT; or a DataStore keyed by the account
    tag). A test must assert it is cleared on sign-out (R295) and never sent.
  - THE GAP, in ONE TESTED FUNCTION (pure, JVM-tested), rounded DOWN to the
    half-day, never UI arithmetic:
        points = abs(employerRate - releveRate)            // two decimals
        basisDays = the year's basis = dossier.tiles.workedDays
                    (240 for a full simplified year, or the exact/prorated total
                    - it is the SERVER's basis, already prorated, SPEC 7.4)
        rawDays = points / 100 * basisDays
        environDays = floor(rawDays * 2) / 2               // down to the half-day
    Render "Ecart : <points formatSignedDays-style, 2 dp> points, soit environ
    <environDays formatDays> jours." The function takes values and returns
    values; a JVM test pins it (e.g. 2,09 points on a 240 basis -> 5,01 raw ->
    environ 5,0 jours, matching the design sample). Round DOWN (floor) so the
    "environ" never overstates the gap.
  - R340 governs: computing a comparison is a PROJECTION-class read - it is
    NEVER written to entries/queue/server/releve/PDF/annex. A test must assert
    computing a comparison leaves every store unchanged (the ForecastR340Test /
    SimulationR340Test shape), and the employer figure is phone-only (R342).
