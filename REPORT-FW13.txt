ROUND-TRIP (AC1)
--------------------------------------------------------------------
decode(encode(input)) equals input over 10 000 generated cases, in
tests/unit/params/codec.test.ts.

THE GENERATOR'S DOMAIN IS THE DESIGN DECISION. `debut` carries a
DATE while the engine holds a periodFraction, so the representable
fractions are the ones remainingYearFraction produces for days of
the tax year. An arbitrary 0,3333 is a valid TeleworkInput and is
NOT a shareable scenario - no date produces it, so no URL can carry
it, and a generator producing one would be asserting that encode
should invent a date the user never chose. The generator produces
DATES and derives the fraction, which is what the form does. encode
omits `debut` when no date reproduces the fraction rather than
guessing one.

COVERAGE IS ASSERTED, NOT ASSUMED (R120's shape). A second property
samples the generator and fails unless it produced every one of:

  part-time (employmentRate < 100)            covered
  mid-year start (periodFraction < 1)         covered
  the exact method                            covered
  granularity day                             covered
  granularity halfDay                         covered
  granularity hours                           covered
  both mission fields non-zero at once        covered
  fractional days (step 0,5)                  covered

Without it the 10 000 cases could all be the ordinary scenario and
the property would pass loudly.

A THIRD PROPERTY, added in increment 6 over 5 000 generated
QUERIES rather than inputs: every name decode reports as IGNORED was
really in the query, every name it reports as INVALID is one of the
frozen nine, no name is ever both, and no non-finite number ever
reaches the engine.

METADATA MATRIX
--------------------------------------------------------------------
Count-asserted per R119, in tests/unit/pages/param-metadata.test.ts.
The two halves come from two places, which is the operator's ruling:
the canonical from static metadata, the noindex from middleware as
an X-Robots-Tag header.

  URL shape                    X-Robots-Tag  canonical
  ---------------------------------------------------------------
  bare path                         0        ./  (the route)
  "?" empty                         0        ./
  ?canton=GE                        1        ./
  all nine params                   1        ./
  ?utm_source=facebook              1        ./
  ?canton=GE&tt=abc                 1        ./

  header count on a param URL       exactly 1, not 2
  table shape                       6 rows, 4 noindex, 2 not

The count is 1 or 0, never a presence check: a presence check passes
on a page that sets the header twice, and on one that sets it for
every route including the bare path - which would quietly de-index
the page the whole SEO strategy rests on. The header itself is
counted because Headers.append would leave a crawler reading the
first of two.

THE CANONICAL NEEDS NO CONDITION. The layout declares it RELATIVE -
canonical: './' - so Next resolves it per ROUTE, and a route has no
query string. A canonical that cannot carry a query already names
the bare path from every param URL. Both R81 arms are asserted:
absent when no origin is configured (a canonical pointing at
localhost is an instruction to a crawler, and absence is the safer
failure), relative once there is one. The resolved value is asserted
in e2e against a nine-param URL, because the resolution is the
framework's and only a served page shows it.

ROBOTS SAYS "noindex, follow", not "none": the links on a shared
calculator page are the same links as on the bare one, and there is
no reason to stop a crawler walking to /sources from here.

STORAGE NOTE
--------------------------------------------------------------------
THE DISTINCTION, STATED SO NOBODY LATER READS ONE GREEN AS COVERING
THE OTHER.

e2e/home.spec.ts asserts `await context.cookies()` is empty and no
third-party request is made (SPEC 17, SPEC D12). That test:
  - reads COOKIES, not storage;
  - runs on "/", and never visits the calculator;
  - would pass unchanged if this page wrote a megabyte of
    localStorage, and pass unchanged if this page were deleted.

So it does not cover the handoff, and the handoff does not weaken
it. SPEC D12 still holds and is now also asserted directly at the
moment of the write: tests/unit/pages/storage-handoff.test.tsx
checks document.cookie is "" while the key is present.

WHAT IS STORED. One key, frontalier.calculateur.v1, holding
{"version":1,"params":"<query string>"} - the same nine names the
URL carries, produced by the same encode(). Written only on a VALID
COMPUTATION, debounced onto the same 400 ms timer as the URL so
there is one synchronous write per settled scenario rather than one
per keystroke. Nothing on the web reads it; SPEC 10's install-
referrer handoff to the Android app is its reader.

WHY THE DIFFERENCE MATTERS AND IS NOT A LOOPHOLE. A cookie is
attached to every request to the origin, which makes it a tracking
mechanism whether or not anybody intended one. This never leaves the
device until the reader installs an app and that app reads it.

NOTHING PERSONAL IS REPRESENTABLE. The guarantee is structural
rather than careful: the payload is whatever encode() produces, and
encode() can only produce the nine names, so there is no field for
anything else to arrive in. The test asserts it as a WHITELIST -
only names from PARAM_NAMES may appear, and every value must match
^[A-Za-z0-9.,-]{1,12}$ - because a blacklist of things we thought of
is not a guarantee. A probe adding navigator.userAgent to the
payload reddens it.

setItem THROWS in Safari private mode, with site data disabled, and
on a full quota - the ordinary case for the in-app browser a social
link opens in. It is caught and ignored deliberately: the reader did
not ask for this, nothing they can see is affected, and a notice
about storage would be the first thing on the page that is about us
rather than about them.
