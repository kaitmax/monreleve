SETTINGS AND R290
====================================================================
AC1. The settings screen edits canton, taux d'activite, methode (240 /
exact + total), decompte (granularity) and debut d'activite, through
PATCH /api/v1/me - the SAME SettingsSaver seam onboarding uses, so the
settings write has no second transport (R206). Validation has no third
copy of the rule (R196): the controller runs calculateTelework and
accepts iff the engine does.

R290 - a change that would move the year's declarable rate shows it
BEFORE and AFTER before saving. The rate is computed by the DEVICE
engine over the device's OWN entries (deviceDeclarableRate), the same
path Aujourd'hui's year panel takes (R206) - so "moves the rate here"
means exactly "moves the rate the person already sees, and, once
synced, on the releve". save() computes both; when they differ it does
NOT save - it exposes a pendingRateChange the screen shows (formatPercent
over the engine's own figures, never typed - R181), and only confirmSave
commits. When the year has no entries, or the rate does not move, it
saves directly.

THE GRANULARITY TRAP (advisor). A decompte switch to DAY against
recorded half-days makes the recorded year uncountable
(GranularityMismatch -> deviceDeclarableRate null). save() REFUSES it
(CHANGE_CONFLICTS_WITH_RECORD) rather than reading the null as "nothing
moved" and silently saving a setting that invalidates the year. Tested.

DELETION (R289)
====================================================================
"Supprimer mon compte" erases the server AND the device in one action.

THE CONFIRMATION names what is destroyed - the recorded days and,
SEPARATELY, the unsynced ones that never reached the server and cannot
be recovered - the irreversibility, offers export first, and requires
the typed word SUPPRIMER (one home, R206: the gate, the copy prompt and
the request body all read DELETE_CONFIRMATION, the value the server
compares).

THE SERVER ERASURE. POST /api/v1/account/delete {"confirm":"SUPPRIMER"}
(a POST, not a DELETE verb - SPEC 14) through the existing
authenticatedPost; no new HTTP verb. The receipt is parsed - removed as
a MAP (SPEC 14.1), alertSubscriptionRemains surfaced (SPEC 14.3).

THE DEVICE ERASURE happens ONLY after the server accepts
(clearForDeletion, the strict SUPERSET of sign-out that also clears the
settings and the pending sign-in). A partial erasure where the device
is wiped but the server rolled back is what SPEC 14.2 forbids. A server
refusal (Refused) and a call that did not complete (Unknown, SPEC 14.6
- not idempotent) BOTH keep the device intact and say so, in distinct
copy.

THE LOCAL NEGATIVE SWEEP, two guards (FW26's shape on the device):
  - a controller test drives the REAL DeviceLocalStore through
    confirmDelete and asserts every seeded store empty afterwards -
    presence proven first;
  - ErasureCensusTest reads every "monreleve.*" storage identifier out
    of main source and requires each erased by deletion or exempted with
    a reason, so a NEW store cannot escape the erasure the way a re-read
    of the clear-list would let it. The cacheDir/exports directory is a
    PATH, not a name, so the census is blind to it (R246's shape) - it
    is covered by the clearExports seam instead, found before the
    walkthrough (see the increment-5 opening commit).
