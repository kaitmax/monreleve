THE DOSSIER ENDPOINT
--------------------------------------------------------------------
GET /api/v1/dossier?year=. The route assembles nothing; it serialises
DOSSIER_RESPONSE_FIELDS.

SIX NAMED REFUSALS (R198):
  missing_token        401  no bearer
  coordinates_refused  400  checked FIRST, before the year
  unknown_parameter    400  including a planted userId
  invalid_year         400  not four digits
  future_year          400  a year that has not happened
  titulaire_missing    422  no name, so no attributable document

future_year IS ITS OWN CODE rather than invalid_year. The engine WOULD
answer for 2031 - full basis, nothing logged, 0 % declared - and that
answer is not so much wrong as MEANINGLESS, which is worse because it
looks like a compliant year. invalid_year would send a client author
to check their parser.

BOTH TENANCY PLANTS AT THE HTTP BOUNDARY. A planted userId is REFUSED
as unknown_parameter rather than ignored - the stronger answer, since
a route that silently ignored it would still have served the caller's
own data and passed a laxer test. Two accounts each holding data get
their own, so "did not leak" is not satisfied by an empty answer.

THE NO-RECOMPUTATION PLANT is the one the prompt said to watch, and it
fired precisely.

`result` STAYS OFF THE WIRE. It duplicates declarableRate, rawRate and
both headrooms, all of which zone already carries. Two sources for one
figure inside a frozen contract is R206's drift where it is most
expensive to undo. R217 permits additive fields, so its unique ones
can be named later.

THE ERASURE PATH
--------------------------------------------------------------------
WHAT I CHOSE: nothing new. FW21 had already built the door-less
answer and proved it empirically on throwaway tables BEFORE writing
the trigger.

PostgreSQL deletes a parent row before firing the referential action,
so during a cascade from User the person is already invisible to the
transaction, while a direct DELETE on EntryEvent still sees them. The
trigger asks exactly that question:

  direct delete  -> the user is still visible -> REFUSED, by name
  cascade        -> the user is already gone  -> permitted

WHAT IT REFUSES: every removal of an event on its own. An event may
disappear WITH the person; never by itself.

HOW AN ATTACKER OR A BUG WOULD HAVE TO LOOK TO USE IT: they would need
a valid access token for the account, and the result is the TOTAL
destruction of that account. There is no partial form - the capability
IS the erasure. Nobody can tidy one inconvenient event without
destroying the whole record, which is the loudest possible side
effect. The failure mode worth guarding is therefore "somebody erases
an account they should not have", which is ordinary authentication.

The alternatives - a transaction-local setting, a dedicated role, a
marker row - are each a way of teaching a guard to stand aside, and
each is a door. This has none.

ONE TRANSACTION. The counts are taken BEFORE the cascade, because
afterwards there is nothing left to count and a receipt of zeros is
indistinguishable from a deletion that did nothing.

VerificationToken DOES NOT CASCADE - it is keyed by ADDRESS, not by
userId - so a pending sign-in link would have outlived the account it
was issued for. It is deleted explicitly, in the same transaction.

APPEND-ONLY STILL REFUSES, BY NAME
--------------------------------------------------------------------
Three ways, because a file that only proved the erasure works would be
satisfied by a disabled trigger:

  a direct DELETE on EntryEvent   rejected, /append-only/
  an UPDATE                       rejected, /append-only/
  both, AFTER a successful erasure of a different account

The third matters most: a trigger quietly dropped would pass every
erasure test and fail nothing until an audit.

EXPORT COMPLETENESS
--------------------------------------------------------------------
AC2's census is DERIVED FROM prisma/schema.prisma. Every model
carrying a userId is either EXPORTED or EXCLUDED WITH A REASON, and a
model that is neither fails the test - which is the point, because the
way an export goes wrong is not that somebody breaks it but that
somebody adds a table in two years and nobody remembers the file
exists.

  EXPORTED   User -> settings, Entry -> entries, EntryEvent -> trail,
             Device -> devices, DeviceSession -> sessions
  EXCLUDED   SessionToken, Account, Session, VerificationToken

Each exclusion argues for itself and the test refuses a reason under
60 characters. The sharpest is SessionToken: hashed credentials tell
the person nothing and put a credential-shaped artefact in a file they
will email to an accountant. The SESSIONS are exported, so every
signed-in device is still visible.

matching the database exactly, with presence proven first.

THE TRAIL IS IN IT, and that is the point. An export of the entries
alone hands somebody a list of days they already know.

WHAT SURVIVES AND WHY
--------------------------------------------------------------------
AlertSubscriber, deliberately.

It is keyed by EMAIL, not by user: a separate consent under a separate
identity. Most addresses on that list never had an account, and one
that does had it added by a different act on a different day.

  DELETING IT would revoke a consent nobody withdrew.
  KEEPING IT SILENTLY would be worse - somebody who asked to be
  forgotten and then receives an email has been told something untrue
  by the ABSENCE of a sentence.

So it survives, the response SAYS so (alertSubscriptionRemains), and
/confidentialite states the rule. The row keeps its unsubscribe token,
so the one-click route that already exists still works - destroying it
would strand somebody on a list they could no longer leave.

Both directions asserted: true for a confirmed subscription, false
when there is none and false for one already unsubscribed.

PARKED
--------------------------------------------------------------------
PARK26-1. THE EXPORT CENSUS FINDS DIRECT OWNERSHIP ONLY. SessionToken
   belongs to a person through sessionId -> DeviceSession.userId and
   is invisible to it. It is in EXCLUDED with a reason, so today's
   partition is complete - but a future table owned only indirectly
   would slip past. Closing it means walking the relation graph, and a
   census that walked it wrongly would be worse than one whose reach
   is written down.

PARK26-2. CLOSED BY R242, AFTER THE REPORT WAS FIRST WRITTEN.
   /confidentialite said "Dans l'application" twice where there is no
   application - a present-tense claim about a channel that is not
   open, which R138 governs plainly. I had parked it rather than edit
   published privacy copy on my own judgement.

   THE RULING: correct it, and the vagueness I was worried about is
   not forced, because THE FIX IS TENSE RATHER THAN SPECIFICITY.

     "Dans l'application, Exporter mes donnees produit..."
     -> "Dans l'application mobile, lorsqu'elle sera disponible,
         Exporter mes donnees produira..."

   The reader still learns exactly HOW, and the sentence stops
   asserting a channel that is not open. Same move as FW15's analytics
   line, where stating a fact and then promising a mechanism was
   stronger than the claim it replaced.

   A THIRD INSTANCE WAS CHECKED AND LEFT ALONE: the detection
   paragraph's "polygone des frontieres suisses embarque dans
   l'application" is already conditional - it opens "Si vous
   choisissez le mode automatique" - so it asserts nothing about the
   app existing. A fourth, in lib/fr/application.ts, is a NEGATIVE
   claim ("ni dans l'application, ni sur nos serveurs") and is safe.

   WHAT STAYED UNCONDITIONAL, correctly: the alert-list bullet. That
   unsubscribe works today, through the web, without an app.

   CLAIM 8 and CLAIM 9 in the privacy map now pin the conditional, so
   it cannot be dropped without a failing test.

   Verified by cropping the rendered page rather than by reading the
   baseline: both bullets keep their detail and gain the conditional.

PARK26-3. THE EXPORT'S clientMutationId IS IN THE FILE. It is a sync
   identifier with no meaning to a person, sitting in a document
   otherwise being made readable. It is genuinely their data and
   removing it would make the export less complete; leaving it is one
   more line of noise. Not decided.
