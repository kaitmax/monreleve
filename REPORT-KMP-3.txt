R447 - EACH INTERFACE AND ITS CONTRACT
--------------------------------------------------------------------------------
The three contracts were written BEFORE anything moved (commit ae41e8c, "nothing
moves in this commit"), so the move that followed was a file relocation and not a
redesign. The test applied to every sentence: could somebody implement this against
a Keychain or NSUserDefaults WITHOUT reading the Android class - which they cannot,
because it is Android. No method was added, removed or renamed; the only lines that
changed were documentation.

TokenStore - what an implementation must guarantee
  - at most ONE pair; save() replaces whatever was there.
  - save() is DURABLE AND WHOLE before it returns, and the reason is given rather
    than asserted: the old refresh token beside a new access token would make the
    next refresh a REPLAY, and a replay ends the whole session (R210). So the pair
    is written as ONE value - a single commit() on Android, a single Keychain item
    on iOS, never four items in sequence.
  - load() before any save() returns null, and null is the only thing that means
    "sign in".
  - load() returns null RATHER THAN THROWING, and CLEARS the store when it does: an
    unreadable pair is not an error a caller can act on.
  - clear() erases the pair and NOTHING ELSE; LocalStore owns the rest (R295). A
    clear() on an empty store is a no-op and must not throw.
  - clear() must not need the network, a session, or the user present, because it
    runs inside withContext(NonCancellable) at the end of sign-out.
  - must not log or back up the tokens; must NOT require the device unlocked,
    because silent refresh runs while the phone is locked.

DossierCache - what an implementation must guarantee
  - stores the server's bytes VERBATIM; generatedAt travels inside them and the
    device's own fetch time must never stand in for it (R181).
  - load() returns null for a year never saved, even when other years were.
  - save() replaces that year and leaves every other year alone.
  - clear() erases EVERY year, not the current one (R295/R289).
  - durability is DELIBERATELY WEAKER than the token store's, with the reason
    stated: a cached document lost to a process death costs a round trip, not a
    sign-out. It must still survive an ordinary restart.
  - must not log or transmit the body (it carries the titulaire's name); must not
    repair, normalise or re-serialise a stored body.

SettingsStore - what an implementation must guarantee
  - load() returns null until a COMPLETE Settings has been saved, and null sends
    the person to onboarding.
  - save() replaces the WHOLE set; there is no per-field write and no merge.
  - ABSENT AND NULL ARE DIFFERENT AND MUST STAY DIFFERENT. A null
    exactTotalWorkDays is a real answer (the simplified basis) and so is a null
    activityStartDate (the whole year). Both must round-trip as null, and the
    contract explicitly does NOT prescribe how: the Android implementation stores
    one as the sentinel -1 and simply omits the other, because SharedPreferences
    removes a key written as null - two nulls, two mechanisms, in one file - and an
    iOS implementation is free to encode them alike.
  - clear() erases every field, and the reason it is safe is given: the six settings
    live on the server and a re-sign-in restores them from GET /api/v1/me (R297).
  - isOnboarded() is a DERIVED DEFAULT AND MUST NOT BE OVERRIDDEN - it is the one
    completeness definition the server path uses too, and an implementation
    substituting its own is the drift R335 exists to prevent.

NO INTERFACE METHOD EXISTS THAT ONLY THE ANDROID IMPLEMENTATION NEEDS. The three
interfaces have 3, 3 and 3+1 members and every one is called from commonMain.

that out is what this ruling bought.

  only the current account's rows drain, never UNOWNED, never another account's
      AccountScopeTest.syncSendsOnlyTheCurrentAccountsRows

      SyncEngineTest.aRejectedBatchIsIsolatedSoTheGoodItemsStillSync  ALREADY PINNED

      SyncEngineTest.aNetworkFaultIsRetryableAndLeavesRowsPending   ALREADY PINNED
  the drain result the worker maps to SUCCESS/RETRY                 *** GAP ***

THE GAP AND WHY NOTHING HAD CLOSED IT. doWork() is a CoroutineWorker method needing
a Context and WorkerParameters, which a JVM unit test has not got - so the mapping
sat unguarded while every branch around it was tested. It is not a mapping anyone
would guess: Settled -> success (defects included: re-sending a payload the server
refused is a queue that never drains, R198), Retryable -> retry (the ONLY case the
exponential backoff should see), and Unauthenticated -> SUCCESS, not retry (rows
wait for a sign-in; retrying backs off forever against a session that is not coming
back). Map the last one wrong and the symptom is a phone quietly backing off for
hours.

SyncWorkerResultMappingTest closes it as a SOURCE FENCE on the shape of the `when`,
and it also DERIVES the case list from SyncEngine.kt - following that file into
:shared - so a fifth SyncOutcome added later fails here instead of on a phone. Its
exhaustiveness check reads only the sealed SyncOutcome's own block, because
SyncEngine.kt ALSO declares a private sealed BatchResult whose case names overlap
(Retryable, Unauthenticated) and a regex over the whole file would have silently
folded the two together - a guard measuring something other than what it claims.
