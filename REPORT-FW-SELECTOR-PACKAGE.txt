R415 - THE COST, MEASURED, BECAUSE THAT IS THE RULING'S OWN CONDITION
--------------------------------------------------------------------------------
THE RULING: both files map to every suite. No cleverness, no reading of which
keys moved. The operator's reasoning, recorded in the code beside the list:

  - A dependency bump can break anything, and NOTHING IN THE DIFF TELLS YOU
    WHAT. A selector that tried to be clever - full run for a scripts change,
    something narrower for dependencies - is exactly how the next uncovered
    file gets through.
  - They are RARE, so the full matrix on each one costs little in total.
  - The other side is NOT KNOWING, which every gate here exists to prevent.

AND THE CONDITION ATTACHED TO IT: revisit WITH MEASUREMENTS if bumps ever become
frequent enough to hurt. Without a number that condition has nothing to revisit,
so here is the number.

THE RUN: a real package.json change (its `version` field, reverted afterwards)
staged alongside this task's own files, timed end to end.

  FOR SCALE, measured separately: test:container:e2e ALONE, with the image

WHAT THE NUMBER IS FOR. The ruling's condition is "revisit WITH MEASUREMENTS if
bumps ever become frequent enough to hurt". This is the baseline any argument to
narrow the rule has to beat. At one or two dependency bumps a month it is
plainly affordable; at one a day it would not be, and that is the threshold to
watch rather than a feeling about cost.

the next person does not re-derive it: a script can change what a DIFFERENT
suite does. db:generate is chained into test:db by FW-PRISMA-GENERATE, and
gate:changed is itself a script. Key-to-suite is not a function, so a rule that
read keys would be a worse rule wearing a better one's clothes.

       Error: expect(received).toBeNull()
       Received: true
       > 195 |   expect(database?.ok).toBeNull();

    1 failed | 323 passed

THE CAUSE, from the spec's own comment. R355 gives the database check a third
state: when the process is NOT marked as serving the check is not evaluated and
reports ok: null, so that a build needing no database is not blocked and a
check that stopped running cannot read as a pass. On the host that holds. IN
THE CONTAINER THE PROCESS IS SERVING, so the check IS evaluated and returns
true. The spec encodes a host assumption and is run unchanged against the
container.

R416 - THE CENSUS CLOSES THE CLASS, AND ITS FIRST RUN IS THE EVIDENCE
--------------------------------------------------------------------------------
WHAT IT COULD NOT SEE, AND WHY. The census scanned ENTRY_EXTENSIONS - the code
extensions - plus a two-name list of extensionless files. R251 added that list
for `Dockerfile`, recording the reason: "the closed-world root census could not
see a Dockerfile, because it scanned for code extensions and a Dockerfile is not
code." That closed the INSTANCE. package.json is .json, which is not code
either, and the CLASS stayed open.

WHAT IT COVERS NOW: .json, .yaml, .yml, .toml, in a list of its own -
ROOT_CONFIG_EXTENSIONS - deliberately NOT added to ENTRY_EXTENSIONS, because
that list is also what the import-graph walk follows and a walk that started
following .json would be a far larger change than widening a census of one
directory.

WHAT IT STILL DOES NOT SEE, named rather than left silent: the root also holds
.env, .env.example, .gitignore and two .tsbuildinfo files. None matches those
extensions. The first two are secrets and a sample of them; the last two are
generated output; none decides which suite runs. A future root file that is
none of those and still decides something arrives as a new extension, and the
list is where it goes - which is the argument R246 made for its own convention
list, made here against the person writing this one.

ITS FIRST RUN FOUND SIX MORE, all previously selecting the base chain only:

  pnpm-workspace.yaml   -> EVERY SUITE. The same class as the two the ruling
      named, and FW14 measured it: that file's own header records that an
      unanswered dependency build script made "every `pnpm run` and every
      `pnpm exec`" die inside pnpm's dependency-status check - `pnpm typecheck`

      stop every suite from starting belongs to all of them.

  tsconfig.json         -> EVERY SUITE. Every TypeScript tool resolves through

      import through the `@/` alias it defines. Break the alias and nothing

  tsconfig.scripts.json -> ['typecheck']. `typecheck` is literally

  tsconfig.parity.json  -> ['parity:check'], AND THIS ONE IS THE FINDING.
      It looked exempt and was not. parity:check runs in `pnpm gate` and in
      gate:clone's step list - so it is not unused - but gate:changed had no

  identity.json         -> ['test']. Read by tests/unit/content/identity.test.ts,
