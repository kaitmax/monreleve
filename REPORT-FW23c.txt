SUMMARY
--------------------------------------------------------------------
The data-loss defect FW23b found is closed. A replayed mutation is now
recognised by the append-only trail rather than by the day's current
row, so a queue retrying an old item can no longer revert a newer
edit.

The fix is INSIDE the freeze because it makes the documented sentence
true rather than changing it. The contract has always said a batch
carrying a seen clientMutationId writes no row and no event. It meant
"the server has applied this mutation"; the implementation meant "the
current row carries this id" - a narrower accidental meaning nobody
chose, and false in exactly the case that costs a user their
correction.

THE SECOND HALF IS NAMED AND NOT FIXED. A genuinely NEW mutation that
arrives late still wins on server receipt and still reverts a day.
Same symptom, different cause. That is a change to a STATED RULE, so
it is parked with its mechanism written into the contract document and
a test that stops the note being tidied away.

NOT BACKFILLED, AND THE REASON MATTERS
--------------------------------------------------------------------
The tempting migration is to fill EntryEvent.clientMutationId from the
Entry each event points at. It would be WRONG, and wrong in the
specific way this project keeps finding: the id on the Entry is the
LAST write's, not the one that created the event. Backfilling would
write a plausible falsehood into an append-only table - the one table
whose entire value is that it records what actually happened.

The database says the same thing independently: EntryEvent is
UPDATE-blocked by its own trigger, so the backfill cannot be performed
without first disabling the guarantee.

So Entry is still consulted for the duplicate set. It covers exactly
the rows written before this migration - including the demo year - and
nothing else, because every write after this point records the id on
the event too. The test builds that shape by INSERTING it rather than
by editing a row afterwards, since reaching past the append-only
trigger to construct a fixture would be testing a state the database
forbids reaching.

A THING I HAD ASSUMED AND HAD WRONG
--------------------------------------------------------------------
The tenancy test was written expecting the second account's write to
LAND, on the reasoning that the duplicate set is scoped by userId and
the ids are the client's own.

It does not land. `Entry.clientMutationId` is `@unique` GLOBALLY
rather than per account, so the second account collides at the
database and the batch is refused 409 `conflict`.

TWO CONSEQUENCES, and the first answers a question asked yesterday:

  Q79 IS ANSWERED BETTER THAN EXPECTED. `conflict` is not a dead
  branch awaiting a plausible future producer - it has a LIVE one
  today. The document now records that, and keeps the code reserved
  for the ordering case as ruled.

  AND IT IS A CROSS-TENANT COUPLING, which is new. One account can
  make another account's write fail by using the same id first, and
  can learn that an id is taken globally. With client-generated UUIDs
  this is not practically reachable, but the mechanism is real and it
  is not what the column is for. See QUESTIONS.

The test now asserts the real behaviour and says in its own comment
what I had expected and why it is not that.

Adding EntryEvent.clientMutationId added a STORED COLUMN, and the

the column was either disclosed or justified as not personal - which
is the decision being forced rather than defaulted.

DISCLOSED AS `history`, with the rest of the event record, rather than
as `day` like Entry.clientMutationId. The category describes WHICH
RECORD holds the column, and this one is the modification trail.

NO PLANT WAS WRITTEN FOR IT, deliberately - R178. The guard fired on a
REAL instance on its first exposure to this change, and a live
instance is better proof than a planted one. Planting it afterwards
would only demonstrate what the gate had already demonstrated.

It is also the answer to a question nobody asked in this session: what
stops a schema change from quietly widening what the product stores?
This did, on the first run, without anyone remembering to check.

WHAT IS STILL OPEN, WRITTEN INTO THE CONTRACT
--------------------------------------------------------------------
Section 6.4 now distinguishes two failures with one symptom:

  A REPLAY of an old mutation          refused, as of R219
  A NEW mutation arriving LATE         still wins, on server receipt

The second still reverts a day to older content. SPEC 13.2 orders
writes by server receipt, and receipt order is the wrong order for an
offline queue - clientClaimedAt is the honest one. Changing it is a
change to a stated rule rather than to an implementation, so it waits
for AN5's evidence about what the queue actually emits.

The document says so, and tells a client the only thing it can act on
today: do not assume the last write you sent is the one the server
kept; read the year back after a queue drain.

A TEST ASSERTS THE PARKING NOTE SURVIVES. Without it, the next session
reads the replay fix, sees a section headed "replay and ordering", and
tidies away the half that is still broken - which is exactly how a
known defect becomes an unknown one.

NOTICED BUT NOT TOUCHING
--------------------------------------------------------------------
1. `Entry.clientMutationId` IS GLOBALLY UNIQUE. See above. The natural
   shape for an idempotency key that a CLIENT generates is
   @@unique([userId, clientMutationId]) - unique within the account
   that issued it. Changing it is a schema change and a migration on a
   table with data, and it would remove `conflict`'s only live
   producer, so it is a question rather than a repair.

2. THE DEDUP IS NOW TWO QUERIES RATHER THAN ONE. Sequential inside the
   transaction, deliberately: an interactive transaction is one
   connection, and issuing two concurrently is not something to rely
   on for a guard whose failure mode is silent data loss. Both are
   indexed lookups bounded by the batch's 200 ids. If the second ever
   needs to go, it can - once no pre-migration row remains, which is
   not knowable from here.

3. THE GATE REPORTS TRACKED AND UNTRACKED PATHS FROM DIFFERENT
   ROOTS, and this run is where it showed. The selection printed

     web/prisma/schema.prisma                  (tracked)
     prisma/migrations/..._mutation_id/...     (untracked)

   for two files in the same directory. gate-for-changes.mjs runs
   both git commands with cwd: web. `git diff --name-only HEAD`
   reports from the REPOSITORY ROOT; `git ls-files --others`
   reports relative to the CURRENT DIRECTORY. Measured, not
   inferred.

   HARMLESS TODAY, and only by luck: toPackagePath strips a leading
   `web/` and passes an already-package-relative path through
   unchanged, so both forms land on the right rule.

   THE SHARPER HALF: an untracked file OUTSIDE web/ is invisible to
   the selector entirely - `git ls-files --others` with cwd: web
   cannot see it. Verified with a probe file at the repository
   root: zero hits. Nothing selectable lives outside web/ today, so
   nothing is missed; a new top-level directory that ever needed a
   suite would be missed silently on its first commit, which is the
   run where it matters most.

   Not touched - it is the gate, on a task the gate is checking.

QUESTIONS
--------------------------------------------------------------------
Q80. Should `Entry.clientMutationId` become
     @@unique([userId, clientMutationId]) rather than globally
     `@unique`? It is a client-generated id, so scoping it to the
     account that issued it is the shape that matches what it is.
     Against: it removes `conflict`'s only live producer, which
     yesterday's ruling deliberately kept. The two decisions are
     coupled and should be taken together.
