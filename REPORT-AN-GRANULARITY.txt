R497 - WHAT THE SERVER TASK (FW-GRANULARITY) INHERITS
--------------------------------------------------------------------------------
THE RULE AS IMPLEMENTED (:shared, data/repo/DayGranularity.kt):
  - a day's granularity: the rows' own when it has any - FULL alone = whole day;
    AM and/or PM, no FULL = halves; FULL AND a half = MIXED - and the setting's
    (Settings.granularity == "HALF_DAY" -> halves, anything else -> whole) only
    when it has none;
  - a write is REFUSED when its portion has NO row of its own for (account, day)
    and the day holds a row of the other granularity: FULL when AM or PM exists,
    AM/PM when FULL exists. Writing a portion that already has a row is an edit and
    is always allowed - so a day already mixed can have its rows' kinds edited and
    can never gain a row. An empty day accepts either for its first write;
  - nothing ever retires a row (option B parked, PARK-W1); counting is unchanged
    (option C rejected): an already-mixed day still counts FULL 1 + AM 0.5 +
    PM 0.5 in both engines.
THE REFUSAL RESULT: RecordResult.MixedGranularityRefused(dayDate: String,
  requested: Portion, held: List<Portion>) - from LocalEntryRepository.record(),
  which otherwise returns RecordResult.Recorded(entry). Nothing is written and no
  sync is requested on a refusal.
MIXED DAYS SEEN ON THE S9: NO RESULT (the device database is unreadable and R496
  never ran); the test account holds none on the server. On the LOCAL dev database
  3 of 1391 account-days are mixed, all test accounts (listed under R494).
WHAT FW-GRANULARITY MUST KNOW:
  - The phone now never SENDS a write that mixes a day - but an OLD client, the web,
    or a replayed queue still can, and the server's write.ts upserts per (userId,
    dayDate, portion) with no such check. The same predicate belongs on the server
    for the record to hold the rule; the phone's typed refusal has no wire shape
    yet - a server refusal would need one (a 409 code, say) and the phone's
    SyncEngine would treat it as it treats any 4xx today (FAILED, held, said).
  - A day already mixed downloads and displays as its rows (AN-PULL stores it as
    served; R494 shows it); the phone will edit its existing rows' kinds (MODIFIED
    events for those rows) and will never add or remove one. Whatever the census
    decides (repair, retire, leave), a phone that holds such a day keeps it until
    the server's rows change and a download replaces them.
  - Bulk confirmation and Aujourd'hui in half-day mode now write an EMPTY day as two
    rows (AM + PM, two CREATED events) where they used to write one FULL row (bulk)
    - same count, different trail.
  - The evening notification still writes an empty day whole in half-day mode
    (PARK-W2, a question).
