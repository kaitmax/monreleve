SUMMARY - AND THE FIRST THING IN IT IS THE FINDING
====================================================================

**EVERY TRANSACTIONAL WRITE FAILS IN A PRODUCTION BUILD. RECORDING A
DAY - THE ENTIRE PURPOSE OF THIS PRODUCT - DOES NOT WORK WHEN
DEPLOYED.**

  Fresh container, nothing else running, 7 of 100 connections, ONE
  request:

    POST /api/v1/entries
    {"entries":[{"dayDate":"2028-05-10","kind":"HOME",
                 "clientMutationId":"fw30-single-write-proof"}]}
    -> HTTP 500  {"code":"write_failed"}
       rows written: 0

  Not load. Not a race. Not intermittent. The log names it:
    Transaction API error: Transaction not found.

  MECHANISM, and it takes both halves. web/lib/db/client.ts:
    (1) create() memoises ONLY when NODE_ENV !== 'production', so in
        production every property access builds a new PrismaClient
        around a new pool.
    (2) the Proxy does Reflect.get(client, property, receiver) with
        receiver = THE PROXY, so prisma.$transaction() runs with
        `this` bound to the Proxy and every `this.x` inside builds
        yet another client.
  So $transaction opens on one client and resolves its internals
  against others. Either half alone would be survivable.

  THE APPLICATION CODE IS CORRECT. lib/entries/write.ts:71 opens the
  transaction and uses the `tx` handle properly. The fault is
  entirely in the client module.

  PROVEN THREE WAYS, independently:
    CODE    the Proxy and the conditional memoisation, read
    MODULE  $transaction driven directly:
              NODE_ENV=test        SUCCEEDED {"a":199,"b":3131}
              NODE_ENV=production  THREW "Transaction not found"
    SYSTEM  one POST to a production container: 500, zero rows
  A fourth from the other direction: the SAME write is 200
  in-process under NODE_ENV=test and 500 against production.

  SECOND CONSEQUENCE - CONNECTIONS. ~4 new pools per request, never
  reused, released only by node-postgres's ~10 s idleTimeoutMillis:
    baseline                        5 of 100
    after 10 authenticated reads   45 of 100
    after 20 authenticated reads   85 of 100
    after ~25                      psql itself could not connect
    15 s later                      1 of 100
  A request carrying `Bearer <garbage>` opens pools on its way to a
  401, so NO ACCOUNT IS NEEDED: about twenty-five HTTP requests
  carrying a made-up token exhaust the database. A request with no
  Authorization header short-circuits and costs nothing.

  WHY EVERY GUARD HERE IS BLIND:
    unit and db tests   NODE_ENV=test        -> memoised
    pnpm dev            NODE_ENV=development -> memoised
    R176's walkthrough  runs against pnpm dev
    gate:changed        never builds production and drives it
    gate:clone          skips the container suites, and SAYS SO
    CI's container job  HAS NEVER PASSED (see F-CI)

  AND IT IS OLDER AND MORE STRUCTURAL THAN F-CI. Reconciled against
  FW28 and FW29, which both record test:container:e2e 270 + 9 HTTP
  passed against a production image:
    scripts/container-e2e.mjs NEVER POSTS AN ENTRY
    e2e/ NEVER TOUCHES /api/v1/entries - by design, since D14
      removed the signed-in web area and the write path's only
      intended caller is an Android client that does not exist
    the suites that DO exercise it all run under NODE_ENV=test
    git log -- lib/db/client.ts -> 9c22ffd, 2026-09-13, FW14
  SO A GREEN CONTAINER JOB WOULD NOT HAVE CAUGHT IT EITHER. The
  reason this shipped is that NOTHING exercises a production write,
  and that has been true since 13 September.

  WHY IT WAS NOT THE SESSION'S HARD STOP. The prompt names
  authentication bypass, cross-tenant data access, secret exposure
  and remote code execution. This is none of them - nothing is read
  that should not be, nothing is bypassed, nothing leaks. It is a
  total functional failure and a denial of service. So the audit
  continued, and this is first and in full, which is the binding
  half of that instruction.

THE REST, IN ONE LINE EACH. Authentication, tenancy, injection,
secrets and logging came through clean under probe, each with a
working control. The predicted finding - the PDF at 2 600 annex rows
- DOES NOT EXIST, because the dossier is year-scoped. Seventeen
findings are parked. SIX TIMES a measurement produced a finding that
was not there, and section 8 of the audit document is about that.

SEVEN TIMES A MEASUREMENT PRODUCED A FINDING THAT WAS NOT THERE.

    the grep demanded process.env.FCM_PROJECT_ID and the code reads
    env.FCM_PROJECT_ID through an INJECTABLE PARAMETER, written that
    way so a test can supply a fake.
 2. "CSV formula injection is defended", 0 lines matching. FALSE
    TWICE: the formula was planted in User.name, which the CSV has
    no column for, and an earlier probe had overwritten that name.
 3. "The magic-link endpoint is unrated and sends mail." FALSE: it
    IS limited, and every refusal maps to 202 SO AN ATTACKER CANNOT
    TELL THEM APART. The limiter is invisible BY DESIGN and I was
    looking for it by status code.
 4. "The alert send does a seq scan while the purge is indexed."
    FALSE: the plan was read off tables never ANALYZEd.
 5. "Every injection shape refused", eighteen clean 400s. FALSE:
    the payloads used items: where the schema says entries:, so
    every one was rejected for a FIELD-NAME MISMATCH before any
    injection content was examined.
 6. "Connections leak and never drain, 87 of 100." FALSE: those 87
    belonged to MY OWN vitest process and vanished when it exited.
    The container's real leak was found afterwards, with curl.
 7. "No user data reaches the log." FALSE: a PRINT TOKEN does, and
    the probe missed it because a print token has none of the shapes
    it searched for.

THREE OF THE SEVEN WERE CAUGHT BY A CONTROL - a positive case
asserted beside the negative one. That is R196's both-directions
rule, and it earned its place three times in one session.
