R27 - NODE FLOOR IS 22. web/package.json had NO engines field at all, so
nothing declared the floor the code already assumed; it is now ">=22.12". SPEC
sections 19 and 21 read "Node 22 and 24", as does todo.md's manual-check row.
CI's parity matrix goes from [20, 22, 24] to [22, 24].

The lane's PURPOSE changed with the floor, so its rationale is rewritten
rather than renumbered. FW6 built it to work around vitest 5 excluding Node 20
outright; with the floor at 22 it instead keeps the two SUPPORTED versions
honest against ICU and CLDR drift, which is what actually moves a separator
codepoint - those ship with a Node major. Commit 31c2985.

R28 - A CALENDAR DAY IS AN ISO STRING. formatDate(isoDay: string) and
formatDateTime(iso: string); the Date overloads are gone and DATE_ZONE with
them.

This DELETES a defect rather than guarding one. A Date is an instant, and
reading an instant's calendar fields means choosing a zone; FW6 measured the
consequence, where an unpinned formatter was right in the dev checkout AND
right in CI (both non-western) and a day wrong for every user west of
Greenwich. A YYYY-MM-DD string carries no instant, so formatDate now touches
no zone, no Intl and no Date arithmetic. The four child-process TZ tests are
kept, but for formatDate they no longer prove anything - they demonstrate
there is nothing left to prove.

VALIDATION IS ONE ROUND TRIP, because a NaN check is not enough. Measured: new
Date does not reject an impossible day, it ROLLS IT OVER.
'2026-02-30T00:00:00.000Z' parses to 2026-03-02, and '2026-02-29' - 2026 is
not a leap year - parses to 2026-03-01. A NaN check alone would have printed
"30.02.2026" on a filing. Rebuilding the canonical ISO day from the parsed
fields and requiring equality with the input rejects that, and in the same
comparison rejects a timestamp, a one-digit day, a two-digit year and a
Swiss-formatted string. 2028-02-29 is accepted.

THE TYPE TEST IS THE ONLY THING THAT CATCHES THE REGRESSION. Planting
`formatDate(isoDay: string | Date)` leaves all 31 runtime tests GREEN and
fails only at the type level, two ways: the @ts-expect-error on a Date call
becomes "unused", and Parameters<typeof formatDate> stops equalling
[isoDay: string]. Commit b11c516.

PARITY PROOF
================================================================================

e2e/rail-parity.spec.ts, run against a production build in Chromium.

  MATRIX SIZE      21 cases
  DIFFERENCES      0

The matrix: every variant x zone (9), plus the rates that carry a formatting
decision - 0, the Geneva 4,16 and 39,16, both ceilings exactly, a repeating
fraction 66,666666666, 100, and both clamping cases (-5 and 140) - plus a
width of 317 chosen so every derived coordinate is a long fraction, plus the
200 px thumbnail width.

THE COMPARISON IS ON THE RETURN VALUE, and the suite DEMONSTRATES why rather
than asserting it. A fourth test puts the same string through innerHTML and
reads outerHTML back: the U+00A0 returns as the six-character entity &nbsp;,
so a round-trip comparison would have measured the browser's re-serialiser
against Node's generator.

WHAT THIS TEST CANNOT DO, recorded in the spec itself. It cannot catch a
reordering of the geometry's arithmetic, because both sides run the same
source. Measured: 376 * (49.9 / 100) is "187.624" and 376 * 49.9 / 100 is
"187.62399999999997" - four bytes apart, and this suite passes with either.
That hazard is closed in geometry.ts by rounding every coordinate to three
decimals, which makes the arithmetic order irrelevant to the output. Claiming
the parity test covered it would have left the real gap uncovered.

Two guards on the guard: the matrix size is pinned so it cannot be trimmed to
make a failure go away, and one test requires two different inputs to produce
different strings in the browser, so a page that echoed a fixture - or a
harness that silently compared Node against Node - would fail.

NO-HEX PROOF
================================================================================

Nothing in this repository can see inside a TypeScript template string.
stylelint reads .scss and never .ts; eslint carries no colour, size or radius
rule; the threshold guard strips template literals whole. SPEC section 21
claims "zero raw hex, radius, or spacing literal outside the token set in web
src/ ... all lint-enforced", and for lib/ui/core/rail that claim was false.
The tests make it true:

  no hex               /#[0-9a-f]{3,8}\b/i asserted absent from all three
                       zone renders
  no raw px            every style="" attribute asserted free of \d+px
  var() resolves       every var(--name) the SVG emits, looked up in the
                       COMPILED tokens.scss
  tabular figures      asserted on every <text> node, both properties

The var() check is the load-bearing one. An undefined custom property does not
render as nothing - measured in this repo's Chromium, it renders BLACK for a
fill and 16 px for a font-size, silently, and identically for all three zones.
Nine screenshot baselines could therefore pass with every rail the same black
bar. The visual suite carries a second, independent check of the same thing:
it reads the computed fill of all three zones from the live page and requires
them to differ and not to be rgb(0, 0, 0).

WHY GEOMETRY IS NUMBERS WHILE COLOUR AND TYPE ARE TOKENS. Measured, with and
without a cascade:

                                  with cascade      standalone
  fill: var(--colour-success)     rgb(21,128,61)    black
  font-size: var(--type-...)      13px              16px
  height: var(--size-...)         8px               0px - TRACK VANISHES
  rx: var(--radius-pill)          999px             auto

Colour degrading to black is wrong and visible. Geometry via var() makes the
rail disappear with no error, on a document filed with an administration. So
the geometry constants are numbers - and CHECKED MIRRORS rather than hardcoded
values: rail-tokens.test.ts compiles tokens.scss and asserts TRACK_HEIGHT
equals --size-progress-height, TICK_PROTRUSION equals --space-1, and the four
font sizes used for baselines equal their --type-*-size tokens. Drifting
TRACK_HEIGHT to 10 fails with "expected 10 to be 8".

rx is derived as TRACK_HEIGHT / 2, so no radius literal is written at all: a
pill on an 8 px bar IS half its height. That also dissolved the rx=4 versus
--radius-pill question without needing a ruling.

R33 PROOF
================================================================================

  zoneFor not reached      STRUCTURAL, not a spy
  colour variable absent   all three band tokens asserted absent

"Never calls zoneFor" is asserted by reading the module's own source and
requiring that zoneFor appears neither in its imports nor as a call anywhere.
That is stronger than the spy the relay asked for: a spy proves the function
was not called for one input, the source proves it cannot be called for any.
It is available because RailData carries the Zone in - the rail MAPS rather
than decides.

R33's instruction was incomplete, and the report should say so plainly. It
named only zoneFor as the call to skip. All three of zoneFor, railGeometry and
formatPercent reject a non-finite value, each deliberately, so a rail that
guarded only zoneFor would still have thrown one call later. The branch
bypasses all three, which is why the geometry is computed from a substituted 0
rather than from the real value.

The state renders a WORD - "Taux indisponible", with an accessible name saying
the same - and carries no band colour at all, asserted against
--colour-success, --colour-warning and --colour-error. The track, the ticks
and the band names still draw: without them the rail is a blank box, which
reads as a broken layout rather than an unknown value, and the ceilings are
still where they are.

Clamping bounds the geometry and never the label: -5 draws an empty rail
labelled "-5,00 %" and 140 draws a full one labelled "140,00 %". The relay
wrote those examples at one decimal; R40 has since made the rate two.

1. renderRailSvg TAKES A SECOND PARAMETER (R35, ruled). SPEC 6.3's stated
   signature is renderRailSvg(data: RailData): string, and it cannot place a

   Worth knowing: the guard would NOT have caught the alternative. It strips
   template literals whole, so `${w * 40 / 1e2}` inside a backtick passes
   while `const FISCAL_TICK = 40` fails. Relying on that would have put the
   product's two load-bearing numbers in lib/ui/core behind a regex. Named at
   the fence under R43.

2. THE RATE LABEL HAS ITS OWN ROW, making the inline rail four rows tall. It
   cannot share with the band names, which are centred over their bands, nor
   with the tick labels, which R39 anchors outward from the ceilings. Every

   y = 78 in a 78-tall SVG. Baselines now sit at rowTop + the step's font

   protrusion but no thickness; the FW7 brief says 1,5 and
   FD1-calculateur-desktop.md draws 2. rail-tokens.test.ts asserts its ABSENCE
   from the spacing scale, so if a token ever appears the test fails and the
   constant must become a mirror.

5. THE DOM FENCE AND THE ESCAPING WERE NOT IN THE INCREMENT LIST. Both were
   asked for in the ruling message and both turned out to be necessary rather

6. A /dev/ ROUTE WAS ADDED FOR EACH OF INCREMENTS 5 AND 6 - rail-parity, which
   renders nothing and exposes the function, and rail-gallery, which renders
   the nine combinations. /dev/** is excluded from the size gate by segment

7. THE GALLERY USES dangerouslySetInnerHTML, which todo.md reserves for FW8's

8. CI GAINED A `visual` JOB running IN the Playwright container, so it calls
   playwright directly rather than `pnpm test:visual`, which shells out to

QUESTIONS FOR THE OPERATOR

Q1. THE SOCIAL CARD SHIPS A PERCENTAGE WITHOUT A BADGE. SPEC section 20 Never
    includes "ship a percentage without its status badge". The social variant
    renders the rate at Display, and the badge is a React component that does
    not exist until FW8, so on the OG card there is nothing to pair it with.
    Three readings, and I have shipped the first: (a) the rail's band names
    and tick labels ARE the words that keep it from being colour-alone, which
    is what section 16 actually requires; (b) the OG card should carry no
    number at all, since SPEC 6.3 says it is generic and never per-result -
    which would also settle it structurally; (c) FW15 pairs it with a rendered
    badge when the OG route lands. If (b), the change is small and now is the
    cheapest time.

Q2. THE BAND NAMES COLLIDE, AND IT IS VISIBLE IN THE COMMITTED BASELINE. This
    is the one I would most like ruled, because it is a defect at the DEFAULT
    width and not merely in the thumbnail.

    Measured at Micro 11/500: "Imposition Suisse" 52,5 px, "Imposition France"
    93,7 px, "Sécurité sociale France" 122,9 px, against band centres at 20 %,
    45 % and 75 % of the track. Confirmed by eye in the baselines: at 200 px
    the three run together illegibly; at 376 px the first two touch and read
    as "SuisseImposition".

    R39 fixed exactly this class of problem for the TICK labels by anchoring
    them outward. The band names have the same problem and no ruling, and they
    cannot be fixed the same way - they are centred over BANDS, not anchored
    to points, and a string generator has no font metrics to measure them
    with.

    Three options, and I have shipped none of them: truncate to fit the band;
    drop them below some width, which is what compact already does at every
    width; or stack them on separate lines. The second is the smallest change
    and matches an existing precedent.

Q3. THE 200 PX ARTIFACT IS FOR EYES, and this is the formal request: the
    file is docs/review/rail-200px.png. The question is whether two ticks
    9,9 percentage points apart - 19,8 px at that width - are distinguishable
    at a Facebook-thumbnail size. No test can answer it.

Q4. TICK_WIDTH 1,5 px versus FD1's 2 px (R42 says 1,5 stays, not blocking).
    Noting only that at 200 px the two ticks rendered visibly differently from
    each other at 1,5 px - one a symmetric grey pair, the other asymmetric -
    because 1,5 does not align to the device pixel grid. 2 px would not have
    that problem. Purely a rendering observation for the Checkpoint A review.
