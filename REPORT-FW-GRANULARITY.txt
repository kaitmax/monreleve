SUMMARY
--------------------------------------------------------------------------------
The database now refuses a day holding FULL beside AM or PM for one account: an
exclusion constraint, entry_one_granularity_per_day, in a real migration
(20261025200000_entry_granularity_exclusion, raw SQL, commented R490). The write
path maps its violation to a 400 granularity_conflict, never a 500; the whole
batch rolls back and no EntryEvent is written. docs/api-v1.md says so (6.1, 7).
Android needs no change (R502, proven from SyncEngine). Prisma reports no drift
and does not drop the constraint (R499). Readiness reads "unmigrated" without the
migration and ready with it (R503). Driven over HTTP on a dev server against a
scratch-migrated database (R504).

ONE DEVIATION TO READ FIRST (DEVIATIONS 1): R500 speaks of a "per-entry refusal
... through the same refused path the existing per-entry refusals use". The
server has NO per-entry refusal: a batch is all-or-nothing and every refusal
(conflict, future_day, write_failed) rejects the whole POST. The per-item
behaviour lives in the CLIENT, which isolates a refused multi-item 400 item by
item (R296). So the refusal is a whole-batch 400, the closest existing shape,
and that is what makes Android behave as R500 wants.

R499 - THE CONSTRAINT
--------------------------------------------------------------------------------
CHOICE: EXCLUSION CONSTRAINT, not a trigger.
    CREATE EXTENSION IF NOT EXISTS btree_gist;
    ALTER TABLE "Entry" ADD CONSTRAINT "entry_one_granularity_per_day"
      EXCLUDE USING gist ("userId" WITH =, "dayDate" WITH =,
                          ((("portion" = 'FULL'))::int) WITH <>);
Two rows for one user and day may not DISAGREE on "is FULL". AM beside PM agree
(both 0) and stay legal; a row never conflicts with itself, so edits and kind
changes are untouched.
WHY: it is atomic under concurrency by construction (a trigger needs an advisory
lock to be, and is one more thing to get wrong); 100 concurrent FULL-vs-AM races
below all resolve to exactly one winner.
AVAILABILITY on production (from the repo, not by connecting): docker-compose.yml
pins postgres:16-alpine; docs/deploy.md does not name production's image. Dev is
16.14 and ships btree_gist 1.7, TRUSTED (PostgreSQL 13+ lets a role with CREATE on
the database install it; no superuser needed). Official images, alpine included,
ship contrib. NOT PROVEN for production itself - the pre-deploy check is a
read-only query in R505 step 1.
THE DRIFT PROOF (Prisma 7.10, fresh scratch database, all migrations):
  - `prisma migrate dev` on a fresh database applied all four migrations (it
    replays them in a shadow database to detect drift) and ended "Your database

R502 - THE ANDROID APP NEEDS NO CHANGE
--------------------------------------------------------------------------------
android/shared/src/commonMain/.../data/sync/SyncEngine.kt, handleOk(): it
branches on the HTTP STATUS ONLY and never reads a 400's body.
  400 on a multi-item batch -> isolate(batch): each item re-sent once; the good
    ones sync, the refused one stays FAILED and named. 400 on a single item ->
    FAILED. Never retried (R198, R296). 409 / 413 -> the whole batch FAILED.
So the new 400 granularity_conflict is marked refused (FAILED), not retried
forever, and cannot crash (no body parse on this path). A 409 would have held
every good item beside the bad one, which is why 400.
SyncEngineTest (:app) pins this with {"code":"invalid_payload"}
(aRejectedBatchIsIsolatedSoTheGoodItemsStillSync). No golden/test was added:
SyncEngineTest is :app, so a test there runs :app's gate for a case the
status-only branch already covers. PARKED as PARK-Q1 (an Android task). The phone
itself no longer sends a mixed day (an-granularity); this guards old clients,
the web, a replayed queue, iOS next.
