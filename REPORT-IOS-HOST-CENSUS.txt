R1202 - THE iOS-ONLY GAPS THE HOST ITSELF MUST FILL (Swift or iosMain)
================================================================================
G1 THE WINDOW SCENE. A SwiftUI App (or UIKit scene delegate) hosting a ComposeUIViewController through
   UIViewControllerRepresentable, with .ignoresSafeArea() so AppRoot owns the insets as on Android (R1170).
   - Info.plist keys: CADisableMinimumFrameDurationOnPhone = true (R1203), UIApplicationSceneManifest, UILaunchScreen.
   - Also: the API base URL (Android: BuildConfig.API_BASE_URL) and the version line (CFBundleShortVersionString /
     CFBundleVersion for ParametresCopy.version, R894).
   - Needs no account (iOS Ruling 2).
G2 THE SIGN-IN LINK.
   - Android's CallbackActivity is a verified https App Link (assetlinks.json).
   - The iOS equivalent is a universal link. It needs an apple-app-site-association file naming "<TeamID>.<bundle id>"
     and the com.apple.developer.associated-domains entitlement. Apple's capability table lists Associated Domains for
     the paid programmes only, not the free tier, and ?mode=developer needs a development profile.
   - So a universal link is NOT available to an ad-hoc simulator build. That it is actually refused there is ARGUED
     from those two facts, not tested.
   - WHAT THE SIMULATOR CAN DO INSTEAD:
     (i) sign in by the six-digit CODE. CodeController and CodeScreen are commonMain, and the code path is a full
         second way in (AN-ONBOARD). It needs no link and no entitlement.
     (ii) a custom URL scheme (CFBundleURLTypes, no entitlement) delivered by `xcrun simctl openurl <udid> <url>`.
         That is a TEST hook only, because the server's e-mail carries the https link and no mail client on the
         runner would open it.
   - The host's v1 sign-in on the simulator is (i). Whether iOS v1 ships the universal link at all is the account's
     (Q2).
G3 THE FIRST-LAUNCH KEYCHAIN CLEAR (iOS Ruling 2).
   - A UserDefaults marker; a reinstall wipes it. When it is absent: clear KeychainTokenStore, KeychainPendingSignInStore
     and KeychainAccountStore, then set the marker.
   - It must run BEFORE the session is built or startDestination reads isSignedIn().
   - The pieces exist (each store has clear()); the ordering is the host's.
G4 THE LOCAL EVENING REMINDER (iOS Ruling 2).
   - UNUserNotificationCenter: authorization at the toggle and at onboarding's "Oui" (R323 / R1145).
   - One UNCalendarNotificationTrigger request per next working day at 19:00 device-local, at most 7 days ahead.
   - Re-planned on every foreground and on every day recorded on the phone; recording today removes today's request.
   - "Already notified" is read from getDeliveredNotifications. The copy is NotificationCopy, today in :app.
   - Gaps against it:
     - FINDING 1: IosNotificationPlan plans today only, at 17:00 Paris. FallbackReminder.kt's pure decision is the one
       that matches, but it is java.time.
     - FINDING 2: there is no iOS session-end seam to remove pending requests at sign-out, deletion or a server-ended
       session. Android's A11 seam calls FallbackReminderScheduling.cancel for exactly this.
     - The tap must route to Aujourd'hui, the EXTRA_OPEN_AUJOURDHUI equivalent, through a
       UNUserNotificationCenterDelegate.
   - Simulator: local notifications need no entitlement (aps-environment is push only). Delivery on the simulator for
     an ad-hoc app is not stated by Apple. It is I1's probe, as iOS Ruling 2 already says.
G5 THE SHARE SHEET (PARK-IF2). A UIActivityViewController presented from the scene's root view controller with the file
   URL IosExportFiles.write returns. The two export failures need a non-Toast presentation; the same need covers the
   other Toast sites (R1200 A).
G6 FOREGROUND SYNC.
   - IosSyncTrigger.afterWrite / requestDrain exist (in-process).
   - The host calls requestDrain on every foreground. That is available in common code via LocalLifecycleOwner
     (MEASURED, R1200), or from Swift via scenePhase.
   - BGTaskScheduler is NOT available on the simulator: Apple, BGTaskScheduler.Error.Code.unavailable is raised when
     "The app runs on Simulator which doesn't support background processing", and the _simulateLaunch debug commands
     "work only on devices".
   - PARK-IF1's proof therefore stays device-only, as iOS Ruling 2 foresaw.
G7 ALSO HOST-SIDE, found by the census:
   - legal links: UIApplication.open or SFSafariViewController, with R299's no-handler fallback;
   - "Ouvrir ma messagerie": no general iOS "open the mail app" intent exists. The equivalent and its fallback are a
     copy/behaviour question (Q5);
   - a native date picker in the two startDatePicker slots: M3's is unlinked on iOS;
   - the Keychain entitlement (R1203 item 5).

1. THE FRAMEWORK DECLARATION (android/shared/build.gradle.kts). The file today has no `binaries.framework` (read above).
   What it would add:
       listOf(iosArm64(), iosSimulatorArm64()).forEach { it.binaries.framework { baseName = "Shared"; isStatic = true } }
   - The default is DYNAMIC: KGP 2.2.21 NativeBinaries.kt, `var isStatic = false`.

     https://kotlinlang.org/docs/multiplatform/multiplatform-build-native-binaries.html (page dated 13 May 2026)
     https://kotlinlang.org/docs/multiplatform/multiplatform-direct-integration.html (01 Oct 2026)

   Sources: github.com/JetBrains/compose-multiplatform @ v1.7.3 gradle-plugins/compose/.../resources/IosResources.kt,
   IosResourcesTasks.kt; components/resources/library/src/iosMain/.../ResourceReader.ios.kt (copies in research/).
5. AD-HOC SIGNING, NO ACCOUNT, AND THE KEYCHAIN.
   - Build: xcodebuild -sdk iphonesimulator -destination 'platform=iOS Simulator,...' with CODE_SIGN_IDENTITY="-",
     DEVELOPMENT_TEAM="" and CODE_SIGN_STYLE=Manual (suggested; Automatic with no team may ask for a team, UNCONFIRMED).
   - Simulator entitlements are SIMULATED: Apple DTS, forum thread 733449: "Entitlements on the simulator are weird ...
     we simulate the entitlements". They are embedded in the binary's __TEXT,__entitlements section. Without them the
     Keychain returns -34018, the same code IOS-1a R565 met for the test binary.
   - CODE_SIGNING_ALLOWED=NO is reported to strip them: Bitrise thread 17257, "Client has neither
     application-identifier nor keychain-access-groups entitlements" (not Apple-confirmed).
   - SO: keep signing ALLOWED with identity "-" plus CODE_SIGN_ENTITLEMENTS (application-identifier +
     keychain-access-groups, as android/shared/ios-test.entitlements does for the test binary). I1 proves it with
     `otool -s __TEXT __entitlements -V` and a Keychain round-trip (iOS Ruling 2's probe).
   - Gradle side: KGP's embedAndSign reads SDK_NAME, ARCHS, CONFIGURATION, BUILT_PRODUCTS_DIR, TARGET_BUILD_DIR,
     FRAMEWORKS_FOLDER_PATH and EXPANDED_CODE_SIGN_IDENTITY from Xcode (XcodeEnvironment.kt). Both KGP and CMP refuse
     when ENABLE_USER_SCRIPT_SANDBOXING=YES, so the project sets it NO.
