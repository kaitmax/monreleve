INCREMENT 2 - the schema read back
--------------------------------------------------------------------
tests/db/schema-shape.test.ts. It runs in tests/db, AFTER db:deploy,
which is the only moment its answer means anything (R182).

WHY AN EXIT CODE IS NOT THE CLAIM. `prisma migrate deploy` succeeding
says the files ran. It does not say the schema is the one they
describe: a DROP that found nothing, an index created under a name
nothing looks for, a column added to the wrong table - each exits 0.
Same distinction as counting `<link>` tags versus fetching the
stylesheet.

ASSERTED CENSUSES, NOT SPOT CHECKS (R206's corollary). The index sets
are compared WHOLE, so an index added next year is a deliberate edit
here, and - the half that matters - an index REMOVED cannot pass by
not being looked for.

  Entry       4 indexes, including Entry_userId_clientMutationId_key
  EntryEvent  4 indexes, including
              EntryEvent_userId_clientMutationId_idx

  AND ONE ASSERTION STATED SEPARATELY THOUGH THE CENSUS IMPLIES IT:
  Entry_clientMutationId_key is ABSENT. R220's migration is a DROP
  then a CREATE, and a DROP that found nothing to drop exits 0 exactly
  like one that worked. The equality above fails for many reasons;
  this names the one that matters.

  NULLABILITY IS ASSERTED TOO, because the no-backfill argument
  depends on it: a migration that made EntryEvent.clientMutationId
  NOT NULL would have to invent values for legacy rows, and inventing
  them is what R219 refused to do.

  AND THE APPEND-ONLY TRIGGERS, because the entire R219 fix rests on
  EntryEvent being append-only. A trail a later write could edit would
  be no better than the row it replaced.
