READING IT: "(no logs)" on every attempt means Docker had not recorded a single
probe result, not even a failing one, in the 41 s Coolify watched. The app itself
was up: it logged Ready. #443, two hours earlier, passed the same Dockerfile
healthcheck on its first read. Nothing in d204fa0 touches startup, /api/health,
the entrypoint or the HEALTHCHECK. Its runtime changes are one migration and the
code using it. So this is a failure in the probe window, not in the code. Why
Docker recorded no probe cannot be established now: that needs the container's
`docker inspect` / `docker events` from the server, and the container is gone.

TWO LATENT RISKS IT EXPOSED:
  - Coolify printed "The healthcheck needs a curl or wget command". THE IMAGE
    HAS NEITHER (checked in the local image: no-curl no-wget). Coolify's own
    health check is currently disabled (health_check_enabled: false), so the
    Dockerfile's node-based probe is used. If anyone enables Coolify's check
    as configured (path "/"), it can never pass.
  - THE WINDOW HAS NO HEADROOM: 20 s start period + 3 x 10 s. A slow start on a
    loaded server fails the deploy and rolls back. If it recurs, redeploying is
    the remedy, and raising Coolify's retries is the cheap widening.
    The Dockerfile HEALTHCHECK is also the runtime liveness probe, so it should
    not be loosened casually.

4. RESEND_API_KEY AND FCM_PRIVATE_KEY ARE BUILD-TIME - PLAN ONLY, NO CHANGE
--------------------------------------------------------------------------------
THE FACT, from the application's variables (names and flags only, no values):
    RESEND_API_KEY        build=true  runtime=true
    FCM_PRIVATE_KEY       build=true  runtime=true
    also build-time with no build use: FCM_CLIENT_EMAIL, FCM_PROJECT_ID,
    EMAIL_FROM, ANDROID_PACKAGE_NAME
    correctly runtime-only: AUTH_SECRET, DATABASE_URL
    legitimately build-time: NEXT_PUBLIC_SITE_URL (Next inlines NEXT_PUBLIC_*;
    the Dockerfile declares it), CHROMIUM_VERSION (see 1)

THE BUILD DOES NOT NEED EITHER SECRET, on three counts:
  - the Dockerfile declares exactly three build args: NODE_IMAGE,
    CHROMIUM_VERSION, NEXT_PUBLIC_SITE_URL;
  - nothing evaluated at build time reads them (next.config.ts, prisma.config.ts,
    the Dockerfile). Only the runtime mailer reads RESEND_API_KEY;
  - gate:clone builds from a clean clone with no .env at all, and passes.

THE PLAN:
  a. In Coolify, untick "Build Variable" for RESEND_API_KEY and FCM_PRIVATE_KEY.
     Do the same for FCM_CLIENT_EMAIL, FCM_PROJECT_ID, EMAIL_FROM and
     ANDROID_PACKAGE_NAME: they are not secrets, but nothing builds with them.
  b. Deploy once, so the serving image no longer carries them.
  c. On the server, remove the earlier images of this application, and prune the
     build cache. Images and cached layers built while the flags were set still
     hold the values.
  d. ROTATE BOTH SECRETS: a new Resend API key, and a new FCM service-account
     key, deleting the old one in Google Cloud IAM. Treat them as exposed to
     anyone who could read the server's images, or any registry they reached.
  e. WHILE ROTATING THE FCM KEY, FIX ITS ENCODING. Production's own startup log
     says "[push] no push sender (malformed_private_key): the daily reminder will
     NOT be scheduled". The value the container receives today does not parse.
     The usual cause is a PEM whose newlines arrived escaped.
  f. A GUARD, so this cannot come back silently. test:container already builds
     the image. One more check there: `docker history --no-trunc` of that image
     contains none of the secret names. And a test that the Dockerfile's ARG set
     is exactly the three above. The Coolify flag itself lives outside the repo;
     a read-only check against Coolify's API is possible but is a separate
     decision.

BLOCKERS - WHY MAIN WAS NOT PUSHED
--------------------------------------------------------------------------------
A. THE COOLIFY PIN. Until CHROMIUM_VERSION is changed or deleted (see 1), a push
   to main deploys and fails exactly like #445-#470.

B. THE CodeAttempt MIGRATION, very likely never applied to production.
   - fw-code-cap (d204fa0) added prisma/migrations/
     20261015104441_code_attempt_budget: one table, two indexes.
   - REPORT-FW-CODE-CAP.txt says it "runs with the rest on deploy". IT DOES NOT.
     The entrypoint spawns server.js and runs no migration. The application has
     no pre-deployment command (pre_deployment_command: null). docs/deploy.md
     section 4 says migrations are "not run on boot" and are a separate,
     deliberate step. That section was rewritten after production ran unmigrated
     for about a week on 14 October.
   - #444, the only deploy that carried it, was rolled back.
   - It cannot be confirmed from outside. /api/ready on the CURRENT image reports
     ready:true, but it checks the migrations of the image it runs in, and #443's
     image predates this one.
   BLAST RADIUS if the new image serves without it: the served code that queries
   CodeAttempt is web/lib/auth/magic-link.ts (claimCodeAttempt), used by
   /api/v1/auth/code and imported by /api/v1/auth/callback, and
   web/lib/account/delete.ts, used by /api/v1/account/delete. SIGN-IN BY CODE AND
   ACCOUNT DELETION WOULD RETURN 500. Public pages would not be affected.
   NOTHING WOULD CATCH IT AT DEPLOY TIME. The deploy is judged by the
   Dockerfile's /api/health, and that does not check migrations. docs/deploy.md
   says the deploy check is /api/ready, but Coolify is not configured that way.
   THE SAFE ORDER: the migration is backward-compatible. It creates a new table
   and takes no lock on existing data, so applying it FIRST, while #443's code
   still serves, harms nothing. Then deploy. This session has no authorisation
   to run anything against the production database, and did not.
