SINGLE START (AC1's proof)
====================================================================

lib/scheduler/boss.ts keeps the scheduler on `globalThis`, and the
guard is TWO things rather than one:

  __monreleveBoss          the scheduler, once there is one
  __monreleveBossStarting  the IN-FLIGHT PROMISE

The second is part of the guard, not an optimisation. Two concurrent
callers would otherwise both find the slot empty and both start, which
is the double-scheduler the module exists to prevent arriving through
the one door a simple "is it set?" check leaves open. Next can call
register() from more than one entry point.

Asserted in tests/db/scheduler-start.test.ts:

  starts, and reports itself running            (presence first, R169)
  returns the SAME instance on a second start
  survives module re-evaluation, which a module-level variable does not
  starts ONCE under three concurrent callers
  can be stopped and started again              (R196: not a one-shot
                                                 latch)

A MODULE-LEVEL `let` WOULD NOT DO IT. Next hot-reload re-evaluates a
module and hands the new copy a fresh module scope, so the old
scheduler keeps its connections and its timers while the new one starts
beside it. The symptom is two reminders, which SPEC 13.3 says gets a
compliance tool uninstalled.

R243 AT THE SAME PLACE: the scheduler refuses a non-local database
host, named (R198) as `non_local_database`, distinct from
`no_database_url`. Both directions proved - four refusals by code, and
`ACCEPTS a local host, so the guard is not refusing everything`,
without which a guard that rejected every URL would pass all four.

FW27 increment 4 added the entry point itself:
tests/db/scheduled-jobs.test.ts imports `register` from
@/instrumentation and drives it, asserting that it starts the
scheduler, registers the purge, does NOT register the reminder in a
test environment, and does nothing at all outside the Node runtime.

====================================================================
IDEMPOTENCY: WHERE IT IS ENFORCED AND WHY A RETRY CANNOT DEFEAT IT
====================================================================

IN THE DATABASE. `ReminderSent` has a unique index on
(userId, sentOn), and the INSERT is what claims the day - not a set in
memory, not a "does a row exist?" check.

  the check-then-insert door   two concurrent runs both find nothing
                               and both send. Asserted closed: two
                               runs in Promise.all produce exactly one
                               send, and exactly one skippedAlreadySent
  the guarantee stated where   a second create() for the same
  it lives                     (user, day) is asserted to THROW. If
                               that ever stops throwing, every test
                               above rests on application code alone

THE ORDER IS THE WHOLE DESIGN, and it is a choice between two losses:

  insert-then-send   a crash between them costs one MISSED reminder
  send-then-insert   a crash between them costs one DUPLICATE tomorrow,
                     and on every retry until the insert succeeds

SPEC 13.3 decides: a tool that nags gets uninstalled, so the missed
reminder is the cheaper failure. When the send then fails, the row is
REMOVED again, so the window in which a crash loses a reminder is the
few milliseconds between the insert and the failure rather than the
whole delivery.

FCM SEAM: WHAT IS BUILT, WHAT IS PARKED, WHAT THE OPERATOR SUPPLIES
====================================================================

BUILT AND PROVEN AS FAR AS THE WIRE:

  lib/push/sender.ts     the interface, and the CLASSIFICATION
  lib/push/fcm.ts        the real adapter - credential reader, signed
                         assertion, token exchange, message envelope
  lib/push/fake.ts       the tests' sender, scriptable per token
  lib/push/console.ts    development: it PRINTS and delivers nothing
  lib/push/resolve.ts    which sender this process gets, or none
  lib/push/message.ts    one reminder, as it will appear
  lib/push/transport.ts  fan-out over devices, and pruning

WHAT IS PROVEN, POSITIVELY (R154), without a credential:
  the assertion is DECODED and its claims asserted field by field, and
    its signature VERIFIED against the public half of a key pair the
    test generates
  both requests are captured from an injected fetch and read against
    Google's published shapes - the form body, the bearer header, the
    message envelope
  the access token is CACHED: three calls for two devices, not four
  a refused token exchange NEVER reports token_dead

WHAT IS NOT PROVEN, said rather than implied: the wire. No request has
ever left this machine for googleapis.com and none can, because there
are no credentials. FW28 is where that changes.

WHAT THE OPERATOR MUST SUPPLY (as precisely as PARK4-2 named AN14's
fingerprints):

  1. A FIREBASE PROJECT. console.firebase.google.com, add a project,
     add an Android app with the package name the client will ship
     under. The project id is the string in the messages:send URL.

  2. A SERVICE ACCOUNT JSON. Project settings -> Service accounts ->
     Generate new private key. It downloads a JSON file containing
     `project_id`, `client_email` and `private_key`. The file is a
     CREDENTIAL: it authorises sending a push to every device
     registered to that project, and it never enters this repository.

  3. THREE ENVIRONMENT VARIABLES, in FW28's env checklist beside
     DATABASE_URL, RESEND_API_KEY and AUTH_SECRET:

       FCM_PROJECT_ID    the JSON's `project_id`
       FCM_CLIENT_EMAIL  the JSON's `client_email`
       FCM_PRIVATE_KEY   the JSON's `private_key`, newlines escaped as
                         backslash-n so it fits on one line in a .env
                         file, a Coolify variable or a CI secret. The
                         code restores them; a key with literal
                         backslash-n in it is refused by node:crypto at
                         SIGNING time, which is a failure a whole
                         deployment away from its cause, so the reader
                         does that transformation once, up front.

     .env.example ships all three as PLACEHOLDERS, and the code refuses
     those three strings BY VALUE with a distinct code
     (`placeholder_credentials`, not `not_configured`) because the two
     send whoever is debugging to different places. A test reads
     .env.example and asserts the shipped values are the refused ones -
     R181, because "the value .env.example ships" had been a COMMENT on
     PLACEHOLDER_SECRET since FW25 with nothing checking it.

PARKED, WITH THE REASON:

  PARK27-1  THE NOTIFICATION CANNOT CARRY THE DETECTED COUNTRY.
            SPEC 13.3 asks for a notification naming the detected day -
            and the SERVER DOES NOT HAVE IT. Detection happens on the
            device, D16 writes nothing until the person taps, and no
            table holds a pending proposal. The payload carries `day`
            and `mode` so a client in auto mode composes SPEC's
            sentence from the proposal it already holds locally; the
            notification's own fallback text names the DECISION
            (confirm or correct) rather than a country this product
            cannot claim to know.
            To do it server-side would mean STORING PROPOSALS: a new
            table, a new thing to disclose on /confidentialite, and a
            new thing to erase. That is a product decision, not an
            implementation one.

  PARK27-2  NO REAL CREDENTIAL WAS SOUGHT (R243). Creating a Firebase
            project would have made every later test one environment
            variable away from delivering to a real device.

  PARK27-3  THERE IS NO `DELETE /api/v1/devices`. Signing out revokes
            the session; a dead token is pruned when the service says
            so; deleting the account removes the row (D11). A
            deregister endpoint would be a fourth way to remove a row
            and the only one a client could get wrong.

  PARK27-4  A TIME-BASED DEVICE SWEEP. `Device.lastSeenAt` exists, and
            "prune a device not seen for N days" would need N - which
            is a RETENTION PERIOD, which is a product decision and a
            /confidentialite sentence. Not invented (R156).
            Consequence today: a device row for an uninstalled app
            survives until the next send refuses it. Bounded, because
            the reminder is the only send and it happens daily.

  PARK27-5  THE REMINDER CADENCE IS FIVE MINUTES, and whether that is
            right is an operational question about a machine that does
            not exist yet. "Exactly one per day" is the unique row and
            holds at ANY interval; the cadence only bounds how late a
            17:30 reminder can be. R236's shape: FW28 measures on the
            real image.

RETENTION: THE 29/31 BOUNDARY, AND 404/410 VERSUS TRANSIENT (AC3)
====================================================================

THE BOUNDARY ALREADY EXISTED, from FW14, and FW27 did not rewrite it:
tests/db/purge.test.ts asserts the 31-day row goes and the 29-day one
stays, IN ONE TEST. The pair is the point - a purge with the comparison
inverted passes "deletes old rows" and passes "keeps new rows" when
each is tested alone. Beside it: a CONFIRMED row however old is never
touched, and an UNSUBSCRIBED row is never touched, because the rule is
about subscriptions lapsing rather than about deleting subscribers.

WHAT FW27 ADDED IS THE SCHEDULE. Until this task the promise
/confidentialite has published since FW10 depended on somebody
remembering to type a command. FW12 measured what that is worth in this
repository: `pnpm test:runtime` had not run since FW10.

  purge      17 3 * * *      Europe/Paris   missed: 'once'
  reminder   */5 * * * *     Europe/Paris   missed: 'skip'

BOTH IN PARIS, because both are statements about the reader's calendar
and a job evaluated in UTC drifts an hour twice a year against the only
clock anybody here cares about.

THE MISSED-OCCURRENCE POLICY DIFFERS BY JOB, deliberately:
  purge     'once'  a deployment down at 03:17 should still purge on
                    the way back up - the promise is about how long a
                    row may LIVE, not about a particular minute
  reminder  'skip'  the next pass is five minutes away, and a backlog
                    would all find the same people due and race for the
                    same claim rows to no purpose

DEAD-TOKEN PRUNING IS NOT A SEPARATE SCHEDULED JOB, and that is the
honest answer rather than a gap. A token is only KNOWN to be dead when
a send is refused, so the rule lives where the send happens.

  prune      404, 410, and nothing else
  keep       every other answer, including 401, 403, 429, 500, 503 and
             a network error with no status at all

IT IS A WHITELIST, NOT A LIST OF EXCEPTIONS, and the difference is the
whole safety argument. Deleting a device row is destructive and SILENT:
nothing appears on the phone, nothing surfaces in the application, and
the registration only returns when the client next launches - which,
for the population reminders exist for, may be never. A credential
outage answers 401 for EVERY device in the database, so "prune unless
the send succeeded" empties the table in a single run.

THE SWEEP IS OVER THE WHOLE SPACE, not a table of statuses somebody
thought of: every status from 100 to 599 is classified, exactly two
prune, exactly one hundred deliver, and the set of outcomes is exactly
three with no undefined. A status nobody anticipated - a proxy's 502, a
future 451 - cannot widen the rule by being absent from a list.

PROVED IN BOTH DIRECTIONS AT THE TRANSPORT TOO:
  prunes on 404, and keeps the device that accepted
  prunes on 410, so the rule is not one vendor's status
  every token dead -> zero devices, rows gone, does NOT throw (nothing
    to retry)
  every device 503 -> throws, and DELETES NOTHING
  every device 401 (the credential outage) -> throws, three rows intact
  mixed: the dead one pruned, the transient one kept, in one run

R244 COUNTS: WHAT EACH JOB REPORTS
====================================================================

A SCHEDULED JOB REPORTS WHAT IT DID, NOT THAT IT RAN. "Completed" is
true of a run whose query was wrong, and unlike a test, nobody is
looking when it happens.

  runDailyReminders returns
    day, parisTime            what moment this run represents
    considered                due and opted in
    sent                      somebody received something
    skippedAlreadySent        the claim row was already there
    skippedDayLogged          they filled the day in at lunchtime
    skippedNoDevice           reminders on, nowhere to deliver
    failed                    the transport threw; the claim released

  purgeUnconfirmed returns
    cutoff                    the moment a row had to be older than
    considered                every unconfirmed row, any age or state
    deleted
    keptUnsubscribed          past the cutoff, asked not to be written
    keptTooRecent             still inside its thirty days

AND THE PURGE'S FOUR HAVE TO ADD UP. considered = deleted +
keptUnsubscribed + keptTooRecent is asserted, so a census that stops
summing means the query and the count disagree - which a single number
cannot show. A plant that moved the counts AFTER the delete made
`considered` 2 where it should be 3, and the test said so.

skippedNoDevice IS THE ONE THAT WAS NOT THERE IN INCREMENT 2, and it
arrived because increment 3 produced the first transport that can have
NOWHERE to deliver. Reporting that as a failure retries for ever on
something retrying cannot fix; reporting it as a send puts a reminder
nobody received into the one number R244 exists to make trustworthy.

RFC 8058 (R141)
====================================================================

Every LIST message now carries two headers a mail client reads:

  List-Unsubscribe       <https://.../api/alertes/desinscription?token=...>
  List-Unsubscribe-Post  List-Unsubscribe=One-Click

Gmail, Outlook and Apple Mail each render their own unsubscribe control
from them, at the top of the message, before the reader has to look for
anything. A reader who cannot find the way off a list marks it as spam
instead, and that is a domain-level cost paid by every later message.

ONE URI, NOT TWO. RFC 2369 permits a `mailto:` alternative and RFC 8058
requires the one-click POST to go to an https URI. A mailbox this
product does not read would be a published promise nobody keeps - R205
in a header - so the header carries exactly the URI that works, and a
test asserts there is exactly one.

THE SAME URL AS THE BODY'S LINK, from the same token (R206). Two URLs
from two tokens would work and would mean the control at the top of the
message and the link at the bottom expired at different moments.

THE GET STAYS, idempotent and reversible, and both verbs reach ONE
function. They differ only in the answer: a person gets a 303 to the
page that says what happened; a mail client gets 200 and one line of
text, because it has no browser to redirect.

THE POST ANSWERS 200 WHETHER OR NOT THE TOKEN WAS REAL. lib/alerts/
confirm.ts already gives an unknown token and a used one the same
answer so the endpoint cannot be fed tokens to learn which were real. A
person needs to know whether they are off the list, so the GET's page
distinguishes them; a mail client cannot act on the difference and
would only turn this into an oracle.
  SO THE TESTS ASSERT THE ROW, NOT THE STATUS: unsubscribed for a real
  token, untouched for an invented one, 200 both times. A plant that
  made the handler answer 200 and do nothing failed three of them.

THE BODY IS NOT REQUIRED. The RFC specifies what a conforming client
sends; refusing one that sends something else would leave a reader
subscribed because their mail app is imperfect, which is the wrong way
round for an unsubscribe. The token in the URL is the authorisation,
exactly as for the GET.

PREFETCH, ONCE MORE. FW14 argued the GET link was safe because the
action is idempotent and reversible and the row is kept; the one-click
POST is the same mechanism in the same direction, and a prefetch costs
somebody one re-subscription. It is the OPPOSITE of FW22's magic link,
where a prefetch BURNS a credential - same hazard, opposite
consequence, and the consequence is what decides.

ADDRESSES that device rather than a fact about them, and putting it in
a file they will mail to themselves is how a credential leaves the
system. Asserted.

every sentence about what it sends is conditional. The reminder copy
itself is not - a notification is only ever produced when there is a
device to send it to.

D2. "EVERY SEND" WAS READ AS "EVERY SEND OF A LIST MESSAGE".
    Increment 5 asks for List-Unsubscribe headers "on every send".
    There are exactly two callers of sendMail: the alert confirmation
    (a list message) and the sign-in link (transactional). The headers
    go on the first only.
    WHY: an unsubscribe control on a sign-in mail is a promise nothing
    keeps. The reader cannot unsubscribe from their own sign-in;
    pressing it would either do nothing or remove them from a list the
    message has no connection to. RFC 2369 is about mailing lists, and
    R205 is about publishing a claim only where it can be believed.
    ENFORCED RATHER THAN INTENDED: a test requires the sign-in message
    to carry NEITHER header and, in the same run, the list message to
    carry BOTH. If the operator meant literally every sendMail call,
    that test is what would have to be deleted.

D3. ReminderTransport's SIGNATURE CHANGED INSIDE THE TASK.
    Increment 2 typed `send` as Promise<void>. Increment 3 produced the
    first transport that can have NOWHERE to deliver, and increment 3
    changed it to return ReminderDelivery, adding skippedNoDevice to
    ReminderRun. The alternative - leaving it - would have made the job
    retry for ever on a person with no device.
