other looked like. THE LEAK: every step failure called process.exit(1)
from inside its own try block, which does not unwind to a pending
finally - so every FAILED run leaked its clone, not only a killed one,
which is what this project's own framing (REPORT-AN1.txt's "the fix is
periodic manual cleanup, not a code change") had assumed. THE SILENCE:

original 8.5 GB, which disproved disk pressure outright and made the

THE LEAK
====================================================================
web/scripts/gate-clone.mjs called process.exit(1) from inside its own
try block on every step failure (originally at three sites: a clone/
HEAD hash-mismatch check, the main steps loop covering typecheck/
lint/test/build/size, and the database loop covering db:deploy/
test:db/test:container:write). process.exit() terminates immediately
WITHOUT unwinding to a pending finally - a documented Node.js
semantic, not a bug in this file - and the clone's own removal
(rmSync) sat in that try's finally. So every FAILED run leaked its
clone. One of the three paths (the database loop) also called
dropScratch() explicitly before exiting, so it did not leak the
scratch database - but it still leaked the clone directory, since
rmSync never ran.

THE FIX. All three sites now `throw new GateCloneFailure(...)`
instead. The outer try/finally became try/catch/finally: the catch
sets process.exitCode = 1 for an expected GateCloneFailure (already
fully reported via console.error at the point it was thrown) and
RE-THROWS anything else, so a genuine bug in this script still surfaces
its real stack trace rather than being silently reduced to exit code
1. The finally now calls one shared cleanup() function
(dropScratch() + rmSync(clone, {recursive:true, force:true})),
unconditionally, on every exit from the try block, success or
failure. The database loop's redundant explicit dropScratch() call
was removed - cleanup() alone now owns it.

PROVEN, EACH PATH FORCED IN TURN, EACH PLANT VERIFIED LANDED (grep for
a distinctive marker) BEFORE THE RUN, EACH CHECKED AGAINST THE REAL
TEMP DIRECTORY AFTERWARD (R180):

  PATH A (clone/HEAD hash mismatch). Planted: `if (cloned !== head ||
  true)` plus a distinctive marker in both the console.error and the
  thrown message. Ran `pnpm gate:clone` for real. Output showed the
  marker (confirming the RIGHT path fired) and exited 1. Temp
  directory checked immediately after: clean, no clone left behind.

  PATH B (the steps loop). Planted: the FIRST step's (`pnpm install`)
  expect pattern changed to an impossible regex. Ran for real: a

  fired with R133's own message naming the impossible pattern. Temp
  directory checked after: clean.

  PATH C (the database loop). Planted: `pnpm db:deploy`'s expect
  pattern changed to an impossible regex. This required the ENTIRE
  preceding chain (install, typecheck, lint, test, build, size) to
  complete for real first - and on the FIRST attempt, the real
  chain's own `pnpm test` step hit THE SILENCE (see below) before ever
  reaching the plant, an unplanned but directly useful proof: cleanup
  held for this REAL, unplanted failure too (temp directory checked
  after: clean). To reach path C specifically, the `pnpm test` step's
  expect pattern was ALSO temporarily loosened (to `/./`, matching the

  (monreleve_gate_clone_09dd3624, verified via `docker exec ... psql
  -lqt`) were confirmed absent afterward.

  All three plants reverted; the file diffed byte-for-byte against a
  saved copy of the fix after each revert, confirming no residue.

SIGINT/SIGTERM: both now registered, calling the same cleanup() before
an explicit process.exit(). This closes AN1's ORIGINAL leak cause (a
killed process) for a genuine POSIX signal.

WHAT STILL LEAKS, MEASURED RATHER THAN ASSUMED. A SIGKILL cannot be
caught by any process, by definition - not news. What IS news: on
THIS Windows machine, THREE independent kill mechanisms were tried
against a running gate-clone.mjs with this exact handler registered,
and NONE reached it:
  1. This harness's own foreground-timeout kill (a throwaway probe
     script with an identical handler logged "started" and 14 "tick"
     lines then nothing - no SIGINT, no SIGTERM, no exit handler ever
     fired).
  2. A cross-process `process.kill(pid, 'SIGINT')` from an unrelated
     node invocation - threw EPERM on the SENDING side, yet the
     target still died, with no handler message logged.
  3. `kill -TERM <pid>` from the SAME Git Bash shell that spawned it -
     tested twice, once mid-install and once well into a long-running
     step. Both times: the child process died (surfacing as a normal
     step failure through path B's own throw), the parent logged one
     more line, and then EITHER the parent kept running past that
     point undisturbed, or (as later found, unplanned, during
     increment 4's own testing) the parent process itself sometimes
     survived the kill entirely and had to be force-stopped separately
     via PowerShell's Stop-Process - a live, unplanned re-confirmation
     of the same finding rather than a re-run of the same test.
  Both times the shell-level kill was tried, the clone directory
  remained afterward - a real, measured leak, not a hypothetical one.

Node's Windows SIGTERM/SIGINT emulation is built over TerminateProcess
rather than a real POSIX signal, and none of the three tested
mechanisms appear to give an in-flight synchronous try/catch/finally
time to finish before the process is torn down. NOT TESTED: a genuine
interactive terminal Ctrl+C, which Node's own documentation describes
as the supported case on Windows - this session has no interactive
terminal to produce one, and this gap is stated rather than papered
over. So the handler is written correctly and should do what it says
under a real POSIX SIGTERM/SIGINT (Linux CI, macOS, `docker stop`),
and does not close the specific leak class this machine's own tooling
produces - which is exactly why increment 4 exists as a second,
independent line of defence.

tests/unit/meta/gate-clone-cleanup.test.ts (new, 6 tests): a source

  3. BISECT THE CLONE, NOT THE HISTORY (R265's own instruction).
     - Isolated `pnpm test` alone in a manually-created fresh clone
       (git clone --local, pnpm install --frozen-lockfile, nothing
       else run first): PASSED, 164/164 files, 2907/2907 tests, with
       BOTH `--reporter=verbose` and the default reporter, run

       This run is what surfaced the real mechanics: stdout was 673
       bytes (just the run banner and summary), stderr was 7422 bytes
       (nothing but canvas warnings) - confirming gate-clone.mjs's own
       "last 14 lines" console display is ALWAYS just canvas warnings,
       on a passing run as much as a failing one, because stdout+
       stderr are concatenated stdout-first and stderr vastly
       outweighs it in line count. The truncated display was never a
       useful signal either way; only the full-string `expect.test()`
       check was.
     - Ran two of those concurrently to force real contention
       (confirmed by a measured ~50% slowdown, 151-152s vs 83-86s
       solo): BOTH PASSED. Free memory at baseline was already tight
       (~2 GB of 16 GB, matching every gate:clone run's own printed
       resource envelope this session) - genuine contention, still no
       failure.
     - Replicated the REAL SEQUENCE: typecheck, then lint, then test,
       via sequential spawnSync calls in ONE persistent Node process -
       exactly gate-clone.mjs's own steps-loop shape, the one thing
       none of the isolated attempts above had matched. Result: `pnpm
       test` printed "Test Files 164 passed (164)" in its own
       captured stdout, in full - AND gate-clone.mjs's own exact
       regex (`/Test Files\s+\d+ passed/`) evaluated to FALSE against
       the complete captured output.

  4. THE CAUSE, CONFIRMED AT THE BYTE LEVEL. Dumped the captured text
     around "Test Files" as a JSON string:
       "Test Files [22m [1m[32m164 passed..."
     vitest's own colourised summary puts an ANSI escape sequence
     directly between the words "Test Files" and the digits that
     follow - `\s+` cannot match across it. Stripping ANSI first
     (`text.replace(/\x1b\[[0-9;]*m/g, '')`) makes the identical regex
     match immediately. This is a FULLY DETERMINISTIC string-matching
     bug in the CHECK, not a resource, timing, or clone-freshness
     defect - DIRECTLY VERIFIED on the "typecheck, then lint, then
     test" run above, where 2907/2907 genuinely passed and the exact
     regex still returned false against the real captured bytes. The
     earlier "passing" isolated attempts (the verbose reporter, the
     default reporter, the matching-spawnSync script, the two run
     concurrently) were never re-checked against this exact regex -
     each was read by eye, or by a looser stand-in - so their "pass"
     was never in question, only what it was proof OF. Since every one
     of them used the same vitest version producing the identical
     colourised summary line, it is a well-founded inference, not a
     separately re-verified fact, that each would have failed the same
     way had the real check been applied. The bug itself was never
     intermittent; only the CHECKING varied. Stated plainly as a
     method note below.

  5. NOT A NEW DEFECT CLASS. REPORT-FW31.txt's own PUSH PROOF already
     found and named this exact fragility: "NINE PATTERNS SHARED THE
     FRAGILITY - seven in SUITE_COUNTS, one in gate-clone, one in
     container-e2e... Only this one had ever been exercised in a
     colouring environment." FW31 exported `stripAnsi` from
     gate-selection.mjs specifically so it could be reused, and fixed
     only container-e2e.mjs's instance. gate-clone.mjs's own instance
     was left open, and this task is what exercised it.

THE FIX: `stripAnsi`, imported from gate-selection.mjs (R206 - reused,
not copied), applied at the ONE point run() tests every step's expect
pattern against captured output. This covers all eight step checks

THE SWEEP
====================================================================
Bounds the damage even when cleanup still fails - for the cause
increment 1 measured (this machine's own kill mechanisms bypass both
the process.exit fix and a registered signal handler) or one nobody
has found yet. Nine clones accumulated over eleven days in the prior
session because nothing ever looked until the disk hit zero
(REPORT-AN1.txt).

MEASURED, NOT GUESSED: the disk cost of one real clone. Two
independent measurements this task took: a manually-created clone with
a full node_modules install (no build): 1031.20 MB. A live clone from
a real, in-progress gate:clone run, including partial build output:
1196.56 MB. Both in the same 1.0-1.2 GB range.

STALE_HOURS = 4, set from a measured figure rather than a guess: every
full chain this task ran, including the production-write suite's
Docker image build, finished in single-digit minutes (see every
increment's own verification run above and the exit gate below). Four
hours is roughly 30-60x the slowest real run observed, so a clone
still present at that age is not a slow gate - it is one cleanup
already failed to remove.

sweepStaleClones() runs at the very start of every gate:clone
invocation, BEFORE this run's own clone is created (so it structurally
cannot sweep itself): scans the temp directory for monreleve-clone-*
entries, checks each one's mtime against the four-hour cutoff, measures
the size of anything older before removing it, and reports the total -
"swept N stale clone(s) older than 4h, reclaiming ~X MiB", or "no
stale clones (older than 4h) found" - printed unconditionally, never
silently applied (R244's shape).

PROVEN ADVERSARIALLY WITH A REAL AGED DIRECTORY, not a mock: created a
fake monreleve-clone-fw32teststale directory (2 MiB of real content) and
set its mtime to 6 hours in the past via PowerShell, alongside a
genuinely fresh monreleve-clone-fw32testfresh directory with no age
manipulation. Ran the real, unmodified `node scripts/gate-clone.mjs`.
The diagnostic header printed exactly "swept 1 stale clone(s) older
than 4h, reclaiming ~2 MiB" - and, checked on disk immediately after,
the stale directory was gone and the fresh one was untouched. Both
boundary directions proven in one run: what should be swept was, and
what should not be swept was not.

THAT SAME TEST RE-SURFACED THE LEAK's SIGNAL-HANDLING LIMIT, UNPLANNED.
Killing the test run via `kill -TERM` from the same shell left the
gate-clone.mjs process itself STILL RUNNING afterward (confirmed via
`Get-CimInstance Win32_Process`), still holding file locks that turned
a routine cleanup rm -rf into a wall of "Permission denied" errors on
node_modules internals. This is not a new finding - it is THE LEAK's
own signal-handling measurement, reproducing itself during ordinary
increment-4 testing rather than a deliberate re-test, which is stronger
evidence than a second deliberate probe would have been. Closed by a
forceful PowerShell Stop-Process, matching this project's own orphan
discipline (R98/R105/R179).

METHOD NOTE
====================================================================
THE SEQUENCE MATTERS MORE THAN ANY SINGLE ISOLATED TEST, and this task
under-weighted that for longer than it should have. Every isolated
bisection attempt (verbose reporter, default reporter, matching
spawnSync exactly, concurrent load) passed cleanly and was, in each
case, read as "one more data point against the resource-contention
hypothesis" - which was the right conclusion, reached by the wrong
route. The ACTUAL defect was 100% deterministic and present in every
one of those "passing" runs too; the isolated scripts simply never
applied gate-clone.mjs's own exact check to their own output. Only
replicating the real, full multi-step sequence in a single script AND
reusing the real regex against real captured output surfaced it. The
lesson for next time: when bisecting a verifier's own check, apply the
EXACT check under test at every isolated step, not a looser stand-in
(a visual read of "it printed a summary", a different reporter) - a
looser check can pass on the exact bytes that make the real one fail,
and every step that passes on a looser check is a step that looks like
