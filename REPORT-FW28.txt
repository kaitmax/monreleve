SUMMARY - WHAT R249 ACTUALLY BOUGHT

R249 says the claim is not "the Dockerfile builds" but "this image,
on this host, serves this product correctly". Every assertion in this
task runs against a RUNNING CONTAINER.

IT FOUND FOUR DEFECTS THAT NO EXISTING SUITE COULD SEE, and three of
them were in code that had been green for weeks:

  1. /api/alertes REDIRECTED TO AN UNREACHABLE ADDRESS.
     Location: http://0.0.0.0:3000/... - built from
     request.nextUrl.origin, which inside the image is the address
     the server is BOUND to. Every no-JavaScript subscriber was sent
     nowhere. Green under `next start`, broken in the artefact.

  2. CHROMIUM COULD NOT START IN THE IMAGE AT ALL.
     "Failed to create headless user data directory container" - the
     unprivileged user's HOME was /app, owned by root. The PDF - the
     product's OUTPUT OF RECORD - answered 503 renderer_unavailable.
     The build succeeds, the server serves, 270 e2e specs pass, and
     the one thing that needs a browser is the one thing none of them
     exercise.

  3. NEXT_PUBLIC_SITE_URL IS A BUILD INPUT, WHICH NOTHING SAID.
     Static routes render their <head> during `next build`, so an
     origin supplied at runtime arrives too late and the canonicals
     are frozen. 41 of 284 specs, with correct CSS, correct scripts
     and a correct /api/health.

  4. THE SCHEDULED REMINDER PASS REPORTED NOTHING.
     lib/scheduler/jobs.ts awaited runDailyReminders() and DISCARDED
     the result. job.ts's own header says "Nobody is watching when
     this runs. 'Reminders sent' is indistinguishable from 'reminders
     not sent'" - and that was literally true of the scheduled path.
     Every R244 skip reason was computed and thrown away. FW27's
     walkthrough figures came from driving the job BY HAND, which is
     a different code path from the one that fires at 06:00.

NONE of these is a build failure. Each needed a container that was
running, being used.

INC 1 - THE IMAGE, PROVEN AGAINST A RUNNING CONTAINER
        commit c086b28

Multi-stage Dockerfile: deps, builder, runner. Facts read out of a
running container by scripts/container-check.mjs, never out of the
Dockerfile:

  uid 1001 unprivileged     HOSTNAME=0.0.0.0
  TZ=Europe/Paris AND Intl resolving it (tzdata present)
  FRONTALIER_RUNTIME=1      NODE_ENV=production
  server.js + .next/static  fonts present
  @playwright/test ABSENT   10 migrations
  chromium 153.0.8010.52, matching the pin on BOTH halves - the file
  written at build time and the binary's own --version

THE PIN IS VERIFIED, NOT HARD-PINNED. Debian removes superseded point
releases from the mirror, so a bare `=version` turns an upstream
security update into a build failure with no diagnosis months later.
The version is stated, the install attempted, the INSTALLED version
compared. The browser cannot move without a commit; the brittleness
does not come with it.

THREE DEFECTS A GREEN BUILD WOULD NOT HAVE SHOWN:

  pnpm-workspace.yaml WAS NOT COPIED into the build context. It is
  where pnpm 11 records which dependencies may run build scripts;
  without it the install ends in ERR_PNPM_IGNORED_BUILDS with prisma
  unbuilt. The FW14 defect one layer out - a file that exists on this
  machine, is never thought of as an input, and is absent from a
  fresh build.

  THE SUPPLY-CHAIN CHECK SATURATED THE LINK. 16 parallel fetches each
  took 40-50 s and tripped their own deadline. Raising the timeout
  failed twice; --network-concurrency=4 fixed it. THE CONCURRENCY WAS
  CAUSING THE TIMEOUTS IT WAS BEING ASKED TO TOLERATE. The check
  stays: it is a security pass over the lockfile of the image that
  faces the internet.

  output: 'standalone' BROKE pnpm build ON THIS MACHINE. Nine EPERM
  symlink errors - Next's tracer reproduces pnpm's store layout with
  symlinks and Windows refuses them without elevated privilege - with
  typecheck, lint and test already green. Now conditional on
  FRONTALIER_STANDALONE=1, which the builder stage sets.

  THE FLAG IS NOT HIDING A BROKEN PATH, and that is the part to
  check: the standalone bundle is a deployment artefact, the machine
  that must produce it is the image builder, docker build exercises
  the branch every time, and container-check then asserts server.js
  and .next/static are actually there inside a running container.

NON-VACUITY: container-check against node:22-bookworm-slim reports 11
failures and exits 1; against this image it exits 0. Both directions,
because a check that rejects everything passes the negative test.


INC 2 - THE IMAGE REFUSES TO START ON A PLACEHOLDER (R250)
        commit 0160441

A PLACEHOLDER IS WORSE THAN AN ABSENT VALUE. An absent credential is
legible: every "is this configured?" check says no and each feature
takes its designed degraded path. A placeholder PRESENTS AS
CONFIGURED - it is a value, it has the right shape, every naive check
passes - and the discovery otherwise happens when a reader first uses
the feature, in production, quietly.

WHERE THE REFUSAL LIVES, AND WHY NOT instrumentation.ts. That file
carries an explicit, reasoned invariant - IT NEVER THROWS - because
"a web server that will not start is a product with nothing at all".
Making it throw would contradict a decision somebody already made for
a stated reason.

There is no conflict once separated. scripts/entrypoint.mjs runs
BEFORE node server.js, so a refusal means the server process is never
created and the invariant about a RUNNING server is untouched.
Coolify sees the container exit at once, the deploy does not go out,
and the running version keeps serving - R83's outcome, one step
earlier and without a crash-loop.

THREE VERDICTS, TWO OF THEM FAILURES, NAMED APART (R198):
  placeholder, any severity   REFUSE
  required + absent           REFUSE
  degradable + absent         START, and say so

The third is the one worth defending. Turning a designed degraded
state into a crash converts "this deploy did not go out" into a
crash-loop, and a restart cannot supply a missing variable.

R206: ONE TEXT, ONE HOME. The entrypoint needed the same four
placeholder strings print-token.ts and fcm.ts already refuse. Typing
them in with a test asserting they match is what R206 forbids BY
NAME, because such a test only proves they were equal when somebody
last looked. They moved to lib/deploy/placeholders.mjs; both modules
re-export rather than declare.

IT NEVER PRINTS A VALUE. Names and verdicts only - a container log is
a place things get pasted from, and an entrypoint that echoed the
secret it was complaining about would be a disclosure bug inside the
credential guard. Asserted.

R185 GAP FOUND AND CLOSED ON THE WAY. placeholders.d.mts said parity
was "asserted, not argued" and parity was NOT being asserted:
declaration-parity.test.ts globbed scripts/ only - a scope correct
because every .mjs happened to live there. R246's shape on a
different enumeration. The walk is derived now.


INC 3 - THE SUITE AGAINST THE IMAGE
        commit dbd2057

270 of 270 specs against the deployed artefact.

THE REDIRECT DEFECT, and the fix removes the class rather than the
instance. A RELATIVE Location - RFC 7231 has allowed one since 2014 -
means the answer no longer depends on how the server perceives its
own address: proxy, port mapping, wildcard bind, or none of them.

  FIXING IT IN THE PROXY WOULD HAVE WORKED AND BEEN WORSE. Coolify
  sets x-forwarded-host, so production would likely have been fine
  while every direct hit - staging, a health probe, a container run
  by hand - stayed broken. A defect that only appears where nobody is
  looking.

IT MADE AN EXISTING TEST STRONGER. subscribe-route.test.ts sends
`next: '//evil.example'` as an open-redirect payload. Against an
absolute Location that was inert; against a relative one it is live,
because //host is an absolute URL wearing a leading slash - the
browser supplies the scheme. "Starts with /" would have accepted
exactly that payload. It now asserts relative AND not
protocol-relative. Impossible today because the path comes from the
closed RETURN_TO map, and ONE REFACTOR AWAY FROM UNTRUE is a
coincidence with a good track record, not a safety property.

MEASURED PROGRESSION: 41 failed -> 39 (origin as a build arg) -> 14
(the origin the suite actually asserts) -> 10 (relative redirect) ->
0 of 270 (designed exclusions applied).

TWO DESIGNED DIFFERENCES, DERIVED AND NAMED, NEVER TOLERATED (R133):
  9 specs reach /dev/**, which R129 keeps OUT of the production

  1 spec asserts runtime:false; the image is marked as serving (R81)

Seven tests against the running image: link issuance with the token

INC 5 - TWO CONTAINERS, ONE DATABASE (R243 LIFTED)
        commit ca30aee

  monreleve-sched-a  ->  92d25988a890/13     3 executions
  monreleve-sched-b  ->  b6c846e20065/13     3 executions
  total 6, enqueued 6

Distributed, not duplicated - and BOTH REPLICAS DID SOME, which is
the assertion that matters. A correct total with an idle replica is
the shape of a lock nobody released, and it looks exactly like
success because the other container was doing the work.

NO ADVISORY LOCK. A session-held lock survives a container that dies
until its connection is reaped, so the survivor silently never
schedules. Every claim here is a UNIQUE ROW instead - ReminderSent
keyed (userId, sentOn), the insert IS the claim - so a dead container
releases nothing because it holds nothing.

R243 LIFTED BY A MARKER, NOT BY DELETING THE CHECK.
FRONTALIER_SCHEDULER=1, which THE IMAGE DELIBERATELY DOES NOT SET, so
`docker run monreleve` by hand cannot start notifying people. Not
FRONTALIER_RUNTIME, which the image and playwright.runtime.config.ts
both set - keying on it would have made the R81 guard suite a
reminder sender.

AND IT FOUND THE SILENT JOB (defect 4 above).


INC 6 - THE PDF, IN THE IMAGE AND HERE

THE FONT PROBE. STYLE_PROBE proves the STYLESHEET resolved; it cannot
prove the FONT loaded, and in this container those fail
independently. Inter arrives as woff2 OVER HTTP through an @font-face
rule while the image installs fonts-liberation as a fallback - which
is exactly what makes the failure quiet. A document in the fallback
face passes EVERY structural assertion R232 asks for while being in
the wrong typeface.

RendererFontlessError is a separate class from RendererUnstyledError
because the two send a reader somewhere else (R198): unstyled means
the CSS did not arrive, fontless means it did and the font behind it
did not.

THE FAMILY IS READ FROM THE PAGE, NOT TYPED (R206). It lives in
tokens.scss as $font-family-base; naming it again in pdf.ts would be
a copy that goes stale the day the stack changes. The probe reads the
computed value and asserts THE FONT THIS PAGE ASKS FOR is the one
that loaded.

THE COMPARISON, MEASURED:
  image (apt chromium 153.0.8010.52)    155 569 bytes,  9 pages
  here  (Playwright's managed chromium) 189 232 bytes,  9 pages

SAME PAGINATION, 18 % APART IN BYTES. Bytes are deliberately NOT
asserted: two Chromium builds embed different producer strings and
compress differently, and a byte assertion would fail on every
upstream security update and teach everybody to ignore it. THE PAGE
COUNT IS THE STRUCTURAL CLAIM - a renderer that lost the stylesheet,
the font or the print media rule produces a different number of pages
in a paginated A4 document.

The pass is 0,09 % of the interval. THE CADENCE DECIDES PUNCTUALITY

D1. THE PLAYWRIGHT webServer TIMEOUT WENT 240 s -> 600 s (PARK-16).

    R241's consigne lists "a gate, budget or threshold change" as an
    early-exit trigger, so this needs its argument in the open rather
    than in a code comment.

    IT IS A TOLERANCE, NOT A THRESHOLD. It weakens no assertion:
    every spec still runs and every baseline is still compared at
    zero tolerance. R114's no-tolerance rule governs DIFFS, and how
    long a harness waits for a server to EXIST is not one. The cost
    of being wrong is that a genuinely hung server takes ten minutes
    to report instead of four - paid only when something is already
    broken.

    The alternative NOT taken: let the visual container reuse a host
    build. Faster, and it would cost R98 - isolation is the reason a
    baseline means anything.

D2. `docker builder prune -af` REMOVED 27,85 GB OF BUILD CACHE,
    including other projects'. It is regenerable and it was shared

D3. `wsl --shutdown` STOPPED EVERY CONTAINER ON THE MACHINE,
    including a neighbour's. Ours returned by restart policy;
    tizicorp-app-1 has none and did NOT return. It was left alone
    rather than restarted by us - R179 authorises killing only a tree
    this harness spawned, and starting somebody else's container is
    no more mine to do than stopping it. The engine was already
    answering 500 on every route when the reset was issued, so
    nothing that was serving was taken down.

D4. THE E2E SUITE IS RUN AGAINST THE CONTAINER BY FILE LIST, not by

D5. tests/db/container-{auth,pdf}.test.ts SKIP under `pnpm test:db`.

====================================================================
NEEDS - WHAT A HUMAN MUST SUPPLY (R250)
====================================================================

NOTHING BELOW WAS CREATED. R250 is absolute: no real credential is
sought or created, no third-party account opened, nothing deployed to
a real host, no DNS touched, no email or push reaching anybody. Each
line is what is missing, where it goes, and what it blocks TODAY.

N1  A FIREBASE PROJECT, a service account, and its private key.
    ->  FCM_PROJECT_ID, FCM_CLIENT_EMAIL, FCM_PRIVATE_KEY
    BLOCKS: the daily reminder. Without them the queue is NOT
    REGISTERED at all and the refusal is reported by name at boot -
    not a silent failure, but not a feature either.
    NOTE: the FCM seam was proven as far as the wire in FW27 with a
    generated key pair; what is missing is a real project.

N2  A RESEND API KEY and a verified sending domain.
    ->  RESEND_API_KEY, EMAIL_FROM
    BLOCKS: every confirmation and sign-in message. Unset, the mailer
    collects in memory and delivers to nobody - correct for tests,
    and in production it means the alert list accepts subscriptions
    nobody can confirm. It logs once, loudly, for that reason.

N3  SPF AND DKIM for the sending subdomain.
    ->  DNS for notifications.<domain>
    BLOCKS: deliverability. Without both, double opt-in lands in spam
    and the list silently stops growing - a failure that looks like
