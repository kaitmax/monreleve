DEVIATIONS
--------------------------------------------------------------------
1. THE OG CARD IS NOT RENDERED BY opengraph-image.tsx, which SPEC 14
   names and the prompt asked for. It cannot be. Measured, two ways:

     the SVG as a nested <img>   rasterises the SHAPES and silently drops
                                 every <text>. Bands and ticks painted;
                                 product name, both tick labels and the
                                 legend absent. 4784 bytes with a font
                                 passed to ImageResponse and 4784
                                 without - resvg has no font database and
                                 no way to be given one through that API.
                                 A control naming Arial rendered 960
                                 bytes of empty grey, same as Noto Sans.
     the elements inline         refuses: "<text> nodes are not currently
                                 supported, please convert them to
                                 <path>".

   An image route would have shipped a coloured bar with no words on it.
   The alternatives were a second rasteriser - a dependency, a committed
   font binary (satori and resvg both refuse woff2, the only format
   public/fonts ships), and a SECOND IMPLEMENTATION of the rail, which is
   what SPEC 6.3's "one implementation" exists to prevent - or a typeface
   that is not the product's.

   So the card is rendered by the renderer the product already uses, in
   R37's container, and served as a static asset at the same URL
   opengraph-image.tsx would have used. The normative property is
   unchanged: generic (R44), 1200x630, never per-result.

2. THE CARD IS SERVED FROM public/, NOT app/, and this is a SECOND and
   independent reason the file convention cannot be used. With the card
   at app/opengraph-image.png, a build with no configured origin put this
   in the head of every public page:

     <meta property="og:image" content="http://localhost:3000/opengraph-image.png?56ee358a35a09d24">
     <meta name="twitter:image" content="http://localhost:3000/...">

   e2e/guard.runtime.spec.ts caught it. R81 carries over from canonicals
   without modification: a URL a crawler cannot fetch is an INSTRUCTION
   rather than an absence. The convention has no conditional form, so the
   tags are declared behind canonicalsAvailable() instead, and a test
   asserts the file is NOT under app/ and carries the head that made the
   case.

3. ANALYTICS DID NOT SHIP. See R138 MAPPING. The prompt named this
   outcome in advance and it is the one the measurement produced.

4. FOUR OF NINE EVENTS ARE NOT WIRED. See EVENT PAYLOADS. AC3's "all
   events fire with correct payloads" is therefore PARTIALLY met: the
   payload contract is complete and enumerated, five events fire, four

5. WebApplication IS ON ONE CALCULATOR, NOT TWO. /calculateur-lamal-cmu

QUESTIONS FOR THE OPERATOR
--------------------------------------------------------------------
Q39. ANALYTICS, WHICH MECHANISM? SPEC 15 says "same-origin script" and
     SPEC 20 makes any third-party script your call. Three ways to
     satisfy it, and they are materially different:
       (a) proxy a deployed Umami's /script.js through our origin
       (b) commit a copy of that script to public/
       (c) send events from our own code to a same-origin endpoint that
           forwards to Umami - no third-party script at all
     FW15 built the event layer so that (c) needs one function and no
     call-site changes. (b) is the one I would refuse without a ruling:
     an unverifiable copy of somebody else's code, shipped to every
     reader.

Q40. SHOULD R132's SELECTOR COVER e2e/** AND tests/visual/**? See
     NOTICED 1. Proposed pattern: a changed file under e2e/ selects the
     suite it belongs to (test:e2e, or test:visual for *.visual.spec.ts),
     and a changed baseline selects test:visual.

Q41. THE OG CARD'S REGENERATION PATH is docker-only, like every other
     baseline. That is consistent with R37, but the card is a SHIPPED
     ASSET rather than a review artifact - a contributor without docker
     cannot change the rail and ship a matching card. Acceptable, or
     should FW28 make the card a deploy-time artifact instead?
