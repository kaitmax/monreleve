THE Json CONFIGURATION (WireJson.kt - one config, every flag vs org.json)
--------------------------------------------------------------------------------
  explicitNulls = false
    org.json NEVER wrote a key for a null optional (the code did x?.let{put(...)}),
    so a null was an ABSENT key, never "x":null. The server's zod is .optional() (absent
    allowed) and NOT .nullable() (literal null -> 400). explicitNulls=false omits a null
    property on ENCODE (reproducing the omission) and reads an absent nullable key as null
    on DECODE - exactly org.json's `if (isNull(key)) null else ...` for both absent and
    explicit-null.
  encodeDefaults = false
    org.json wrote precisely the keys the code put(). The request DTOs give their
    always-sent fields NO default, so encodeDefaults=false can never drop one; it only
    affects a nullable optional at its null default, which explicitNulls already omits.
  ignoreUnknownKeys = true
    org.json read only the keys it named and ignored the rest. Contract 6.5 makes this a
    CLIENT OBLIGATION (so the server can add a response field without breaking the client).
  isLenient = false
    org.json parsed the strict JSON the server sends; strict parsing of a real server body
    gives the identical accept/refuse decision, and a malformed body is refused by both.
  coerceInputValues = false
    org.json never coerced null/invalid to a default - a missing required field threw
    (getString on an absent key), caught by runCatching to null / Malformed. false keeps
    that: a missing mandatory field throws MissingFieldException. Coercing would invent a
    value org.json never produced.

UNKNOWN RESPONSE KEYS, case by case (R380): org.json ignored them everywhere (it read
only named keys), so ignoreUnknownKeys=true matches for every response - the token pair,
the entries response, and (via explicit tree reads) parseServerFailure and parseDossier.
No decoder refused on an unknown key today, so none does now.
