R410 - THE REFUSAL
--------------------------------------------------------------------------------
IN THE ROUTE, NOT THE SCHEMA, AND THE CODE IS ITS OWN. The batch schema already
carries cross-entry rules (the duplicate-pair check), and they surface as
invalid_payload with per-item issues. This one does not go there, for the
reason the dossier route gives about its own refusal: a generic code "would
send the caller to check their parser; this names what is actually the matter."

A client that sent tomorrow has not malformed anything. It has a clock problem
or an offering-days problem, and `future_day` says which.

Keeping it out of the schema also keeps the schema time-independent: a Zod
refine reading the clock is a validator whose result depends on when it runs.

REFUSED WHOLE, NOT PER ROW. One future day refuses the batch and writes none of
it, matching how a duplicate pair inside one batch is already treated. A
partly-written batch is the state a client cannot reconcile.

THE LOG LINE CARRIES THE COUNT AND THE SERVER'S OWN DAY, never the reader's
days. Whoever is wondering why a client is being refused needs the shape of the
problem, not a record of when somebody worked.

THE COPY lives in lib/fr/auth-api.ts as `futureDay`, in the house style (APOS,
the no-break space before a colon). It NAMES THE RULE AND NO DATE (R153) - an
example day in an error message is stale the moment the clock passes it - and
it explains rather than scolds, because the ordinary way to meet this is a
phone whose clock is ahead.

--------------------------------------------------------------------------------
R411 - TODAY IS COMPUTED IN PARIS, AND THIS IS THE WHOLE SUBTLETY
--------------------------------------------------------------------------------
    const today = parisDayOf(new Date());

parisDayOf is lib/entries/day.ts's, not a second copy (R206). String comparison
on both sides, because YYYY-MM-DD sorts lexicographically as it sorts
chronologically - parsing either into a Date to compare them would reintroduce
an instant, and an instant is what has a timezone.

THE FIXTURE IS KMP-2'S OWN, not invented for the test (R171):

    2026-10-19T22:15:28.694Z  is  00:15 on 2026-10-20 in Paris

That is the entry the S9 produced. A rule computing today in UTC would read 19
October, call the 20th the future, and REFUSE THE VERY ENTRY THAT FOUND THE
DEFECT - every night, for the two hours a day the zones disagree.

BOTH SIDES OF THAT BOUNDARY ARE ASSERTED at the same pinned instant:
    2026-10-20 at 00:15 Paris   ACCEPTED   (today for the reader)
    2026-10-21 at 00:15 Paris   REFUSED    (genuinely tomorrow)
The second exists so that a rule which simply added a day of slack everywhere
cannot pass the first.

A SECOND SITE, FOUND WHILE READING THE PRECEDENT (R267)
--------------------------------------------------------------------------------
THE DOSSIER ROUTE'S future_year HAS THE SAME PARIS/UTC DEFECT, one unit
coarser:

    app/api/v1/dossier/route.ts:89
    if (query.year > new Date().getUTCFullYear()) {
      return refuse('future_year', AUTH_API_COPY.invalidYear);
    }

At 00:30 Paris on 1 January, UTC still reads 31 December of the previous year,
so a request for the year that has just started would be refused as the future.
The Android client asks for the current year on open (KMP-2's device log shows
GET /api/v1/dossier?year=2026 and ?year=2025), so this is reachable - narrowly,
for two hours, once a year, on the one day somebody might well open the app to
look at the year that just ended.

NOT FIXED HERE. This task's own prompt scoped that route out as "already
works", which was written before this was found. Changing scope mid-task is
what the discipline forbids, and the fix is one line plus a test, which is a
task rather than an aside.

IT IS RECORDED RATHER THAN MENTIONED because a finding that names a second site
is not closed until that site is checked (R267), and REPORT-FW31's own
nine-pattern finding is what that ruling is made of.
