THE FRAMING THAT SHAPED IT
--------------------------------------------------------------------
This is where the engine meets real rows for the first time. Every
fixture it has been fed since FW3 was a TeleworkInput somebody typed.
lib/dossier is the first thing that BUILDS one, and it sits between
two verified things - R175's position exactly.

IT COUNTS, IT DOES NOT CALCULATE. Nothing in aggregate.ts divides,
rounds or compares against a threshold. FW12's tile defect was a panel
recomputing what the engine had already produced, and it passed
because every fixture agreed; the two only diverge on inputs nobody
wrote down. The defence is having no second implementation.

ABSENCES NEVER REACH THE ENGINE, asserted as IDENTITY rather than
absence: the engine's input AND its result are equal with and without
them. "Absences are excluded" is satisfied by code that excludes them
from three of four counters. A third test asserts they are still
COUNTED, or both identity tests pass against an aggregation that drops
them on the floor.

FINDING 1 - A DEFECT IN MY OWN MODULE, CAUGHT BY ONE GUARD
--------------------------------------------------------------------
`calculateTelework` returns Result<TeleworkResult, ValidationError[]>,
not a bare result. The first monthly.ts read `.declarableRate` off the
wrapper, which is `undefined`.

THREE TESTS PASSED ON THAT:
  "December equals the annual figure"  undefined === undefined
  "the column rises through the year"  undefined vs undefined, x12
  "every month has a row"              never read a rate

The one that caught it asserted the December figure was GREATER THAN
ZERO. A non-vacuity guard, doing exactly what R133 says it is for -
inside my own work, an hour after I wrote the guard for a different
reason.

It now throws rather than returning zero on a refusal: a rate of 0
because validation failed is indistinguishable, on the page, from a
rate of 0 because the person never left Switzerland.

FINDING 2 - THE ACCUMULATION TRAP, MEASURED
--------------------------------------------------------------------
The cumulative column is the engine's answer for January through each
month - twelve calls, no arithmetic. Planting the obvious alternative,
adding each month's rate to a running total:

  expected 19.919999999999998 to be 20

Twelve truncations compounding in one direction. Every row plausible,
the arithmetic internally consistent, and only the December figure
disagreeing with the annual one - which is the single assertion that
separates the two implementations.

FINDING 3 - THE HAND-CHECK DISAGREED WITH THE ENGINE, AND THE ENGINE
WAS RIGHT
--------------------------------------------------------------------
Increment 6's instrument, run against the demo year. March, counted
from the rows by hand:

  CH 13   HOME 9   MISSION_FR 0   MISSION_THIRD 0   ABSENT 0

The service agrees exactly. December's cumulative (42.7) equals the
annual rate (42.7), so the computed-not-accumulated property holds on
real data and not only on a fixture built for it.

THEN THE ANNUAL FIGURE DID NOT MATCH MY ARITHMETIC:

  by hand   (102.5 + 1 + 1) / 240  =  43.54
  engine    declarableRate          =  42.70
  engine    rawRate                 =  43.60

I had used the wrong numerator. The engine computes the declarable
rate from `waterfall.daysCountedAgainstCeiling` - telework only,
102.5/240 = 42.7083, truncated to 42.70 - while `rawRate` counts every
day outside Switzerland, 104.5/240 rounded UP to 43.6. calculate.ts
says so two lines below the call: days outside Switzerland are "a
different quantity from the declarable numerator and legitimately
larger".

WHY IT IS WORTH RECORDING RATHER THAN QUIETLY CORRECTING. Two rates,
two numerators, two rounding rules, and both are percentages of the
same denominator that differ by under a point. SPEC 12's monthly
column is "cumul % declarable", so it takes the first. The zone
panel's annualised percentage is not yet decided, and putting the
wrong one there would be invisible to every test that checks a rate is
a plausible percentage. Increment 4 chose it deliberately - see Q82.

AND THE DEMO YEAR CROSSES THE THRESHOLD, which matters for FW25:

  remainingToFiscal  -6.5
  warnings           FISCAL_CEILING_EXCEEDED, A1_REQUIRED

A fixture that never crossed could not exercise the warning path at
all.

R223 - THE REFUSAL IS NAMED HERE
--------------------------------------------------------------------
CI_FULL is unset; window 2 is closed. The guard that names the
private-plus-CI_FULL condition CANNOT LIVE IN THE WORKFLOW, which is
the whole reason it exists: in that state GitHub starts no job, so a
guard job would be refused with the rest. It runs in gate:clone, which
already gates every push.

It reports rather than refuses, and says so: the push is sound, what
is wrong is what CI will do with it. A test asserts that sentence is
present - without it the next session reads "your work is broken".

R133 on the unknown path: an unauthenticated gh is reported as
UNKNOWN, because "the guard found nothing" and "the guard could not
look" read identically in a log.

NOTICED BUT NOT TOUCHING
--------------------------------------------------------------------
1. `ruleSetFor` FALLS BACK TO THE LATEST KNOWN RULES for any year it
   does not have, and only 2026 has a RuleSet. A dossier for 2019 is
   therefore computed with 2026's thresholds. The engine is honest -
   it warns when the applied year differs from the requested one - so
   this is not a defect, but it makes carrying the warnings an
   obligation of every caller. Three tests hold lib/dossier to it,
   including the negative case.

2. THE SESSION PROMPT LANDED AT THE REPOSITORY ROOT because I staged
   with `git add -A`. Moved to relay/, where every other prompt is
   tracked. The lesson is the small one: stage what the increment
   changed, not what the tree happens to hold.

QUESTIONS
--------------------------------------------------------------------
Q82. ANSWERED - R224. The panel takes the DECLARABLE rate, the same
     figure as the monthly column and the one that positions the rail
     (SPEC 6.2). A panel whose number and whose rail disagreed by
     0,84 points would contradict itself on one card. The RAW rate
     travels beside it: FD3 specifies a two-rate state, and
     discarding the raw rate would make that state unbuildable in
     FW25. Geneva is the precedent - 39,16 declarable published
     against 45,0 raw.

     Implemented in increment 4 and planted BOTH ways. Taking the raw
     rate as the figure fails two tests, and the second is the one
     that matters: the monthly column still reads the declarable
     rate, so the same card disagrees with itself.
