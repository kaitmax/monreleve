INTERPRETATIONS
--------------------------------------------------------------------------------
I1. THE PUBLIC FORM'S DEFAULT GRANULARITY IS 'halfDay'. The increment asks for
    this to be stated. SPEC 9.3 puts step 0.5 on the visible day field; the
    engine rejects a half-day value declared under 'day' with
    GRANULARITY_MISMATCH. Both cannot hold. 'day' remains reachable in the
    accordion, where choosing it makes 0,5 an error, correctly.
    Asserted through behaviour, not by reading state: a half day draws no
    complaint, a quarter day does. The pair matters - "accepts 0,5" alone
    would also pass under 'hours', which accepts anything.

I2. THE STATE IS NOT A TeleworkInput, though the increment describes it as one.
    canton has no empty member; the numbers are TEXT while being typed, and
    Number of the empty string IS 0, so clearing the day count would silently
    answer a question the user was in the middle of un-asking; and
    periodFraction is not a thing a person knows about themselves - they give
    a date. The state holds what the CONTROLS hold and is converted at one
    boundary.

I3. NOTHING IS VALIDATED UNTIL A CANTON IS CHOSEN. validateInput is internal
    to the engine and exporting it would change the engine's public API, an
    ask-first item under SPEC 20. So validation goes through calculateTelework,
    which needs a complete input, and a complete input needs a canton.
    Asserted rather than left implicit. See Q13.

I4. THE THREE FIELDS' HELPER TEXT IS NOT IN SPEC 9.3. Its table gives a "Why
    visible" column - "Determines the regime", "Scales ceiling and mission
    cap", "The number they came to enter" - which is rationale addressed to
    whoever builds the form, and the last of those is plainly not something to
    say to a user. Each helper states the field's CONSEQUENCE in the terms
    SPEC 7 already uses and names no figure. The day field's helper carries
    SPEC 9.3's own observation that leave and sick days are not asked because
    the annual basis absorbs them.

I5. RadioGroup IS NOT FieldGroup. FieldGroup wires exactly one control: it
    renders a label with a for attribute and hands back aria-describedby and
    aria-invalid for the element that id names. A for attribute pointing at a
    fieldset is inert - a fieldset is not a labelable element - so the label
    would look right and announce nothing. A legend IS a group's accessible
    name. So "every field wrapped in FieldGroup" is read as: every field with
    one control. axe passes on all four states.

I6. WHICH FIELD EACH ValidationError BELONGS TO. Only two codes carry a field
    name. The mapping is explicit, exhaustive over the union and ends in a
    never assignment, so a new code is a compile error rather than a message
    that renders nowhere:
      RATE_OUT_OF_RANGE            -> taux d'activite
      PERIOD_OUT_OF_RANGE          -> debut d'activite (the date, not the
                                      fraction, which the user never sees)
      NEGATIVE_DAYS / MISMATCH     -> by its own field; 'denominator' is the
                                      exact method's total
      DAYS_EXCEED_TOTAL            -> jours de teletravail, the field the user
                                      is editing when it happens and the one
                                      they can shrink to fix it
      TOTAL_WORK_DAYS_NOT_POSITIVE -> the exact total

I7. ERRORS ARE ROUTED BY WHAT IS ON SCREEN, not by code alone. A start date in
    a later year is reported against the date field, which lives inside the
    disclosure; close it and the message would vanish while the form stayed
    un-calculable and silent about why. Anything unplaceable surfaces in a
    form-level list, which is therefore not decoration.

I8. THE EXACT METHOD'S TOTAL IS PREFILLED FROM THE RULE SET. SPEC 9.3 says the
    user supplies it. An empty field reaches the engine as NaN, which it
    reports as "cannot be negative" - a wrong message about a field nobody has
    typed in yet. The simplified basis is the number the calculation was
    already using, so starting there states the default rather than inventing
    one.

I9. TOTAL_WORK_DAYS_NOT_POSITIVE IS SUPPRESSED UNDER THE SIMPLIFIED BASIS.
    Found in a baseline. With the rate at 0 the engine reports both
    RATE_OUT_OF_RANGE and, correctly, TOTAL_WORK_DAYS_NOT_POSITIVE - because
    ceil(basis x 0 x period) is 0. Two messages for one mistake, the second
    naming a quantity the user has never seen. Under the simplified basis that
    error is ALWAYS derived: with a rate of at least 1 and a period above 0
    the total is the ceiling of a positive number, so at least 1. Under the
    exact method the user supplies the number, nothing else explains it, and
    suppressing it would leave a form refusing to calculate in silence.

I10. THE MISSION GUIDE IS NAMED, NOT LINKED. SPEC 9.5 puts the full rules at
    /guides/jours-de-mission-hors-suisse, which is FW17. R85's principle is
    that a target renders only when it is live, so a link here would promise a
    404 from a helper. Asserted: no link whose name contains "guide".

I11. YEARS ARE NOT FORMATTED AS QUANTITIES. The fallback banner writes 2099,
    not "2 099": a year is a label, not a count, and SPEC 6.4's group
    separator has no business in one.

I12. THE METHOD HELPER IS SPEC 9.3 VERBATIM WITH ONE SUBSTITUTION. SPEC prints
    the basis as digits; here it arrives as an argument from
    RuleSet.simplifiedBasisDays. Every other character is SPEC's. Copy holding
    its own copy of a rule constant is the staleness R73 forbids, and this is
    the same treatment increment 1 gave the explanatory prose.

FINDING 1 - CI HAD BEEN RED FOR EIGHT COMMITS AND THE GATE COULD NOT SEE IT.

R97 made formatPercent's precision required, and I fixed the TypeScript call
sites. scripts/check-format-parity.mjs is .mjs, so tsc never sees it: R97 was
enforced as a COMPILE ERROR, and a compile error cannot reach a file that is
not compiled. CI's output, reproduced locally byte for byte by reverting the
call:

  1 parity failure(s):
    formatPercent(100)
      wanted U+0031 U+0030 U+0030 U+002C U+0030 U+00A0 U+0025
      got    U+0031 U+0030 U+0030 U+00A0 U+0025

TWO CALLS WERE WRONG AND ONLY ONE SHOWED IT. formatPercent(34.6) with no
precision renders "34,6 %" anyway, because Intl.NumberFormat falls back to at
most three fraction digits when min and max are undefined - the right answer
from a broken call, one line above the one that failed.

WHY IT SURVIVED EIGHT COMMITS is ruling R94, which I quoted and did not
follow. "The local gate is the CI command." pnpm gate ran floor, typecheck,
lint, coverage, build, e2e and size; CI also runs pnpm parity:check on two
Node majors. I asserted the gate was the CI command without ever reading the
workflow against it. The gate now ends with pnpm parity:check.

STILL NOT COVERED, stated rather than implied: the local run is node 22.14.0 /
ICU 76.1, and CI runs 22.23.2 / ICU 78.2 and 24.20.0 / ICU 78.3. Two ICU
majors from either. That matrix exists because a separator codepoint moves
with an ICU release, so a green local parity run narrows the risk and cannot
close it. Only CI can, which is the argument for looking at CI every time
rather than at the end.

FINDING 2 - force-dynamic BROKE THE PAGE'S SEO.

A dynamically rendered route STREAMS its head, so Next emitted the title and
the canonical AFTER the closing head tag. Measured on a production build:

  closing head tag at  1115
  title at             7672      (after)
  canonical at         7921      (after)

and in a browser: the calculator gave titlesInHead 0, hasCanonical 0, against
1 and 1 for the static /cgu. The HTML parser puts a link it meets after the
closing head tag into the BODY, and Google ignores rel=canonical outside head
- so the tag was present, correct, and discarded.

Replaced with revalidate = 3600. A static render keeps the metadata in head
and the year still refreshes, where a build-frozen year would state the
previous year from 1 January until somebody deployed. Both of my earlier
justifications for force-dynamic were wrong and the page's comment says so:
the second appealed to R54's gate, which cannot need dynamic rendering because
LAST_REGULATORY_REVIEW is a module constant whose change is itself a code
change.

THE REASON A DIFFERENT TEST CAUGHT IT: routing.spec.ts asserted the canonical
link UNSCOPED, which matches in the body too. It passed happily while the tag
was being ignored. Both spec files now scope the selector to a direct child of
head. The 404's assertion stays deliberately unscoped - count 0 anywhere is
strictly stronger than count 0 in head - and the asymmetry is commented so it
does not get "fixed".

FINDING 3 - R98 WAS REWRITING TWO COMMITTED FILES ON EVERY VISUAL RUN.

R98 gives each visual run its own distDir. Next then rewrites the two
TypeScript files it considers its own to point at it, because they sit on the
bind mount. The distDir is deleted when the run ends; the edits are not.

  tsconfig.json   APPENDS a glob to include. Eight had accumulated, each
                  pointing at nothing, and the list could only grow - one per
                  run, forever, in a file that goes into every commit.
  next-env.d.ts   REPLACES the reference to ./.next/types/routes.d.ts. Not an
                  addition: the live path was GONE.

AND tsc --noEmit EXITS 0 WITH THE DEAD REFERENCE IN PLACE. Measured, with it
actually committed: typecheck 0 and the whole four-command gate green. A
missing triple-slash reference target is not an error and the sources are
swept up by the recursive include regardless. The defect had no symptom
anywhere in the gate.

I FIXED tsconfig.json AND SHIPPED THE IDENTICAL BUG IN next-env.d.ts IN THAT
VERY COMMIT, because the guard I had just written named one file. A guard
written for one instance of a class catches one instance of a class. Now a
list, OWNED_BY_NEXT, snapshotted before the container starts and restored
first in the finally - before the mount-point check, which can set a failure
code and return, and a failed run is exactly the one whose leftovers nobody
looks for. tests/unit/meta/distdir-leaks.test.ts is the half that would SEE
the restore break, with a per-file mustContain so an emptied file fails rather
than passing an absence check.

Proven on a live run: both files named as restored, both md5-identical
afterwards, 48 visual passed. The machinery then survived my own interference
(FINDING 6) unaided.

FINDING 4 - THE BASELINES FOUND TWO DEFECTS THAT 1383 TESTS PASSED, AND TWO
KEYBOARD PROBES FOUND TWO OVERCLAIMS.

Looking at the pictures:
  NO GAP BETWEEN FIELDS. FieldGroup lays out its own label, control, hint and
  error with a gap and carries NO outer margin - correctly, since the
  workbench spaces its specimens from a grid. Nothing on this page supplied
  one, so all four helper lines sat flush against the next field's label. Not

Probing the keyboard tests:
  Hiding the accordion with the hidden attribute instead of not rendering it
  kept the test GREEN, which disproved my own code comment. hidden implies
  display:none, and display:none really does remove descendants from the tab
  order. The comment now gives the narrower true reason - not rendering cannot
  be got wrong, where visibility, opacity, height 0 and aria-hidden alone all
  leave a focusable control behind - and says plainly that the test does not
  distinguish this implementation from a correct display:none one.

  flex-direction: row-reverse on a stepper ALSO kept it green, because Tab
  follows DOM order and the test compared tab positions only. That is the
  defect the test was named for: WCAG 1.3.2, a keyboard user tabbing
  left-to-right through controls drawn right-to-left. It now measures
  boundingBox().x and requires the tab sequence and the on-screen sequence to
  agree. Re-probed and red: "tab 012 vs screen 210".
