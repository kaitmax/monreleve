WHAT IS READ AS THE DATABASE: the URL's path, decodeURI'd - the way
node-postgres (pg-connection-string 2.14.0, read in node_modules) reads it,
which is what the Prisma adapter and every tests/db file use. The user, host,
password, `schema` parameter and fragment never count. Refused outright: an
unset/empty URL, an unparseable one, any protocol but postgresql:/postgres:,
pg's socket and unix-path forms, an empty path (the driver would fall back to
PGDATABASE or the user name), and a `database` / `dbname` / `db` query
parameter in any case (pg lets the path win; libpq-style clients read
?dbname=). Names over 63 bytes are refused (PostgreSQL truncates them).

GATE:CLONE'S ADMIN CONNECTION (the orchestrator's live-state question)
====================================================================
Read in web/scripts/gate-clone.mjs: postgres() takes DATABASE_URL from the
environment or web/.env, requires a local host, and uses the URL AS IS -
database path included - as the admin connection that runs DROP/CREATE
DATABASE for monreleve_gate_clone_<sha8> and drops it at cleanup. The clone's
own steps get a URL with the path replaced by the scratch name. So:
- From a checkout whose web/.env names `frontalier`, the admin connection
  OPENS a session on `frontalier`. It runs only CREATE/DROP DATABASE of the
  scratch name; it reads and writes no table there.
- Nothing in gate:clone's route NEEDS `frontalier`: any database on the
  server serves as the admin connection. C5 used `postgres`; this session
  used its own in-pattern monreleve_testdb_guard, so `frontalier` was never
  opened by gate:clone here.
- The guard admits gate:clone's database by construction: the name now comes
  from scratchDatabaseName(); the census asserts it.
- The admin connection itself is not guarded and does not need to be. Making
  it always use `postgres` is a change to the push gate this task was not
  asked for (QUESTION 1).
