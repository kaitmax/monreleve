WHAT WAS BUILT

NEW ROUTE  app/(public)/calculateur-teletravail-frontalier/resultat/
           page.tsx + resultat.module.scss

  It computes NOTHING itself. decode() is SPEC 9.4's codec, the same
  pure function the island calls on mount; calculateTelework() is the
  same engine entry; ResultPanel is the same component rendering the

  reader without are answered by ONE implementation (R206) - the only

  It is allowed to be dynamic because it has nothing to protect: no

           tests/unit/content/result-path.test.ts (6 tests) asserts
           the literal, that it is a child of the calculator, that it

           the middleware's literals EQUAL the constants, and that the
           matcher is literal rather than a ":path*" prefix.

           WHY A PATH NOTHING LINKS BECOMES PERMANENT. SPEC 14 freezes
           a slug once published, and "published" usually means a
           crawler saw it. This one is never crawled - noindex, absent
           from the sitemap - yet it is at least as frozen, because a
           FORM ACTION is an address a reader lands on and bookmarks.

           nothing BUT an answer to someone's figures.

           every control carries its SPEC 9.4 name, and "Calculer" is

SHARED LINKS are untouched, as R351 requires. The share row builds its

THE DEFECT THE FORM WORK FOUND, MEASURED
====================================================================
Giving the controls their names was the easy half. The RADIO VALUES
were the defect.

  Before: <input type="radio" name="decompte" value="halfDay">
          <input type="radio" name="methode"  value="simplified240">

  Those are the ENGINE's names. SPEC 9.4's codes are j/dj/h and
  240/exact. Run through decode():

    decompte=halfDay       -> invalid:["decompte"], falls back to day
    methode=simplified240  -> invalid:["methode"],  falls back to 240

  So a reader who chose half-days would have been shown the WHOLE-DAY
  answer. Measured on the real page, before the notice existed:

    /resultat?canton=GE&tt=84&mfr=24&decompte=halfDay
    -> 39,16 %   (the whole-day answer), no notice, no word that
       anything had been dropped.

  It was invisible until now because the group was a pure UI control:
  nothing serialised those values, so nothing could be wrong with them.
  Wrapping the fieldset in a form turned them into a wire format.

  Both directions now come from ONE place: granularityCode() and
  methodCode() are exported from lib/params/schema.ts, encode() uses
  them (it had the reverse mapping inline), and the island's radio
  values are built by calling them. A second map in the island would
  have been exactly the duplication R206 names.

THREE MORE THINGS A SUBMITTED FORM BROKE, AND WHAT WAS DONE
====================================================================
1. EMPTY CONTROLS. A browser submits EVERY named control, touched or
   not. decode() read params.get(name) directly, so "?...&total=
   &debut=" reported total and debut in "invalid" - telling a reader
   two values could not be read when they never typed any.

   It was already inconsistent: "mfr=" has always decoded as zero with
   no complaint, because readDays treats it as nothing; "taux=",
   "total=" and "debut=" came back invalid. Same input, two answers,
   decided by which reader happened to be written first.

   FIXED in decode()'s read(): an empty string is an ABSENT value, not
   an unreadable one. SPEC 9.4's rule is unchanged - "taux=abc" is a
   VALUE and is still reported and still falls back. No existing test
   asserted empty-is-invalid; every invalid-value test uses non-empty
   garbage ("taux=abc", "canton=XX"), and hostile-params.test.tsx's
   "every value empty" case asserts invariants rather than specific
   names, so all of them still hold.

2. THE PARAM NOTICE WAS NOT ON THE RESULT PAGE AT ALL. My first
   version branched only on "input === null", so it would have
   rendered a figure over a silently dropped value - R351's own
   premise, one route over. The notice now renders there, reusing
   PARAM_NOTICE's lead and its two list sentences (R206) and writing
   its OWN last line, because the calculator's advice reads "vous
   pouvez corriger les champs ci-dessus" and this page has no fields
   at all (R165).

3. THE MISSION QUESTION. The calculator asks about missions OUTSIDE
   the accordion because SPEC 9.3 says a user with missions who never
   opens it gets a silently wrong answer. The two count fields are
   revealed by the island, so with no scripting a reader can answer
   "Oui" and has nowhere to put the numbers - and the engine computes
   from zero.

   Two consequences, both handled:
   - "missions" is a form control the engine does not read, so
     decode() correctly reports it as unknown. Printing it in the
     notice would tell a reader who had just answered that question
     that the calculator ignores it. FORM_ONLY_PARAMS
     (lib/params/schema.ts) exempts it, asserted to contain exactly
     that one name AND nothing the codec actually reads - both
     directions, because an exemption list that swallowed every
     unknown param would pass the first check perfectly.
   - Where missions were DECLARED and no count arrived, the result
     page says so rather than counting zero in silence. Conditional on
     the condition (R225): nothing is shown when the counts arrived.

was written into resultat.nojs.spec.ts, where it would have been

LIMITS, STATED RATHER THAN HIDDEN
====================================================================
1. THE ADVANCED ACCORDION DOES NOT OPEN WITHOUT SCRIPTING. It is
   rendered only when open, so with no JavaScript "methode", "total",
   "decompte" and "debut" are never in the form and the codec's
   defaults apply. A no-JS submit from the calculator therefore
   carries canton, taux, tt and missions, which is the core
   calculation.
