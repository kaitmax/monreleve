REPORT-FW5 - Property tests, shared fixtures, coverage gate
===========================================================================

SUMMARY
-------
The engine is closed. Eight invariants hold over 10 000 generated cases each,
the coverage gate is at 100/100/100/100 and proven to fail below it, no
snapshot can enter the module, and the three shared fixture files are frozen
for AN2. 401 tests across 23 files. Median calculateTelework is 0,01330 ms,
about seven times inside the 0,1 ms budget.

Every invariant is paired with a deliberately broken variant that fast-check
must falsify, and those pairings are permanent rather than one-off RED runs.
That is the difference between a property suite and decoration: a property
that has never failed might be vacuous, or the generator might never reach the
region where it could break, and neither shows up as a red test.

Two things are worth the operator's attention. First, a correction to my own
FW4 report: it said the rate defect was "wrong in 36 of 125750 pairs", pairing
a count measured to denominator 400 with a pair total measured to 500. The
honest figures are 36 of 80 600, or 72 of 125 750 - and the fixture now uses
the complete 72. Second, and more useful, FW4 implied the fix was integer
arithmetic versus one float form. There are two float forms and they fail on
different sets: multiply-first, which is exactly what R10's hygiene rule
prescribes for the proration, is wrong in 72; the more natural divide-first is
wrong in 172. So "multiply before dividing" is correct for the proration and
INSUFFICIENT for the rates, and the fixture, the test and the engine comments
now all say so.

The engine is code-complete and frozen pending Checkpoint A. What is proven,
what is proven only against itself, and what is not proven at all are now
written down where an operator will read them, because a green 100 % badge
invites conflating the three.

Eight invariants, each with the break that falsifies it and the counterexample
fast-check produced. Every break is a plausible mistake rather than a
contrived one - the shape of error someone would actually write.

The RED here is stronger than a one-off run: each pairing is a PERMANENT test
of the form "expect this break to be falsified", so the suite is green only
when the engine is right AND the property still has teeth. A break that
stopped being detected would fail the suite.

     BREAK   the two ceilings swapped - the copy-paste mistake.

     GREEN   10 000 cases pass, plus a second property asserting it holds for
             NEGATIVE headroom specifically, which is where a clamp would
             break it.

  5  increasing teleworkDays never decreases rawRate
     BREAK   rawRate built from swissTaxedDays instead of days outside
             Switzerland - the inversion. As telework rises the headroom
             shrinks, fewer missions are credited, swissTaxedDays FALLS, and
             a rate built on it falls with it.
     RED     falsified (permanent test asserts it).
     GREEN   10 000 cases pass.

  6  declarableRate <= rawRate
     BREAK   a rawRate that forgets the mission days. rawRate is the share of
             days spent OUTSIDE Switzerland, so omitting them makes it

             credited.
     RED     falsified (permanent test asserts it).
     GREEN   10 000 cases pass.

     BREAK   rounding to nearest instead of truncating. 39,1666 rounds to
             39,17, above the exact value - the whole reason SPEC 7.3
             specifies truncation.
     RED     falsified (permanent test asserts it).
     GREEN   10 000 cases pass, and a SECOND property asserts the other side:
             it loses less than one hundredth. A "truncation" that discarded
             more than the last digit would satisfy "never above" alone.
     NOTE    This invariant is only provable because of R16. Truncation can
             be checked against the exact unrounded value only if that value
             is computed on integers; comparing two floats would be comparing
             the defect against itself.

     BREAK   imputing against the raw France input instead of the credited

             budget - creditedFrance. When France alone exceeds the budget

     RED     falsified (permanent test asserts it).
     GREEN   10 000 cases pass, and a stronger property is pinned alongside:
             swapping leaves the credit IDENTICAL, not merely no larger,
             because the credit is min(missionTotal, budget) and that is
             symmetric. What the France-before-third-state order decides is
             which days are credited and therefore who collects the tax on
             the rest - never how many.

GUARDS AGAINST A VACUOUS SUITE. Three properties exist only to stop the
others proving less than they claim:

  - the generator produces only inputs the engine accepts, over 10 000 cases;

  - the two rates are asserted to actually DISAGREE on some generated input,
    so neither is dead code, and each rate function is asserted to agree with
    the wired result for the same numerator, so the pipeline cannot diverge
    from the units it is built from.

The 18.39 failure is the one the ruling is named for. 23/125 is exactly
18,4 %; the float form yields 18,39; truncation rounds toward zero so the
error is biased downward and never cancels, on the number filed with the AFC.

Both anti-examples are kept in the test file as documented forbidden shapes,
and a PERMANENT test asserts they still get every case wrong. If that ever
passes, either the fixture has been emptied or floating point has changed.

Three further properties of the set, each asserted:

  - the float form UNDERSTATES in every one of the 72 cases, never overstates;
  - it is wrong by exactly one hundredth every time;
  - the divide-first form is wrong on a different and larger set, so nobody
    concludes the fix is "multiply before dividing".

Reachability, recorded in the file: every disagreement has a denominator that
is a multiple of 125, because n/125 lands on an exact tenth of a percent and
exact tenths are what binary cannot hold. Denominator 125 is reachable on the
simplified basis at employmentRate 52. 250, 375 and 500 are reachable only
through the exact method - which is the path that already carries
EXACT_METHOD_UNVERIFIED.

The other two fixture files still pass: 5 denominator cases including the
three float cases from R10, and 4 mission-cap cases added by R19.

measurement ran with the expected sample count and that nine of the ten inputs
produce a result while the tenth is rejected - so the number above cannot be
stale or fabricated.

QUESTIONS FOR THE OPERATOR
--------------------------

1. SHOULD CI DROP THE UNINSTRUMENTED TEST RUN? It now runs `pnpm test` and
   `pnpm test:coverage` back to back over the same 23 files, and the eight
   10 000-case property suites dominate both. `test:coverage` runs every test
   the plain run does, so the second pass buys only the small chance that v8
   instrumentation itself changes behaviour. Dropping `pnpm test` roughly
   halves the slowest part of CI. I did not do it because `pnpm test` is named
   in the project-wide Definition of Done in tasks/plan.md, and editing that
   is not FW5's.

2. WHO OPENS THE AFC PUBLICATION? The Checkpoint A list has the seven
   constants each with an unchecked box, but the six Geneva cases themselves
   were transcribed from SPEC 7.5 rather than from the AFC. The ENGINE STATUS
   section says so plainly. It is worth being explicit that the fixture TABLE
   needs verifying too, not only the constants - if a published figure was
   mistyped into the spec, every test in this project would agree with the
   mistake and nothing would notice.

3. SHOULD THE PROPERTY SEED ROTATE IN CI? Fixed at 20260907, every run
   explores the same 10 000 cases: reproducible, and blind to anything the
   seed does not reach. The usual arrangement is a random seed in CI with the
   failing seed printed on failure, keeping the fixed seed locally. That
   trades reproducibility for reach, and it means CI can fail on a case that
   passed yesterday - which is either exactly what you want from a property
   suite or a nuisance, depending on how the team reads a red build. My
   inclination is to rotate, but it is a policy choice.

4. THE 29 APRIL 2026 INTERPRETATIVE AGREEMENT is the highest-leverage
   unverified item in the project and I want to name it once more. It is the
   source for the mission sub-cap sitting INSIDE the 40 % rather than beside
   it. If it sits beside instead, every Geneva case, every property and the
   whole waterfall are wrong together, and consistently - which is the worst
   failure mode available, because nothing in the suite would show it. It is
   held second-hand, through an advisory summary.
