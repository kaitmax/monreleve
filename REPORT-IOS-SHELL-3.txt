R1374 - THE RESTORE RACE, MEASURED, THEN FIXED
================================================================================
(1) IN CODE:
    - startDestination is MAIN for a signed-in phone with cached settings, and RESOLVING only without them. GET /me is
      asked by RESOLVING alone.
    - So RESOLVING does NOT run on every signed-in cold launch, only on one with no cached settings. That happens in
      three cases:
      - a process ended between decideStartAfterSignIn's opt-in write and its settings cache (that order is
        deliberate);
      - the same, between onboarding's onReminderSaved and store.save;
      - an account whose settings stay incomplete.
      In each case, a persisted ON can exist.
    BY TEST:
    - r1374aSignedInOnboardedColdLaunchNeverResolves...: MAIN, no GET /me, a persisted ON stands while the server
      says OFF. Passed on base and after.
    - r1374aColdLaunchThroughResolving...: no cached settings, a persisted ON, the server's ON, the centre answering
      300 ms late. RED in run 2: "R1374: a restore that ran before the centre's first answer wrote OFF over the
      server's ON". THE DEFECT IS REAL for that case.
    FIX, iOS-side, with no common edit:
    - IosShell keeps authorizationKnown (set by the first answer, or by any later one).
    - IosShellRoot composes the router only once it is true, bounded at 2 s. Past the bound it starts as before, so a
      silent centre cannot hold the app blank.
    - Meanwhile the canvas is AppRoot's, with no text.
    - The restore stays synchronous (SHELL-2 increment 4), and it now reads an ANSWER. GREEN in runs 3/final,
      including "the switch reads ON".
(2) IN CODE: two iOS paths write the opt-in to the server, and both send the PERSON's choice:
    - Parametres' switch (setEveningNotification, the tap's value);
    - onboarding's save (its RAPPEL answer).
    Parametres' own save carries no reminder key (mePatchBody()). iOS v1 has no push registration.
    BY TEST: r1374bARestoredOffIsNeverSentBackToTheServer.
    - Setup: the server says ON, the phone may not notify, and the phone held ON.
    - The restore writes OFF; that is the case, asserted present.
    - Then the tabs, Parametres and a foreground cycle.
    - Result: no request body carries reminderEnabled, and there is no PATCH /me. It passed on base and after.
    So (2) is NO, and the defect does not reach Android through the account. Android's PushRegistration does write the
    PHONE's opt-in, but only FALSE where that phone turned it on, and Android's restore reads
    areNotificationsEnabled synchronously, so it has no race.

QUESTIONS
================================================================================
Q1. R1374's fix waits at most 2 s for the centre's first answer before starting the router regardless. Past 2 s, the
    pre-fix race could recur on that one launch. Keep 2 s, or should IOS-WALK measure the real first read on the
    simulator and iPhone and set the bound from that?
Q2. iOS stops a year download on EVERY ending, the server-ended one included: the seam runs on all three paths.
    Android stops it only in clearRecord, which a server-ended session does not reach, because the record is kept
    (R521). On Android, a download in flight when the server ends the session still finishes. Its in-transaction
    account re-read writes only while the tag is unchanged, and R521 keeps that tag, so the year can still land under
    the same account. Accept the difference (iOS stricter; nothing crosses accounts on either), or align Android in a
    later Android task?
Q3. The year downloads re-plan the evening reminder after every year that lands, even when the year changed nothing.
    That is cheap, and it is what makes "today recorded elsewhere" drop today's request. Android's fallback reminder
    has no such hook: its 19:00 wake reads the record when it fires. Accept the asymmetry as iOS's (its requests are
    planned a week ahead), or record it for the operator?
