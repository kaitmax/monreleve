THE RED RUN - BEHAVIOURAL, NOT A COMPILE ERROR
--------------------------------------------------------------------------------
The first draft of these tests used the FIXED signature, so they would have
failed to compile. A compile failure is a poor red: it proves the API changed,
not that anything behaves differently. They were rewritten against the EXISTING
signature so the failure is the defect itself.

Three failures, each for its own reason:

  a day recorded after signing in carries the account, not UNOWNED
      expected:<acct-a-tag> but was:<UNOWNED>
      THE DEFECT.

  the row reaching the dao carries it too, not only the returned object
      the stored row must be visible under the account that recorded it
      expected:<1> but was:<0>
      THE USER-FACING SYMPTOM - the row is invisible. Asserting the RETURN
      VALUE alone would have passed on a repository that computed the right
      tag and stored the wrong one (R133).

  signing out mid-session stops tagging new rows with the old account
      expected:<UNOWNED> but was:<acct-a-tag>
      THE MIRROR DEFECT, AND IT WAS NOT IN THE BRIEF. The same capture means a
      day recorded AFTER a sign-out carries the departed person's tag. That is
      mis-attribution rather than loss, which on a shared phone is the worse
      half and is precisely what R303 exists to prevent. It surfaced only
      because R196 requires both directions.

R423 - THE TAG IS READ WHEN THE ROW IS WRITTEN
--------------------------------------------------------------------------------
    private val currentAccount: () -> String? = { null },
    ...
    val resolved = currentAccount()
    val account = resolved ?: UNOWNED_ACCOUNT

A function, not a String. Signing in is exactly the event that changes the
answer, so the same question asked twice in one app session must be allowed to
give two answers.

LocalRhythmRepository took the same change for the same reason: a weekly rhythm
saved in the sign-in session was lost by the same line of code.

THE CORRECT PATTERN WAS ALREADY IN THE FILE, THREE LINES ABOVE THE DEFECT.
MainActivity:189 passes a lambda to SharedPrefsEmployerFigureStore, with a
comment saying "The tag is read live from accountStore, so a re-sign-in under a
different account cannot read the previous one's figure (fail closed when
null)." Line 196 did the opposite, four lines later.

AND THE DEFECTIVE LINE'S OWN COMMENT WAS ITS JUSTIFICATION:
    "A new account signs in through CallbackActivity, which restarts this
     activity, so onCreate re-reads the current tag"
True of the magic LINK, which does restart the activity. FALSE of the CODE
path, which sets the account in place. The comment documented an assumption
that one of the two sign-in paths violates, and it read as reassurance for as
long as nobody tried the other path on a device.

R425 - AN UNOWNED WRITE WHILE SOMEBODY IS SIGNED IN FAILS LOUDLY
--------------------------------------------------------------------------------
    if (resolved == null && isSignedIn()) {
        check(!BuildConfig.DEBUG) { complaint }
        Log.e("EntryRepository", complaint)
    }

isSignedIn is a SECOND, INDEPENDENT read of the account store. In production
both read the same store, agree, and this never fires. IT FIRES PRECISELY WHEN
THEY DISAGREE - which is what a stale capture looks like: a provider frozen at
composition saying nobody is signed in while the store says somebody is. The
canary is shaped like the defect rather than like its symptom.

R303 IS UNTOUCHED when genuinely nobody is signed in: the probe says false too,
there is nothing to disagree about, and the row is tagged UNOWNED silently and
correctly. That case has its own test.

Both halves asserted: the disagreement throws and stores nothing; the genuine
no-session case returns UNOWNED without complaint.

PENDING), created by this chain's own diagnostic. Not re-tagged. Re-tagging an
orphan to whoever signs in next would hand one person's days to another on a
shared phone, which is the case R303 was written for - the cure would be the
disease.

IT IS NOW GONE, AND NOT BY MY HAND, which the count alone would misrepresent.
R427 requires a SIGN-OUT, and sign-out erases local data by design. The
confirmation dialog says so in the product's own words:
    "La deconnexion efface les donnees de cet appareil : vos journees
     enregistrees, le releve en cache, vos reglages de calcul et votre session."
So the orphan count went 1 -> 0 by the product doing exactly what it tells the
reader it will do. Erasure by design, not adoption, and not deletion by this
session.
