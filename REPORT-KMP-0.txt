R371 (java.time -> kotlinx-datetime in moved code only)
--------------------------------------------------------------------------------
PINNED: kotlinx-datetime 0.6.1 (R136 in the version catalog). Compatible with Kotlin
2.0.21 (a regular multiplatform library; its klib metadata is consumable by this
compiler), released 2024-08 (far over two weeks old). 0.6.x (not 0.7.x) on purpose:
through 0.6.x, DayOfWeek/Month are JVM TYPEALIASES to java.time - 0.7.0 made them
multiplatform enums. VALIDATED EMPIRICALLY: it resolves, compileCommonMainKotlinMetadata
and :shared tests are green, and :app passes its java.time.DayOfWeek rhythm keys and
SimChange.ExtraWeekday into the shared kotlinx signatures with NO conversion and compiles
green - which only holds if the typealias holds. api() in :shared so :app sees the
calendar types for the boundary mapping.

PARIS/DST TESTS (commonTest dossier/ParisDayDstTest.kt), written FIRST (6a):
  - parisDayOf resolves the correct Paris calendar day near midnight and across BOTH 2026
    DST changes (spring-forward Sun 29 Mar, fall-back Sun 25 Oct): e.g. 2026-01-15T23:30Z
    -> 2026-01-16 (CET, +1); 2026-07-15T22:30Z -> 2026-07-16 (CEST, +2); 2026-03-28T23:30Z
    -> 2026-03-29; 2026-10-24T22:30Z -> 2026-10-25; 2026-10-25T23:30Z -> 2026-10-26.
  - plus the kotlinx arithmetic semantics the move relies on: daysUntil == ChronoUnit.DAYS
    .between (364 from 1 Jan to 31 Dec 2026), plus(1,DAY) as a pure calendar step across a
    DST date, isoDayNumber 1=Monday (29 Mar -> 7, 30 Mar -> 1).
  RED THEN GREEN (R180 verified plant): with the correct Europe/Paris zone the suite is
  GREEN; switching PARIS_ZONE to UTC fails exactly the five near-midnight cases where the
  Paris day differs from the UTC day ("expected 2026-01-16 but was 2026-01-15"); reverted.
  A DST test that still passes under UTC asserts nothing - that is the point of the plant.
EVERY date conversion in the moved files is exact and DST-invariant (a LocalDate carries no
offset): LocalDate.of -> LocalDate(); plusDays -> plus(n,DAY); isBefore/isAfter -> </>;
dayOfWeek.value -> isoDayNumber; toEpochDay -> toEpochDays; ChronoUnit.DAYS.between ->
daysUntil; toEpochMilli -> toEpochMilliseconds. daysUntilLate keeps its Long return
(kotlinx daysUntil is Int) so a caller's inference cannot silently shift.
