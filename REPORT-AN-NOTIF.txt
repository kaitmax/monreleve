THE ONE REPOSITORY PATH (R206). A recording button fires an IMMUTABLE BROADCAST PendingIntent (distinct
request code per button) to EveningActionReceiver, which records through LocalEntryRepository.record - the
SAME writer AujourdhuiController and the calendar use. So the clientMutationId is born at the tap (AN5), the
account tag is stamped at the tap (R303), clientClaimedAt is the tap (R275), and detectedAt (for a
confirm/correct) is the tap - exactly as for an in-app tap. It syncs like any other entry (requestSync),
later if offline. There is no second way of writing entries.

THE CONFIRMATION AND ITS DELAY. After a tap records the day, the actionable notification is REPLACED (same
id, EVENING_NOTIFICATION_ID = 1001 - so it never stacks) by a one-line confirmation:
  title  "<cote>"   text  "Enregistre pour le <date>"   one button  [Modifier]
"Enregistre", never "envoye": it is the phone's record, as on Aujourd'hui; the sync state stays the app's
business. [Modifier] opens the app on today (an ACTIVITY PendingIntent). The confirmation disappears on its
own after CONFIRMATION_TIMEOUT_MS = 8 seconds (setTimeoutAfter). WHY 8 s: long enough to read the one line
and tap Modifier if the tap was a mistake, short enough that it does not sit as a nag (the product is a
support, not a reminder that persists). A mistake past the window is still fixable in the app - no undo
button is needed beyond Modifier.

WHY "Autre..." AND "Modifier" ARE ACTIVITY PendingIntents. Android 12+ forbids a receiver that a
notification launched from starting an activity, so the two "open the app" actions are ACTIVITY
PendingIntents built directly (openAujourdhui), not routed through the receiver. Only the RECORDING buttons
are broadcasts.

THE CHANNEL. Its own channel "Rappel du soir" (NotificationCopy.CHANNEL_NAME), IMPORTANCE_DEFAULT, so the
person can silence it in Android's settings. lockscreenVisibility = PRIVATE. (The word "rappel" is in
NotificationCopy, which ParametresR282Test does not scan; the Parametres toggle copy is untouched and still
free of "rappel"/"notification".)

WHAT MUST NEVER HAPPEN (each a test)
------------------------------------
Every section-3 case that is a DECISION is a branch in the pure, JVM-testable decideEveningTap (R291,
notification/EveningTap.kt), tested in EveningTapTest (12 cases). The lock-screen protections are asserted
from the code in EveningNotifierLockScreenTest. The at-most-one / non-working-day / reminder-off cases are
in EveningNotificationDecisionTest.

  - A RECORD FROM THE LOCK SCREEN. EveningNotifierLockScreenTest asserts, from EveningNotifier.kt:
      * the PUBLIC (lock-screen) version carries NO actions (the publicVersion function has no addAction) and
        says only the neutral "Mon Releve / Une journee a enregistrer." (D18 - never where someone was);
      * every recording action calls setAuthenticationRequired(true) - on Android 12+/API 31+ the device
        must be UNLOCKED to record (NotificationCompat gates it to 31+; a no-op below, where there is no
        lock-screen action gate). Someone picking up the phone cannot write to the owner's tax record.
    (The `dumpsys notification` confirmation that the posted notification actually renders this way is the
    DEVICE half - PARKAN-47.)
  - A RECORD FOR THE WRONG ACCOUNT (R303). The button carries the account it was shown for; decideEveningTap
    refuses (WRONG_ACCOUNT, nothing written) if a different account - or no account - is signed in when it
    is tapped, and the receiver then dismisses the notification. Tested: different account, and null account.
  - A RECORD FOR A FUTURE DAY, or a day other than the one shown. decideEveningTap refuses (NOT_TODAY) unless
    the shown day equals today. Tested: a notification left overnight (shown day < today), and a future day.
  - A STALE TAP OVERWRITING A NEWER ENTRY. If the day already has an entry, decideEveningTap refuses
    (ALREADY_RECORDED, nothing written) and the receiver shows the existing value. Tested. And recording the
    day by ANY in-app path (Aujourd'hui or the calendar) cancels the notification (incr 5, see below).
  - MORE THAN ONE NOTIFICATION. One id (1001) for the day; a new post REPLACES rather than stacks, and the
    confirmation reuses the same id. "At most one per working day" is EveningNotificationDecisionTest
    (alreadyNotified -> null), enforced by the store's last-notified day.
  - A NOTIFICATION ON A NON-WORKING DAY, or when the reminder is off. EveningNotificationDecisionTest:
    workingDay=false -> null; optedIn=false -> null (off by default).

CANCEL ON RECORD (incr 5). MainShell cancels today's evening notification the moment today becomes recorded,
by ANY in-app path. Both Aujourd'hui and the calendar write through the ONE repository, which the Aujourd'hui
controller observes, so "today became recorded" is a single signal (a LaunchedEffect keyed on it); cancel is
idempotent. A notification BUTTON records through the receiver, which replaces the notification with its
confirmation, so that path needs no separate cancel.
