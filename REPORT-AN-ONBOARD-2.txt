R335 - COMPLETE MEANS WHAT THE RELEVE NEEDS; ASK ONLY WHAT IS MISSING
====================================================================
THE DEFECT (AN-ONBOARD Q1). StartupDecider treated an account as
onboarded when it had a canton, so an older account with settings but no
name landed on Aujourd'hui and its PDF was refused (R205).

ONE DEFINITION, ONE PLACE (R206):
android/.../settings/ReleveCompleteness.kt. COMPLETE = every field the
releve needs. The required fields, in onboarding order, with each
field's presence predicate over a GET /api/v1/me view (MeView):
  - NAME        - a non-blank name
  - CANTON      - a non-blank canton
  - RATE        - employmentRate present
  - METHOD      - denominatorKind present AND (not EXACT, or the exact
                  total present)
  - GRANULARITY - a non-blank granularity
  - PERIOD      - the account exists (a non-blank canton)

WHY PERIOD RIDES ON CANTON (R156 conservative, recorded). The period
answer cannot be told apart from its default: activityStartDate = null
is a valid "whole year" answer AND the server's default, so an existing
account's period is always a resolved answer. The only honest signal the
period was never asked is an account that was never set up - no canton.
So PERIOD is satisfied once the account exists. A brand-new account (no
canton) is sent the FULL eight-step flow regardless.

ASK ONLY WHAT IS MISSING. onboardingPlanFor(view) returns Complete, or
Onboard(prefill) where the prefill carries the ordered MISSING steps and
every known value read from /me (never sent back through the whole flow).
A brand-new account (no canton) runs all eight steps; a partial account
runs only the missing releve-field steps and NEVER the mode/reminder
steps (those are not releve fields and are not missing - a partial
onboarding leaves the server's detection mode and consent UNTOUCHED, by
keeping the prefill's mode MANUAL so mePatchBody omits loggingMode /
detectionConsent). The progress bar counts only the asked steps:
"Etape 1 sur 2", not "1 sur 8". A complete account goes straight to
Aujourd'hui.

THE LOCAL PATH USES THE SAME DEFINITION. SettingsStore.isOnboarded() now
keys on load()?.toMeView()?.isComplete(), so a locally-cached account
missing a name is sent to finish onboarding rather than onto Aujourd'hui
(the Q1 fix on the device path too, not only the server path - R206: the
two cannot drift).

THE WIRING. decideStartAfterSignIn now returns StartDecision
(Main | SignIn | Onboard(prefill)); MainActivity carries the prefill
(rememberSaveable OnboardingSnapshot) into OnboardingRoute, which seeds
the controller through the SAME `restored` seam R310 restore uses - one
mechanism. The App Link callback and the code exchange are unchanged;
/v1 is unchanged (additive reads only).
