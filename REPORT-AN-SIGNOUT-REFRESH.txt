R705 - THE CAUSE, NAMED
================================================================================
THE LIFETIME. web/lib/auth/tokens.ts:41
    export const ACCESS_TTL_MS = 15 * 60 * 1000;
A constant - no environment variable reads it (see R708 / DEVIATIONS).

THE PATH EVERY OTHER CALL TAKES (22b16bb, shared/.../auth/SessionManager.kt):
    194  private suspend fun <T> attempt(request: ...): Attempt<T>
           -> AuthedResult.Unauthorized -> onUnauthorized(code, request)
    207  if (code == EXPIRED_TOKEN || code == ROTATED_TOKEN) retryAfterRefresh(...)
    216  when (val outcome = refresh()) { Refreshed -> retryWith(new pair) ... }
           -> retryWith: a second 401 ends; never a second refresh.
authenticatedGet / authenticatedPost / authenticatedPatch / authenticatedGetBytes
all go through it. The app never refreshes on a clock (accessExpiresAt is stored
and never read for that); it refreshes only when a call meets a 401.

THE PATH SIGN-OUT TOOK (22b16bb):
  MainActivity.kt:321   revokeServer = session::revokeServerSession
  ParametresController.confirmSignOut (line 515): revokeServer(), then in a
                        NonCancellable finally clearForSignOut() + SignedOut.
  SessionManager.kt:333 suspend fun revokeServerSession() {
                            val pair = tokenStore.load() ?: return
                            api.signOut(pair.accessToken)      // NOT attempt
                        }
  (signOut() at :317, the debug probe's, the same: api.signOut(pair.accessToken).)
  AuthApi.kt:409        suspend fun signOut(accessToken: String): Boolean
  AuthApi.kt:422            transport.execute(request).status in HTTP_OK..HTTP_OK_MAX
So a 401 expired_token became `false` - the code discarded, the result ignored by
the caller - and the wipe ran: "sign-out never fails" held for the DEVICE and
silently failed for the SERVER.

WHY IT DEPENDED ON IDLE, AND ON WHAT WAS PENDING. ParametresController.
requestSignOut (line 442) drains pending days first only when there are some
(line 444: `if (pendingDatesNow().isEmpty())` -> straight to the prompt). That
drain is an authenticatedPost, which DOES refresh - so a sign-out after idle
revoked the session by accident when days were waiting, and failed when nothing
was (AN-TALKBACK's case, and this session's control). Any screen that fetched
after the expiry (e.g. opening Releve) also refreshed by accident; a phone left
on Parametres past fifteen minutes did not.

R706 - THE FIX
================================================================================
Commit 61e5be2. Files: android/shared/src/commonMain/kotlin/ch/monreleve/app/auth/
SessionManager.kt, .../data/remote/AuthApi.kt; test edits below (R707).
- AuthApi.signOut(accessToken): AuthedResult<String> - the same three-way shape as
  authenticatedGet/Post/Patch: Ok(status, body), Unauthorized(code) on a 401,
  Failed(Network) on a TransportException. THE REQUEST IS UNCHANGED: POST
  /api/v1/auth/sign-out, one Authorization header, no body. HTTP_OK_MAX (used only
  there) removed.
- SessionManager.revokeServerSession() = attempt(ending = {}) { api.signOut(it) }.
  So: 401 expired_token/rotated_token -> ONE refresh (the same single-flight
  refresh, the same Mutex - a worker refreshing at the same moment cannot make the
  sign-out replay) -> ONE retry with the new access token. A refused refresh, a
  dead session's 401 (revoked_session/unknown_token: not refreshed, as on every
  other call), a refresh the server could not answer, or a retry that meets a 401
  - each stops there. Never more than one refresh and one retry: the structure is
  `attempt`'s, which has no loop.
- signOut() (the debug probe's) = revokeServerSession() then the NonCancellable
  clear, unchanged.
- THE ONE PARAMETER, `ending`: what a session found dead does. Every existing call
  passes nothing and gets end() exactly as before (tokens cleared, onEnded told -
  R520). The sign-out passes an empty one, because a sign-out the person asked for
  is never a session the SERVER ended: firing onEnded there would record a
  SessionEnds signal and run clearForSessionEnd while confirmSignOut's own wipe is
  in flight - the shell could open sign-in on the FORCED path ("session closed by
  the server, N days held") in the middle of the voluntary one. The local wipe that
  follows is the one it always was (clearForSignOut, R295), in every case.
- R210 is not weakened: a refresh with a replayed token is still refused by the
  server, which revokes the whole session TOKEN_REPLAYED (tested below). The
  client side of a replay on the sign-out path is the wipe, which is already the
  strongest local answer.
- Not touched: the controller, the wipe, any copy, any web file, the schema, /v1.
  No new user-facing state, so no French was needed.
STOP CONDITION CHECKED: the client HAD a reusable 401 path (`attempt`), and no new
API shape was needed (no sign-out by refresh token) - so no STOP.
