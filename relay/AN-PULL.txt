====================================================================
WHY
====================================================================
There is no server-to-phone pull. Someone who reinstalls, changes
phone, or signs out and back in sees the Releve - fetched from the
server, so correct - but an EMPTY calendar and an empty Aujourd'hui.
KMP-4 saw it on the S9: eleven rows on the server, none on the phone.
They would reasonably believe their record was lost. And docs/api-v1.md
6.4 already tells clients to read the year back after a queue drain,
because the server orders writes by receipt.

====================================================================
THE RULINGS
====================================================================
R481. ON SIGN-IN, THE APP DOWNLOADS THE ACCOUNT'S YEARS. The current and
    the previous tax year, from GET /api/v1/entries?year=, into the
    local store, tagged with the signed-in account, with the server's
    values EXACTLY as returned - provenance, detectedKind, detectedAt,
    clientClaimedAt, firstRecordedAt, lastModifiedAt, clientMutationId,
    serverId. A downloaded row is SYNCED. It is not a new record:
    nothing is queued, nothing is sent back, no mutation id is minted,
    no event reaches the server's trail.

R482. THE LOGIC LIVES IN :shared. The download and the reconciliation
    sit beside the sync engine in commonMain, using the API client, the
    DAO and the account provider already there; KMP-3's "reconcile from
    the server's row" is reused, not re-written. :app only TRIGGERS it
    (after sign-in; on start, R485). Tests in commonTest with KMP-1's
    fake HttpTransport and the in-memory DAO, so iOS inherits them.

R483. RECONCILIATION RULES, keyed on (dayDate, portion) as 6.2 says -
    never on id:
      - local PENDING (or any not-yet-sent state) -> KEPT, untouched:
        it is the person's newer choice and will sync;
      - local SYNCED and the server's row differs -> the SERVER's row
        replaces it (the server is the record; 6.4: the last write sent
        is not necessarily the one kept);
      - local SYNCED and identical -> no write at all (AN-CALENDAR's
        rule: nothing changed, nothing written);
      - server row, no local row -> inserted, SYNCED;
      - local SYNCED for this account and year, ABSENT from the server
        -> NOT deleted. Entries have no DELETE, so this is an anomaly:
        keep the row, record it (a counted log line and a PARK in the
        report), and do not show it as a problem to the person;
      - rows tagged UNOWNED or another account -> never read, changed or
        shown (R303).
    FULL rows beside AM/PM for the same day (a granularity change; 6.2
    allows it) are stored as the server holds them; how they display is
    AN-CALENDAR's rule, not changed here.

R484. A YEAR ARRIVES WHOLE OR NOT AT ALL. 6.2: a year that cannot be
    served whole is read_failed, never partial. The local apply for one
    year is ONE Room transaction: a failure part-way leaves the store as
    it was. A failed download changes nothing and says so in words on
    the screen that is waiting for it, with a retry; propose that copy
    (fr/, quoted verbatim). A 401 goes through KMP-3's refresh like any
    call; Unauthenticated ends quietly as sign-out would.

R485. ON START, ONLY WHEN NEEDED. On app start, a signed-in account whose
    current (or previous) tax year has NO local rows while the server
    may have some gets that year downloaded - a cheap local check, not
    a full download every launch. Say exactly what the check is and
    what it costs. Also after a queue drain that sent at least one row,
    read that year back (6.4) - or, if that is too much for this task,
    PARK it with the reason; do not half-do it.

R486. THE DOWNLOAD MAKES NO WRITES THE PERSON DID NOT MAKE. Tests: the
    mutation queue is empty after a download (assert it, R340's shape);
    the fake transport received only GETs; the account tag on every
    inserted row is the signed-in account; the server's firstRecordedAt
    is preserved byte for byte.

R487. TESTS FIRST, RED ON main: a fresh store receives both years; a
    pending day survives the download; a SYNCED row the server changed
    is updated; an identical row is not rewritten; a server-absent
    SYNCED row is kept and counted; another account's and UNOWNED rows
    are untouched; a failure mid-year leaves the store unchanged; the
    queue is empty afterwards; the start check downloads only when the
    year is empty locally.

R488. THE SAME NUMBER EVERYWHERE. After a download, Aujourd'hui's rate
    equals the Releve's (R281) for the same account - a test where it
