CONTEXT
====================================================================
AN-AUDIT: an adversarial audit of the Android app at Checkpoint F,
before anything is released. It builds nothing new.

THE QUESTION FW30 TEACHES US TO ASK FIRST. Every walkthrough in the
Android series drove the DEBUG build - it had to, because the session
injection that gets past sign-in is debug-only, and the debug build is
the one allowed to reach the emulator's host over plain HTTP. So:

  THE RELEASE VARIANT HAS VERY LIKELY NEVER BEEN RUN.

The release build is minified by R8, which renames and strips classes,
and is the classic place a Kotlin app works in debug and breaks on
release: a serialised class whose fields R8 renamed, a reflective
lookup R8 removed, a Room entity or a Compose class shrunk away.
Nothing has exercised it. That is FW30's F-WRITE shape exactly: the
configuration that ships is the one nothing tests.

And it cannot simply be walked the usual way: it has no injection, it
refuses cleartext, and monreleve.ch does not resolve - so a release
build currently has no server it can reach at all. Part of this
audit's job is to say what WOULD exercise it.

Read: SPEC 11, 13, 20; docs/android-skills.md (the r8-analyzer and
play notes); the app's build.gradle.kts release configuration and its
proguard or R8 rules.

====================================================================
ACCEPTANCE CRITERIA
====================================================================
AC1. THE RELEASE CONFIGURATION IS EXERCISED. A build carrying the
     RELEASE variant's R8 and shrinking configuration is installed on
     the emulator and driven - at minimum launched, through onboarding
     to a screen that decodes a server response - and whatever it
     reveals is recorded. If that needs a variant that keeps release's
     minification but debug's network access, build that variant and
     say exactly how it differs from release.
AC2. WHAT THE APK DECLARES MATCHES WHAT THE APP DOES. Every permission,
     every exported component, every host contacted and every library
     bundled is enumerated FROM THE BUILT RELEASE APK - not from source
     - and each is either justified by a feature this build has or is a
     finding.
AC3. Every finding carries a severity, the evidence of what was run
     and what it returned, and what it would take to close. A section
     named UNEXAMINED says what was not looked at and why.

====================================================================
INCREMENT 3 - WHAT THE APK DECLARES (AC2)
====================================================================
From the BUILT release APK - aapt2, apkanalyzer, or the merged
manifest - never from source:
  - PERMISSIONS. Every one, and the feature that needs it. IN
    PARTICULAR: does this manual-only build declare any location
    permission? Detection code and the border polygon ship in the APK
    (R280). If ACCESS_FINE_LOCATION or ACCESS_BACKGROUND_LOCATION is
    in the release manifest, the app asks for something it never uses
    - a finding for Play review, for the data safety form, and for
    R282, since asking for a permission is claiming a feature.
  - EXPORTED COMPONENTS. Every activity, service, receiver and
    provider, whether exported, and what an outside app can make it
    do. The App Link activity is the one that must be; anything else
    exported is a finding. Confirm the debug injection receiver is
    absent (checkReleaseNoDebugInjection is a source check; this is the
    built-APK check).
  - HOSTS. Every host the release build could contact, from its
    network configuration and its constants. 10.0.2.2 in a release
    build is a finding.
  - LIBRARIES AND SDKS. Every bundled library. Any analytics, crash
    reporting or advertising SDK is a finding against the privacy
    notice.
  - SECRETS. Scan the decompiled release APK for anything
    secret-shaped. Nothing in an APK is private.
- Commit: "AN-AUDIT: what the APK declares". Push.

====================================================================
INCREMENT 4 - SECURITY AND PRIVACY, PROBED
====================================================================
- TOKENS. From a second app installed on the emulator (a probe APK,
  committed as test tooling): can it read the tokens, the Room
  database, the cached releve or an exported file? Try each. Confirm
  backup exclusion by running adb backup or the device-to-device
  transfer path, and confirm FLAG_SECURE on token screens by capturing
  the recents thumbnail.
- INTENTS. Fire malformed, oversized and foreign-host intents at every
  exported component, and the App Link with every hostile shape the
  android-intent-security skill names. Nothing may write a day, sign
  in, or crash.
- PENDING INTENTS. Every one carries an explicit mutability flag.
- D18, from the running app. Capture every network request the app
  makes during a full walkthrough and assert none carries a coordinate
  or a coordinate-shaped field. The source fence and the DDL scan
  prove it cannot be written; this proves it is not sent.
- LOGS. Capture logcat during a full walkthrough and scan it for
  tokens, email addresses and entry payloads.
- Commit: "AN-AUDIT: security and privacy, probed". Push.

====================================================================
INCREMENT 5 - INTEGRITY, RESILIENCE, PERFORMANCE
====================================================================
- ONE ACCOUNT'S QUEUE NEVER DRAINS INTO ANOTHER'S. Record days offline
  as account A; let the refresh token expire or be revoked
  server-side; sign in as account B. Nothing of A's may reach B's
  record. This is the case R295 does not cover, because an expired
  session is not a sign-out.
- THE DEVICE CLOCK. Set the device clock days ahead, then behind, and
  record. clientClaimedAt is sent verbatim and lateness is the
  server's (R216) - but R286's pending warning and the on-device rate
  use the device clock. What does a wrong clock do to each?
- STORAGE FULL, PROCESS DEATH mid-write, and a server returning 500s
  and malformed JSON: what does the person see, and is anything lost?
- PERFORMANCE at increment 1's volume: cold start of the app (not the
  emulator), the calendar scrolling ten years, the on-device engine
  over a full year, and memory. Measured, with R233's
  did-it-observe-its-subject line.
- Commit: "AN-AUDIT: integrity, resilience, performance". Push.
