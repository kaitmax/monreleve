====================================================================
INCREMENT 2 - the mutation queue
====================================================================
- Every mutation gets a clientMutationId (a UUID) at the moment the
  person taps, persisted with the mutation BEFORE any network call.
  An id generated at send time is regenerated on retry, which turns
  a safe replay into a duplicate write.
- The queue persists across process death. Pending is a durable
  state, surfaced in the UI as a persistent "en attente de
  synchronisation", never a toast (DESIGN-SYSTEM section 2).
- clientClaimedAt is the device's clock at the tap, sent verbatim.
  The client never computes lateness - the server's observation is
  the only one that counts.
- Commit: "AN5: a durable mutation queue". Push.

====================================================================
INCREMENT 3 - sync
====================================================================
- WorkManager, network-constrained, with backoff. One worker at a
  time: two concurrent drains of the same queue would send the same
  mutation twice, and while R219 makes that harmless on the server
  it doubles the traffic and hides the bug.
- Batch per the server's limit (R0.2 - the named constant, not a
  guess). R217: the response carries the written rows, so pending
  clears in ONE round trip, from the server's rows, not from what the
  client sent.
- Every server refusal maps to its own state (R198). A 400 for a
  payload the client built is a CLIENT DEFECT and must be loud, not
  retried forever - retrying a rejected payload is the queue
  equivalent of a test that can never pass.
- Commit: "AN5: sync, one worker, one round trip". Push.
