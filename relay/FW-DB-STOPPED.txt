R945. THE SCENARIO IS THE REAL ONE. The database goes away AFTER the
    container has started and served. A database that was never there
    tests the entrypoint's refusal instead, which test:container already
    covers (scripts/container-check.mjs). So:
    - the run starts its OWN throwaway Postgres container, uniquely named
      and on a free port;
    - it migrates that database, starts the image against it, and proves
      a page served;
    - it STOPS ITS OWN database container;
    - then it measures.
    Never stop frontalier-postgres or any other container: other
    worktrees' scratch databases live there.

R946. WHAT "KEEPS SERVING" MEANS, ASSERTED. With the database stopped:
    - every public route in the sitemap answers 200 with its own content
      (a known heading, not merely a 200; R169's shape);
    - /api/health is 200 (liveness, R375);
    - /api/ready is NOT ready and names the database (the deploy gate
      would refuse);
    - one database-backed route (e.g. /api/v1/...) answers its documented
      error status with no stack trace and no connection string in the
      body;
    - after the database is started again, readiness recovers without a
      container restart.
    Whatever the product actually does differently from this list is a
    FINDING to hand back, not an assertion to adjust.

R947. WHERE IT RUNS (R251). Establish whether an existing container
    script owns this claim (container-e2e.mjs? container-write.mjs?) and
    extend it, or add one script registered with the gate selector, with
    a test that the selector picks it. test:container is deliberately
    narrow (R251), so do not put a database there. The run cleans up its
    own containers in a finally, including on failure. Give proof of the
    cleanup: docker ps -a after a run that you made fail on purpose.

R948. A VERIFIED PLANT (R180). Make one public route read the database

R949. NOTHING ELSE MOVES. No route, readiness or entrypoint change. A
