CONTEXT
====================================================================
FW26 ONLY: the account routes - settings, data export, and deletion.

THIS IS WHERE THE PRIVACY NOTICE BECOMES CODE. /confidentialite has
claimed since FW10 that a person can export their data and delete
their account. FW14 made the alert-list half true. This task makes
the account half true, or corrects the page (R138's tense rule).

AND IT HAS A REAL TECHNICAL TENSION, which is the interesting part:
FW21 made EntryEvent APPEND-ONLY with database triggers rejecting
UPDATE and DELETE. Account deletion must remove those rows. R203
already draws the line - the trail outlives the ROW, not the ACCOUNT
- but the trigger does not know that. How erasure passes a guard
built to refuse it is this task's central design decision, and it must
be a NARROW, NAMED path rather than a disabled trigger.

Read: SPEC 8 (the model and its rules), SPEC 11.5 (Parametres), SPEC
20; /confidentialite as shipped; docs/api-v1.md; REPORT-FW21.txt for
the trigger design; REPORT-FW25.txt.

====================================================================
ACCEPTANCE CRITERIA
====================================================================
AC1. GET /api/v1/account/export returns EVERY row belonging to the
     caller - entries, events, devices, sessions, settings - asserted
     against direct row counts per table, not against a sample. A
     table added later and not exported is a silent gap, so the test
     enumerates the schema's user-owned tables and fails on one it
     does not cover.
AC2. POST /api/v1/account/delete removes every row belonging to the
     caller across every table, and the proof is a NEGATIVE SWEEP:
     after deletion, no row anywhere references that user id. Not
     "the delete returned ok" - a query per table, asserted empty.
     Tokens are revoked in the same transaction; a previously valid
     access token is rejected afterwards.
AC3. The append-only guard still refuses an ordinary DELETE on
     EntryEvent after this task. Proven by attempting one outside the
     erasure path and capturing the refusal by name (R198).

INCREMENT 3 - the erasure path through the append-only guard
====================================================================
THE CENTRAL DESIGN DECISION. Choose and justify:
  - a trigger condition that recognises an erasure - a transaction-
    local setting, a dedicated role, a marker row - so the guard
    refuses every ordinary DELETE and permits exactly this one; or
  - deletion performed by a path the trigger cannot see, with its own
    narrow authorisation.
State what you chose, what it refuses, and how an attacker or a bug
would have to look to use it. A disabled trigger is not an option.

- AC3: an ordinary DELETE on EntryEvent still refused, by name.
- The deletion is ONE TRANSACTION. A partial erasure that succeeds
  halfway is worse than a refusal: the person believes they are gone.
- Tokens revoked in the same transaction (R193).
- RED first: the delete fails before the path exists, with the
  trigger's own message.
- Commit: "FW26: account deletion through a named erasure path".
  Push.

INCREMENT 4 - the negative sweep, and what is NOT deleted
====================================================================
- AC2's sweep: a query per table asserting no row references the user
