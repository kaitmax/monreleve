CONTEXT
====================================================================
FW26 ONLY: the dossier endpoint, then the account routes - settings,
data export, and deletion.

THIS IS WHERE THE PRIVACY NOTICE BECOMES CODE. /confidentialite has
claimed since FW10 that a person can export their data and delete
their account. FW14 made the alert-list half true. This task makes
the account half true, or corrects the page (R138's tense rule).

AND IT CARRIES A REAL TECHNICAL TENSION, which is the interesting
part rather than an obstacle: FW21 made EntryEvent APPEND-ONLY with
database triggers refusing UPDATE and DELETE. Account erasure must
remove those rows. R203 draws the line - the trail outlives the ROW,
not the ACCOUNT - but the trigger does not know that. How erasure
passes a guard built to refuse it is this task's central design
decision, and it must be a NARROW, NAMED path. A disabled trigger is
not an option.

Read: SPEC 8 (the model and its rules), SPEC 11.5, SPEC 12 (the
payload the endpoint returns), SPEC 20; /confidentialite as shipped;
docs/api-v1.md; REPORT-FW21.txt for the trigger design;
REPORT-FW25b.txt.

ACCEPTANCE CRITERIA
====================================================================
AC1. GET /api/v1/dossier?year= returns the payload lib/dossier
     computes, bearer-authenticated, tenancy from the token only
     (both plants, both verified, at the HTTP boundary). A provisional
     year is marked with the period covered; an empty year is honest
     rather than zeroed; a future year is refused BY NAME (R198).
     R226's fallback sentence is already in the contract - assert the
     warning actually travels in the payload.
AC2. GET /api/v1/account/export returns EVERY row belonging to the
     caller, asserted against direct row counts per table. The test
     ENUMERATES the schema's user-owned tables and fails on one it
     does not cover, so a table added later is a failing test rather
     than a silent gap (R175).
AC3. POST /api/v1/account/delete removes every row belonging to the
     caller, proven by a NEGATIVE SWEEP written from the schema - a
     query per table, asserted empty - not by the delete returning
     ok. Tokens are revoked in the same transaction and a previously
     valid access token is rejected afterwards. The append-only guard
     still refuses an ordinary DELETE on EntryEvent, proven by
     attempting one outside the erasure path and capturing the
     refusal by name.

INCREMENT 4 - the erasure path through the append-only guard
====================================================================
THE CENTRAL DESIGN DECISION. Choose and justify:
  - a trigger condition that recognises an erasure - a transaction-
    local setting, a dedicated role, a marker row - so the guard
    refuses every ordinary DELETE and permits exactly this one; or
  - deletion performed by a path the trigger cannot see, with its own
    narrow authorisation.
State what you chose, what it refuses, and HOW AN ATTACKER OR A BUG
WOULD HAVE TO LOOK to use it. A disabled trigger is not an option.

- The deletion is ONE TRANSACTION. A partial erasure that succeeds
  halfway is worse than a refusal: the person believes they are gone.
- Tokens revoked in the same transaction (R193).
- RED first: the delete fails before the path exists, with the
  trigger's own message.
- Commit: "FW26: account deletion through a named erasure path".
  Push.

INCREMENT 5 - the negative sweep, and what survives
====================================================================
- AC3's sweep, written from the schema like AC2's enumeration so it
