CONTEXT
====================================================================
AN2 ONLY: the calc-engine port and its shared conformance suite. It
does NOT touch UI, does not touch detection, does not touch anything
under android/.../ui, .../data, .../detection. It ships no product
screen - AN3 is what renders anything this task computes.

WHY THIS IS ITS OWN TASK. AN1 scaffolded calc/ as an empty, fenced
package - fence 1 (FencesTest.kt) already asserts it imports nothing
from android.*/androidx.*/other project packages, and that fence
holds against EnginePlaceholder.kt today. AN3 (core components),
AN4 (auth/onboarding) and AN5 (Room/repository/sync, "local engine
output matches the server dossier" as its own acceptance criterion)
all sit downstream and cannot be built against a placeholder that
returns `true`. The engine is the one piece of this product where
being subtly wrong is not a bug that ships and gets patched - it is a
number filed with a tax authority.

TWO ENGINES, ONE SOURCE OF TRUTH, FOREVER. fixtures/geneva-cases.json,
fixtures/denominator-cases.json and fixtures/rate-cases.json are
consumed by BOTH the TypeScript engine and this Kotlin port, from now
on. Nothing in Kotlin re-types a fixture's expected value as a
literal - JSON is read at test time, same as
web/tests/unit/calc-engine/fixtures.test.ts already does. A future
session that "simplifies" this by hand-copying six numbers into
Kotlin source is undoing the entire point of the file.

THE ARITHMETIC IS THE HARD PART, NOT THE STRUCTURE. Two rounding
rules that must never merge (SPEC 7.3): declarableRateFor truncates,
computed on the integer numerator/denominator BEFORE any percentage is
formed (web/lib/calc-engine/declarable-rate.ts's own comment: forming
the percentage first and truncating after gives 18.39 instead of
18.4, wrong in 36 of 125 750 pairs up to denominator 500).
floorToHalfDay floors, and floors a possibly-negative value without
clamping. Kotlin's Double has the identical IEEE 754 representation
as JavaScript's Number for this purpose - the same binary fractions
fail to represent exactly, so the same integer-arithmetic techniques
apply verbatim, not merely "similarly".
