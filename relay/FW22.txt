    ORTHOGONAL, and the contract says so in those words:
      detectedKind - what detection PROPOSED for that day, if
        anything.
      provenance   - how the STORED value came to be.
    A MANUAL row MAY carry a detectedKind: auto mode proposed, the
    proposal expired unconfirmed, and the user backfilled the day in
    the calendar later. No proposal was accepted or corrected, so the
    provenance is MANUAL - and the annex is more honest for recording
    that detection had proposed something. The FORWARD constraint
    stays: a DETECTED_CONFIRMED or DETECTED_CORRECTED row without a
    detectedKind is incoherent and is refused. The reverse is legal.
    Do not add the reverse constraint.

     a revoked refresh token is rejected.

     and NOTHING else - no cookie, no body field, no query parameter
     carries identity.

INCREMENT 3 - token issuance and rotation
====================================================================
- A short-lived access token (state its lifetime and the reasoning)
  and an OPAQUE refresh token stored HASHED, one row per device
  session, rotated on use.
- Tokens are opaque and revocable by row: a compliance product must be
  able to end a session the moment an account is deleted, and FW26's
  deletion path depends on it. No self-contained token carrying claims
  that cannot be withdrawn.
- A REUSED refresh token invalidates the whole chain and is recorded
  as a security event - state the policy chosen and why.
- Revoking one device leaves another's session alive - assert it.
- Commit: "FW22: opaque revocable token pair with rotation". Push.
