====================================================================
ACCEPTANCE CRITERIA
====================================================================
AC1. POST /api/v1/entries accepts a BATCH and assigns recordedAt and
     firstRecordedAt from the SERVER CLOCK. A payload attempting to
     set either is rejected or ignored - proven, with the server value
     winning. clientClaimedAt is stored verbatim when supplied.
AC2. A payload containing latitude, longitude, accuracy, altitude,
     speed, heading or a provider name is REJECTED with 400. The test
     is NAMED so it cannot be deleted quietly, and it covers nested
     objects, arrays, and unknown keys whose names contain those
     words.
AC3. Every write appends an EntryEvent; editing preserves
     firstRecordedAt and detectedKind; a replayed batch carrying a
     seen clientMutationId writes no row and no event and is
     ACKNOWLEDGED, not errored.

====================================================================
INCREMENT 1 - the payload contract
====================================================================
- Zod schema for the batch item: clientMutationId, dayDate (ISO day
  string, R28 - never a Date), portion, kind, absenceReason (required
  iff ABSENT), note, provenance, detectedKind, detectedAt,
  clientClaimedAt.
- UNKNOWN KEYS ARE REJECTED, not stripped. A client sending a field we
  do not know is a client we disagree with, and silently dropping it
  means the app believes something was stored that was not.
- R202: a MANUAL row MAY carry a detectedKind. The forward constraint
  stays - DETECTED_* without detectedKind is refused. Assert both
  directions so a later reader cannot mistake the asymmetry for an
  oversight.
- Batch limits: a maximum item count and a maximum body size, both
  named constants, both tested at the boundary. An unbounded batch is
  a denial-of-service surface on a route that writes.
- RED first per behaviour.
- Commit: "FW23: the entries payload contract". Push.

INCREMENT 3 - the write path
====================================================================
- Upsert on (userId, dayDate, portion); latest server receipt wins for
  kind; an EntryEvent appended per write; clientMutationId
  deduplication; tenancy from the bearer token ONLY (FW22's
  middleware - plant a body userId and a query userId, verify both
  plants landed, assert both ignored).
- Day boundaries in Europe/Paris, with unit tests at BOTH DST
  transitions. A UTC day-boundary bug here is a wrong record, and it
  is the class of defect that only appears twice a year.
- R198: every rejection names which rule fired, with a stable code the
  app can branch on. The trigger work in FW21 moved to P0001 for
  exactly this reason; do not undo it at the API layer by collapsing
  distinct failures into one 400.
