OPT-IN LOOP
--------------------------------------------------------------------
The full sequence, against a real PostgreSQL and the fake outbox.

  subscribe        POST /api/alertes, form-encoded, no JavaScript
                   required. Row created, confirmedAt null.
  email            one message in the outbox, to that address, with
                   the confirm link and a one-click unsubscribe link.
  confirm link     GET /api/alertes/confirm?token=... sets
                   confirmedAt, NULLs the token hash and its expiry,
                   issues an unsubscribe token, redirects 303 to
                   /alertes/confirmation/confirmee.
  reuse            the same link again -> "unknown". The row is
                   untouched.
  expiry           a token past seven days -> "expired", the token is
                   cleared, confirmedAt stays null.
  unsubscribe      GET /api/alertes/desinscription?token=... sets
                   unsubscribedAt, redirects to
                   /alertes/desinscription/ok. Twice -> the same
                   answer, because a mail client that prefetches has
                   already clicked once.
  re-subscribe     a fresh double opt-in: unsubscribedAt and
                   confirmedAt cleared, a NEW token issued, and the
                   address is NOT on the list until it is confirmed
                   again. The old confirmation token stays dead.

TOKEN SHAPE, the decision the prompt left open:
  HASHED       SHA-256 of 32 random bytes; the plaintext exists only
               in the link. A database copy contains no working
               links.
  SINGLE-USE   confirming clears the hash in the same write, and the
               update is conditioned on the hash it read - so two
               simultaneous clicks confirm once.
  EXPIRING     seven days. A confirmation link is a capability to add
               an address to a mailing list, and one sitting in an
               inbox forever never lapses. Short of the thirty-day
               purge, so days 8-30 hold a row that can no longer be
               confirmed - correct: the reader subscribes again.

A SECOND TOKEN FOR UNSUBSCRIBING, because the lifetimes are opposite.
Confirmation is single-use and cleared the moment it works; an
unsubscribe link has to keep working for as long as the reader might
still hold one of our messages. Minted per send, never cleared on use.

ENUMERATION
--------------------------------------------------------------------
Four states - absent, unconfirmed, confirmed, previously unsubscribed
- take four different amounts of work and produce ONE answer.

If a confirmed address answered differently from a new one, anybody
could type an address into a public form and learn whether that person
is on a list about cross-border tax compliance, which says something
about where they work. Membership is the sensitive fact.

ASSERTED AS A SET, not as a table: the four Location headers are
collected and the test requires ONE distinct value. Four "contains ok"
assertions would pass on four different query strings.

The distinction is kept exactly as long as the mailer needs it -
recordSubscription returns the outcome so increment 3 knows whether
to send - and thrown away before the response.

CONSEQUENCES ACCEPTED DELIBERATELY: a second subscribe on a confirmed
address does NOT move confirmedAt and does not rewrite `source`. That
date records when the READER agreed; moving it because a stranger
typed their address would make the record say something untrue.

NOT CLOSED: TIMING. A confirmed address does less work than a new one
- no token, no insert, no send - so an attacker with a stopwatch and
many samples could still distinguish them. Constant-time work on a
public endpoint is a real cost against a much weaker attack, and the
rate limit is what prices the sampling at five per ten minutes per
client. Question Q38.

QUESTIONS FOR THE OPERATOR
--------------------------------------------------------------------
Q37. WHAT CLOSES THE CLASS R132 CANNOT? Two commits went red in CI
     this task, both because my machine has something CI does not - a
     generated client, a .env. Every selected suite passed both times.
     Options as I see them: (a) leave it to CI, which is what caught
     both, at the cost of red on main for the minutes between push and
     result; (b) a `pnpm gate:clean` that builds in a scrubbed
     environment - no .env, node_modules restored from the lockfile -
     which is minutes per increment and would have caught both; (c) a
     narrower rule: any increment that adds a dependency or reads a
     new environment variable runs that clean build once. I would take
     (c). It is a cost decision about the session's shape.

Q38. IS THE ENUMERATION TIMING GAP WORTH CLOSING? The response is
     byte-identical across all four states; the WORK is not - a
     confirmed address skips a token, an insert and a send. Constant-
     time would mean doing that work anyway, on a public endpoint, to
     defeat an attacker who already needs many samples through a
     five-per-ten-minutes limit. I have left it and said so.

Q39. DO lib/params/**, lib/alerts/** AND lib/content/** BELONG IN
     R132's SELECTOR? Measured above: a change to lib/params/codec.ts
     alone changes the calculator's notice and selects no browser
     suite. You amended R132 once on a measurement, so I have not
     extended it on my own.

Q40. THE ANALYTICS CLAIM ON /confidentialite IS PUBLISHED AND
     UNENFORCED. "La mesure d'audience est auto-hebergee, sans cookie
     et sans identifiant publicitaire" - FW15's to make true. It is
     the same shape as the sentence FW14 corrected, and it is live
     today on a page about privacy. Options: leave it to FW15;
     correct it now to the future tense; or remove it until the code
     exists. AC3's rule - a published claim that is not true of the
     code - arguably already applies to it.

Q41. RFC 8058 ONE-CLICK UNSUBSCRIBE. The unsubscribe endpoint is a
     GET, so a mail client that prefetches links can unsubscribe
     somebody who never clicked. Acceptable only because the action is
     idempotent and reversible. The proper fix is the
     List-Unsubscribe-Post header and a POST endpoint, which belongs
     with the alert SENDS - and FW14 does not build those. Naming the
     task that owns it would stop it being nobody's.
