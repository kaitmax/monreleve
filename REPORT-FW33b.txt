R301 - THE SUITE IDENTIFIES THE INSTANCE, NOT JUST THE PRODUCT
====================================================================
THE DEFECT. R169 makes /api/health NAME this product, which is what
made reusing a port safe. It cannot tell a SIBLING instance of the
SAME product - another session's container on the same port, built
from a different checkout with a different AUTH_SECRET - from the one
under test. FW33 hit exactly that: a sibling passed R169, then every
live PDF test 503'd because the print token this process minted was
signed with a key the sibling did not hold. R169 saw the right
product and the wrong instance.

THE FIX. A harness that starts a server for a live suite sets a
per-run value; the server echoes it from /api/health; the suite
refuses any server that does not echo it.
  - lib/content/identity.ts: INSTANCE_ID_ENV ('FRONTALIER_INSTANCE_ID')
    and instanceRefusal(expected, found) - a pure matcher. OPT-IN by
    construction: no expectation set => no check, so an ordinary
    `pnpm test:e2e` reusing its own warm server is untouched (R170).
  - app/api/health/route.ts: echoes `instance` from the env (null when
    unset). R169's `service` still first in the payload.
  - e2e/global-setup.ts: after the service check, refuses by name
    (R301) when an instance is expected and not echoed.
  - scripts/container-e2e.mjs: mints a random instance per run, starts
    the container with it (-e FRONTALIER_INSTANCE_ID=...) AND hands the
    SAME value to the vitest process.
  - tests/db/container-auth.test.ts, container-pdf.test.ts: refuse by
    name in beforeAll when the container does not echo the value.

PROOF (POSITIVE). gate:changed selected test:container:e2e (I changed
the harness, R247). It built the image, started a real container with a
per-run FRONTALIER_INSTANCE_ID, and ran the live suites against it:
e2e 278 passed, and the auth+pdf round trip 9 passed - container-auth.
test.ts and container-pdf.test.ts each refused unless the container
echoed the value, and both passed, so the PDF print-token round trip
that FW33 saw 503 on now runs against the right instance. exit 0.

PROOF (NEGATIVE, the relay's). A second instance was started WITHOUT
the value (next start on :3200, no FRONTALIER_INSTANCE_ID). Its
/api/health answered {"service":"monreleve","instance":null,...} - it
PASSES R169 (same product). The e2e suite was then pointed at it with
an expectation set (FRONTALIER_PORT=3200 FRONTALIER_INSTANCE_ID=
proof-run-7f3a9c), and global-setup refused BY NAME before any spec:

    R301: the e2e suite refused to run.
      expected  monreleve at http://localhost:3200
      found     expected the instance this run started (proof-run-7f3a9c),
                but the server answered (no instance marker)

The sibling was then killed and :3200 verified free (R179).

AUTH_SECRET (which was true)
====================================================================
AUTH_SECRET WAS REINTRODUCED AFTER R209, so the SPEC line is stale and
FW33's report used the RIGHT name.

- R209 (FW23, commit 203f35f) withdrew Auth.js and SPEC section 18
  recorded AUTH_SECRET and AUTH_URL as "removed ... read by nothing".
- FW25 (commit 4ca198f, AFTER R209) wrote lib/export/print-token.ts,
  which signs the short-lived PDF print token with
  createHmac('sha256', process.env.AUTH_SECRET). So AUTH_SECRET HAS a
  reader again. Confirmed by env-contract.test.ts (R250) asserting a
  deployment must supply AUTH_SECRET "signs the print token", by
  .env.example carrying it, and by container-e2e.mjs handing it to the
  image for the live PDF round-trip.
- The print-token secret's name IS AUTH_SECRET (not a different name),
  so FW33's NOTICED was correct to call it that.

CORRECTED THE SPEC (R9), and said so in the SPEC itself:
  - SPEC section 18, the "removed (R209)" bullet: now records AUTH_URL
    still removed (origin is a constant) and AUTH_SECRET reintroduced
    by FW25 as the print-token key, a required deployment variable.
  - SPEC section 18, the "Env additions for v2" line: named
    PDF_TOKEN_SECRET for this key, but the implementation reused
    AUTH_SECRET and nothing reads PDF_TOKEN_SECRET; corrected to name
    AUTH_SECRET (which is itself the "variable read by nothing" defect
    the original bullet warned about, one phantom over).
