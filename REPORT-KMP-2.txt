R395 - WHICH migrate() DOES ROOM 2.7.2 CALL? THE QUESTION THAT DECIDES THE DESIGN
================================================================================
ANSWER: the CONNECTION form, migrate(connection: SQLiteConnection).
CONSEQUENCE: ONE body, written against SQLiteConnection, serves Android and iOS.
             NOT a stop. Nothing needs two copies of the SQL.

EVIDENCE 1 - DOCUMENTARY. Room 2.7.2's Migration.android.kt, read from the Gradle
cache sources jar - the exact artefact this build resolves:

    open fun migrate(db: SupportSQLiteDatabase) { throw NotImplementedError(...) }

    actual open fun migrate(connection: SQLiteConnection) {
        if (connection is SupportSQLiteConnection) {
            // Compatibility mode
            migrate(connection.db)
        } else { throw NotImplementedError(...) }
    }

and the KDoc on the Support form says it outright:

    "This function is only called when Room is configured without a driver. If a
     driver is set using [setDriver], then only the version that receives a
     [SQLiteConnection] is called."

Read precisely: migrate(connection) is ALWAYS the entry point. The Support form
runs only as a DELEGATION out of it, and only while the migration has not itself
overridden the connection form.

EVIDENCE 2 - THE DEVICE. A probe was planted in MIGRATION_1_2, in BOTH overrides,
run on the S9, and removed. The harness's own logcat capture:

    13:51:18.241 14469 14492 I SQLiteOpenHelper: DB version upgrading from 1 to 6
    13:51:18.241 14469 14492 E R395PROBE: CONNECTION FORM ENTERED,
                          connection=androidx.room.driver.SupportSQLiteConnection
    13:51:18.241 14469 14492 E R395PROBE: SUPPORT FORM ENTERED

THE TWO LINES DO NOT SAY ROOM CALLS BOTH FORMS, and that is the one way this
evidence could be misread. Room entered the CONNECTION form, handing it a
SupportSQLiteConnection - the compatibility mode the source names. The SUPPORT
line exists ONLY because the probe's own connection override ended with
super.migrate(connection), which is the delegation branch quoted above. Same
thread (14492), same millisecond. A migration that overrides the connection form
and does not call super never reaches the Support form at all.

COUNTS: one fire of each, the EXPECTED number rather than a dropped log. The probe
was on MIGRATION_1_2 only, and exactly one test (migratesFromVersion1ToLatest)
starts at version 1.

A THIRD CONFIRMATION arrived by accident while wiring Room into :shared: Room's
KSP output for a commonMain @Database imports androidx.sqlite.SQLiteConnection and
androidx.sqlite.execSQL. The extension the rewritten migrations need is a
commonMain API - established from Room's own generated code rather than from docs.

PROBE REMOVED. MonReleveDatabase.kt is byte-identical to HEAD; the only residual
R395PROBE strings are under android/app/build/ (untracked output).

R395'S SECOND HALF - THE SQL CANNOT CHANGE BY A CHARACTER
================================================================================
app/src/test/resources/migration-sql.txt records every statement each migration
executes, in order: 10 statements, 1 / 4 / 2 / 2 / 1.

THE FIXTURE IS GENERATED, NEVER TYPED (R181). A hand-transcribed expectation is
correct the day it is written and silently wrong afterwards - the exact defect
this test exists to catch, reproduced inside the test meant to prevent it. It is
the output of RUNNING the five migrations against a recording proxy.

Regeneration is an explicit opt-in (-PrecordMigrationSql=true) and the recording
run ALWAYS fails, so it can never be mistaken for a pass (R135).

PROVEN TO BITE: the same one-character plant failed
everyMigrationExecutesExactlyTheRecordedSql in the JVM gate.

A SECOND TEST ASSERTS THE RECORDER RECORDS (R154). Without it a double that
captured nothing would compare equal to an empty fixture - an absence assertion
satisfied by absence. The proxy also REFUSES any unmodelled SupportSQLiteDatabase
call rather than silently dropping it (R133); it threw on none, which establishes
that the bodies only ever call execSQL.

WHEN THE MIGRATIONS MOVE, the test switches from driving the Support form to
driving the connection form and THE FIXTURE DOES NOT CHANGE. git then proves
verbatim-ness by itself: the diff of migration-sql.txt must be empty.

TWO MECHANISM DEFECTS FOUND WHILE WIRING IT, both fixed and both worth recording
because each produced a convincing false signal:
  - a -D system property does NOT survive the Gradle daemon into a forked test
    JVM. The opt-in was silently ignored and the recording run merely looked like
    an ordinary failure. Switched to a PROJECT property, the idiom this build file
    already uses for the device-drive overrides.
  - inputs.file() on a not-yet-existing fixture makes Gradle REFUSE to run the very
    task that creates it. inputs.files() tolerates absence; the TEST reports the
    missing fixture with a message naming how to generate it (R133), which is the
    better place for that failure. The R283 input declaration is kept either way,
    so editing the fixture re-runs the comparison instead of leaving the task
    UP-TO-DATE with the assertion unrun.
