SUMMARY
====================================================================
/api/ready gained a "database" check that passes only when the
database is REACHABLE and MIGRATED. Either half failing returns 503,
which stops a Coolify deploy and leaves the running version serving.

THE GAP THIS CLOSES WAS NOT HYPOTHETICAL AND WAS MEASURED THE SAME
DAY. Production's database was reachable but unmigrated: every
data-backed request returned 500 - sign-in, the alert form,
/verifier/<code> - while /api/ready answered 200 with its single
site-origin check and a deploy would have sailed through. The deploy
gate R83 built for exactly this case could not see it.

Proven end to end in the walkthrough below: with the database stopped
/api/ready is 503 "unreachable"; with an empty schema it is 503
"unmigrated"; after prisma migrate deploy it is 200. Throughout,
/api/health stays 200 and the public pages serve.

====================================================================
R355 - THE THIRD STATE, AND WHY ok IS NULLABLE
====================================================================
`ok` is now `true | false | null`.

A check that did not run must not report `ok: true`, because a check
nobody ran reading as a check that passed is the exact shape this
project keeps finding (R133, R154). It must also not be DROPPED from
the list, because then a check that silently stopped being evaluated
becomes invisible - which is the reason the list reports its passes at
all.

So: `ok: null`, present in the list, with a detail saying it was not
evaluated and why. `ready` is computed as `every(check.ok !== false)`,
so a null does not block (pnpm build and CI need no database) and
cannot be mistaken for a pass.

====================================================================
R356 - HEALTH DOES NOT CHECK THE DATABASE, AND THAT IS A DECISION
====================================================================
R356 PERMITS health to add "database" to its degraded reasons ("MAY").
It does not, and the reasoning is recorded in the test rather than
only here. R83's own argument, one level down:

  AN ORCHESTRATOR RESTARTS WHAT FAILS LIVENESS.

A liveness endpoint that queries the database fails when the database
is merely SLOW, and the restart that follows cannot repair a database.
The container crash-loops while the previous version stays down -
precisely the failure R83 exists to prevent, reintroduced through the
body instead of the status code. A database problem belongs to
readiness, where failing stops a DEPLOY and leaves the running version
serving.

ASSERTED BY TIMING, because "it did not query" is otherwise invisible:
tests/db/readiness-route.test.ts requires /api/health to answer in
under 100 ms, which a handler awaiting even a fast local SELECT would
not, and which against a stopped database would sit on the 2 s budget.
The walkthrough confirms it with the database actually stopped.

====================================================================
THE NO-LEAK TEST (R354)
====================================================================
Three, at three levels, because the leak can be reintroduced at any:

  unit  - a probe is handed a realistic driver error containing a
          connection string; the serialised readiness body must not
          contain the host, the password, the port or "postgres://",
          and MUST still contain "database" and "unreachable" (R133:
          every absence assertion above passes against an empty body).
  db    - the probe's own return value must not contain the migration
          name it logged, nor anything from DATABASE_URL.
  route - the response body from the real handler, same assertions.

The migration name goes to the server log and never to the body: a
migration name describes the schema, and /api/ready is unauthenticated.
