REPORT-FW-CODE-CAP
==================

TASK   FW-CODE-CAP - the six-digit code exchange gets a ceiling that survives
       a restart, and the rate limiter stops trusting the caller.
BASE   0ddc646 (FW-READY / R353-R357)
BRANCH fw-code-cap, worktree C:/wt/fw-code-cap (R349), lock held and released


SUMMARY
-------

Two defects, one layer apart, both invisible to a green suite.

R362 - THE RATE LIMITER BUCKETED ON A VALUE THE CALLER CHOSE. clientKey read
the FIRST X-Forwarded-For entry. Proxies APPEND, so the first entry is
whatever the client sent and the last is what our own Traefik wrote. Any
caller could therefore pick its own rate-limit bucket - or share somebody
else's - by sending one header. Every per-IP limit in the product was
advisory against exactly the person it exists to stop.

  THE SUITE ASSERTED THE BUG. tests/unit/alerts/rate-limit.test.ts contained
  "takes the FIRST x-forwarded-for entry, not the last", expecting 9.9.9.9,
  with a comment reasoning it out: "the proxy appends the real peer; anything
  before it was sent by the client". The first half of that sentence is true
  and the conclusion inverts it.

R358/R359 - THE PER-CODE LIMIT WAS NEVER THE CEILING. consumeCode allows five
attempts against one issued code, and tests/db/code-sign-in.test.ts proves
that limit exactly. But issueMagicLink DELETES the previous row on every new
request, so asking for a new email resets the counter to zero. Five per code,
and codes are free.

  What actually bounded a guesser was the route's in-memory window: 20 per 10
  minutes, about 2 880 guesses a day against one chosen address out of 10^6 -
  roughly 0.3 % a day, about 8 % over a month of sustained effort - and
  weaker than that, because an in-memory Map empties on every deploy, so the
  attacker's real limit was how often we ship.

  NO TEST COULD SEE IT. Every test was asking about ONE code.

The fix is a CodeAttempt table: 10 attempts per address per rolling 24 hours,
counted across every code issued in the window, claimed atomically before the
code is compared. A month of sustained attack becomes about 0.03 %.

NOTHING HERE IS A NEW REFUSAL FOR A CLIENT. The code (too_many_attempts) and
the status (429) are unchanged - deliberately, and that is also what forced
the copy change in increment 5: one sentence now answers two different
refusals and has to be true for both.

R362 - EVERY CALLER WHOSE KEY CHANGED
--------------------------------------

clientKey has three callers, and the bucket each one computes changed:

  app/api/v1/auth/code/route.ts:55   the code exchange, per source

THE SHAPE OF THE FIX. The code takes the n-th entry FROM THE RIGHT, where n is

container-internal and change on every redeploy; the number of hops does not.
A list would be a second thing to keep in step with the deployment, and the
failure mode of a stale list is silent.

carries the old reasoning verbatim together with what is wrong with it,
because the next person to read "the proxy appends the real peer" will find it
persuasive for the same reason it was persuasive the first time.


THE TABLE
---------

prisma/migrations/20261015104441_code_attempt_budget/migration.sql

  model CodeAttempt {
    id          String   @id @default(cuid())
    emailHash   String                       -- SHA-256 of the normalised address, hex
    attemptedAt DateTime @default(now())     -- server clock, like every stamp here
    @@index([emailHash, attemptedAt])        -- serves the window query
    @@index([attemptedAt])                   -- serves the sweep
  }

WHAT IT DELIBERATELY DOES NOT STORE (R361). No IP, no user agent, no user id,
no code, and NOT THE ADDRESS - only its SHA-256. The table can answer "has
this address spent its budget" for an address somebody already holds, and
cannot answer "which addresses have tried". It is therefore not a list of who
attempted to sign in.

NO RELATION TO User, ON PURPOSE. A foreign key would make a row's existence
depend on registration, which is the enumeration signal docs/api-v1.md 1.5
forbids. The erasure path deletes by hash instead.

THE PRIVACY ENUMERATION IS CLOSED, so a column it does not cover makes
/confidentialite false rather than merely incomplete. All three columns are
mapped in lib/content/personal-data.ts to a new codeAttempts disclosure, and
that disclosure is rendered on the page - the mapping alone is a claim about a
constant (R225).

  NOT_PERSONAL stays empty and is asserted empty. "It is only a hash" is
  exactly the argument that would have opened it, and a hash OF personal data
  is personal data.


THE BUDGET (R358, R359)
-----------------------

MAX_CODE_ATTEMPTS_PER_DAY = 10 and CODE_ATTEMPT_WINDOW_MS = 24 h, named beside
MAX_CODE_ATTEMPTS with the arithmetic above in the comment.

CLAIMED BEFORE THE ROW IS READ, not merely before the comparison:

  - it makes the refusal identical in every case. An attempt against an
    address with no outstanding request costs a slot exactly like a guess
    against a live one. Spending it only when a row exists would make the
    budget itself an oracle for "has a code been asked for here".
  - it is the stricter reading. An attempt is an attempt.
  - the person it locks out still has the LINK, which never touches this
    budget - which is what makes a per-address budget acceptable at all,
    since ten attempts can be spent by somebody who is not the owner.

ATOMIC VIA A TRANSACTION AND A PER-ADDRESS ADVISORY LOCK. The obvious
implementation - one conditional INSERT ... WHERE (SELECT count(*)) < 10 - is
one statement, atomic, and wrong under load: READ COMMITTED fixes the
statement's snapshot before it runs, so two bursts each count the rows
committed before either began, both see nine, both insert. An advisory lock
INSIDE the same statement does not rescue it either, because by the time the
lock is held the snapshot is already taken. It has to be two statements in one
transaction: take the lock, THEN count under a fresh snapshot.

  The lock is per address, in the TWO-argument form, so it cannot collide with
  pg-boss's single-argument locks whatever keys those use. Prisma's maxWait
  and timeout are STATED at 10 s rather than inherited (R345).

EACH TEST, AND THE RED RUN IT CAME FROM (tests/db/code-budget.test.ts,
5 failed | 5 passed before the implementation):

  x refuses the eleventh attempt even when the code is CORRECT
      expected { ok: true, ... } to deeply equal { ok: false, ... }
  x counts every attempt, whichever code it was aimed at
      expected +0 to be 10
  x still counts an attempt made an hour inside the window
      expected { ok: true, ... } to deeply equal { ok: false, ... }
  x keeps every attempt on the record after a correct code is accepted
      expected +0 to be 4
  x grants exactly ten slots to a burst of thirty parallel guesses
      expected 30 to be 10

  THE BURST IS THE HEADLINE: all thirty parallel guesses were compared.

  FOUR OF THE FIVE GREEN TESTS IN THAT RUN WERE GREEN BECAUSE NOTHING REFUSED
  ANYTHING. "leaves the ninth and tenth inside the budget", "is per address",
  "stops counting an attempt older than the window" all hold trivially when
  there is no budget at all. That is R169's corollary, and it is why the five
  red ones are the evidence rather than the tally.

THE BURST RESULT AFTER THE FIX: compared 10, refused 20, rows 10.

  The burst runs with NO outstanding code, deliberately. With one issued, the
  per-code counter would stop the comparisons at five and the test would pass
  while proving nothing about the budget. With none, the only thing that can
  distinguish the thirty answers is whether the slot was granted - so "no more
  than ten were ever compared" is proven as "exactly ten slots were granted",
  and a comparison requires a slot.

A SUCCESS DOES NOT REFUND: three wrong guesses plus one accepted code leaves
four rows. A budget that cleared on success is a budget an attacker resets by
signing in to an address they do hold.

THE WINDOW ROLLS, PROVEN BOTH WAYS (R196): an attempt aged past the window
stops counting; one aged to an hour INSIDE it still counts. A budget that
refuses everything passes the first half perfectly.

THE EXISTING SUITE NEEDED ITS FIXTURE WIDENED, AND THAT IS THE BEHAVIOUR.
Two tests in tests/db/code-sign-in.test.ts failed the moment the budget became
real - not because either was wrong, but because each spends attempts against
the same address and the sixth test in the file was starting with the first
five already gone. The budget outliving a request is the point of it; the
fixture had to catch up. Same for auth-code-route.test.ts and
account-delete.test.ts.


ENUMERATION, PURGE, ERASURE (R361)
----------------------------------

ENUMERATION, asserted AT THE ROUTE rather than against consumeCode (R204),
because what a caller sees is a status and a body, and the status comes from
the route's switch and not from the function. Eleven attempts against an
address with an account and eleven against one without, compared as whole
responses - status and parsed body, every one. Eleven, because the run then
crosses all three answers: five comparisons, five refusals from the per-code
counter, and the eleventh from the budget.

  A second test asserts that an address nobody ever requested a code for still
  spends budget, which is the property that makes the first one true.

PURGE. claimCodeAttempt already deletes the expired rows OF THE ADDRESS IT IS
CLAIMING FOR before it counts, so every address that comes back is cleaned
continuously. The scheduled sweep is the backstop for an address attempted
once and never again - exactly the row the claim path can never reach.

  IT IS HOURLY AND HAS ITS OWN QUEUE. See DEVIATIONS.

ERASURE. CodeAttempt is keyed by a hash of the address and does not cascade
from User, like VerificationToken beside it, so it is deleted explicitly or
not at all. deleteAccount deletes by the same key the budget claims with
(R206: not a second sha256 computed in the erasure path), inside the same
transaction, and the receipt names CodeAttempt.

  The fixture seeds a row before the receipt is asserted - an erasure
  assertion with nothing to find is satisfied by absence (R169's corollary,
  and the reason the issuance record beside it is seeded too).

  IT COSTS NOTHING IN SECURITY. Clearing a budget this way requires already
  holding a valid access token for the account and destroying that account to
  do it.

ABLATIONS, because a test that passed on its first run is evidence of nothing:

  erasure delete removed     -> account-delete: expected +0 to be 1
  sweep delete removed       -> code-budget: expected +0 to be 2, +0 to be 1
  claim moved after the read -> auth-code-route: expected +0 to be 3

One of my own expectations was wrong before those ablations and the suite
caught it: the first sweep test claimed for an address that already had an
aged row, the claim path swept it, and the sweep saw two rows where the test
said three. The behaviour was right and my model of it was not.


COPY (R360) - THE DECISION, VERBATIM
------------------------------------

too_many_attempts has TWO causes now, and a caller cannot tell them apart -
deliberately, because R358 leaves the code and the status unchanged:

  the per-code five   -> asking for a new code WORKS (if budget remains)
  the per-address ten -> asking for a new code DOES NOT WORK

The sentence that was there said to ask for a new code. That is advice which
fails in a whole class of cases, in the message whose entire job (R198) is to
say how to recover - and one constant rendered for two refusals has to be true
for both (R165).

  BEFORE  Trop de tentatives pour ce code. Par securite, il n'est plus
          valable : demandez un nouveau code depuis l'application.

  AFTER   Trop de tentatives. Par securite, ce code n'est plus accepte :
          utilisez le lien de connexion contenu dans le meme e-mail.

WHY THE LINK. It is the one recovery that works in both cases: it travels in

address is refused.

The budget is exhausted through the route and the 429's message is required to

A sentence pointing at a link nobody tried is a sentence that reads well.

     a. from a machine whose public address you know, request any page;

   rate limiting still works - it just buckets on the wrong thing, which is
   why this is worth checking once rather than assuming.
