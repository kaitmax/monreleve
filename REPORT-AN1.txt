THE SIX FENCES
====================================================================
Implemented as source-scanning JUnit tests (FencesTest.kt) - this
project's already-established idiom (RadiusTest.kt, ThemeCensusTest.kt;
the web side's R147-style scans), not a new dependency, running under
`test` so already in the gate. Every scanner strips comments first
(this codebase's KDoc routinely quotes the very identifiers a fence
looks for - "android.*", "Location" - in explanatory prose, which would
otherwise self-trigger) and reads FULL FILE TEXT, not just import
lines, because a fully-qualified reference with no import statement is
a real evasion an import-line scanner misses.

1. calc/ imports nothing from android.*/androidx.*/other project
   packages. STRAIGHT VIOLATION: `import android.util.Log` in
   EnginePlaceholder.kt - RED, plant verified via grep before the run.
   EVASION: removed the import, used `android.util.Log` fully-qualified
   inline with no import statement - STILL RED. FENCE HELD.

2a. detection/ never references data.remote or Retrofit. STRAIGHT
   VIOLATION: `private const val marker = "data.remote"` - RED.
   EVASION: split the literal across a concatenation, `"data." +
   "remote"` - GREEN (evasion succeeded). FENCE DID NOT HOLD. Known
   limit: a text scan cannot see through string operations; closing it
   needs semantic analysis, out of AN1's zero-new-dependency scope.
   Documented in the test file at the point of the check.

2b (D18, the most important fence in the file). No coordinate type
   (Location, LatLng, latitude, longitude) appears outside detection/.
   STRAIGHT VIOLATION: `import android.location.Location; private val
   plantedFix: Location? = null` in EntryRepository.kt (outside
   detection/) - RED. EVASION: re-exported the same shape under an
   innocuous name, `private data class DeviceFix(val x: Double, val y:
   Double)` - GREEN (evasion succeeded). FENCE DID NOT HOLD. Known
   limit: this is a NAME-based scan; a renamed coordinate pair evades
   it by construction. Closing it needs a semantic/type-level check (a
   custom detekt rule reading the resolved type), out of scope here and
   documented as such in the test.

3. ui/ carries no radius/colour/spacing literal outside the token set.
   STRAIGHT VIOLATION: `RoundedCornerShape(10.dp)` and
   `Color(0xFFAABBCC)` in AujourdhuiScreen.kt - RED. EVASION: constant
   indirection - `val r = 10; RoundedCornerShape(r.dp)`, `val c =
   0xFFAABBCC; Color(c)` - GREEN (evasion succeeded). FENCE DID NOT
   HOLD. Same limit class as 2a/2b: each regex anchors on the literal
   appearing AT the call site; a one-hop indirection moves it off that
   anchor. Documented; not chased into a dataflow analysis.

4. No String literal in ui/ (French comes from fr/). STRAIGHT
   VIOLATION: `Text(text = "Bonjour direct", ...)` - RED. EVASION:
   hoisted the same literal to a top-level `private const val` OUTSIDE
   the composable's own braces, referenced from inside - STILL RED.
   FENCE HELD. (The scanner is scoped to the whole ui/ file rather than
   only text lexically inside a @Composable's braces, specifically
   because a same-file hoisted constant is still a hardcoded string in
   ui/ and defeats the rule's intent - this was the deliberate design
   choice the evasion was chosen to test, and it held.)

5. ui/ writes entries only through EntryRepository (a stub today; the
   rule exists before the thing it governs). STRAIGHT VIOLATION:
   `private const val plantedDaoRef = "direct Dao access"` - RED.
   EVASION: split concatenation, `"direct " + "Da" + "o access"` -
   GREEN (evasion succeeded, same limit as 2a). FENCE DID NOT HOLD;
   documented.

6. No Material default shape or elevation. Scoped to Card(...) in ui/
   (the one M3 component this project calls that carries a live
   default; Surface's own defaults are already a zero-elevation
   rectangle, not a live risk today). STRAIGHT VIOLATION: a second
   `Card(modifier = Modifier.fillMaxWidth()) { ... }` with no shape/
   elevation args - RED. EVASION: passed shape/elevation EXPLICITLY,
   but spelled out as `shape = CardDefaults.shape, elevation =
   CardDefaults.cardElevation()` - Material's own defaults, written by
   name - GREEN (evasion succeeded: presence-only checking passed while
   intent failed). FENCE STRENGTHENED IN RESPONSE (the one fence where
   the found gap was cheap to close, unlike 2a/2b/3/5's structural text-
   scan limits): now also rejects those two exact default-accessor
   spellings by name. Re-ran the same evasion - RED. FENCE NOW HOLDS,
   with the same one-more-hop limit as the others documented in the
   test (`val d = CardDefaults.shape; Card(shape = d, ...)` would still

THE INSTRUMENT
====================================================================
scripts/emulator.sh, scripts/screenshot.sh, scripts/walkthrough.sh
(android/scripts/). Split from a single "start" command into
`launch` (spawns the AVD, returns in under a second) and `wait-boot`
(polls adb, idempotent, safe to re-run) - found necessary, not designed
in advance: this environment kills long-running foreground commands
(observed four separate times across this session, on plain `df`,
`docker system df`, and two `emulator.sh start` attempts), and the
spawned emulator process survives that kill, so a single blocking
"start" would repeatedly get cut off mid-boot with no way to recover
except by re-launching a whole new emulator from scratch.

ORPHAN DISCIPLINE (R98/R105/R179), and the strongest evidence for it in
this report is not a plant: after the first killed `emulator.sh start`,
a live check found BOTH `emulator.exe` (PID 31004) and its child
`qemu-system-x86_64-headless.exe` (PID 18256) still running - neither
PID matched the one this session's script had originally tracked (PID
3126, recorded from `$!` at launch). On Windows, `emulator.exe` spawns
qemu as a genuine child process rather than exec-replacing itself, so
the launcher PID is never reliably the long-lived one. `emulator.sh`
therefore sweeps by AVD-NAME COMMAND-LINE MATCH (via
`Get-CimInstance Win32_Process` filtered on both name and command line)
rather than trusting a tracked PID, and verifies zero remain after
killing. This exact sweep found and correctly killed both orphaned
processes on its first real use - not a planted test, a live defect
this harness's own behaviour created and the discipline closed.

PLAY-STORE AVD, FOUND NOT ASSUMED: the only local AVD (`Pixel_10`,
android-37.0, `PlayStore.enabled=true`) is a production-signed build,
which requires on-screen ADB key authorization - impossible with
`-no-window`. First boot attempt: `adb devices` reported the device as
`unauthorized`, then `offline`. A device's very FIRST-EVER boot
auto-trusts the host's existing `~/.android/adbkey` because there is no
prior state to protect yet, so `emulator.sh launch` always passes
`-wipe-data`, forcing a fresh first boot every run. Verified: after
`-wipe-data`, `adb devices` reported `device` (authorized) and
`sys.boot_completed=1` within the polled timeout. Costs the AVD's
persisted state every run, acceptable for a placeholder screen with
nothing to persist.

FAILURE MODES OBSERVED, all real: (1) unparseable ambient JDK -
diagnosed via `IllegalArgumentException: 26` stack trace pointing at
`JavaVersion.parse`, fixed via `~/.gradle/gradle.properties`
`org.gradle.java.home`. (2) killed foreground wait, spawned process
survives - closed by the launch/wait-boot split plus the command-line
sweep. (3) ADB unauthorized/offline on a Play-Store image - closed by
`-wipe-data`. (4) a cold-start render race - closed by polling logcat's
"Displayed" line instead of a fixed sleep.

BASELINES
====================================================================
Paparazzi 1.3.5, not Roborazzi. THE DECIDING ASSUMPTION WAS CHECKED,
NOT TAKEN ON FAITH: Paparazzi has a documented history of running only
in library modules, and this project is a single application module -
which would have made Roborazzi the forced choice regardless of
dependency weight. Applied Paparazzi's plugin to `app/build.gradle.kts`
and ran `./gradlew :app:tasks --all`: `recordPaparazziDebug`/
`verifyPaparazziDebug`/etc. registered normally. The only failure on
first real use (`verifyPaparazziDebug`) was a missing
`src/test/snapshots` directory - a mundane first-run gap, not a module-
type rejection. Paparazzi 1.3.5 evidently supports application modules;
whatever historical restriction existed does not hold at this version,
checked against this exact module rather than assumed from general
knowledge. This avoids Roborazzi's mandatory Robolectric dependency and
its ~150-300 MB `android-all` download entirely, so no R136
justification burden was even incurred.

DEVICE CONFIGURATION, PINNED: `DeviceConfig.PIXEL_5`,
`android:Theme.Material.Light.NoActionBar`, light mode only (matches
FrontierTheme's own light-only wiring - there is no dark variant to
pin against). Changing this device configuration regenerates every
baseline in the file; stated here per the relay's requirement, not
left implicit in a config file nobody reads before regenerating.

WHAT A BASELINE CERTIFIES, AND WHAT IT DOES NOT (R135): stability, not
correctness. This session's own experience is the proof rather than a
citation - the FIRST recorded baseline was accepted by
`recordPaparazziDebug` without complaint despite being wrong (a white
canvas instead of the grey token canvas, because the test's bare
`Surface()` silently used Surface's own default colour instead of
MainActivity.kt's explicit `color = background`). A baseline recorder
has no opinion about whether what it captured is right; only comparing
it against the real device walkthrough (the increment-4 instrument)
surfaced the mismatch. The two are not interchangeable, and the
instrument is what closed the gap the baseline could not see.

Test floor: `checkTestFloor` covers this file's one test as part of the
15-count floor (see THE CANARY). R114 (zero tolerance): Paparazzi's
default snapshot handling is an exact pixel comparison; no threshold
was configured, so none needed disabling. R128 (a baseline asserts its
own dimensions): not separately asserted in this test - Paparazzi's
own image-diff mechanism already fails on any dimension mismatch
between the current render and the stored PNG, which is R128's
property by construction of the library rather than something this
test needed to add on top.

`./gradlew gate` (android/app/build.gradle.kts): assembleDebug,
testDebugUnitTest (includes the six fences in FencesTest.kt and the
theme/radius censuses), checkTestFloor, ktlintCheck, detekt,

    which an unattended gate task cannot do.
  - connectedDebugAndroidTest (the instrumented canary): same reason,
    needs a running device; exercised by the instrument, not this gate.

R132's SELECTOR: NOT extended with an `android/**` pattern, and this is
a considered decision rather than an oversight - checked empirically
before deciding. `web/tests/unit/meta/gate-selection.test.ts` has an
explicit, deliberate invariant: "gives every pattern a suite to
require" - "A pattern with no suites would match, be reported as
matched, and change nothing about what runs." An `android/**` entry
genuinely has no web suite to add (no web test verifies Android
correctness), so the only way to satisfy that invariant would be to
attach some web suite to an Android-only change for no real reason, or
to violate the invariant with an empty `suites: []` array the
project's own test explicitly forbids. Verified directly:
`selectSuites(['android/app/.../MainActivity.kt'])` already returns
"no path matched the selector - base chain only" - exactly the correct
outcome (an Android-only change gets the same base sanity check as any
unrelated change, and nothing web-specific, because Android has its
own separate gate, `./gradlew gate`, not orchestrated by this
selector). Recorded as a QUESTION rather than resolved by force-fitting
a pattern into a mechanism whose own tests say it should not fit.

CI: one new job, `android`, added to `.github/workflows/ci.yml`
(inserted between `web` and `visual`). Gated on the exact SAME
condition as `web` (`vars.CI_FULL == 'on' || github.event_name ==
