R576 - THE EVENING NOTIFICATION FOLLOWS THE SETTING (b6e93d0)
--------------------------------------------------------------------------------
WHAT THE CODE DID (main): decideEveningTap returned ONE RecordCommand with
`portion = Portion.FULL`, whatever the setting; the receiver wrote it through
LocalEntryRepository. It wrote only a day with no row (any recorded portion ->
ALREADY_RECORDED), so R492's refusal guarded only a race.

WHAT IT DOES NOW (:app, notification/ only):
  - decideEveningTap(tap, at: TapMoment, hasEntryForShownDay, setting) returns
    Record(commands) - one command per portion `portionsToOffer(held =
    emptyList(), setting)` gives the empty day: [FULL] in whole-day mode, [AM,
    PM] in half-day mode, each carrying the whole tap (kind, provenance,
    detected side, detectedAt). The day is empty whenever this branch is
    reached, so "a day already held keeps its own" is the unchanged
    ALREADY_RECORDED branch: such a day is never written.
  - recordEveningTap(tap, at, deviceRows, settings, repository) is the
    receiver's write without the Android glue: the stale-tap check over the rows
    the receiver read, the setting read from the store AT THE TAP (R475), each
    command through the repository (R206, R492). Typed outcome: Ignored(reason) /
    Recorded(commands) / Refused(written).
  - EveningActionReceiver calls it with SharedPrefsSettingsStore; Recorded ->
    sync + "Enregistre" confirmation as before; Refused -> the day as it now
    stands (as before), plus a sync if a row went in before the refusal (only
    possible across two repository instances, PARK-W4).
  - TapMoment (the account, the Paris day and the clock at the tap, one value)
    exists because detekt's LongParameterList (threshold 6) failed the first
    shape on fastCheck - restructured, not suppressed.
