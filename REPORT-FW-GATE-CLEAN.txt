SUMMARY
-------

KMP-0 commits d808d05 and dfffee9 committed `java.time` imports into
commonMain - the one thing R369's platform-free fence exists to forbid - and
every check was green while they did it.

NOTHING WAS WRONG WITH THE FENCE. The sequence was:

    git mv <file> shared/...              the move is STAGED
    <edit it to use kotlinx-datetime>     the edit is UNSTAGED
    ./gradlew :app:gate                   compiles the WORKING TREE: green
    git commit                            commits the INDEX: no edit in it

Gradle compiled what was on disk. Git committed what was in the index. Each
tool was correct about its own input, and none of them was positioned to
notice they had diverged.

So the guard is not a stricter fence. It is the one assertion neither tool
could make: that the two agree before anything is tested. After it,
"the gate passed" always means "what will be committed passed".


THE CHECK, AND WHY IT IS `git diff --quiet` AND NOTHING CLEVERER
-----------------------------------------------------------------

`git diff` with no revision argument is exactly "tracked files whose
working-tree content differs from the index" - the gap that produced the
defect. `--quiet` makes it an exit code.

UNTRACKED FILES ARE NOT A FAILURE, deliberately. `.env`, `local.properties`,
`android/.kotlin/`, a session lock and a scratch APK are all untracked, all
normal, and none of them can reach a commit by accident. A guard that fired on
them would be switched off within a week.

STAGED CHANGES ARE NOT A FAILURE EITHER, and that is the point rather than a
concession: once staged, the tree and the index agree, so the build reads what
the commit will write.

IT DOES NOT BREAK SUITE SELECTION. `pnpm gate:changed` derives its selection
from `git diff --name-only HEAD`, which compares against the COMMIT and
therefore sees staged changes too. Checked before the guard was written,
because a guard that forced everything to be staged and then left the selector
seeing nothing would have run the base chain only and read as a pass.

IT NAMES THE FILES. A refusal that says "the tree is dirty" sends somebody to
`git status`, which lists untracked files too and buries the one line that
matters.

TEST: web/tests/unit/meta/clean-worktree-guard.test.ts, 6 tests. Each builds
its OWN scratch git repository and runs the real script as a child process -
the entry point, not an imported function (R204). A test that depended on the
state of the tree it runs in would pass or fail according to whether the
person running it had saved a file.

    clean tree                         -> exit 0
    unstaged change to a tracked file  -> exit 1, and NAMES the file
    the same change, STAGED            -> exit 0
    untracked files only               -> exit 0
    not a git repository at all        -> exit 0
    `gate` script starts with the guard

The last one is there because a guard nobody calls is a comment, and the
position matters as much as the presence.


THE ANDROID GATE (:app:gate)
----------------------------

android/app/build.gradle.kts, in `gradle.taskGraph.whenReady`.

IT IS NOT A dependsOn TASK, and that is the difference between "refuses to
start" and "fails eventually". `dependsOn` gives no ordering guarantee against
the gate's other dependencies, so a compile could run - and a stale build
directory be produced - before a `doLast` ever fired. The task graph is
resolved before ANY task executes, which is the last moment at which nothing
has happened yet.

IT IS SCOPED TO THE GATE. An ordinary `./gradlew assembleDebug` during
development is untouched; a guard that blocked every build while somebody was
editing would be switched off the same day.

RED, with one unstaged edit to a tracked file:

    GATE REFUSED TO START (R393): unstaged changes to tracked files.
    1 file(s) differ from the index:
        android/shared/src/commonMain/kotlin/ch/monreleve/app/fr/CodeCopy.kt
    Stage them (git add) and run the gate again. Untracked files are not
    BUILD FAILED in 3s

THREE SECONDS, and that number is the evidence rather than decoration: a full
:app:gate is three to ten minutes, so nothing was compiled before it refused.

GREEN, same tree with the edit reverted:

    [clean-worktree] OK: no unstaged changes to tracked files (R393)
    BUILD SUCCESSFUL in 3m 46s
    218 actionable tasks

TEST: android/app/src/test/.../fences/CleanWorktreeGuardTest.kt, 4 tests,
confirmed to have RUN rather than been skipped (tests="4" skipped="0").

    WHY IT READS THE BUILD SCRIPT INSTEAD OF EXERCISING THE GUARD, stated in
    the file so nobody reads it as laziness: a JUnit test runs INSIDE the
    build it would have to drive. It cannot start a second Gradle, and a
    guard that fires in `taskGraph.whenReady` has by definition already
    decided before any test executes. The behaviour is proven empirically
    above; what the test holds is the part that rots silently - that the
    guard is still wired, still in `whenReady` rather than demoted to a
    `dependsOn`, still reading `git diff --name-only`, and still scoped to
    the gate.


WHAT WENT WRONG WHILE BUILDING IT
---------------------------------

THE FIRST RED ATTEMPT TESTED NOTHING, and the guard was right to stay quiet.
I appended a comment to `app/src/main/kotlin/ch/monreleve/app/fr/SignInCopy.kt`
to create an unstaged change - but that file lives in `shared/`, not `app/`,
and `>>` CREATES a file that does not exist. So I made a new UNTRACKED file,
`git diff --name-only` correctly reported nothing, and the gate correctly did
not refuse. It then failed four minutes later on ktlint: "File 'SignInCopy.kt'
should not be empty".

  Two things worth keeping from that. The guard behaved exactly as specified -
  untracked files are not its business - and my `||` fallback could never have
  fired, because `>>` cannot fail on a missing path. The second red attempt
  checked `git ls-files --error-unmatch` FIRST, so the target was proven
  tracked before the edit was made (R180: verify the plant).

THE STRAY FILE WAS REMOVED after confirming it was untracked and therefore
mine (R334). ktlint then kept failing on it for one more run from stale
incremental state; cleared `app/build/intermediates/ktLint` and the ktlint
reports, after which the task passed.

THE .gitignore BUG BIT AGAIN, exactly as FW-FOLLOWUP predicted it would:

    .gitignore:46:MonReleve/   android/app/src/test/kotlin/ch/monreleve/
                               app/fences/CleanWorktreeGuardTest.kt

This branch is off `main`, which does not yet carry FW-FOLLOWUP's anchor fix
(`/MonReleve/`). Staged with `git add -f` here rather than duplicating that
one-line change on two branches and conflicting at merge. IF FW-FOLLOWUP IS

SCOPE - WHAT WAS NOT GUARDED, AND WHY IT IS A QUESTION
-------------------------------------------------------

`pnpm gate:changed` IS NOT GUARDED. The instruction named `:app:gate` and
`pnpm gate`, and those are what this delivers.

It is worth raising rather than quietly extending, because `gate:changed` is
the gate R132 actually requires before every commit - so the defect class this
ruling closes is still open on the command most used. Extending it is one
line. It is NOT done here because it changes the everyday workflow: every
session would have to `git add` before gating, and that is a workflow decision
rather than a bug fix. See QUESTIONS.
