    HEALTHCHECK.

    since FW28. Every deploy with the check disabled sets
    custom_healthcheck_found (Application.php 2704-2743); with it set,

    gate still runs (2727) - on the IMAGE's HEALTHCHECK, i.e.

    flag is cleared by one of the three paths above WHILE the check is
    enabled, the next deploy does not re-parse (2704 runs only when
    disabled), writes Coolify's /api/ready check into the compose, and
    (a)+(c) apply in full. The UI toggle and a health_check_* PATCH -
    the routes the operator would use - cannot clear it; an API PATCH

    CONSEQUENCE FOR PRODUCTION TODAY (inferred from source plus the

    Healthcheck page and that deploy-log line.

(b) WHEN IT FAILS - DOES THE OLD CONTAINER KEEP SERVING?  YES, ON THE
    ROLLING PATH ONLY. rolling_update() starts the new container beside
    the old, runs health_check(), then stop_running_container():

    failDeployment() (4971), the new container shut down (4972), the old

(c) DOES TRAEFIK STOP ROUTING TO A CONTAINER DOCKER MARKS UNHEALTHY?

QUESTION 1 (R844's condition met). WHERE MAY COOLIFY'S CHECK POINT?
  Finding: on Coolify 4.5.0 the release gate and the container's
  life-long healthcheck are ONE Docker healthcheck (a), and Traefik
  unroutes any container that is not healthy (c). So "Coolify's deploy
  check on /api/ready" cannot be had as a release-only gate: where it
  takes effect it makes readiness the container's liveness, and a
  database blip takes every page - static ones included - out of routing
  (R375, R357). Where it does not take effect - while the Dockerfile has a
  HEALTHCHECK, which R846 requires - enabling it is silently ignored, and
  releases stay gated on /api/health (inferred; tells in R849 item 4) -
  unless the flag is ever cleared while it is enabled, which turns it
  into the forbidden case (R844 (a), the three paths).
  Nothing was enabled, changed or papered over; docs/deploy.md section 3
  says "do not enable until question 1 is ruled".
  Options seen:
    A. LEAVE IT OFF (status quo, no change anywhere). Releases stay
       gated on liveness through the image's HEALTHCHECK; readiness is
       checked by the after-deploy checklist (R849) and by the
       migrate-before-promote order (docs/deploy.md section 4). An
       unmigrated release goes live: static pages serve, data-backed
       requests fail, until it is migrated. curl's only consumers: operator
       checks inside the container, and R847's proof.
    B. READINESS STRICT ONLY IN A START WINDOW, INSIDE THE IMAGE'S
       HEALTHCHECK (no new route): the probe asks /api/ready until it
       has passed once in this container's life, then /api/health for
       the rest of it (a latch file in /tmp). Coolify's existing poll
       (via custom_healthcheck_found) then gates the release on
       readiness, and a later database blip cannot unroute. Costs: it
       amends R375 (the continuous probe touches /api/ready during the
       window), and a container (re)started while the database is down -
       a host reboot - stays unrouted until the database returns. The
       command may stay node; curl is optional here.
    C. A NEW START-WINDOW PATH (e.g. /api/startup: strict for the first N
       seconds of process life, then liveness) with Coolify's check on
       it. Needs a new route (outside this task) AND either the image
       HEALTHCHECK removed (to clear the flag, against R846/R375) or the
       image HEALTHCHECK pointed at it (then it is B by another name).
       curl is consumed only if Coolify's own command runs.
    D. THE RELEASE GATE DONE ANOTHER WAY: the entrypoint refuses to
       start the server while the database is unmigrated, so the new
       container never turns healthy and the rolling update rolls back.
       Costs: R83/R250's crash-loop argument (Coolify's compose sets
       restart: unless-stopped, bootstrap/helpers/constants.php 62), and
       a database outage at boot becomes a crash loop. curl not needed.
    E. Remove the Dockerfile HEALTHCHECK and enable Coolify's check on
       /api/ready - the forbidden case, listed only to be rejected.
  Leaning, for the ruler to overrule: A now; B if a release-time
  readiness gate is wanted, as its own task with its own ruling on R375.
  Whatever is ruled, R844 (b) applies: there is no gate at all unless
  Port mappings is empty and container naming is not consistent.
