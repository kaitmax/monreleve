THE FOUR DEFECTS (each cause, each fix, seen)
--------------------------------------------------------------------------------
1. THE MONTH COUNTS ROW - "Non renseigne" wrapped and its number sat lower/right.
   CAUSE: MonthSummaryRow was a plain Row of four Columns, each CenterHorizontally;
   when "Non renseigne" wrapped to two lines its column grew taller and pushed its
   number below the others.
   FIX: rebuilt as FIVE equal tiles from the ONE MonthSummary (monthSummaryTiles,
   a pure JVM-tested function - R328, one way of counting). A FlowRow with
   maxItemsInEachRow = 5 at default and 3 at the list font scale (so the tiles WRAP
   to a second row at 200 % rather than squeezing). Each tile's label reserves two
   lines (minLines = maxLines = 2) so every NUMBER sits at one baseline whatever the
   label's length. SEEN: calendrierMonth baseline + device cal-01 (Suisse/Domicile/
   Mission/Absence/Non renseigne, numbers aligned). "Non renseigne" (13 chars) still
   wraps to two lines - it cannot fit one line in a fifth of a 320-360 dp row at a
   legible size - but ALIGNED, which was the operator's actual defect. See PARKAN-41.

2. ABSENCE HAD NO COUNT.
   CAUSE: the model already counted absences (MonthSummary.absent, added by AN-HOME)
   but the calendar's row omitted the tile.
   FIX: monthSummaryTiles adds the Absence tile (LegendCopy.forKind("A"), R206). The
   legend's four kinds now all carry a count. TEST-FIRST: MonthSummaryTilesTest went
   RED with four tiles (Absence missing), GREEN with five. SEEN: calendrierMonth
   (Absence 1) + device cal-01 (Absence 0).

3. THE STRAY VERTICAL LINE on the left edge - hypothesised "a card's border drawn
   partly off-screen in the shared app frame".
   CAUSE (diagnosed on the device): it is NOT an app element. It is the Samsung
   Edge-panel HANDLE, a SystemUI overlay. Proven three ways on the SM-G960F:
     (a) IDENTICAL content-independent position on Aujourd'hui, Calendrier AND
         Parametres (an app card would sit at a different y on each screen);
     (b) a uiautomator dump of the app window has NO node with left bound < 30 px in
         that band - all app content is inside the 20 dp screen padding (the
         Explorer's source audit confirmed no shared bordered card, no negative
         offset, no x<0 content in the shell/frame);
     (c) the device has an active Edge panel: settings system
         cocktail_bar_enabled_cocktails = AppsEdgePanelProvider, and
         edge_handler_position_percent = 76.91441, i.e. 0.769 x 2220 = 1707 px -
         exactly where the line's bottom sits.
   FIX: none in app code - there is nothing in the frame to fix (the hypothesised
   off-screen card does not exist); the app frame is correct. Recorded as PARKAN-40.
   To clear the screenshot artifact, disable the device's Edge panel (a device
   setting, outside the app). CONSERVATIVE (R156, advisor stalled): I did not invent
   an app layout change that removes nothing.

4. THE BOTTOM NAVIGATION pill - Material 3's pink indicator pill + a red selected
   icon.
   CAUSE: AppBottomBar's NavigationBarItems set no `colors`, so M3 defaults applied:
   the indicator used colorScheme.secondaryContainer (FrontierTheme maps that to
   switzerlandSoft, a pale pink) and the selected icon/label used onSecondaryContainer
   (switzerlandText, a red).
   FIX: overrode the colours once in AppBottomBar (brandNavItemColors): indicator
   Color.Transparent (no pill), selected icon/label LightColors.brand, unselected
   textSecondary (DESIGN-SYSTEM section 1 BOTTOM NAV: "active = brand colour, inactive
   = neutral. No oversized pill."). Fixed at the nav component, so every screen is
   corrected at once. SCREENSHOT ASSERTION added so it cannot return:
   AppBottomBarScreenshotTest / appBottomBarCalendrierActive. SEEN: the baseline
   (Calendrier brand, no pill) + device cal-01/cal-03 (brand active item, no pill, on
   every tab).

SELECTION (C2)
--------------------------------------------------------------------------------
On CalendarController, test-first (CalendarSelectionTest):
- startSelection() enters the mode empty; a long press seeds the pressed day.
- tapDay(iso): toggles an individual day; with an anchor set, fills the recordable
  range between the anchor and this day (a holiday week in two taps); clears the
  anchor after a range so the next tap starts fresh.
- Future / out-of-period days are refused (selectableDay checks `recordable`, the
  SAME rule single-day openDay uses - whatever single-day editing cannot record,
  selection cannot).
- days is a Set, so a day is never selected twice (C3); an overlapping range does
  not duplicate.
RED proof (R178/R180): disabling the range branch and dropping the recordable guard
reddened the range, future-refusal and no-dup tests; reverted.
DEVICE (today = 5 Oct 2026, so only 1-5 are recordable): tap "Jour 1" -> one
selected (anchor); tap "Jour 4" -> range 1..4 ("4 jours selectionnes", cells 1-4
ringed + checked); tap "Jour 10" (future) -> REFUSED, count unchanged (cal-12/13/14).
At 200 % the grid is a list (R271); a long press on a row enters selection and each
recordable row gains a CHECKBOX (cal-21).

THE ACTION PANEL
--------------------------------------------------------------------------------
SelectionActionPanel, in the space the "a completer" card otherwise holds. It states
the count ("N jours selectionnes", a polite live region), offers the choices and
"Annuler". The choices reuse Aujourd'hui's vocabulary EXACTLY as the edit sheet does
(R206, one record surface): En Suisse, Domicile, Mission (nests into En France /
Pays tiers), Declarer une absence (nests into its reasons - chosen ONCE for all the
days). Whole days only (section 2: a split day stays in the single-day editor). A
leaf choice opens the one confirmation; nothing is written in the panel.

--------------------------------------------------------------------------------
THE CONFIRMATION (both conditional lines) (C4)
--------------------------------------------------------------------------------
BulkConfirmation is a PURE function (JVM-tested, BulkConfirmationTest), computing the
two CONDITIONAL lines from the chosen days, the stored rows, the choice and the
clock:
- "N jours deja renseignes seront modifies" - shown iff some chosen days already
  hold a value (alreadyRecordedCount > 0).
- "N jours ... plus de 7 jours apres la journee ... saisie tardive ..." - shown iff
  some chosen days are older than the late threshold. The threshold comes from the
  ONE shared value (LatenessForecast.BACKFILL_DAYS, R286/R153) - never a 7 typed in
  the copy.
RED proof: a zero-count stub reddened both conditional-count tests; GREEN with the
real counts.
DEVICE: October (days within 7 of today) -> confirmation lists the days + choice,
NEITHER conditional line (correct - no day is late or already recorded). September
(all days > 7 days old) -> the "saisie tardive" line appears, threshold 7
interpolated (cal-31). "Annuler" on the confirmation wrote NOTHING and left the
selection intact (cal-32).

--------------------------------------------------------------------------------
WHAT IS WRITTEN (the five rows read back) (C3)
--------------------------------------------------------------------------------
confirmBulk() writes ONE mutation PER DAY through the SAME repository single-day
editing uses (record() per day, FULL portion): each gets its own clientMutationId
(born at the confirmation tap), the account's tag (R303) and clientClaimedAt = the
confirmation tap (R275, deviceClaimNow). Nothing in the record says "bulk" - a bulk
entry is exactly the same rows as entering the days one by one. Then ONE requestSync;
the existing SyncEngine batches within MAX_BATCH_ITEMS (200, parity-tested) and a
month never needs more than one batch; R296 isolation still applies per item.
JVM (CalendarBulkWriteTest): five days -> five rows, five distinct ids, all FULL, all
ABSENT/FERIE, all tagged with the account, all carrying the confirmation tap's claim
time; Annuler writes nothing; a bulk over an already-recorded day coalesces it. RED
proof: recording only the first day reddened the per-day test; reverted.
DEVICE READ-BACK (R204, end to end): provisioned a scratch Postgres + monreleve:write
container, signed in a real account, bridged the SM-G960F with `adb reverse tcp:3000`,
recorded a holiday week (Sept 7-11) as Absent/Jour ferie in a handful of taps, waited
for the WorkManager drain, and read the server's Entry table:
    ROWS = 5   DISTINCT clientMutationId = 5   DISTINCT userId = 1
    dayDate 2026-09-07..09-11 (Paris), portion FULL, kind ABSENT, absenceReason FERIE,
    all under userId cmuvaglsn... (email ancal2@example.com).
Five separate rows, distinct ids, the account's tag - exactly C3. (A first run drained
NOTHING because the injector sets the account tag only when an `email` extra is passed,
R303 - without it the rows are UNOWNED, never sent; adding the extra fixed it. This is
the R303 account-scoping that post-dates AN10b's own sync drive.)

STATE (R310, C2)
--------------------------------------------------------------------------------
The selection survives a rebuild. SelectionSnapshot (Serializable) is carried in
CalendarSnapshot and persisted in ShellState's rememberSaveable (the saved-instance
Bundle, which outlives a config change AND process death); CalendarController seeds
from it. JVM (CalendarSelectionTest): a controller built with a SelectionSnapshot
restores the mode, the days and the anchor.
DEVICE: with days 1-2 selected, a font-scale change (the rotation config-change class,
AN-STATE's R310 trigger) KEPT the selection (cal-41, "Selectionne. Jour 1/2"); a
process death (HOME -> am kill -> launcher resume via monkey) RESTORED it on the
Calendrier tab (cal-42, "2 jours selectionnes", both cells selected). The confirmation
is transient (a rebuild closes it with the selection restored beneath, so re-opening
is one tap and its counts are re-derived, R181).
