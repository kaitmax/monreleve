ITEM 1 - THE CONTAINER'S HEALTHCHECK (R375)
-------------------------------------------

THE ORIGINAL REASONING, FOUND AND QUOTED. The Dockerfile carried:

    # The readiness endpoint, NOT liveness (R83). Coolify's DEPLOY health
    # check points here: /api/ready returns 503 while degraded, which stops a
    # bad deploy and leaves the running version serving. /api/health returns
    # 200 whenever the process answers, because an orchestrator RESTARTS what
    # fails liveness and a restart cannot supply a missing environment
    # variable.

EVERY SENTENCE IN IT IS TRUE AND IT DESCRIBES THE WRONG PROBE. Coolify's
deploy check is configured in Coolify and runs ONCE, at release; the
Dockerfile instruction runs every ten seconds for the life of the container.
Two different checks, and only the first is about readiness.

IT WAS NOT A RULING BEING FOLLOWED. R83's own next sentence, as
tasks/todo.md records it, says "Wire the restart policy, if any, at
/api/health" - which is exactly what a Docker HEALTHCHECK is. So this was one
ruling half-applied to the probe it does not govern, and R375 records the
correction rather than leaving the citation to read as agreement. REPORT-FW28
states the split as an operator instruction (deploy -> /api/ready, restart ->
/api/health) and never rules on the Dockerfile.

IT WAS HARMLESS UNTIL FW-READY, which is why it survived review. While
/api/ready could not fail at runtime the two endpoints answered alike in a
healthy container. R353-R357 gave /api/ready a database check.

NO TEST ASSERTED THE TARGET - there was none to update. The new one is
tests/unit/meta/healthcheck-target.test.ts, RED against the shipped line in
both directions before the fix:

    AssertionError: expected 'HEALTHCHECK --interval=10s --timeout=...'
      to contain '/api/health'
    AssertionError: expected 'HEALTHCHECK --interval=10s --timeout=...'
      not to contain '/api/ready'

Both directions, because "contains /api/health" alone is satisfied by a
command that probes both. A third test pins that the interval, timeout and
retries are still stated rather than inherited from Docker's defaults (R345),
since the proof below is expressed in terms of interval x retries.

PROOF IN THE IMAGE. monreleve:liveness, built from this branch, started with
DATABASE_URL pointing at a port where nothing listens, left for 60 s - past
start-period 20 s plus interval 10 s x 3 retries:

  docker inspect  ->  healthy (failing streak 0)

  GET /api/ready   ->  HTTP/1.1 503 Service Unavailable
    {"ready":false,"checks":[{"name":"site-origin","ok":true},
     {"name":"database","ok":false,"reason":"timeout",
      "detail":"The database did not answer within the readiness budget..."}]}

  GET /api/health  ->  HTTP/1.1 200 OK
    {"service":"monreleve",...,"status":"ok","reasons":[],"runtime":true}

  GET /            ->  200     (a page R357 says must keep serving)

THE REASON CODE IS `timeout`, NOT `unreachable` as the prompt predicted. A
dead port on host.docker.internal drops packets rather than refusing them, so
the probe exhausts its 2 s budget instead of failing fast. Both are valid
ReadinessReason values from FW-READY and the distinction is real: `unreachable`
would need a host that actively refuses. Recorded as measured rather than as
expected.

ITEM 4 - A LOCAL SERVER MINTS LOCAL LINKS (R378)
------------------------------------------------

WHY PRODUCTION_ORIGIN WAS CHOSEN. lib/content/identity.ts records it only as
"the production origin, for FW28's environment checklist", and lib/auth/
request.ts used it with no note at the call site. The substantive reason is
the one the prompt states: App Links verify against the production host -
/.well-known/assetlinks.json is served from monreleve.ch - so a link on any
other origin opens a browser instead of the app. That reasoning is now written
at the call site, where it was missing.

THE CONDITION, AND WHY IT IS TWO THINGS:

    NODE_ENV === 'development'  AND  FRONTALIER_RUNTIME !== '1'

NODE_ENV ALONE IS NOT ENOUGH EVIDENCE, and the repository has already paid for
that: `next build` sets NODE_ENV=production too, and an earlier guard keyed on
it broke every local build (tasks/todo.md's FRONTALIER_RUNTIME entry). Here
the test runs the other way round - development rather than production - so
`next build` and `next start` are both correctly excluded. But "NODE_ENV
happens to say development" is a weak thing to hang a production URL on, so
the runtime marker is checked too: the Dockerfile's runner stage sets
FRONTALIER_RUNTIME=1 and `next dev` does not. A container whose NODE_ENV was
set wrong by hand still mints production links. The dangerous direction needs
both conditions to be wrong at once.

IT FAILS CLOSED. Anything that is not a confirmed dev server gets
PRODUCTION_ORIGIN, including an empty environment.

SHOWN TRUE UNDER pnpm dev AND FALSE UNDER THE BUILT SERVER,
tests/unit/auth/sign-in-origin.test.ts, 7 tests, `env` passed as a PARAMETER
so no case leaks into another file (R171):

  NODE_ENV=production                              -> https://monreleve.ch
  NODE_ENV=production + FRONTALIER_RUNTIME=1       -> https://monreleve.ch
  {} (nothing set)                                 -> https://monreleve.ch
  NODE_ENV=development + FRONTALIER_RUNTIME=1      -> https://monreleve.ch
  NODE_ENV=development                             -> http://localhost:3000
  NODE_ENV=development + PORT=3100                 -> http://localhost:3100

plus one test pinning PRODUCTION_ORIGIN to the literal https://monreleve.ch,
because the other five read the constant and would all still pass if it moved
- and the host App Links verify against is a published fact, not a setting.

THE PORT COMES FROM THE ENVIRONMENT (R170), not from the request, so a dev
server moved off 3000 mints a link that resolves to itself.

NOTHING IS LOAD-BEARING ON THE DEV ORIGIN as far as this session could
establish: no test reads the minted host, and App Link verification is a
property of the production host only.

4. .gitignore WAS SILENTLY SWALLOWING EVERY NEW KOTLIN SOURCE FILE, and this
   task's own test is how it surfaced. `git add` refused CodeCopyTest.kt:

       .gitignore:46:MonReleve/   android/app/src/test/kotlin/ch/monreleve/
                                  app/fr/CodeCopyTest.kt

   The pattern was added to ignore a stray Claude session directory AT THE
   REPOSITORY ROOT - its own comment says so. Unanchored, it matches a
   directory of that name at any depth, and git's ignore matching is
   case-INSENSITIVE here (core.ignorecase=true on Windows), so `MonReleve/`
   matched `ch/monreleve/`.

   ALREADY-TRACKED FILES WERE UNAFFECTED, because .gitignore does not apply to
   tracked paths - which is why every existing test in that package is in the
   repository and nobody had noticed. Only NEW files vanished, and they
   vanished SILENTLY: nothing fails, the file is simply not in the commit.

   Fixed by anchoring to `/MonReleve/`, which is strictly narrower and is what
   the comment already described. No directory of that name exists anywhere in
   the tree today, so nothing that was being ignored stops being ignored.

   OUT OF THE FOUR ITEMS, and done anyway: the alternative was committing this
   task with `git add -f` and leaving the next Android task to lose a file
   without noticing. PARK-F3 covers the guard this still lacks.

5. THE R378 PRODUCTION TESTS PASSED ON THEIR FIRST RUN and are worth less
   than the others because of it: before the change, signInOrigin did not
   exist and the call site named PRODUCTION_ORIGIN unconditionally, so every
   production case was true by construction. The two dev cases are the new
   behaviour and the four production cases are a fence around it. Stated
   rather than presented as six equal proofs.
