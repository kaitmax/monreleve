R947. WHERE IT RUNS (R251)
--------------------------
Established by reading the five container harnesses:
- container-e2e.mjs (test:container:e2e), container-write.mjs
  (test:container:write), container-scheduler.mjs (test:container:scheduler)
  and backup-restore.mjs (test:container:restore) each make a scratch
  database on the SHARED compose server (frontalier-postgres) or on one CI
  supplies. container-check.mjs (test:container) runs no database, by design.
- None owns a database's LIFECYCLE, and the shared server may never be
  stopped (other worktrees' scratch databases live there). So no harness
  could make this claim as written.
- The claim is about what the IMAGE SERVES, which is container-e2e.mjs's
  (R249: "the deployed artefact served the whole suite"), and that harness
  already builds the image for the suite's origin. container-write.mjs owns
  a production WRITE (R256), not this.
- So it EXTENDS container-e2e.mjs, through a module: container-e2e.mjs calls
  runDatabaseStoppedPhase() after its own teardown, on the same port,
  against the image it built. The step keeps its own resources, names and
  cleanup, apart from the harness's fixed ones (monreleve-e2e,
  monreleve_container_e2e).
- Why not a suite of its own: a new `test:*` script edits package.json, and
  package.json selects EVERY suite (R414) on that commit, with no start line
  for it; it would also need a CI step, MAPPING_TARGETS, EVERY_SUITE and
  SUITE_COUNTS. CI already runs test:container:e2e (the container-e2e job),
  so the step is in CI with no workflow change (CI is off, R248).
- The step runs WHENEVER THE IMAGE WAS BUILT, even when a step above it is
  already red, and its refusals join the harness's last line. Otherwise a
  first-failure-wins harness would answer "did the site survive the stop?"
  only on green runs.
