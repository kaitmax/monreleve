THE CODE ON THE SERVER (O1) - the limits chosen, and why; each test
--------------------------------------------------------------------
Additive to /v1 (nothing renamed, removed, or changed in meaning; the
App Link callback is byte-identical - R195).

SCHEMA (additive migration verification_token_code): VerificationToken
gains `code String?` (the six digits, stored as a SHA-256 hash, never in
clear - the same rule the link token follows) and `attempts Int @default
0`. ADD COLUMN only. The privacy map (personal-data.ts) classifies both
under the sign-in-link disclosure (they belong to the one sign-in
request); its schema-census test required it.

THE NUMBERS, stated (the relay asked):
  - SIX digits: a million combinations. Safe ONLY with an attempt limit.
  - MAX_CODE_ATTEMPTS = 5 wrong attempts per request, then the request
    is DEAD (too_many_attempts) - even the right code is refused, and
    the person asks for a new one. Five is forgiving of a phone mistype
    and leaves a guesser 5-in-a-million before the request dies.
  - EXPIRY = MAGIC_LINK_TTL_MS (15 min), SHARED with the link: one
    request, one lifetime.
  - The exchange endpoint's edge rate limit = 20 per 10-minute window,
    per address AND per network source. Set WELL ABOVE the per-request
    counter (5) deliberately: the counter is the real per-code guard;
    this backstop only stops a source hammering across requests, and a
    higher ceiling means an honest fat-fingered person meets
    too_many_attempts, never rate_limited. (checkRate gained an optional
    limit argument; the alert and sign-in-request forms keep the
    default 5.)

CONSTANT TIME: the submitted code is hashed and compared to the stored
hash with timingSafeEqual. SINGLE USE UNDER A RACE: the win is decided
by the count a conditional deleteMany returns, exactly as
consumeMagicLink decides it; the attempt slot is claimed by an ATOMIC
increment before the comparison, so parallel guesses cannot each read
the same low count.

NO ENUMERATION: an address with no pending request is refused
invalid_code, identical to a wrong guess (FW22's guarantee extended). A
VerificationToken row exists for ANY address that requested a link,
registered or not, so even code_expired and too_many_attempts reveal
only that a link was once requested - which anyone can cause for any
address - never that an account exists. The account is created at the
EXCHANGE, carrying only the address (like the callback).

EACH REFUSAL NAMED (R198): invalid_code (400), code_expired (400),
too_many_attempts (429), rate_limited (429), malformed_body (400). The
French messages say HOW TO RECOVER, never just "erreur".

THE EMAIL carries the code beside the link, in French, on its own line
(read from the fake outbox in dev). The code and the minutes are
per-request data passed as arguments, not stale-able constants (R153).

THE NAME (was it stored before? what was added)
--------------------------------------------------------------------
STORED BEFORE: YES, the column. prisma/schema.prisma:194 `name String?`
has existed since FW21, and lib/content/personal-data.ts already mapped
it. SETTABLE BEFORE: NO. No /api route wrote it (only the seed), and it
was DELIBERATELY excluded from PATCH and GET /api/v1/me (the read.ts
header said so). So there was no way for a real user to set a name, and
the PDF would 422 (titulaire_missing) for everyone.

ADDED (additive, no migration - the column existed):
  - web/lib/me/schema.ts: `name` in meObject - trimmed, non-empty once
    trimmed (a blank name is refused, because the dossier/PDF refuse
    without a titulaire, R205), capped at 120.
  - web/lib/me/read.ts: `name` in ME_FIELDS + serialiseMe, so GET /me
    returns it. The header now explains WHY (R297 skip; owner's own
    data behind their own bearer; email stays absent). me-route.test.ts
    updated: GET returns the name, never the email; PATCH sets/trims it,
    refuses a blank, leaves other settings alone (RED then GREEN).
  - docs/api-v1.md section 9: name is settable and returned.
  - Android: Settings gains a nullable `name` (last, defaulted so every
    positional caller is unchanged); mePatchBody sends it when set,
    omits it when absent (the server requires non-empty); parseMeSettings
    reads it back; SharedPrefsSettingsStore persists it; onboarding step
    1 collects it. MeSettingsTest updated (RED then GREEN).

THE PDF GENERATES WITH IT: web/app/api/v1/export/pdf/route.ts holds the
R205 guard (selects name; 422 titulaire_missing before launching
Chromium if titulaireOf(name) is null; renders when present).
web/lib/dossier/service.ts titulaireOf + MissingTitulaireError +
buildDossier use the name as the titulaire. Unchanged by this task and
still green. PROVEN end to end on the device: after onboarding, the
scratch database held User.name = "Camille Martin".
