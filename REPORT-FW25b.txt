WHY CHROMIUM AT ALL, recorded because it will be asked again: the
print route IS the document. A PDF library would be a SECOND
implementation of the layout, and then the browser and the accountant
would look at two documents that agree only while somebody keeps them
agreeing.

IDENTITY TO THE BROWSER
--------------------------------------------------------------------
The route mints the short-lived (person, year) print token FW25 built,
and puts it in the URL Chromium navigates to.

Chromium is a separate process and does not share the request's
Authorization header. The alternative - an extra HTTP header set on
every navigation - leaks to any redirect target and teaches the print
route a second authentication mechanism.

The credential was already in a URL for a reason that PREDATES this
route: a human has to be able to open the document, and a browser
sends no Authorization header for a typed URL.

THE ORIGIN IS THE REQUEST'S OWN, not a configured base URL. The
browser runs on the same host as the server it fetches from, so the
address the request arrived on is the address that works - including
behind a proxy, where a configured public URL would send the render
out through the internet and back (R171).

CONCURRENCY
--------------------------------------------------------------------
One render slot, a waiting room bounded at 2, and a 30 s deadline.

MEMORY MEASURED: one render peaks at 279.9 MB resident across 4
processes, sampled every 200 ms while the route printed a year. The
browser is a TREE - shell plus renderer and GPU children - so summing
only the parent would have under-reported it.

  THE FIRST MEASUREMENT SAID 0 MB AND WAS WRONG. It matched processes
  named `chrome`; Playwright 1.63 runs headless through
  `headless_shell.exe`. 340 samples found nothing and printed zero,
  which reads exactly like a result rather than like a miss. The
  sampler now matches on the executable PATH and reports whether it
  saw the browser at all - R133's positive signal, on a measurement.

WHY BOUNDED AND NOT MERELY SERIALIZED: a mutex alone converts
concurrency into latency, which sounds like the safe failure until you
follow it - each waiting request holds its connection, its context and
its computed payload, so the queue is itself a memory cost and the
machine OOMs anyway, later and with a symptom pointing elsewhere.

R198: renderer_busy (retry-after 30) and renderer_timeout (retry-after
60) are separate codes. Turned away at the door and waited-then-gave-
up call for different client behaviour.

THE `finally` HAS ITS OWN TEST. Without it one failed render holds the
only slot for ever, every later export queues behind it, and the route
answers 503 indefinitely while nothing is running - "exports stopped
working" on a machine that looks healthy.

THE FONT ASSERTION IS NOT A /FontFile CHECK, and the distinction was
earned. Chromium writes /Subtype /Type3 fonts for the variable Inter
family - each glyph is a drawing procedure under /CharProcs - so this
document has NO /FontFile and is nonetheless fully embedded. A
/FontFile assertion would have FAILED on a correct document, and the
tempting fix, deleting it, would have removed the only guard against
the real defect: a font named but not carried, which renders in
whatever the opening machine happens to have.

THE EXTRACTOR MAPS PER FONT, and the first version did not. Merging
every ToUnicode CMap into one table produced 2 conflicting glyph ids
of 62 - 0x17 was both "E" and ",", 0xcf both "p" and a no-break space,
which is why the rate first extracted as "100p%". Two is a small
number and the wrong thing to reason about: that text is what the
banned-word assertion runs on, so a table that can turn one letter
into another can hide the word it is looking for.

IT REFUSES A SUSPICIOUSLY EMPTY RESULT (R154). An extractor that
silently yields "" makes every absence assertion pass, and "no banned
words in this document" is satisfied perfectly by a document nobody
managed to read.
