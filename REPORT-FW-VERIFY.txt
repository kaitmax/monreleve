THE ISSUANCE RECORD (R329) - fields, migration, erasure
====================================================================
MODEL IssuanceRecord (prisma/schema.prisma), migration
20261006071936_verification_issuance_record:
  code                   String  @unique  - the public identifier, 128 random
                                            bits as hex (newVerificationCode =
                                            randomBytes(16).toString('hex')).
  userId, taxYear, version
  supersededAt           DateTime?        - null while current; set to the NEXT
                                            version's generatedAt when superseded
  name                   String           - the name AS PRINTED
  declarableRate, teleworkDays, missionDaysFrance, missionDaysThirdState  Float
  periodFraction Float, periodStartDate String?   - DossierPeriod's own fields
  sha256                 String           - SHA-256 (hex) of the produced PDF
  generatedAt            DateTime         - server clock = the printed date
  createdAt              DateTime @default(now())
  @@unique([userId, taxYear, version]); @@index([userId]);
  onDelete: Cascade from User.

R196 INVARIANT IN THE DATABASE: the migration adds a PARTIAL unique index
  CREATE UNIQUE INDEX IssuanceRecord_one_current_per_year
    ON "IssuanceRecord"("userId","taxYear") WHERE "supersededAt" IS NULL;
so "at most one current version per (account, year)" survives any writer, not
only recordIssuance's transaction. Proven both ways in tests/db/issuance-
record.test.ts (a second current row is refused by the database).

WRITTEN WHEN THE FILE IS PRODUCED: the PDF route (app/api/v1/export/pdf/route.ts)
assigns the instant and the code once, builds the dossier with that instant,
passes the instant (and the code) into the print URL so the printed date equals
the record's, renders, hashes the produced bytes, and calls recordIssuance in a
transaction that supersedes any current version with the NEW row's generatedAt.
IF RECORDING FAILS, THE DOCUMENT IS NOT RETURNED (code record_failed) - an
unrecorded releve is one nobody can verify. Figures are DERIVED from the dossier
(figuresFromDossier, R181), never transcribed; the mission split is summed from
the dossier's months.

ERASURE (R203/R329): IssuanceRecord carries a userId and cascades, so it joins
FW26's schema-derived negative sweep automatically; the receipt also counts it
(lib/account/delete.ts, removed.IssuanceRecord). It is also in the account
EXPORT (lib/account/export.ts, key 'issuances') - the person's own data, with
the code, so they keep the means to verify documents they have shared. The
export census (account-export.test.ts) and the whole-schema table-list censuses
(alert-subscriber.test.ts, fw14-era-migration.test.ts) were updated.

TESTS: tests/db/issuance-record.test.ts - newVerificationCode is 32 hex / 128
bits and non-repeating; sha256Hex matches node crypto; v1 current with all
printed fields + file hash; regenerate -> v2, v1 supersededAt = v2's instant;
at most one current per year; years independent; the partial index refuses two
currents. RED first (missing module/model), then GREEN. Route integration (hash
of the returned bytes, v2 supersedes v1) is in export-pdf.test.ts, live-gated.

NAME CHANGES (R331)
====================================================================
MODEL NameChange { id, userId, changedAt DateTime @default(now()) }, migration
20261006094423_name_change_dates. DELIBERATELY NO column for the former value -
the harm (a maiden or pre-transition name on a tax document) is designed out,
not guarded against. Cascades + joins the sweep + export (key 'nameChanges',
dates only) + receipt.

RECORDED on a REAL change only: PATCH /api/v1/me (app/api/v1/me/route.ts) now
selects the current name and, in the SAME transaction as the update, inserts a
NameChange iff an existing non-empty name becomes a different one. A first-time
set (onboarding) records nothing; re-sending the same name records nothing.

THE DOCUMENT LINE: buildDossierFor queries the latest NameChange WITHIN the tax
year (a coarse UTC calendar-year window) and passes the date to buildDossier,
which puts it on Dossier.nameChangedAt (an ISO day, NOT on the /v1 wire). The
print route renders one line in the identification block - "Nom modifie le
<date>" - as a second <dd> under the Nom term, only when the name changed in that
year. It NEVER renders a former name; the dossier never carries one (NameChange
has no value column, and the query selects only changedAt).

TESTS (tests/db/name-change.test.ts, RED then GREEN): a real change records one
row and no former value; a first-time set and a same-value re-send record none;
a second change is a second row; a dossier for the change's year carries the
date and the current name with the former name absent from the whole payload; a
prior year's dossier carries no date.

THE DOCUMENT (the decoded QR)
====================================================================
The releve prints a verification block ONLY when the permanent origin is set
(R332, below): the code as TEXT (for anyone who cannot scan), the verification
address, and a QR - all pointing at the same URL,
https://<origin>/verifier/<code>.

DECODED FROM THE PRODUCED FILE (R232), validated LIVE against pnpm dev with
MONRELEVE_VERIFICATION_ORIGIN=https://monreleve.ch:
  tests/db/verification-qr.test.ts PASSED. The QR was extracted from the
  produced PDF's embedded image XObject (tests/db/support/pdf-image.ts: Node
  zlib inflate + PNG-predictor un-filtering + RGBA; no pdfjs, no native canvas)
  and decoded with jsqr to EXACTLY
    https://monreleve.ch/verifier/f18c9d3a78234267667e0f18e786bf5d
  for a run whose stored record carried that same code. The printed address and
  code text were also found in the extracted PDF text.

DEV DEPENDENCIES (R136), named and justified:
  qrcode (RUNTIME) - the QR encoder; the print route renders a PNG data URI at
    render time, only when the origin is set. No built-in encoder exists and
    hand-rolling Reed-Solomon is not sane.
  jsqr (DEV) - the QR DECODER the prompt pre-authorises; reads the QR out of the
    produced PDF.
  @types/qrcode (DEV) - types for qrcode.
  (No PDF library added: support/pdf-image.ts recovers the image with Node's own
  zlib, so the proof stays on the produced file without pdfjs/native canvas.)

The extractor handles the shape Chromium writes for a lossless image (FlateDecode,
8 bpc, DeviceRGB/Gray, PNG predictor or none); a shape it does not handle returns
null and the test says so rather than guessing. This proved sufficient against
the real Chromium output.

THE VERIFICATION PAGE (R330)
====================================================================
app/(public)/verifier/[code]/ - force-dynamic, in the public group (inherits the
shell), noindex via its own metadata, zero cookies, no client JS.

PRIVACY BOUNDARY AT THE SOURCE: lib/verification/lookup.ts selects ONLY the
printed columns and NO relation - the email is never loaded, so it cannot be
rendered. It returns the printed fields or null; a malformed code returns null
WITHOUT touching the database. Unknown, withdrawn (erased) and malformed all
resolve to the one neutral null by one path - no content or timing difference.

The page shows: name, taux a declarer (2 dp, as filed), teletravail days,
missions in France and in third states, the period (the document's own sentence,
derived from DOSSIER_COPY - R181), the generation date, the version, and a
"newer version issued on <date>" notice when supersededAt is set (the date only,
never the newer version's figures). The vouch says the document CORRESPONDS to
the one issued; it never says certifie/atteste/conforme/valide/approuve.

TESTS:
  tests/db/verification-lookup.test.ts - the printed fields are returned; the
    account email is NEVER in the view (seeded a known email, asserted absent,
    presence-first); the supersession instant is carried; null for unknown and
    for malformed codes.
  tests/unit/pages/verifier.test.tsx - the Content render (jsdom): the printed
    fields present; a FORMER name never appears (it only renders the view given);
    the superseded notice appears only when supersededAt is set; the neutral
    unknown page; the rate-limited page (does not leak the unknown wording); NO
    banned word.
  e2e/verifier.spec.ts (single-file playwright, ran green) - a code with no
    match gets the neutral page SERVED, carries meta robots noindex, and sets
    NO cookie (context.cookies() == []).

EMAIL-ABSENT: proven at the source (lookup never loads it) and on the rendered
HTML (the walkthrough's /verifier fetch: email absent == true). FORMER-NAME-
ABSENT: proven in the unit test and live in the walkthrough (step 4).

RATE LIMIT: the page calls checkRate(clientKey(headers()), limit 30) before the
lookup (lib/alerts/rate-limit.ts, the existing in-memory per-address limiter);
over the limit it renders the neutral rate-limited page. 30 is above a
fiduciaire's honest burst and the real anti-guessing defence is the 128-bit code.

R332 - WHAT THE PDF SHOWS TODAY, WITHOUT THE PERMANENT DOMAIN
====================================================================
By DEFAULT the PDF carries NEITHER the QR, NOR the printed address, NOR the code
text. lib/verification/origin.ts reads MONRELEVE_VERIFICATION_ORIGIN and returns
a believable https origin or null; it refuses http, localhost/loopback, a
non-bare origin (path/query/fragment), and unset. The print route renders the
block only when the origin is believable AND a code was issued.

VALIDATED BOTH WAYS live:
  origin UNSET  -> tests/db/verification-qr.test.ts default-off block PASSED
                   against pnpm dev with no origin: the produced PDF contains the
                   title but NOT the verification heading, and extractFirstImage
                   returns null (no raster image).
  origin SET    -> the QR-decode block PASSED (above).

This is a NEEDS item for release: the permanent production origin must be chosen
and MONRELEVE_VERIFICATION_ORIGIN set before the QR/address can print. Recorded
here and in .env.example-adjacent reasoning (the var is documented in
lib/verification/origin.ts). A releve must never point at localhost or a host
the operator may not keep (R205), which is why the default is off.
