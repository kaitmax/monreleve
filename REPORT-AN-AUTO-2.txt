R320 - THE WINDOWS, THE VOTE, THE MIGRATION, THE PROTOCOL (the operator's decision, done first)
----------------------------------------------------------------------------------------------
FOUR WINDOWS (detection/CheckWindows.kt), Europe/Paris, chosen to avoid lunch:
  09:30  11:00  14:30  16:30, each +/- 30 minutes (a 60-minute window).
WINDOW LENGTH, and why 60 minutes: WorkManager delivers background work no more often than
every 15 minutes and cannot promise an exact time (the exact-alarm permission is restricted and
is NOT requested, R320), so a window must hold several wake opportunities; 60 minutes holds about
four at the 15-min cadence and keeps the windows disjoint and clear of lunch (window 2 ends 11:30,
window 3 opens 14:00, so 11:30-14:00 is never sampled). A check runs anywhere inside its window;
a check that cannot run inside its window is MISSED (null), NEVER taken late - a fix whose instant
falls outside every window is ignored (DetectionSession.onFix / the worker), so an 11:00 check
delayed to 13:00 does not sample lunch.

THE VOTE (detection/Vote.kt), replacing the minutes-and-hysteresis tally in the product path.
AN6a's polygon and 150 m border-strip classifier are UNCHANGED (Classification stays
INSIDE/OUTSIDE/BUFFER); only how a day is DECIDED changed:
  HIGH   >= 3 checks taken, ALL the same side, none in the strip;
  MEDIUM >= 3 taken, exactly one on the other side or in the strip;
  LOW    anything else.
One bad GPS reading can never decide a day alone (a lone dissenter drops HIGH to MEDIUM, two drop
it to LOW). Half-day granularity: each half is decided from its own two checks (AM = checks 1-2,
PM = checks 3-4) - both taken, both the same side, neither in the strip, else not sure. Under R311
only HIGH proposes; MEDIUM/LOW show the not-sure message. JVM tests cover EVERY vote case incl. a
missed check and a check outside its window (VoteTest, CheckWindowsTest, DetectionSessionTest).

R313 TRANSLATED: a day is near-border when >= 2 of its 4 checks land in the strip (50 %, above the
40 % MEDIUM ceiling); told on 3 of the last 5 working days with data (NearBorder.kt, NearBorderTest).

check1..check4 (TEXT, nullable; a Classification name or NULL=MISSED). MIGRATION_3_4 (DB version 4)

AUJOURD'HUI AUTOMATIC
---------------------
The controller reads today's four checks and renders the vote's outcome, honouring granularity:
  DAY granularity    -> one surface: HIGH -> "Proposition - verifiez" + the proposed kind + Confirmer
                        (DETECTED_CONFIRMED) / Corriger (DETECTED_CORRECTED + detectedKind, R202), one
                        tap, nothing written without it (D16); not sure -> R312 message + manual choices;
                        near-border -> R313 message once + the choice.
  HALF_DAY granularity -> the morning (checks 1-2) and the afternoon (checks 3-4) each get their own
                        surface, confirmed/corrected on their own slot. This is new in R320 (AN-AUTO's
                        continuous path could not split AM/PM and recorded a full day).
Nothing is proposed until the day is concluded (after the last window, the evening - "Votre journee
vous sera proposee ce soir."). The tier is WORDS, never a percentage (R27); no map, no position, no dot.
AujourdhuiAutoControllerTest covers day + half-day + confirm/correct provenance + near-border-once.
The existing day-granularity paparazzi baselines are UNCHANGED (the render is pixel-identical; the
refactor only threaded a slot and bundled the callbacks) - verified by :app:gate's paparazzi verify.
