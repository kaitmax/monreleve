R861 - A KEY REFUSAL THAT SAYS WHICH RULE FAILED, NEVER THE VALUE
--------------------------------------------------------------------------------
readFcmCredentials's malformed_private_key now carries `detail`, the first
shape the restored, trimmed key fails. The order is the contract: the
outermost cause wins.
  quoted                   wrapped in matching quotation marks
  backslash_after_restore  a backslash left after \n was restored
  no_pem_header            "-----BEGIN PRIVATE KEY-----" nowhere
  text_before_pem_header   the header present, something before it
  no_pem_footer            "-----END PRIVATE KEY-----" nowhere (cut short)
  text_after_pem_footer    the footer present, something after it
The startup line (describePushSender(resolvePushSender()), instrumentation.ts
54) reads, for example:
  [push] no push sender (malformed_private_key: quoted): FCM_PRIVATE_KEY is
  wrapped in quotation marks: the value starts and ends with the same quote
  character. The daily reminder will NOT be scheduled. ...
The not_configured and placeholder_credentials lines are byte-identical to
before, pinned by a test. No route serialises the refusal: grep of app/ and
lib/ finds it only in logs and the scheduler's skipped reasons.

THE "LITERAL BACKSLASH-N LEFT AFTER THE RESTORE", AS THE CODE CAN SEE IT.
replaceAll leaves no literal \n. A key escaped twice (\\n) restores to a lone
backslash before a real newline, so the shape tests for a lone backslash. A
PEM key never contains one. With a trailing newline, such a key ends in a
backslash, which a footer-first rule would have misreported as "text after
the footer". The backslash test runs first, and a test pins that.
