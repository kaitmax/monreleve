1. THE BURGER
====================================================================
WHAT WAS WRONG. The phone menu had been a React useState disclosure
since FW9: the panel was rendered as `{menuOpen ? <div/> : null}`. With
scripting disabled the button was inert and a phone reader had no
navigation at all. Every existing check passed, because jsdom runs the
handler and Playwright's default context runs the script - the two
environments that cannot see the defect.

WHAT IT IS NOW. A native details/summary in the SHARED header, so every
page gets it:
  - summary: 44 x 44, --radius-md, 1 px --colour-border-strong, the
    Lucide menu glyph at --size-icon-lg in --colour-brand, aria-label
    "Ouvrir le menu". list-style: none AND ::-webkit-details-marker are
    both suppressed - the two engines hide the disclosure triangle
    through different properties, and without both a stray arrow sits
    beside the hamburger.
  - panel: absolute (design/home), so opening it does not push the page
    down; --size-menu-panel-width, --radius-lg, 1 px border.
  - rows: SHELL_NAV's entries in SHELL_NAV's order, 44 px each with a
    rule between and none under the last, then MENU_ACTION
    ("Calculer ma situation") as a 48 px brand-filled action.
  - above the breakpoint the WHOLE disclosure is display:none, not just
    the summary: with details/summary the panel is in the markup whether
    or not it is open, so hiding the button alone would leave an opened
    panel on screen after a resize.
  - Escape remains a script - a progressive enhancement over markup that
    already works without it - and returns focus to the summary.

MENU_ACTION's HREF IS DERIVED, NOT TYPED. It reads TELEWORK_CALCULATOR's
own path, the object the nav and footer already share, so the menu
cannot come to point somewhere other than the navigation above it
(R206). SPEC 14 freezes that slug, which is exactly why it is not
retyped. Only the label is new copy.

TWO THINGS GIVEN UP, BOTH DELIBERATE AND BOTH RECORDED IN THE SOURCE:
  - The trigger no longer renames itself "Fermer le menu". A summary
    cannot, without the script this exists to do without. It costs
    nothing a reader relies on: the browser reports expanded/collapsed
    from the element itself, which is more than a swapped label ever
    told anyone. SHELL_COPY.menuClose is now unused by the component and
    is left in lib/fr (nothing else referenced it).
  - The panel takes its own landmark name, SHELL_COPY.menuNavLabel
    ("Menu principal"). Both navigations are in the document at every
    width - the inapplicable one is display:none, so a browser keeps it
    out of the accessibility tree - and two navigation landmarks
    announced by the same name is a defect the moment a stylesheet fails
    to load, which is the state this whole task is about.

POSITION KEPT, NOT MOVED. design/home draws the hamburger on the RIGHT;
FD2 draws it first/left and FW9's comment records that as deliberate
("the thing that reveals the navigation before the navigation"). The
prompt names the fold behaviour, not the position, so the conservative
option was taken: FD2's position stands. Recorded under DEVIATIONS.

2. THE VISUAL SUITE WAS CERTIFYING CHANGES IT COULD NOT SEE
====================================================================
THE SYMPTOM. With the burger built, pnpm test:visual reported 3 failed /
108 passed. The header had changed on every page; 34 phone baselines
should have failed. The run was repeated and reported 3 failed / 108
passed again - deterministic, not a flake.

WHY IT WAS NOT ACCEPTED. The container had plainly rendered the change:
its failure artefact for composants-shell-mobile-open showed the new
bordered button and the new panel. Yet composants-shell-mobile - the
same specimen, the same viewport, 1.7 s apart in the same run - passed
against a baseline showing the old borderless hamburger. Cropping the
two at identical dimensions (312x1255) showed a bordered button against
a borderless one. Independently, the computed style on a served page
gave `1px solid rgb(208, 213, 221)` in `rgb(23, 59, 99)` at 44 px, on
/tarifs as well as /.

THE CAUSE. playwright.config.ts set no expect.toHaveScreenshot, so
Playwright's DEFAULT applied: threshold 0.2, a 20 % per-pixel colour
allowance (its own types: "defaults `threshold` value to 0.2"). A pixel
counts as different only when its YIQ delta exceeds the threshold. The
pixels this change touched sit under it:
    new border --colour-border-strong on white   delta 0.119
    glyph --colour-brand over --colour-text-primary  delta 0.098
So every pixel of the burger's header change was inside the vendor's
default tolerance, and 34 baselines were certified unchanged.

WHY NO GUARD CAUGHT IT. tests/unit/meta/visual-zero-tolerance.test.ts
asserts R114 - "a visual baseline runs at zero tolerance" - by scanning
for the words maxDiffPixels / maxDiffPixelRatio / threshold / mask, and
its last test required playwright.config.ts to contain NONE of them. So
`threshold: 0`, the one line that makes the claim true, was the one line
the guard rejected. Declining to configure a tolerance is not zero
tolerance; it is the vendor's. An absence assertion satisfied by
absence (R154's class).

WHY IT WAS BLOCKING RATHER THAN A SIDE QUEST. --update-snapshots only
rewrites a baseline whose comparison FAILS. The 34 could therefore not
be regenerated at all: the picture was frozen. B4 ("every phone baseline
regenerated against its list") was unachievable without fixing this.
This is the guard file's OWN header story - maxDiffPixels: 600 freezing
six calculator baselines in FW13 - one layer down: FW13 removed the
explicit allowances and never set the default to zero, closing the
explicit hatch and leaving the implicit one open.

THE FIX, test-first:
  1. The config guard was REPLACED, not supplemented (R268 - two tests
     bounding one property is a reader's trap). It now reads the VALUES
     off the config object - expect.toHaveScreenshot.threshold === 0 and
     maxDiffPixels === 0 - rather than grepping the source, because a
     scan cannot tell `threshold: 0` from `threshold: 0.2`.
     RED: "playwright.config.ts sets no expect.toHaveScreenshot, so
     Playwright applies its own threshold of 0.2".
  2. playwright.config.ts now states threshold: 0, maxDiffPixels: 0.
     GREEN, 9 passed.
  3. The compare then reported 39 failed where 3 had been.
The per-spec half of the guard is unchanged: per-call tolerances are
still forbidden, and stylePath remains R114's sanctioned answer to
genuine environmental instability.

R267 - SECOND SITES CHECKED. playwright.runtime.config.ts takes no
screenshots (no toHaveScreenshot caller outside e2e/*.visual.spec.ts and
this guard), so it needs nothing today; if it ever captures one it would
inherit the same default, which is worth knowing. e2e/baseline.ts's
header claimed a tolerance "is a compile error rather than a test
failure" - true of call sites, and never true of the project, since a
type cannot reach a default nobody wrote. It now says so.

THIS DESERVES A RULING NUMBER, which is the operator's to assign. The
proposed statement: A DEFAULT IS A SETTING NOBODY CHOSE. Where a tool
applies a tolerance, a timeout or a limit unless configured, the project
STATES the value it wants and a test asserts that VALUE - never the
absence of the word. A guard that forbids writing the setting forbids
fixing it.

3. R344 - A TOKEN IS CHOSEN BY MEANING
====================================================================
Recorded in DESIGN-SYSTEM.md beside R77, with its own paragraph and the
explicit limit that it is not a licence to mint a token per declaration:
a value belonging to a scale takes the scale's step, and the radius set
stays closed at nine names.

FW34's TOKENS list, gone through entry by entry.

REPLACED (the name did not mean the use):
  .phone max-width      --size-toc-column (280)
                     -> --size-phone-frame-width (300)
     The hero's phone card is a PICTURE OF THE APPLICATION. It was sized
     by the guides' table-of-contents column because that token happens
     to carry 280, so widening the table of contents would have resized
     the illustration. The prompt names this one.
  .phoneCaption max-width  same swap - it means "as wide as the phone".
  .phone border         --space-2 (8) -> --size-phone-bezel (10)
     A SPACING step used as a stroke width: a category error before it
     is a value one.
Both take the approved design's figure (R77), not the nearest token's,
so the substitutions' 280 and 8 become 300 and 10.
--size-menu-panel-width (300) is the burger's own, and is a second name
for the same number on purpose (R68: distinct names where values
coincide) - a menu panel and a phone frame move independently.

KEPT, each because the name means the use:
  --size-button-large-height on a button; --size-input-height on an
  input; --size-toast-min-width on the phone card's notification (a
  notification is what a toast is); --radius-2xl on a frame radius (the
  radius set is closed, R64/section 4.1); the spacing and type scales,
  which are scales.
  --colour-france-soft on the hero eyebrow: the eyebrow reads "Pour les
  frontaliers France - Suisse", so the France tint means its use. The
  alternative - a new brand-soft COLOUR - is a palette addition rather
  than a component dimension, and is not what R344 authorises.
