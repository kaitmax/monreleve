SUMMARY
====================================================================

POST /api/v1/entries RETURNS 200 AND WRITES ITS ROW ON A PRODUCTION
BUILD. It had returned 500 with zero rows since 13 September.

  test:container:write   4 failures -> 10 passed
  connections over 60 requests   +96 -> +1
  CI container job       never passed -> PASSED with CI=1
  /api/v1 routes documented      9 of 13 -> 13 of 13

THE CAUSE TOOK BOTH HALVES, and the brief's account of the second was
WRONG IN ITS MECHANISM. FW30 said `Reflect.get(client, property,
receiver)` passed the Proxy as `this`. Read from the shipped runtime:
Prisma 7's constructor ends `return this._appliedParent = <composite
proxy>`, and that proxy's trap is `get(o,s)` - TWO PARAMETERS, THE
RECEIVER DISCARDED. The third argument was inert. The real mechanism
is that the trap returned an UNBOUND function, and
`prisma.$transaction(cb)` binds `this` to the outer Proxy by ordinary
method-call semantics whatever the trap was told; Prisma then read
this._engine and a dozen more back through the trap, and with
memoisation skipped each re-entry built a DIFFERENT client.

THE CONDITION WAS THE FINDING, AND IT IS THE PART THAT IS FIXED FOR
GOOD. Dev and test memoise; gate:clone skipped the container suites;
CI's container job had never passed; container-e2e.mjs never POSTs an
entry; and no e2e spec touches /api/v1 BY DESIGN since D14 removed
the signed-in web area. Five layers, each individually reasonable,
and the intersection was a hole the size of the product's main use
case. gate:clone now builds the image and writes through it.

AND THE WALKTHROUGH FOUND A SECOND THING NOTHING HAD DRIVEN. THE
TITULAIRE CANNOT BE SET THROUGH ANY ROUTE, so a client that signs in,
configures everything the API exposes and records a year of days
still receives 422 titulaire_missing when it asks for the Releve
annuel - forever. Demonstrated with a control: the same request is
422 without a name and 200 with one, and the only change between them
is a column write no client can perform. PARK31-6, parked because
R255 binds and this task was given three findings. IT IS THE ONE TO
ANSWER FIRST.

F-CI - one paragraph, and it is FIXED rather than parked
====================================================================

playwright.config.ts set `reuseExistingServer: !process.env.CI`, and
scripts/container-e2e.mjs starts the image on port 3100 and then runs
that suite against it. In CI reuse was off, so Playwright insisted on
starting its own server, found the port held BY THE CONTAINER IT WAS
MEANT TO TEST, and refused before a single spec executed - "Error:
http://localhost:3100 is already used". The suite was STRUCTURALLY
INCAPABLE of passing in CI and never once did, which is why FW30
could find three consecutive red runs on main with seven of eight
jobs green. The paragraph directly above that line argues that reuse
is safe now because R169's global setup refuses any server not naming
this product - and then the clause disabled it in exactly the
environment where the harness depends on it. The fix is not to widen
reuse generally but to let the process that STARTED the server say
so: FRONTALIER_SERVER_IS_OURS=1, set by container-e2e.mjs, honoured
by the config, with R169 still verifying the claim before any spec
runs. VERIFIED BY REPRODUCING CI's CONDITION - `CI=1 pnpm
test:container:e2e` now ends "CONTAINER E2E PASSED - the deployed
artefact served the whole suite (R249)", plus nine auth round-trip
tests over HTTP against the image.

WHAT WOULD HAVE CAUGHT THIS EARLIER
====================================================================

ONE TEST THAT DROVE THE PRODUCT'S MAIN USE CASE AGAINST A PRODUCTION
BUILD - and nothing else would have, which is the part worth
carrying forward. More unit tests would not have: the defect could
not exist under NODE_ENV=test. More guards would not have: every
guard this project owns was green throughout, and several of them
were green ABOUT THIS FILE. More CI would not have: the container job
never ran, and even green it would not have helped, because
container-e2e.mjs never POSTs an entry. The project had container
suites and it had write tests; what it did not have was one test at
the INTERSECTION, and the intersection was the only place the defect
lived. The generalisable form: WHEN A DEFECT CAN ONLY EXIST IN ONE
ENVIRONMENT, COVERAGE MEASURED IN ANY OTHER ENVIRONMENT IS NOT
EVIDENCE ABOUT IT - and a suite's environment is a property nobody
lists beside its name, so the gap is invisible in every coverage
report. R177 said a suite that only sees built output cannot tell you
the development path is broken; nobody had written the inverse, and
the inverse is where the product lived. The cheapest closure is the
one now in gate:clone: build the image, sign in, write one row, read
it back from the database. It costs 102 seconds warm and it is the
only thing in this repository that makes a claim about production.
