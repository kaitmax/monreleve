THE DEFECT (R322) - F-DETECT-GPS, fixed test-first (incr 1)
----------------------------------------------------------
CAUSE (from AN-AUTO-2's diagnosis, re-confirmed LIVE this session before touching anything): the
SamplingWorker runs every window (logcat SUCCESS, standby bucket WORKING_SET), and the Paris-window
logic is correct, but LiveLocation.awaitClassifiedFix requested LocationManager.GPS_PROVIDER ALONE.
Indoors - where a telework day is spent, the exact day detection most needs to classify - GPS returns
no fix, awaitClassifiedFix times out and returns null, recordCheck is NEVER called, and no daily_tally
row is written. Re-confirmed on the phone this session (no reinstall, read the current build): the
pulled Room DB held rows for 2026-09-28..10-02 (the A4 seed) and NONE for 2026-10-03 (today), despite
the worker having run all morning. The defect is live and reproduced.

FAILING TEST FIRST: tests/.../detection/LiveLocationFallbackTest.kt exercises the extracted fallback
ORCHESTRATION firstClassifiedFix(providers, fix). RED run (shown): "Unresolved reference
'firstClassifiedFix' / 'FIX_PROVIDERS'" - the fallback did not exist. Then GREEN after the fix. Cases:
GPS silent records nothing (the defect); the NETWORK fallback records when GPS is silent; GPS present
short-circuits and NETWORK is never consulted (precision preferred for the 150 m buffer, D25).

THE FIX (conservative, reversible - R156): awaitClassifiedFix now tries FIX_PROVIDERS = [gps, network]
in order and stops at the first classified fix, via the pure firstClassifiedFix. GPS first (the buffer's
precision); NETWORK (wifi/cell) as the indoor fallback. NETWORK works indoors, is already covered by the
ACCESS_FINE_LOCATION grant, and needs NO new dependency - no Play Services / FusedLocationProviderClient
(R136). Each provider's fix is classified and the coordinate discarded in the same breath (D18 intact;
requestOneFix is the one place a coordinate briefly exists, as before). The dev-replay helper
classifyCurrentLocation is left on GPS (the mock replay drives a GPS test provider) - the narrow change.
RECORDED ALTERNATIVE (R156): accepting GPS-only remains the operator's option - detection would then
serve outdoor/commute days and home days would fall to manual (a peer, D19). This fix is the
conservative-reversible choice; it is one provider in a list and trivially reverted.

R323 - ONE EVENING NOTIFICATION FOR THE PROPOSAL (incr 3, PARKAN-36)
-------------------------------------------------------------------
Each rule, and where it is enforced:
  - AT MOST ONE per working day / after the day concludes / only if no entry yet / never on a non-working
    day / only in auto mode / only when opted in: the PURE eveningDecision(EveningConditions, outcome),
    unit-tested six ways (EveningNotificationDecisionTest, test-first RED->GREEN). "Working day" = weekday
    (Mon-Fri), the calendar's existing WEEKEND convention (R206-adjacent). "At most one" = the store's
    last-notified day. "Only in auto mode" is the conservative reading of "separate from automatic mode"
    (judgment call below).
  - OPT-IN, separate, off by default: EveningNotificationStore (SharedPrefs, shares monreleve.detection so
    sign-out's clear sweeps it). The Parametres toggle « Me prevenir le soir » shows only when detection is
    on (without detection there is nothing to propose). Asks POST_NOTIFICATIONS only when switched on and
    only on API 33+ (MainActivity launcher); API < 33 (the S9 is 29) enables with no ask - both paths coded.
  - LOCK SCREEN SHOWS NOTHING PRIVATE: the posted notification is VISIBILITY_PRIVATE with a PUBLIC VERSION
    that reads only that a proposal waits (NotificationCopy.publicLines); unlocked it names the side (En
    Suisse / Domicile, reused from AujourdhuiCopy, R206). Channel lockscreenVisibility = PRIVATE.
  - A "not sure" day gets the SAME single notification inviting manual recording.
  - Tapping opens Aujourd'hui (EXTRA_OPEN_AUJOURDHUI, consumed once in MainActivity); nothing is recorded
    from it (D16). Fence 7 holds: the glue reads entries via the DAO, never EntryRepository/RecordCommand.
  - Trigger: folded into the SamplingWorker's post-window wake (maybeNotifyEvening), self-gating - no new
    scheduler, no new dependency (R136). French from fr/; notification copy reachable from the background
    notifier and allowlisted in CopyReachabilityTest (the Toast pattern); the toggle copy is reached from
    ParametresScreen. R282 untouched: the toggle is a « proposition », worded without « rappel »/
    « notification », because the rules forbid a nagging reminder - it is not one.
