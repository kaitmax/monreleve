SUMMARY
--------------------------------------------------------------------------------
THE ONE FINDING THAT GATES A RELEASE is F4 (HIGH): an expired or revoked session
does not clear the offline queue, so one account's queued days drain into the
NEXT account that signs in on the same device. CONFIRMED ON-DEVICE this session -
account A's two offline days landed under account B's server record (Postgres
oracle: B owns 3 days, A owns 0, CROSS_ACCOUNT_LEAK = true, drained via POST
/api/v1/entries under B's token). It is NOT the FW30 immediate-stop (a legitimate
multi-user sequence, no attacker; a sign-in occurred; A had no server data for B
to read - the pre-decided, advisor-ratified branch), but on a shared, resold or
handed-over device it silently alters a stranger's audit-defensible tax record.
It is #1 of the three findings that deserve a task.

OTHERWISE THE APP IS SOUND WHERE IT MATTERS MOST. The per-app sandbox holds (a
second app installed on the device read NONE of the tokens, the database, the
cached releve or an exported file). The running app sends NO coordinate (D18
verified from captured traffic) and logs no credential. The release APK carries
no analytics / crash / advertising SDK and no secret. The write queue is durable:
process death, a full disk, a server 500 on a GET, and being offline all leave
PENDING rows intact with DB integrity ok. The on-device engine reproduces the
expected rates. Accessibility is strong (labels, roles, rich per-day
announcements, 48 dp targets, AA contrast, 200 % text reflow).

THE REMAINING FINDINGS are one MEDIUM and six LOWs, all structural and parked
(R255): F1 (MEDIUM) four dev-only activities exported in the release APK; F2/F6
the location permission plus a detection feature no shipping UI reaches; F3 no
FLAG_SECURE on the tax record; F5 Kotlin<->TS ports not mechanically drift-tied;
F7 a vacuity gap in the fence tests; F8 today/taxYear captured at Activity
construction (a session across midnight can misdate a day).

EVIDENCE STANDARD (self-audit, R254). The security, D18, resilience, clock,
performance and accessibility sections are PROBED on-device or read from the
built APK. The CODE QUALITY section is a WEAKER zero-JVM TEXT SCAN (read-based,
not mutation-proven) and says so. Two things were NOT reproduced on-device this
session and are marked as such, never claimed: the offline-queue POST-drain under
a 500/malformed response (WorkManager deferral), and the TRUE R8-minified release
end to end (R8 is off, monreleve.ch does not resolve, no release key - PARKAN-31).

INTEGRITY AND RESILIENCE (increment 5)
--------------------------------------------------------------------------------
FINDING F4 (HIGH) - one account's queue drains into another's. CONFIRMED
ON-DEVICE. android/scripts/an-audit-crossaccount.mjs ran against a scratch
Postgres + the write container behind a blockable proxy: A and B sign in (real
callback tokens); A records two PAST days OFFLINE (PENDING, 0 on A's server); A is
revoked; B's real session is injected over A's intact PENDING queue (the faithful
post-expiry device state); the proxy unblocks; B records one day and the queue
drains. Postgres entriesByUser() then showed, verbatim:
  ["anaudit-acct-b:2026-09-28","anaudit-acct-b:2026-09-29","anaudit-acct-b:2026-10-01"]
  B owns 3 (its own is 1); A owns 0; POST /api/v1/entries; CROSS_ACCOUNT_LEAK=true
A's two offline Suisse days landed under B's userId; A owns ZERO server rows. The
source chain (SessionManager clears only the token, StartupDecider/CallbackController
clear NO record, EntryEntity has no userId, SyncEngine drains under the CURRENT
token) is byte-identical to what ships (minify off). CAVEAT (R233): the explicit
server-side revoke deleted 0 session rows (the opaque-hashed-refresh model does not
populate those tables), so the proof rests on the device-state reproduction, which
is exactly what SessionGone->SIGN_IN and the callback produce.

THE DEVICE CLOCK. Moved headless with `cmd alarm set-time` (adb root/su blocked on
the Play user image; verified by adb shell date). Measured across four states:
- dayDate + clientClaimedAt FOLLOW THE CLOCK verbatim (a day recorded at device
  instant 2026-09-30T22:38 UTC was filed under Paris date 2026-10-01 with that
  instant). R216 holds: the client sends its instant; the server assigns lateness.
- R286 PENDING WARNING follows the clock: the SAME pending day showed "En attente
  de synchronisation" at the real clock and escalated to OVERDUE ("la plus ancienne
  depasse 7 jours ... saisie tardive des sa synchronisation") at +8 days. The
  forecast is clock-dependent; the real flag is still the server's.
- THE ON-DEVICE RATE follows the clock's YEAR: 2026 -> 28,33 %; 2027 -> "Aucune
  journee enregistree cette annee" (the rate VANISHES); 2020 -> 37,50 % (a
  different year's rate). A wrong-year clock shows the wrong year's rate, or none.
- FINDING F8 (LOW): today/taxYear are captured once at Activity construction and
  not refreshed, so a session held open across midnight (or a clock change) can
  misdate a recorded day (observed: a day filed under 2020-06-01 after the clock
  was restored). Self-correcting on relaunch.

- STORAGE FULL: /data filled to 100 % (~5 MB free); the app launched, recorded a

  lost (final DB: 3592 rows, 3 non-synced intact) and no crash.
- VERDICT: nothing observed loses a recorded day or crashes the app.
