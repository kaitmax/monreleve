R1042 - THE FIX, IN THE COMPONENT
====================================================================
web/app/(public)/calculateur-lamal-cmu/DeadlineHelper.tsx, the whole change:
  - import { useLayoutEffect, useRef, useState } from 'react';
  - const eventField = useRef<HTMLSelectElement>(null);
    const dateField = useRef<HTMLInputElement>(null);
  - useLayoutEffect(() => {
      if (eventField.current !== null) setChoice(Number(eventField.current.value));
      if (dateField.current !== null) setDate(dateField.current.value);
    }, []);
  - ref={eventField} on the select, ref={dateField} on the date input.
The select HAS the same shape (controlled, server-rendered, state from a
constant), so it gets the same treatment, with its own RED above. The email
field does not: it renders only once a date is computed, so it is never in the
server's HTML.
No new copy; no dependency; no visual change - setting a state to the value it
already holds renders nothing, so a page nobody typed into renders exactly as
before (and the visual suite: R1045).

WHY IT CANNOT LOSE A VALUE TYPED BETWEEN THE FIRST RENDER AND THE EFFECT
(for a hydration that succeeds - one that fails is client-rendered on NEW
nodes, and nothing could read the server's):
THE ARGUMENT RESTS ON ONE FACT: nothing writes either field between the
server's HTML and the effect's read.
1. Typed before the scripts arrive: there is no listener, so the value lives
   only in the field. Hydration does not write it (initInput's isHydrating
   branch; a select's hydration only adds an 'invalid' listener), and nothing
   else writes the field before the effect reads it.
2. Typed during the hydration render (root listeners attached, commit not yet
   made): the value is in the field for the same reason, and the read takes
   it. It does NOT rest on React dispatching that event: 'input' and 'change'
   are discrete events, so a blocked one makes React hydrate synchronously and
   then dispatch - but if that forced hydration is what first reaches the
   input, track() (react-dom-client :1064) creates the value tracker already
   holding the typed value, and no change event fires. Without the read, that
   value would be lost even after the scripts had arrived. (READ from the
   source - track() itself, not the comparison it feeds - and NOT DRIVEN; the
   argument does not rest on it.)
3. Between the commit and the read: impossible. A layout effect runs inside the
   commit, in the same task; the browser cannot run an input event in between.
   (A passive effect would leave a gap - harmless, since onChange is attached
   by then - but the layout effect needs no such argument.)
4. After the read: onChange is attached, and every change comes through it.
