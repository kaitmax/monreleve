- THE CADENCE. The pin has broken three times in three weeks:
    .47 -> .73    FW-CHROMIUM-PIN, RED measured 2026-11-02
    .73 -> .79    FW-CHROMIUM-PIN-2, measured 2026-11-11
    .79 -> .108   this task, measured 2026-11-24 (FW-CALC-REDESIGN's gate:clone)
  Debian keeps only the newest point release in bookworm-security. Each new
  Chromium build there turns every uncached build into R249's refusal until
  a one-line commit lands, and this time it blocked every gate:clone, and
  so every push, through test:container:write. The options, NOT chosen here
  (the same list as REPORT-FW-CHROMIUM-PIN-2.txt):
    (a) keep the exact pin and bump it on each release. This is the current
        practice: a renderer change is always a commit, at the cost of a
        build and push outage between Debian's release and the bump.
    (b) keep (a) and add a scheduled read-only check (`apt-cache madison`
        against the ARG) that reports the drift before a deploy or a
        gate:clone hits it.
    (c) install the pinned .deb from snapshot.debian.org. The version stays
        installable, but security fixes arrive only when someone bumps it.
    (d) a base image with Chromium preinstalled, built once and referenced
        by digest. Stable and fast, but it needs a registry and its own
        refresh process.
    (e) verify the major only and record the resolved version in the image.
        This relaxes R249's "the browser cannot move without a commit".
    (f) render with Playwright's own Chromium, pinned through the lockfile,
        instead of Debian's package. The pin moves into the lockfile, at the
        cost of image size and of R229's packaging decision.
