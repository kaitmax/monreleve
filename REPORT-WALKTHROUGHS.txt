HOW THE PARTIAL STATES WERE PRODUCED, AND A FINDING ON WHAT IS
REPRODUCIBLE AT ALL.
The onboarding plan is computed server-side from GET /api/v1/me
(StartupDecider.decideStartAfterSignIn -> onboardingPlanFor(parseMeView)).
I probed the R196 database constraints EMPIRICALLY rather than assuming
(web/scripts/_wt-setup.mjs), and all three illegal partial states were
REJECTED by the database:
  - granularity := NULL              -> REJECTED (column is NOT NULL,
                                        default DAY);
  - denominatorKind=EXACT with       -> REJECTED (CHECK
    exactTotalWorkDays NULL             User_exactTotalWorkDays_iff_exact);
  - employmentRate := 0              -> REJECTED (CHECK
                                        User_employmentRate_range).
CONSEQUENCE / FINDING: on the REAL server the only partial state an
account can hold is a MISSING NAME (name is the one nullable releve field
with no CHECK), or a missing canton (which routes to the full flow). The
completeness branches for a missing GRANULARITY, METHOD or RATE guard
states the database forbids, so they are reachable only with a synthetic
MeView - which is exactly what the JVM suites ReleveCompletenessTest /
StartupDeciderTest use. So the prompt's "an account missing only
granularity, asked only that" is NOT reproducible on the real server
without a schema change (which I did not make - verification pass, and it
is the shared dev DB); it stays covered at the JVM level. I drove the
reproducible cases instead and verified the granularity STEP itself in
the fresh full flow (where every step is asked).

Accounts created for this (minted sessions): wt-fresh@example.invalid
(no canton, no name), wt-noname@example.invalid (canton GE, name NULL,
else defaulted). Camille is the complete account.

FINDING WT1-F1 (new) - THE AUJOURD'HUI GREETING IS HARD-CODED
"Bonjour Camille". PARKAN-50.
On the fresh flow I set the name to "Walkthrough" (confirmed stored:
the DB row wt-fresh has name "Walkthrough", and the Pret summary showed
"Titulaire: Walkthrough"), yet Aujourd'hui greeted "Bonjour Camille". The
cause is in the code, not the data: Fr.kt line 12 is
`const val GREETING = "Bonjour Camille"`, rendered verbatim by
AujourdhuiScreen.kt line 127 (`Text(text = Fr.GREETING, ...)`). The
greeting is a fixed placeholder that ignores the signed-in account's
name - every account sees "Bonjour Camille". It was never caught because
the only account whose AUJOURD'HUI was screenshotted before (SEED-RELEVE)
was Camille, for whom the hard-coded name happens to be correct. Recorded
as PARKAN-50; NOT fixed (verification pass, no product code change).
