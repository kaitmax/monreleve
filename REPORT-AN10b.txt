R291 -- WIRING THE JVM CAN TEST (increment 2, commit 7345646)
--------------------------------------------------------------------------------
The AN10 bug (a calendar Save that recorded to Room but never synced) lived in
MainShell, a Composable, where no JVM test reaches: CalendarController was built
WITHOUT requestSync, and only the device walkthrough caught it. The controller's own
test passed because it injects requestSync - the defect was in the WIRING.

MOVED OUT OF THE COMPOSABLE: a plain Kotlin object, MainGraph, is now the ONE
construction site for both day-writing controllers. MainShell calls
remember { MainGraph.build(...) } and reads controllers.aujourdhui / .calendar.
AujourdhuiController and CalendarController implement a DayWriter interface exposing
requestSync.

THE TEST CHECKS THE GRAPH THE APP USES, NOT A COPY: MainGraphWiringTest calls the
SAME MainGraph.build the app calls. It ENUMERATES the day-writers by reflecting over
MainControllers' own properties (not a hand-kept list), and asserts (a) each is built
with the shared requestSync - invoking each fires the one spy, total == writer count
- and (b) each requests a sync when it WRITES a day, driving the real record() and
save() through the graph (R204: the entry point, not the module).

THE PLANT (AC2, R180): building the calendar without requestSync in MainGraph.kt
(verified present at line 53 by reading the file - MainGraph.kt was untracked so git
diff could not show it) turned BOTH tests RED - the built-with assertion (syncs 1 !=
writers 2) and the delivered-on-write assertion (a save fired no sync). Reverted;
GREEN. Because there is one construction site, that omission fails the test AND
breaks the app; they cannot diverge.

KNOWN LIMITS (named, not closed): the MainActivity -> MainGraph seam (that the REAL
SyncScheduler lambda is the one passed) stays JVM-untestable - the walkthrough's
server-DB check covers it live (below); and a day-writer the graph builds but does
NOT store on MainControllers would escape the reflection census. The defaults on the
controllers' requestSync were kept (removing them would break seven existing direct
constructions); the guarantee lives in the graph.

R296 -- A REJECTED BATCH IS ISOLATED (increment 5, commit 01601f8)
--------------------------------------------------------------------------------
PARKAN-4 amended. On a 400 for a MULTI-item batch, SyncEngine now retries the batch
item by item, ONCE (isolate, reusing syncBatch so each item takes the same
reconcile/markFailed path): the good items sync, the refused item stays FAILED and is
named (R198), and is never retried again - re-sending a payload the server refused is
a queue that can never drain. A single-item batch is already isolated, so it goes
straight to FAILED (unchanged). A 500 is the SERVER's problem: NOT isolated, retried
with backoff as before. 409 and 413 stay whole-batch FAILED (PARKAN-25): isolating a
409 would replay the out-of-order hazard the ordering evidence guards, and 413 is
unreachable under the parity-tested caps. "Named as a client defect" is the FAILED
state plus the defect count; no failure-reason column was added (a Room migration is a
stop-and-ask boundary).

THE THREE CASES (tests):
  one bad among good - the good syncs, the bad stays FAILED; the refused payload
    appears exactly twice (batch POST + one isolation POST) and never again (a second
    drain sends nothing, both rows out of pending()).
  an all-bad batch - every item FAILED, Settled(written 0, defects 2), three POSTs.
  a 500 - NOT isolated, Retryable, rows left PENDING, ONE POST only (backoff, as
    before).
RED PROOF: disabling isolation turned the two isolation tests RED (whole-batch fail)
while the 500 test stayed green; restored.
