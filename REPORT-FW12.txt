EXHAUSTIVENESS - the Warning and Status unions
--------------------------------------------------------------------------------
WARNINGS. Three mechanisms, and two of them are compile-time.

  1. warningEntry is a SWITCH over Warning['code'] whose default branch
     assigns the narrowed value to `never`. A ninth code is a compile error.

     WHY A SWITCH AND NOT A RECORD, since every other exhaustive map in this
     repo is a Record: four of the eight codes carry data, and a
     Record<Code, (payload) => string> cannot be CALLED without a cast.
     TypeScript will not correlate an index access with an argument
     distributed from the same union member, so `copy[w.code](w)` resolves the
     value to a union of function types and demands an intersection of their
     parameters. A switch on the discriminant narrows both sides at once,
     which is what a discriminant is for. The alternative was `as` on a
     boundary whose entire purpose is type safety.

  2. WARNING_CODES is a const tuple checked in BOTH directions:

       type EveryListedCodeExists = (typeof WARNING_CODES)[number] extends
         WarningCode ? true : never;
       type EveryCodeIsListed = WarningCode extends
         (typeof WARNING_CODES)[number] ? true : never;
       export const CODES_ARE_EXHAUSTIVE:
         [EveryListedCodeExists, EveryCodeIsListed] = [true, true];

     A one-way check is the trap: `satisfies readonly WarningCode[]` alone
     accepts a list of three codes, and the exhaustiveness this file
     advertises would be a list that happened to be complete the day it was
     written.

  3. WARNING_ORDER, in the panel, is checked against the union the same way:

       type EveryCodeHasAPosition = Warning['code'] extends
         (typeof WARNING_ORDER)[number] ? true : never;

     THE ARRAY'S LENGTH SAYS NOTHING ABOUT COVERAGE, and this is the gap the
     increment closed. The list shipped with seven of the eight codes in it
     and read as complete. The missing one was RULE_SET_FALLBACK, and a code
     with no position renders NO banner - silence, from a panel whose whole
     job is to say what the numbers mean. `satisfies` catches a typo in a
     code; this catches an omission, which is the direction that failed.

  Runtime, over WARNING_CODES: one banner per code; a non-empty heading and a
  body over 20 characters each; eight distinct headings; and no threshold
  figure in any heading or body (no "%", and no standalone 40, 49 or 10).

STATUS. `links` is declared `satisfies Record<Status, {text, href}>`, so a
fifth status is a compile error. Runtime: each of the four has non-empty text
and a root-relative href; no two statuses share a text or an href; and the
panel renders exactly one child in the link slot. The four texts being four
distinct strings is what makes the per-status assertions in the a11y suite
mean "only this state contains it".

RULE_SET_FALLBACK's GAP IS CLOSED. Its message names the requested and the
applied year, which is why it could not join a list of static strings. The
island's separate banner is gone - two banners for one warning in two visual
languages is the failure mode of that move - and R112 is why its two R55 tests
moved into the panel's path with a third added asserting exactly one banner
exists.

ONE BODY NOW READS ITS PAYLOAD. FISCAL_CEILING_EXCEEDED named the 1983 clause
