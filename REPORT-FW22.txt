TOKEN POLICY
--------------------------------------------------------------------
OPAQUE AND REVOCABLE BY ROW, and SPEC 10 decides this rather than
taste: "the refresh token is only invalidated by sign-out, account
deletion, or a server-side revoke." A self-contained token stays valid
until it expires whatever the server decides - there is no un-signing -
so that sentence would be a promise the architecture cannot keep, and
FW26's deletion path is where it would be found out. DELETE is a
complete answer; a signature is not, and a test asserts it: delete the
user, the access token stops resolving.

  access    15 minutes. Presented on every request, so it is the
            credential most likely to be captured - a log, a proxy, a
            crash report - and its lifetime is the window in which a
            capture is worth anything.
  refresh   90 days, rotated on every use. SPEC 10: a daily-use app
            must not demand a login every session. Ninety days is what
            happens to somebody who stops entirely.

A test asserts access * 10 < refresh: if they converge, the pair has
stopped being a pair.

STORED AS HASHES, never in clear. Unsalted SHA-256 is right for 32
random bytes and would be wrong for a password: what is defended
against is READING the table, not guessing the input.

ROTATION KILLS THE OLD ACCESS TOKEN TOO, or a captured one outlives
the rotation meant to replace it.

REUSE: THE WHOLE SESSION DIES. A consumed refresh token presented
again means it was CAPTURED - the legitimate client has moved to the
successor and has no reason to send the old one. The server cannot
tell which holder is the thief, so it trusts neither. The real user
signs in again through an email they control; the thief is left with
nothing.

  REFUSING ONLY THE REPLAYED TOKEN is the gentler-looking option and
  is wrong: the thief's stolen SUCCESSOR keeps working.

  DEVIATION: THIS IS A FOURTH WAY A SESSION ENDS, where SPEC 10 names
  three. SPEC's sentence is about not nagging a daily user; this is
  about a credential known to be in two hands. Flagged rather than
  resolved quietly - see QUESTIONS.

RACE PROOF
--------------------------------------------------------------------
consumeMagicLink is ONE STATEMENT: deleteMany carries the whole
validity condition - identifier, hash, not expired - inside its WHERE,
so the row is matched and removed in the same breath and PostgreSQL's
count IS the answer to "did I win".

THE ABLATION IS THE PROOF, and it produced the finding of the task:

  implementation          two concurrent    ten concurrent
  read-then-delete        PASSED            FAILED (2 winners)
  one-statement delete    passed            passed

The prompt asks for "two concurrent consumptions, exactly one wins".
ON THIS RUN THAT TEST PASSED AGAINST THE BROKEN IMPLEMENTATION. Only
the ten-way margin caught it. A race test that has never been seen to
fail certifies nothing, and a two-way race is thin enough to win by
luck often enough to look green.

The cases this prevents are not exotic: a mail forwarded to a
colleague, a link-preview fetcher that follows URLs before a human
does, a phone retrying a tap on a bad connection.

ENUMERATION PROOF (AC2)
--------------------------------------------------------------------
AC2: the request must not reveal whether an address is registered.

FOR THIS PRODUCT MEMBERSHIP IS ITSELF THE SENSITIVE FACT - an account
implies living in France and working in Switzerland, paired with a tax
threshold. /confidentialite promises not to enable that inference, so
an enumerable sign-in form would falsify it on the one endpoint
everybody touches.

IDENTICAL WORK, NOT AN IDENTICAL MESSAGE. A token row is written and a
message sent for ANY syntactically valid address, registered or not.
Whether a User row exists is decided at CONSUMPTION, where no attacker
is watching. So the identical response rests on an identical code path
rather than on a timing pad somebody tunes and then stops trusting.

  asserted: the same result object for known and unknown
  asserted: a VerificationToken row for BOTH
  asserted: a message in the outbox for BOTH
  asserted: rate-limited requests answer as served ones do

THE ACCOUNT IS CREATED AT THE CALLBACK, not at the request - the first
moment somebody has proven they control the address. Creating it
earlier would let anyone fill the table with addresses they do not
own, AND would falsify the "identical work" claim, since a new row is
work an existing address does not need.

TENANCY PROOF
--------------------------------------------------------------------
Identity comes from the Authorization header and from NOWHERE ELSE -
enforced by absence rather than validation: the guard reads one header
and never looks at the body or the URL, so a later handler cannot
forget the rule.

THREE PLANTS, EACH VERIFIED TO HAVE LANDED BEFORE ITS RESULT WAS READ
(R180), because a plant that silently failed produces a passing test

  body      { userId: <victim> }   verified via request.clone().json()

  header    x-user-id: <victim>    verified via headers.get()

the query-plant test failed.

QUESTIONS

Q68. next-auth. SPEC 3 and SPEC 10 name Auth.js v5 with trustHost;
     SPEC 10 also makes the zero-cookie guarantee total with D12

Q69. Reuse detection ends a session, which SPEC 10 does not list. Is
     TOKEN_REPLAYED a fourth invalidation cause, or should a replay
     refuse the token and leave the session alive? I implemented the
     former; the latter leaves a thief's stolen successor working.

Q70. PARK4-1 - are the seven OAuth columns on Account to stay? Only
     needs answering if "this product will never support OAuth" is
     certain rather than merely true today.

Q71. A CANDIDATE RULING I DID NOT INVENT A NUMBER FOR. Three edits in
     increment 6 landed somewhere other than intended: a first-match
     replacement that hit DISCLOSED_RECORDS itself and produced a
     self-referencing record, a line parser that read 26 items where
     there were 10 because continuations start with a quote in that
     file, and hand-retyping that flattened no-break spaces.
     The one that behaved correctly asserted its own arity BEFORE
     writing and aborted, so the bad edit never landed. Proposed: a
     scripted edit states what it expects to match - a unique anchor,
     an expected count - and refuses to write when it does not. It
     would have caught two of the three; R91 caught the third.
     NOTE ON WHAT CAUGHT THE FIRST ONE: `tsc`, via TS7022/TS2448,
     because the corruption happened to be a self-reference and that
     is a TYPE error. A replacement that substituted a different VALID
     string would have been well-typed and silent. The compiler caught
     the shape of this corruption, not the class of it.

Q72. A SECOND CANDIDATE RULING, and the sharper of the two.
     `pnpm test:visual:update` prints its R135 list from `git status`
     rather than from its own output, so a run that FAILED without
     taking a screenshot printed "2 baseline(s) regenerated" naming
     two files a PREVIOUS run had written. That sentence exists to be
     pasted into a report as evidence.
     Proposed: A REGENERATION REPORTS THE FILES IT WROTE, FROM ITS OWN
     OUTPUT, NEVER FROM THE WORKING TREE'S DIFF. The current
     implementation cannot distinguish "I wrote this"from"this
     differs from HEAD for any reason" - a previous run, a manual
     edit, a half-finished attempt - and it prints the same sentence
     for all of them. R133's rule applied to the reporter rather than
     to the thing reported.
     It also needs a non-zero exit to be fatal: the script printed the
     R135 line AFTER `[ELIFECYCLE] Command failed with exit code 1`.
