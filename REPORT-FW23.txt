THE FROZEN CONTRACT (the field list, verbatim)
--------------------------------------------------------------------
POST /api/v1/entries - what a client may send. Derived from the Zod
shape by ENTRY_ITEM_FIELDS, so the document cannot drift from it:

  absenceReason  clientClaimedAt  clientMutationId  dayDate
  detectedAt     detectedKind     kind              note
  portion        provenance

GET /api/v1/entries?year= - what comes back. ENTRY_READ_FIELDS:

  id            clientMutationId  dayDate      portion
  kind          absenceReason     note         provenance
  detectedKind  detectedAt        clientClaimedAt
  firstRecordedAt               lastModifiedAt

  NOT EXPOSED, and asserted rather than merely absent: userId,
  updatedAt. A census against information_schema requires every Entry
  column to be in one list or the other, so a column added next year
  can neither join the contract by accident nor leave it silently.

THE PAGINATION DECISION, STATED
--------------------------------------------------------------------
UNBOUNDED. The year IS the page: no limit, no offset, no cursor, no
hasMore, and the server NEVER TRUNCATES - a short array never carries
a 200.

  THE BOUND IS STRUCTURAL, NOT HOPED FOR:
    @@unique([userId, dayDate, portion])  one row per portion per day
    |EntryPortion| = 3
    366 days in a leap year
    ------------------------------------  1098 rows, ever

  The prompt's "about 260 working days" is the TYPICAL count and not
  the bound, and the difference is reachable by a real user: ABSENT is
  a kind, so all 366 calendar days can be declared; and nothing
  constrains `portion` by the user's granularity, so somebody who
  switches DAY -> HALF_DAY mid-year leaves FULL rows beside AM/PM ones.
  Verified in the schema rather than assumed.

  A CURSOR WOULD BE WRONG HERE, not merely unnecessary. The client
  reconciles a SET, and a half-fetched year is indistinguishable from
  a year with missing days - which is the one fact this product exists
  to report honestly. Tested by saturating a leap year to 1098 rows
  with maximum-length notes, asserting the whole set comes back, and
  only THEN asserting no pagination key exists. On an empty response
  that last assertion holds for the wrong reason.

OPERATOR RULINGS, RECORDED VERBATIM
--------------------------------------------------------------------
Three questions were raised before the contract froze, because SPEC
does not settle them and R187 makes them permanent.

R214. THE WIRE SAYS lastModifiedAt; THE COLUMN STAYS updatedAt.
      SPEC 8's column is `updatedAt`. SPEC 12 line 879 freezes the CSV
      columns as "exact and stable" and names `lastModifiedAt` among
      them. SPEC never names the API field. One published fact gets
      one published name across the API, the CSV and the PDF; the
      column name is an implementation detail that never leaves the
      server.

R215. IT IS DERIVED FROM THE TRAIL, NOT FROM updatedAt.
      max(EntryEvent.recordedAt) over that entry's MODIFIED events,
      null when never modified. Taken against a measurement: see
      FINDINGS 2.

R216. `late` DEFERS TO FW24.
      SPEC 12 lists it as a CSV column and SPEC 11.3 defines the
      seven-day threshold behind it, but it is not an Entry column and
      the threshold has no home in the code. It arrives with the
      dossier, where that home is built. Adding a key is additive and
      breaks nobody. Until then the document forbids a client
      adjudicating lateness from a threshold of its own - a 7 compiled
      into an APK is the least revisable constant in this system.

SERVER CLOCK PROOF
--------------------------------------------------------------------
  firstRecordedAt and recordedAt are refused as INPUT by name: the
  payload schema is .strict(), so a client sending either is answered
  `invalid_payload` rather than having it stripped.

  WALKTHROUGH, END TO END: a day posted with
  clientClaimedAt 2026-04-07T18:44:02.000Z came back with
  clientClaimedAt 2026-04-07T18:44:02.000Z and
  firstRecordedAt 2026-09-19T00:25:02.334Z. The client asserted April;
  the server recorded September; the read path shows BOTH, which is
  the whole point - a reader sees the gap rather than being handed one
  number and asked to believe it.

  IT NEVER MOVES ON AN EDIT, proven through both routes rather than
  trusted to the trigger: the same row after an edit still carried
  firstRecordedAt 2026-09-19T00:25:02.334Z - the batch-1 clock, shared
  with the two rows written beside it - while lastModifiedAt became
  00:25:02.806Z.

COORDINATE REJECTION PROOF (four forms, each plant verified)
--------------------------------------------------------------------
Carried from increment 2 and now extended to the READ path, which the
prompt did not ask for and the boundary demands:

  POST body        top level, nested object, inside an array, and a
                   key whose NAME CONTAINS a banned word. All four
                   refused 400 `coordinates_refused`, each plant
                   verified present in the bytes being sent.
  GET query string latitude, lastKnownLongitude, accuracy, and mixed
                   case Lat. All refused.
  THE ORDER IS ASSERTED: `?year=2026&latitude=46.2` answers
  `coordinates_refused`, NOT `unknown_parameter`. A latitude is both;
  validating first would answer "unknown parameter" and the one
  interesting fact - that a client is sending coordinates - would go
  unrecorded.
  THE VALUE NEVER APPEARS: the answer to a payload carrying 46.20731
  contains neither 46.20731 nor 46.2.

  AND WHAT IT DOES NOT BUY IS WRITTEN DOWN. A `?lat=` is in the
  request line and has ALREADY reached any reverse proxy's access log
  before the handler runs. The refusal is a signal to a client author,
  not a guarantee that nothing was logged. Section 6.5 says so.
  Writing it as the stronger claim would be the overclaim this product
  refuses everywhere else - and on the surface whose whole argument is
  that no coordinate reaches this server.

FINDINGS
--------------------------------------------------------------------
1. A PLANT THAT DID NOT FAIL, AND THE GUARD IT CONDEMNED.

   Removing the portion ordering entirely - `return 0` - left ALL
   FORTY tests passing, including the one written to assert exactly
   that order.

   THE CAUSE, MEASURED RATHER THAN GUESSED: @@unique([userId, dayDate,
   portion]) is a btree index on those columns, so Postgres serves the
   rows already ordered by portion. Rows inserted PM, FULL, AM come
   back FULL, AM, PM with no sort at all. The route-level assertion
   was satisfied by the INDEX, never by the code under test - R171's
   coincidence, inside the guard written to prevent coincidences.

   THE FIX IS NOT TO DELETE THE SORT, and the distinction is worth
   stating because day.ts's own ablation rule points the other way.
   That file removed a second pass because no input could reach it:
   Europe's transitions are at 02:00, never at midnight. This sort IS
   reachable - index order is a property of the QUERY PLAN, and a
   planner choosing a sequential scan plus a sort for a large result
   has no obligation to break ties by portion. So the comparator is
   exported and tested on input the database did not order, and the
   same plant now goes red.

2. A MEASUREMENT TAKEN BEFORE A DESIGN, WHICH CHANGED THE DESIGN.

   The obvious backing for `lastModifiedAt` is Entry.updatedAt. It is
   wrong here, and one probe settled it:

     firstRecordedAt : 2026-09-18T23:03:02.392Z
     updatedAt       : 2026-09-18T23:03:02.397Z
     equal?          : false      delta: 5 ms

   On a row NOBODY HAS EDITED. firstRecordedAt is the batch clock
   taken once at the top of writeEntries; Prisma stamps @updatedAt at
   query execution, a findMany and a findUnique and an upsert later.

   SPEC 12 item 5 prints the last-modified timestamp "WHEN DIFFERENT".
   Backed by updatedAt that fires on EVERY row, and the one thing the
   column exists to tell a reader of the legal document - was this day
   edited? - becomes unreadable. Null-when-never-modified is a state a
   reader can act on.

   WHAT MAKES THIS A FINDING RATHER THAN A DETAIL: every test would
   have been green. A round-trip asserting "lastModifiedAt >=
   firstRecordedAt" passes. The defect would have surfaced in FW25, in
   a PDF, as an annex where every row claims to have been edited.

3. THE WALKTHROUGH CAUGHT THE DOCUMENT CONTRADICTING THE PRODUCT.

   Recorded under WALKTHROUGH above. The instrument worked exactly as
   R176 describes - not copy read across pages, not pixels compared to
   a baseline, but a returned row contradicting the sentence that
   describes it. No test could have found it, because the tests
   asserted the BEHAVIOUR and the behaviour was correct.

   THE ASYMMETRY IS NOW DOCUMENTED AND ASSERTED: detectedKind and
   detectedAt survive an edit that omits them (SPEC 8 - deleting an
   overridden proposal is a review rejection); clientClaimedAt does
   not, because it describes the write that produced the row's current
   state, and after an online edit there is no assertion to report.
   Nothing is lost either way - every write's claim sits on its own
   EntryEvent, and the trail is append-only.

   The push of 1e6e71f produced four failed jobs with ZERO STEPS and a
   40-second run. The annotation:

     "The job was not started because recent account payments have

   THE REPOSITORY IS PRIVATE AGAIN. It was PUBLIC for the whole of
